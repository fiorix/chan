# release-v0.83.4

v0.83.4 is a patch release whose entire scope came from running v0.83.3 on real hardware. With chan-desktop reaching a devserver through the gateway, every mutating surface answered 403 while the window looked healthy; rebooting the remote machine trapped its windows in close and reconnect loops; and terminal reattach had been crawling badly enough to obstruct testing, a regression that turned out to predate the round by three releases.

## What shipped

**Desktop gateway windows can mutate again.** The desktop installs `__Host-devserver_gate` and `__Host-devserver_csrf` into the WebView cookie store natively. WebKit stores the pair and attaches both to requests but never surfaces the csrf cookie to JavaScript, so `document.cookie` was empty in exactly the windows that needed it, the SPA's double-submit mirror emitted no `x-chan-csrf` header, and the gateway's check answered every unsafe method with 403. Reads were unaffected, which is why the window looked fine: browsing, terminal I/O and `/ws` presence all worked while the Computers scope reported "This window was not granted library access", the Rich Prompt mounted without a composer, `cs paste` hung on its reply POST, file upload and replace failed, and session and config writes failed silently. A new origin-scoped `gateway_csrf_token` command returns the live token to the exact `lib-*` window on the minted origin and to nothing else; the SPA mirror prefers it, keeps the readable-cookie fallback for browsers, and re-reads and retries once on a 403 so a mid-session rotation self-heals. A session publisher installs fresh cookies into the shared store after every re-mint, so open windows no longer drift past the gateway's one-hour session cap.

**Windows settle across a remote outage.** Closing a devserver window during an outage records a pending delete instead of unburying the record, so a closed window no longer respawns on the connecting screen in a loop that could not be broken until the remote returned; the delete retries on feed reconnect, bounded, then raises a launcher notice, and the suppression lifts only when the authoritative snapshot confirms the record is gone. An OS-chrome close of a window still sitting on the connecting screen now routes through the same path instead of real-closing with no delete. The connecting probe classifies responses rather than treating any HTTP status as success, so gateway 502/503/504 and transport failures hold the window on the connecting screen, and the probe carries the window's session cookies so an authenticated probe is not read as an outage. A pending close-confirmation prompt auto-cancels on the disconnect and reconnect transitions, and the native close path raises and focuses its window before prompting, so the "closing will stop the shell" prompt can no longer strand invisibly behind newer windows.

**Terminal reattach is fast again with secret masking on.** The reported symptom was a scrollback replay that appeared to loop for a long time before settling. It was not a loop: a controlled socket trace showed each reload, socket drop, wake gap and devserver restart producing exactly one `session`, one bounded replay and one `ready`. The apparent repetition was intermittent paint progress while a single replay monopolised the main thread. The owner's follow-up detail, that the slowness bisects to v0.83.0 rather than to v0.83.3, named the mechanism: v0.83.0's secret masking wrapped every parsed write, replay chunks included, in a per-write masker capture and scan, and a 2.09 MiB ring replay arrives as thousands of chunks. Measured on one fixed ring, masking off ran 1.63 s while masking on blocked past 180 s, over 110x. Replay-window writes now skip the per-write capture and scan and the masker runs one whole-buffer scan after the replay drains; the writes themselves, the replay protocol, and `PtyWriteTracker` ordering are untouched, and live writes keep their per-write scan. The same ring after the fix: 1.39 s off, 2.78 s on.

**Two small fixes.** A failed `POST /api/drafts/new` rejected an unguarded `onMount` await and left the Rich Prompt as chrome with no composer, no error and no way out; the mount now surfaces the failure with a retry that recreates or reloads the draft. And the custom-key wrapper's inverted contract made ghostty-web `preventDefault` the paste chord on every origin, suppressing the browser's native paste event; the chord now resolves a backend-aware result so Ghostty's own KeyV early-return passes the key through, matching xterm.

## Process

The work ran as a four-member chan team round on `v0834-patch`, spawned out of the 2026-08-04 gateway grounding session: three codex lanes (`@@windows`, `@@web`, `@@session`) under a lead terminal, each lane owning one roadmap item with its own worktree and focused gate. Three of the four items were grounded, specified, implemented and gate-validated inside that round.

The replay item arrived differently. It was registered mid-round from live use, investigated as a suspected attach-loop regression in the v0.83.0..v0.83.3 span, and cleared there: the span is byte-identical on the replay decision path, and the controlled repro produced one replay per attach in every leg. That negative result was recorded rather than discarded, which is what made the owner's "extremely slow, since v0.83.0" correction immediately actionable rather than a restart.

The lead terminal's model provider hit its billing quota and stopped mid-release, in the same exchange in which the owner accepted the rebuilt binaries. A second lead took over by reading the first lead's terminal scrollback for the round's state and drove the close: roadmap closure, the release report, the version pins, the Nix fixed-output harvest, the platform checks and the tag. The handover cost nothing because the round's state lived in committed roadmap items and lane reports rather than in the lead's context.

## Verification

- The full `make pre-push` gate ran green twice on this branch: once on `7bc9bfc0`, the tip carrying every fix, and again on the GA commit after the version bump, including the release devserver smoke and the native AppImage package.
- Lane-focused evidence is recorded in each closed roadmap item. The replay fix is pinned by `web/packages/workspace-app/src/terminal/replayMasking.test.ts`, whose six cases cover the contract clause for clause, plus 24 focused terminal, secret-mask, xterm and Ghostty Vitest files (202 tests) and a clean `npm run check`. The gateway CSRF work carries a Rust capability-parity test that pins which window classes are granted `gateway_csrf_token` and, by explicit exclusion, which are not.

- The regenerated `web/package-lock.json` was checked for the failure that cost v0.83.3 its Cachix lane: all five root `@chan/*` workspace links are present and linked, no stray nested entry exists, and a strict `npm ci --dry-run` passes. The regeneration ran on npm 10.9.8, not the npm 9.2.0 that corrupted the lockfile last time.
- Owner hand-smoke on the rebuilt desktop and devserver: reattach speed restored with masking on, the launcher's Computers scope working, `cs paste` working, and a quick pass over the window lifecycle. The full remote-reboot matrix and the image-paste IPC probe were not re-run; both are carried as follow-ups below.
- Platform checks and the publish outcomes are recorded in the follow-up commit to this report, per the convention v0.83.3 established.

## Retrospective

The round's best decision was recording a negative result. The replay investigation spent its first pass disproving the hypothesis it was given, wrote that down in the item, and so when the owner supplied one more detail the mechanism fell out in a single step instead of restarting the hunt. The worst-shaped moment was the same item's framing: "replays loop" came from a reasonable reading of a live symptom and survived in the roadmap README as "needs a spec" long after the item had one, which is the sort of stale row that quietly misdirects whoever picks the work up next.

Two defects in this release were introduced and fixed inside the same branch, never reaching a user: an async CSRF mirror that broke synchronous dispatch timing, and a session-lock guard that deadlocked every gateway connect with a live session. Both were caught by the round's own gates. That is the system working, but it is also two self-inflicted regressions in twenty commits, both from the same class of change: touching a path's synchrony or lock scope while fixing something else on it.

The v0.83.3 Cachix failure was fully visible before that tag was pushed, on the GA commit's own CI run, and nobody looked. The lockfile check in this release exists because of it, and the sequencing gap that let it through is written up as a follow-up rather than left as folklore.

## Follow-ups

- The IPC-over-HTTPS contract in `gateway-served-surface-failures` ships on a static Tauri source audit. WKWebView blocks the `ipc://localhost` custom protocol on HTTPS pages and every invoke degrades to postMessage; the code path was read and no reroute was found to be missing, but no runtime proof exists. The probe that would close it is `cs paste` of an image from a gateway desktop window.
- The remote-reboot matrix in `desktop-window-outage-lifecycle` was proven by unit and component coverage plus an owner quick pass, not by a full live outage. The pending-delete suppression is process-local by design, so a desktop restart before the remote delete settles can still let a window return once.
- The connecting probe treats a gateway 404 as reachable. When a rebooting devserver's tunnel leaves the registry the gateway answers 404, not 5xx, so that window can still navigate onto the gateway's static error page. The 5xx and transport-failure cases are fixed; this one is a deliberate open edge, not an oversight.
- `chan config get` prints 31 dotted keys and `chan config set` accepts 12 of them, so the terminal preferences a user would most want to toggle from a script, `secret_masking` among them, are unreachable from the CLI. Registered as `chan-config-key-coverage` for v0.84.0; it surfaced during this round when the owner needed exactly that toggle to A/B the replay slowdown.
- The packaging failure mode that cost v0.83.3 its Cachix lane is closed in this release rather than carried. `make web-lock-check` runs a strict `npm ci --dry-run` among the gate's static checks, before any target can rewrite the lockfile, so a desynced `web/package-lock.json` now fails the local gate in under two seconds instead of surfacing in the Nix sandbox after the tag; it was mutation-proven against the exact v0.83.3 corruption, a dropped root `@chan/workspace-app` workspace link. The release skill gained the matching rules: verify the lockfile right after the npm regen, treat npm 9.2.0 as known-bad, note that the pre-bump cachix dry run cannot see a bump-introduced desync by construction, and require the GA commit's own `ci.yml` run green before the tag, dispatched explicitly because `ci.yml` triggers only on `main` and pull requests. That CI run is the only place the three fixed-output hashes are verified against a real build while there is still time to fix them.
