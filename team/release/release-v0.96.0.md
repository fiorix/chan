# Release v0.96.0

Status: GA 2026-08-23. No candidates. A three-item integration round: the CI and release pipeline speed-up, a terminal recovering keyboard focus after macOS wake, and FreeBSD becoming a published target on both amd64 and arm64. All three arrived as finished branches and were taken through intake; the FreeBSD port's intake found four defects in code no machine in the round could execute, and the owner ruled them fixed rather than deferred. arm64 was scoped out of the round and added back at the close, after the GA commit had already been staged and proven, because the owner declined to split one platform across two releases.

## What shipped

- **chan publishes FreeBSD amd64 and arm64 builds.** Every release carries `chan-x86_64-unknown-freebsd.tar.gz` and `chan-aarch64-unknown-freebsd.tar.gz`, statically linked binaries packaged like the Linux tarballs, and `https://chan.app/install.sh` supports the FreeBSD target: the installer recognizes a `uname -s` of `FreeBSD`, selects the amd64 build, and downloads through the base system's `fetch` where neither curl nor wget is present. `chan upgrade` resolves the new target and `/dl/cli/latest.json` lists it. Both architectures are selected by `uname -m`; other FreeBSD architectures are still refused by name. Two sibling release jobs cross-build against checksum-pinned FreeBSD 15.0 sysroots, assert the outputs are statically linked FreeBSD ELFs, and upload them as `release-freebsd-cli` and `release-freebsd-cli-arm64`, both of which `publish-release` waits for. amd64 builds on the repository's pinned stable toolchain; arm64 is a Rust tier-3 target with no rustup std, so its job alone uses a pinned `nightly-2026-08-23` with `rust-src` and builds the standard library from source through `-Z build-std`. From `freebsd-port` (`06fa12c6`, `33d6d431`, `f59152a6`, `92091c83`, `719bf6b6`) plus the release arm and the four intake fixes built in the round.
- **The release workflow runs warm and in parallel.** The Rust caches are keyed per OS and architecture and shared between `ci.yml` and `release.yml`, with the three `make ci-*` jobs on `main` as their only writers, so a release branch or tag no longer fills the repository cache cap and evicts `main`'s entries. The Linux and macOS artifact jobs start from `release context` alongside the validation jobs instead of behind them, publication still waits for both, the validation jobs install the prebuilt `tauri-cli` instead of compiling it, `macOS validation` selects the same Xcode the desktop package links against, and the SSL.com CodeSignTool download retries. `make ci-windows` builds the web bundles once, and `chan-server`'s build script no longer tracks a model bundle that does not exist. The release process records the cycle's run ids after the tag instead of re-cutting the GA commit for them. From `ci/pipeline-speedup` (`3e9c19c1`, `81c0c922`, `26e67783`, `aa1dca8c`).
- **A focused terminal accepts keyboard input after macOS wake without switching tabs.** Host resume events and the wall-clock wake detector reassert keyboard focus only when the terminal still owns the active pane and no Find box, tab menu, Rich Prompt, survey, or external DOM surface owns input; renderer recovery and PTY reconnection retain their existing behavior. From `fix/macos-wake-terminal-focus` (`89aebf20`).

## Team and process

A five-member team in the owner's session: a lead, three lane workers (pipeline, FreeBSD, wake), and a gate worker owning the container and every verdict. Lanes were file-disjoint by construction and all four workers shared one worktree, `chan-v0960`, with the main checkout's `target/` bind-mounted over it so the round built against a warm 101G cache rather than a cold one. The gate worker wrote no source and reported every verdict against an exact sha with a status file, never a wrapper exit code.

The owner set scope and stepped away for the first half of the round. Two surveys timed out unanswered. The lead treated the standing decision (nothing else enters, follow-ups go to the release report) as operative rather than reading consent into silence, and deferred every irreversible choice until the owner returned. On return the owner reversed one of those holds, releasing disk the lead had declined to take, and ruled that the FreeBSD intake findings be fixed in the round rather than deferred.

## Validation

The three intakes were merged in sequence, each after its lane's review: `ci/pipeline-speedup` fast-forwarded so its four commits land verbatim, then `fix/macos-wake-terminal-focus` at `98af7f7f`, then `freebsd-port` at `13ca1ff7`. The only merge conflict was the one predicted at setup, `team/roadmap/README.md`, where two branches replaced the same paragraph; it resolved into one `### v0.96.0` Active table in the house shape.

Every measurement in this round was taken as a delta against a recorded baseline rather than as an absolute. The browser smoke was baselined on unmodified code at `41fcf688`: 46 checks run, 34 pass, 12 fail, 1 skip, with the twelve failures recorded by name. The integrated reading at `3125fb64` was 35 pass, 11 fail, 1 skip, no baseline pass regressed, no new check appeared, and the single improvement (`Hybrid Nav staged chips`) was a 20-second timeout at baseline and is recorded as timing rather than as a fix the round earned.

The wake fix was proven by its negative control rather than by its own suite passing: three focused Vitest files at 50 tests green with `svelte-check` at 0 errors and 0 warnings, then the wake focus call commented out, which failed exactly two tests, `a wake restores DOM focus to the still-focused terminal` and `a wake reissues focus when xterm still appears focused`, then restored, with the file's SHA-256 confirmed identical to its pre-control value and all 50 green again. Naming the two failures is what makes the control evidence: a control that broke two unrelated tests would have produced the same count and meant nothing.

The pipeline branch's build-script claim was measured the same way. At `41fcf688`, with the watched model bundle confirmed absent, a second `cargo build -p chan-server` in an unchanged tree recompiled `chan-server` in 9.26s; after the fix the model bundle was no longer the reason. That reading also found what the item's acceptance 3 overclaimed: `crates/chan-server/build.rs` still emits `rerun-if-changed` unconditionally for `web/.chan-build-stamp` and its launcher twin, so the no-op holds on a tree whose frontend was built through the Makefile and not on a gate worktree that never has. The cause was identified with `CARGO_LOG=cargo::core::compiler::fingerprint=info`, which named the missing stamp outright, and the CHANGELOG sentence that claimed the unqualified no-op was narrowed before the cut.

The FreeBSD port's own compile story is a measured before and after. At the round base, `RUSTFLAGS="-D warnings" cargo check -p chan-workspace --target x86_64-unknown-freebsd` failed with exit 101 on dead code at `fd_budget.rs:327`, where `effective_nofile_limit` was gated `#[cfg(unix)]` while its only callers were the Linux and macOS arms. After the port it passes, because `f59152a6` gave FreeBSD a real caller. So the port makes the tree compile clean for the FreeBSD target for the first time, under `make pre-push` warning parity.

The FreeBSD release artifact was verified from the dry run rather than trusted from the job's own assertion: `release-freebsd-cli` holds exactly `chan-x86_64-unknown-freebsd.tar.gz`, whose contents are `./chan`, `./README.md` and `./LICENSE`, and whose binary `file(1)` reports as `ELF 64-bit LSB executable, x86-64, version 1 (FreeBSD), statically linked, for FreeBSD 15.0 (1500068), FreeBSD-style, stripped`. The static claim was confirmed a second way with `readelf -d`, which reports no dynamic section at all. The asset list is pinned by assertion rather than arithmetic: `smoke-verify-release-assets.mjs` asserts `requiredAssets("0.96.0").length == 24`, and that smoke runs inside `web-marketing-check` inside `make pre-push` inside `make ci-linux`.

arm64 was probed before anyone implemented it, because tier 3 meant the amd64 recipe could not simply be retargeted and no amount of planning would settle whether the dependency graph cross-compiles. On the pinned nightly with `rust-src`, `cargo check -Z build-std=std,panic_abort --target aarch64-unknown-freebsd -p chan` returned 0 in 2m13s, building the standard library, the panic runtimes and the full dependency graph including the bundled SQLite, zstd, ring and tokenizers; the `--release` build with `-C target-feature=+crt-static` returned 0 in 9m33s and linked, and `file` reported `ELF 64-bit ARM aarch64, FreeBSD 15.0, statically linked, stripped`. The arm64 sysroot's SHA-256 was verified against that release's `MANIFEST` and against the actual download before it was pinned in the workflow. The probe ran against a scratch target directory and modified no tracked file, so a negative result would have cost one build and nothing else.

Platform and pipeline: `make windows-cross-check` green on the host in a disposable guest at `457e96bd` (release `cargo check` of the CLI crate graph in 2m25s, `cargo test --no-run` for chan-library and chan-server in 8m53s, both Windows `.exe` artifacts produced). The round branch's own dispatches: `ci.yml` green across all nine jobs at `8fc4885e` and again at `540bd2b7`, and `release.yml publish=false` green at `540bd2b7` including the new `freebsd-cli-artifacts` job.

The local full gate did not complete, and the report says so rather than implying it did. The box ran out of disk: `make pre-push` reached `gateway-test` and died on `No space left on device` after clearing the static checks, `web-lock-check`, `cargo fmt --check`, clippy, the root test suites and the no-default-features build, with 45 test-binary summaries reporting ok. A full local gate costs about 12G here and the round had consumed the box's slack. Because `ci-linux` takes `pre-push` as a prerequisite, the GA commit's own `ci.yml` run exercises the same gate on three platforms rather than one, and that is the evidence this cut rests on. What is genuinely lost is the local gate as an independent second environment.

## Retrospective

**Highlights.** Intake earned its place three times over. Static review of the FreeBSD port found four defects that four green dispatches had not: a stale inode identity that could suppress nested descent after inode reuse, a directory reopen that lost close-on-exec parity with the Linux arm of the same function, a debounced catch-up scan whose root could be replaced by a symlink mid-window, and a documentation count that reconciled with nothing. None was reachable by any test the round could run, because all of it is `#[cfg(target_os = "freebsd")]` code that does not compile in an ordinary Linux build. The gate then found two more that review had not: a `cargo fmt` red and a `clippy::doc_lazy_continuation` failure whose five reported lines all traced to one line five earlier, where a `+ ` at the start of a doc comment made rustdoc parse the paragraph as a list.

The strongest single catch came from a reviewer, not a tool. After the symlink fix passed three FreeBSD cross-checks including `--tests`, an adversarial read found that the new traversal retained an open directory handle for every unknown sibling before recursing, so descriptors scaled with tree width rather than depth, and the worst case was the mechanism's own reason for existing: a subtree that arrived whole. The crate caps itself at 4096 descriptors in the very module the port had fixed. Failed opens dropped identities without requeueing, so exhaustion would have produced silently unannounced files. Compile-checking cannot see any of that.

**Lowlights.** Almost every piece of friction in this round came from the coordination layer rather than from the code. The gate worker withheld or refused a verdict seven times: a tree that went dirty mid-preflight, a merge landing under a running unit, a sha announced before the lead's last commit, queue lag between a hold and the instruction it was meant to stop, a gate compiling a tree that changed nine minutes in, and an announcement whose own two halves disagreed because one sha was substituted from the wrong repository. Every one was the lead's doing, every one was correct, and none produced a false verdict. The lead also fabricated a sha suffix once, and wrote a monitor that reported a run complete by matching a substring that a single finished job satisfied.

**Honest feedback.** The round's most repeated defect was documentation written from a change's intent rather than its measured behaviour. Two CHANGELOG sentences claimed more than the code did and were narrowed. Then the lead, having assigned a hunt for exactly that pattern, wrote a FreeBSD changelog entry containing three instances of it, caught only because the reviewer was asked to read it adversarially. The lesson is not that people were careless: writing what a change is FOR is fluent, writing what was PROVEN is not, and the gap is invisible from the inside because both feel like describing the same thing. A commit body is written from the author's vantage, where scoping that is obvious to them goes unsaid, and a reader without the cfg gates in front of them will generalise it every time.

The FreeBSD lane could not run cargo at all: there is no cargo on the host and the container belonged to the gate worker. Every Rust change from that lane therefore arrived unformatted by construction and discovered it inside a gate that stops at `cargo fmt` and discards the rest of the run. That is a workflow defect, not a discipline problem, and the fix adopted mid-round was to request the formatter in the same breath as the commit.

## Follow-ups

- The Windows release job still builds `chan-desktop` twice: the explicit `cargo build --release -p chan-desktop` and sign runs before `cargo tauri build`, which rebuilds it because the tauri build resolves different features. `chan-server` compiles at 10:37, 10:53 and 11:05 in the Windows job of run `32633879594`. A signing-flow decision, not an intake fix.
- `crates/chan-server/build.rs` still emits `rerun-if-changed` unconditionally for `web/.chan-build-stamp` and `web-launcher/.chan-build-stamp`, so a second `cargo build` is a no-op only on a tree whose frontend was built through the Makefile. Guarding both with `if stamp.exists()` was analysed and found safe (the unconditional `rerun-if-changed` on the `web/dist` DIRECTORY covers the empty-to-populated transition under Cargo's recursive directory semantics), about four lines, and was left as scope the round did not take.
- The `Create` arm of `catch_up_candidate` applies no no-follow check, taking `path.parent()` lexically. Whether it is reachable depends on whether notify's recursive kqueue watch descends symlinks, which nothing in the round could test. Recorded as an open reachability question, deliberately not as a finding.
- `.agents/writing-rules.md` says tables target 80 columns or become bullets, while every Active table the roadmap has shipped runs far past that (the v0.95.0 rows measured 474, 240, 330 and 357 columns). The two disagree and someone should settle which wins; this round did not, because reformatting only its own rows would leave the repository inconsistent with itself.
- The `fsync` evidence count in the FreeBSD item is unrecoverable from the evidence that exists: the commit body says 333 of 374, the item said 350, and the item's own suite figures imply 368. The item now states only the measured aggregate transition from 374 failures to 6 and says no per-cause attribution was captured.
- A concurrent terminal creation flake on FreeBSD, `Spawn(Operation not permitted (os error 1))`, reproduced at one failing round in eight under `--test-threads=8` on a loaded guest and passing serially. The port ruled out `openpty` and `setsid`/`ioctl(TIOCSCTTY)` contention with C probes and did not attribute it further.
- Three commits in the range (`ae7f561e`, `540bd2b7`, `6bccf704`) carry a literal `\n\n` in their bodies from shell escaping, and their bodies are single long lines rather than wrapped near 72 columns. Not amended: each had verdict evidence pinned to its sha when the defect was found.

- The FreeBSD arm64 job carries a pinned `nightly-2026-08-23` toolchain because `aarch64-unknown-freebsd` is Rust tier 3 and rustup ships no standard library for it. Pinning converts ambient tier-3 breakage into an explicit maintenance action rather than a release that fails without a change on our side, but it is a standing obligation: the pin must be deliberately revalidated and advanced for future releases, and tier 3 carries no upstream guarantee that a later nightly still builds this target.

## Known gaps

- **No FreeBSD code in this release has ever been executed, on either architecture.** The cross-target checks prove it compiles, under `-D warnings` and with `--tests`, and the arm64 probe proves it links; that is all. The port's own feasibility run on FreeBSD 15.0-RELEASE arm64 is the strongest runtime evidence that exists for chan on FreeBSD, and it was taken at `41fcf6880051`, before the port's fixes and before this release's code. The kqueue catch-up, the `O_PATH` reopen, the `ENOTCAPABLE` classification, the capability-root traversal and its FreeBSD-gated regression test are unexecuted on any machine available to this round.
- `install.sh` on a stock FreeBSD box and `chan upgrade --check` against the published release are unproven on BOTH architectures and remain owner acceptance. The marketing install page labels the FreeBSD command as pending that acceptance rather than presenting it as a completed install path.
- Acceptance 4 of the wake item, sleeping and waking Chan Desktop in a real macOS WKWebView and typing without switching tabs, is unproven; the round's box has no display, no GPU and no macOS.
- Eleven browser-smoke checks fail on unmodified code and this round neither explains nor fixes them. The claim made here is zero regression against that recorded baseline, which is deliberately weaker than "the browser smoke passes".
- The local full `make pre-push` gate did not complete on this box for disk reasons; the gate evidence is the GA commit's own `ci.yml` run.
