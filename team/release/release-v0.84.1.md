# release-v0.84.1

v0.84.1 is a patch release cut the same day as v0.84.0, and its scope came entirely from using that build. One accepted roadmap item shipped, the graph render cost on a large workspace, alongside five fixes found in ordinary use: a search index that kept deleted paths alive, a pane split that wedged the window it split, terminal chrome that ignored a custom background, a devserver join that orphaned its watchdog when its control terminal went away, and a chan-desktop window failure that blamed a browser popup blocker for something no browser was doing. The desktop library-window repair behind that last one was investigated to a root cause, attempted, reverted, and deferred to v0.85.0.

## What shipped

**A settled graph costs nothing to look at.** On a workspace rendering 3519 nodes and 12279 edges at the depth slider's ceiling, selecting a node left the surrounding cluster shaking for seconds and the whole viewport felt heavy while nothing was happening. Two independent causes. `onMouseDown` could not tell a click from a drag, so every press pinned the node and called `sim.alphaTarget(0.3).restart()`; with d3-force advancing alpha as `alpha += (alphaTarget - alpha) * alphaDecay` at an `alphaDecay` of about 0.0228, a 150ms tap raises alpha to roughly 0.05 and then needs about 170 further ticks to decay past `alphaMin`, each rebuilding the charge and collide quadtrees over every node. Pinning and re-heating now wait for the pointer to move past a drag threshold, the same threshold `onMouseUp` already used to separate a tap from a drag, so the two cannot disagree. Separately, the animation loop painted every frame with no condition beyond the keep-alive gate, and the paint pass rebuilt its selection-derived inputs each time: the containment spine allocated two sets, the lit overlay filtered the whole edge list, and each edge pass re-bucketed every edge. Those inputs depend on graph structure rather than node positions, so they are now memoised against a working-set revision and the current selection, a `dirty` flag gates the paint itself, and nodes and edges fully outside the viewport are skipped, with labelled nodes exempt because a label is drawn centred above its disc and can extend well past it. Measured on the same workspace and the same gestures: idle paints over three seconds 196 to 0, paints from one click 412 to 1, and layout motion after that click 6606ms to 0ms. At that size a frame cost roughly 375ms, so the idle graph had been running under 3fps. Dragging still moves the layout and re-heats, releasing still settles, and paged node loading is untouched. `graph/force.ts` is not modified, so the layout looks the same.

**Deleted directories leave search, and the defect v0.84.0 shipped with is closed.** `Bm25Index::known_paths()` walked each segment's path term dictionary directly, and Tantivy retains terms from deleted documents until a segment merges, so deleting a directory left its paths answering user-facing queries. Path terms are now verified against live postings via the segment's `alive_bitset()` whenever a segment carries deletions, and clean segments keep the term-only fast path, so the extra work is paid only where it buys correctness.

This is the accessor v0.84.0's own retrospective recorded as still defective. It is also the reason v0.84.0's tagged release run failed on its first attempt: `indexer::tests::apply_watch_change_directory_delete_forgets_subtree` depended on segment layout for its result, passed in that release's rehearsal and GA CI, and failed in macOS validation on the tag, which was finished with a failed-job rerun rather than a fix. Both halves are now pinned deterministically. A new test merges a two-document index down to one segment carrying one live and one deleted document and asserts `known_paths()` returns only the live path, and the previously flaky test gained assertions that query through the user-facing BM25 path rather than through index internals.

**Splitting a pane that hosts a terminal no longer wedges the window.** The split blanked the terminal body and left the window stuck. The terminal component tears down as its leaf is re-parented, its socket close runs the metadata sink's unregister, and that walks the whole layout through `terminalTabsIn`. The walk runs inside the Svelte batch the split commits, and a torn-down branch reads pre-batch source values, so the new pane and split nodes enumerate as keys but read back `undefined`; `Object.values` then handed out holes and `node.kind` threw. The throw aborted the render flush, so the destroyed terminal was never rebuilt and the reactive graph stayed stuck. The teardown now skips the holes, which is exactly the layout-as-it-was view it wanted.

**Terminal chrome matches a custom background.** v0.84.0 shipped custom terminal colours and resolved contrast for the terminal surface, but the body, host padding, viewport and scrollbar track kept the standard theme's background, so a custom background rendered as a patch inside foreign chrome. All four now paint with the resolved custom background and fall back to the standard theme when custom colours are off.

**A devserver join detaches cleanly when its control input goes away.** A join reading from non-TTY stdin treated EOF as something other than a detach, so losing an SSH session or a control terminal could leave healthy watchdog processes orphaned. EOF on non-TTY stdin is now a clean detach; TTY joins remain Ctrl-C-driven, and both EOF and restart survival are covered at the process boundary. The EOF branch deliberately prints nothing, because the controlling pipe is normally gone with it and `eprintln!` would panic on a broken stderr pipe.

**A chan-desktop window that cannot open says so honestly, and the next occurrence will be legible.** The command deck's library flow depends on `window.open`, which returns `null` in every chan-desktop webview, and the failure surfaced as a message telling the user their browser had blocked a popup. chan-desktop has no popup blocker, so that message sent the user hunting for a setting that does not exist. Both call sites now route their error through `blockedWindowMessage`, keyed on `isTauriDesktop()` alone, which names the failure as a known chan-desktop limitation rather than a browser setting. The window still does not open; only the explanation is fixed.

Diagnostics landed alongside it, because the ACL refuses `gateway_csrf_token` before any command handler runs, so a refused window previously left no trace on either side of the bridge. The webview now records each refusal with its own origin and the window and webview labels it presents, and logs one `console.error` per distinct record, deduped because the transport calls this on every unsafe request and a loopback window's expected denial should cost one line rather than one per request. The record is deliberately not filtered on a `lib-*` label: the minted capability matches `windows: ["lib-*"]` on one exact origin, so a window presenting a different label is itself a candidate explanation, and filtering would hide exactly that finding. On the desktop side, `mint_exact_origin_grant` now logs the `exact_origin` at mint time and a debug line when a mint is skipped as already-minted. Read as a pair, the two distinguish an origin that was never minted from one minted for a different origin or label than the window carries.

## What did not ship

**Opening a library window from chan-desktop is still broken, and the repair is deferred to v0.85.0, specced.** An SPA-only branch was written and reverted whole after live testing, so no part of it ships: the scoped library action mints `WindowOrigin::Browser` unconditionally (`library.rs:825`, `:837`) and the window watcher refuses browser-origin records by design (`window_watcher.rs:230-236`), so the branch created records the launcher listed while no native window ever appeared. Orphan records are worse than the honest error they replaced, which is why the revert was total rather than partial. Raising an already-visible native window was never fixed either: the launcher does it over an HTTP route `workspace-app` cannot reach, and no Tauri command focuses a window by label. The accepted approach is recorded in the item: the desktop mints the native-origin record through a capability-gated command, so the ACL that already scopes `lib-*` windows to an exact origin governs it. That needs new native commands plus permission wiring into both the workspace-window set and the minted gateway capability, which is more than a patch release carries. Setting Tauri's `on_new_window` was evaluated and rejected, because under both Allow and Create it adds a second, differently labelled window: the correct label is not knowable until the record the popup precedes exists. What this release keeps from the investigation is the honest message and the diagnostics, which is the part that was ready.

**Standalone terminal appearance settings are registered for v0.85.0, not specced.** The v0.84.0 appearance settings do not take effect in a standalone terminal window. What is established is recorded, that a standalone terminal is the same SPA in terminal-only mode, that both kinds render the same `TerminalTab`, and that the settings command is reachable there. Where the chain breaks is deliberately not claimed, because the candidate causes need different fixes.

## Process

The round ran on `v0841-base` on 2026-08-05, the day v0.84.0 shipped, as four topic branches merged into the base (graph render perf, the archive-round skill, terminal chrome background, devserver control-input join lifetime) plus direct commits on the base for the desktop library-window investigation chain, the BM25 fix, the split-teardown fix and the vitest Storage pin. Every item entered from the owner running the shipped build, not from a plan.

The desktop library-window work is the shape worth recording. It arrived as a field report of a gateway window losing its IPC grant after an outage, was registered for v0.84.1 with two candidate root causes, and both were retired by evidence rather than by argument: the owner deleted the keychain token, re-authorized through a fresh browser OAuth and reopened the machine, and the refusal was identical, which rules out the mint path since that flow runs the only mint site and creates the window after it. Measuring through the real click path in both a gateway-served window and a local `http://127.0.0.1` one then showed the failure identical in both, so it was never gateway-specific and `gateway_csrf_token` was not involved at all. The item was rewritten and renamed around what had actually been established, the fix that could ship shipped, the fix that could not was specced and deferred, and the reverted attempt stayed in the record with the reason it was weaker than it looked.

The gitignored `dev/` round-artifact handoff to the `chan-dev` archive repository gained a tracked skill, `.agents/skills/archive-round/`, so the release-close step that moves round artifacts out of the working tree is written down rather than re-derived.

One change entered during the release cut itself rather than from the round. The disposable Nix build guest stopped being able to build at all: it sets `/var/tmp` to 0755, then installs its packages, and a systemd tmpfiles pass during that install restores the `q /var/tmp 1777` default from `/usr/lib/tmpfiles.d/tmp.conf`, after which a newer guest Nix refuses to build under a world-writable temporary directory. Nothing in the repository changed to cause it; v0.84.0 harvested its hashes through this path one day earlier, so the trigger is guest package drift from the live Ubuntu archive. Because the fixed-output harvest is the step that keeps the Cachix lane from shipping stale hashes, and v0.81.0 and v0.83.3 both lost that lane by shipping hashes that were never verified, the driver was fixed as part of this release rather than worked around. The mode is now applied both before the install, because package postinst scripts inherit `TMPDIR` and `update-ca-certificates` fails outright when it points nowhere, and again after the install, because that is when the tmpfiles pass has already undone it.

The release was cut by a host agent in the owner's session against an explicit authorization to gate locally, merge onto `main`, run the `publish=false` dry run, and tag if every check was green.

## Retrospective

The best-shaped work in this release is the investigation that shipped least. The desktop library-window item was handed two plausible root causes and disproved both with live evidence, then narrowed the failure from "gateway windows lose their grant" to "`window.open` returns null in every chan-desktop webview" by measuring the same click path in two window kinds. Everything that followed was cheap because the diagnosis was right: a message that named the real cause, diagnostics that make the next occurrence legible, a repair attempt, a revert with reasons, and a spec for the version that can carry it. Registering it against the wrong subsystem cost nothing in the end, because each retired hypothesis was written into the item with the code reason for retiring it.

The BM25 fix is the counterexample worth sitting with. v0.84.0's tagged release run failed on this exact defect, in macOS validation, after the tag was already pushed, and it was finished with a failed-job rerun. The retrospective for that release named the accessor as still defective and moved on. A rerun is a legitimate way to finish a release when the alternative is a bad GA, but it converted a known correctness bug into a flaky test that a later release had to notice again independently. The fix here is small, and it was one day of latency away from being free.

The lowlight is that the terminal appearance settings shipped in v0.84.0 needed two follow-ups within a day: the chrome fix in this release, and the standalone-terminal gap now registered for v0.85.0. Both are the same omission, that a setting was implemented for the surface it was demonstrated on rather than for every surface that renders a terminal. The custom-background work already had to reach padding, scrollbar, find bar and canvas to look right; that it did not also reach the body and viewport, and that nobody opened a standalone terminal, is a coverage gap in how the feature was accepted rather than a defect in how it was built.

One gate finding is worth keeping. Node 24 and later ship a built-in `localStorage` global, an accessor on `globalThis` that yields `undefined` without `--localstorage-file` and that outranks the `Storage` vitest's jsdom environment installs; `sessionStorage`, which Node does not claim, comes through as a real jsdom `Storage`. Two persistence-seam suites died in their own `beforeEach`, 68 tests down. CI pins Node 20 and stayed green, so the gate disagreed with the run that decides the merge, which is the one shape a gate must never take. A setup file now installs an in-memory `Storage` whenever the environment fails to supply a working one, which fixes the local run without loosening what CI verifies.

### Honest feedback

Two of this release's six changes exist because v0.84.0 shipped a day earlier with a known-defective accessor and an appearance feature wired to one surface. Neither was hidden; both were written down. The cost of shipping a recorded defect is that someone rediscovers it from the outside, and here that someone was the release process itself, one release later, at the point where it is most expensive to notice.

## Follow-ups

- `make web-lock-check` does not catch a workspace member's own `version` field drifting from the lockfile, only dependency-pin desync and dropped workspace links. A control mutation of `web/packages/profile/package.json`'s `version` passed the check, because nothing depends on `@chan/profile` with a pinned range, so its version is not a constraint `npm ci` validates. Nothing else asserts the web `version` fields either: `release.yml`'s context job checks the Cargo, desktop, and gateway versions against the tag and not the web `package.json` files. A version bump that missed one web package would therefore ship silently. This release is unaffected, since all seven web pins were bumped and the tree was scanned for residual `0.84.0`, but the gap is real and belongs in the next packaging pass.
- `desktop-library-window-open-unavailable` carries the deferred repair to v0.85.0 with its accepted approach specced and its rejected alternatives recorded. Opening or raising a library window from chan-desktop remains broken until it lands; this release only makes the failure honest and diagnosable.
- `standalone-terminal-appearance-settings` is v0.85.0 scope and needs the break in the chain located before it can be specced. The candidate causes need different fixes, so locating it is the work.
- Settling after a deliberate drag on a graph that size still takes tens of seconds. d3-force's alpha schedule is a fixed tick count and this release does not touch it; bounding the charge force's range and scaling `alphaDecay` with node count are the levers, and both change how the layout looks, so they are a separate decision rather than part of a performance pass.
- The desktop `gateway_csrf_token` refusal record is deliberately not filtered on a `lib-*` label, because a window presenting a label the capability does not match is itself a candidate explanation for a future occurrence. If that shape never appears, the filter can be tightened.
- AUR publication for v0.84.1 is outstanding on an AUR-side maintenance window and needs one dispatch once the git service returns. The larger item is that the AUR has been stale at `0.82.0-1` for six releases while each individual failure was written off as a transient outage. Each release's report recorded its own outage truthfully, and nobody compared those records against what the AUR actually serves, so a per-release non-blocking failure accumulated into a permanently stale package. The publication probe pattern that COPR already uses, asserting that the live published version equals the tag, is the shape that would have caught it; the AUR path has post-push RPC verification but it is advisory and skipped entirely when the push itself fails.
- The Nix guest breakage in this release was caused by package drift in a `--install-packages=yes` guest built from the live Ubuntu archive, which means the harvest path can break between releases with no repository change. It broke here between v0.84.0 and v0.84.1, one day apart. The driver is fixed for this shape, but the general exposure remains: a release-blocking tool whose inputs float.
