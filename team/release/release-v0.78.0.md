# release-v0.78.0

v0.78.0 is a narrow correctness release. It ships two unrelated fix families and nothing else: the editor now converges on external filesystem edits that restore or shrink a file, and the Linux desktop clipboard actually survives a copy while generated supervisors keep pointing at the CLI rather than the GUI. Everything else that was in flight, including video preview with HTTP range serving, the ghostty terminal backend, and the DOOM overlay, was deliberately held for v0.79.0.

This cycle is cut directly to GA with no RC pin. The `0.78.0` commit remains untagged until that exact commit passes the local pre-push gate, a `release.yml` dispatch with `publish=false`, the separate cache-only downstream rehearsal, and artifact inspection. A red rehearsal is a stop condition for the release owner.

## What shipped

**External filesystem edits that restore or shrink a file reach the editor.** A doc or scene session keeps a ring of content hashes so a filesystem that commits asynchronously cannot make the session's own flush echo look like an external edit. Entries did not record where they came from, so bytes the session merely READ from disk earned the same 60s protection as bytes it WROTE, and an external edit returning a file to content the session had already seen was classified as an echo and held back. That is the shape of every undo, revert, and `git checkout`, and the shape agents produce when they edit files through the filesystem rather than through the MCP server. Ring entries now carry an origin: written bytes keep the full 60s window, because an upload queue really can replay them under a re-stamped mtime; adopted bytes get 1500ms, which covers a stale read racing the watcher event that announced them and nothing beyond that. The empty-read refusal now requires a recent write of the session's own to blame, so truncating a file the session never wrote converges after the ordinary corroboration delay instead of waiting out the ring. Measured against the previous behavior, an external restore reaches the editor in 28ms rather than 58.6s, and a truncation in 407ms rather than not at all.

**This closes a root cause that v0.76.0 had only bounded.** The same defect was registered and partially fixed one release earlier as `editor-external-restore-echo-swallow`. That fix made the echo ring re-check after its TTL instead of clearing the observation, which converted permanent staleness into a bounded 60s window, and the window was accepted at the time. v0.78.0 removes the window rather than shortening it, by fixing the classification that created it. The written-versus-adopted asymmetry is deliberate and is recorded in scenario WL-15 so a later reader does not collapse the two origins back together.

**Native clipboard operations no longer block the desktop invoke thread.** A Tauri command that is not `async` runs on the main thread, so the six native clipboard commands held it for as long as `arboard` took. On X11 that is unbounded: probing a target the selection owner never answers stalls for seconds, and the window could not even render the `cs paste` request card while it waited, which reads as a frozen app. macOS keeps the commands synchronous because NSPasteboard must be touched from the main thread; every other platform exposes the same six names as async commands running through `spawn_blocking`, with one process-wide mutex taken inside the blocking closure to preserve the mutual exclusion the single invoke thread previously provided for free. `arboard` gains `wayland-data-control`, target-gated to non-macOS unix, so a Wayland session uses the wlr data-control protocol instead of being served through XWayland; it adds no shared library the desktop binary did not already link.

**A Linux copy survives long enough for the session to take it.** X11 and the wlr data-control protocol serve a selection from the owning client: the bytes live in the owner, not in the display server. Every clipboard operation created its own handle and dropped it in the same expression, so a `cs copy` owned the selection for microseconds and released it before the session's clipboard manager could take a copy, and the paste target kept seeing the previous contents. Measured on X11 plus Plasma, dropping immediately loses the contents and holding the handle 250ms keeps them. The six operations now acquire through one helper that, on Linux, owns a single process-wide handle connected on first use and reused, so chan stays a real selection owner; a failed operation discards it, because a handle whose connection died with its X session would otherwise fail every later operation for the life of the process. Off Linux the helper expands to the expression each command already had, deliberately, because NSPasteboard is server-side and on Windows opening the OLE clipboard locks every other app out until it is closed.

**Generated supervisors keep the chan entry point instead of launching the GUI.** chan-desktop dispatches the CLI only when invoked through a `chan` name, so a supervisor's executable basename is the personality selector. Distro packages ship `/usr/bin/chan` as a symlink to `chan-desktop`, and `current_exe()` on Linux reports the symlink target, so the unit writer persisted `ExecStart=/usr/bin/chan-desktop devserver`: a unit that starts the desktop GUI instead of the devserver, reproduced on Arch with the shipped 0.77.0 binary. Resolution now splits into live discovery plus a pure selector that prefers a `chan`-named `current_exe()`, then an existing `chan` sibling next to a `chan-desktop` binary, then the CHAN_HOME-aware local `bin/chan` shim. The selected path is deliberately not canonicalized, because resolving a `chan` symlink back to `chan-desktop` is the bug. The same resolver feeds the systemd and launchd writers and the `--service=chan` daemon re-exec, which had the same wrong-personality hazard. A desktop binary with no `chan` entry point anywhere is now a clear error rather than a supervisor that would launch the GUI.

## Team and process

No team round. Every commit in this release is the owner's, prepared on two independent branches (`v0780-editor` and `v0780-linux-clipboard`) before the release session, then merged and cut to GA by a single agent session acting as integrator rather than implementer.

The cycle was deliberately kept narrow. Three items with work already on branches, video preview with range serving, the ghostty terminal backend, and the DOOM overlay, were held rather than folded in, on the reasoning that two small, independently verified fix families make a clean release and three larger unspecced ones do not. Both deferred branches still sit on the v0.77.0 GA commit and need rebasing onto post-0.78.0 main; that is recorded in their v0.79.0 roadmap notes rather than done here, so this release touches neither branch.

The clipboard branch was rebased directly onto the editor merge, so integration was a fast-forward-safe `--no-ff` merge with no conflicts possible. The clipboard commits had not been gated by the release session before the merge, so the full gate ran on the merged tree rather than being inherited from the branches.

## Validation

- The full Rust gate on the merged tree passed with 2589 tests, 0 failed, 3 ignored, including 905 chan-server, 640 chan-workspace with 2 ignored, and 314 chan-desktop. Clippy `--all-targets` with warnings denied, `cargo fmt --check`, and the no-default-features build passed on the same tree.
- Shellcheck over 48 tracked scripts, actionlint, and the build-matrix contract passed. These were load-bearing rather than formalities here, because the supervisor-entry commit touches generated systemd units.
- Both editor unit tests and both new browser checks were confirmed to fail when the origin split is removed, and to fail only on the restore, cycle, and truncate steps. This is a mutation proof, not a green-suite claim.
- Clipboard handle reuse, discard-after-failure, and cache-nothing-on-failed-connect were each mutation-checked: never reusing, and keeping a broken handle, each fail the test. A current-thread async test proves a short timer progresses while a 200ms operation runs and fails if the operation runs inline; a concurrency test proves operations never overlap under the guard.
- The supervisor selector carries a table-driven pin over the standalone CLI, distro sibling, local shim, AppImage run, unrecognized name, missing `current_exe`, and both no-entry-point errors, asserting no selection is ever the desktop binary, plus a pin that the generated systemd `ExecStart` and launchd `ProgramArguments` both start `chan devserver`. Verified live on Arch against a real `chan` -> `chan-desktop` symlink: the shipped binary writes `chan-desktop`, the patched one writes `chan`, and a planted broken unit is repaired.
- Browser check `57` previously asserted the old deferral and budgeted 75s for it; it now asserts prompt convergence. New check `63` covers partial shrink, restore of prior bytes, rapid add and remove cycles, truncation to empty, and refill.
- The clipboard evidence is X11 plus Plasma. The Wayland data-control path and the macOS and Windows clipboard branches were compile-checked, not exercised on their platforms. launchd generation is pinned by test, not run on a real macOS host.
- Native macOS signing, notarization, stapling, updater signing, and signed Windows packaging remain proven only by the mandatory `publish=false` release workflow.

## Retrospective

**Highlights.** The editor fix is a genuine root-cause close rather than another bound on a known-bad window, and it was proven by mutation in both directions: removing the origin split fails the new tests, and it fails only on the steps that exercise the bug. The clipboard work resisted the obvious symmetric fix; holding a process-wide handle is correct on Linux precisely because the selection lives in the owning client, and wrong on macOS and Windows for reasons that are written down in the code rather than discovered again later. The supervisor fix was reproduced against a real shipped 0.77.0 binary on a real distro layout before anything was changed.

**Lowlights.** The restore-swallow class survived a full release because the browser-smoke suite had never shrunk a file in any check. Every external-edit check added content or replaced it with novel content, and both of those converged correctly; the bug lived exactly in the untested direction. A suite can be broad and still have a hole shaped like an entire category of user action. The v0.76.0 fix also illustrates the cost of accepting a bound instead of chasing a cause: the accepted 60s window was a real user-visible defect for one more release.

**Honest feedback.** Three of the four platform behaviors this release depends on are not exercised by anything that runs here. The Linux clipboard measurement is real and was taken on real hardware; the Wayland, macOS, and Windows branches are compile-checked reasoning. That is an acceptable trade for a fix whose failure mode on those platforms is "unchanged from before," but it should not be described as tested. Keeping the release narrow was the right call and cost nothing: two fix families with mutation proofs and a live reproduction are a better release than five items where two are unspecced prototypes.

- Check `60-launcher-collapse` hard-fails when the launcher bundle is absent, where its sibling `95-launcher-native-trust` skips. Make the two agree.
- The full browser-smoke suite is contention-sensitive on an 8-core host: a different incidental check reds on nearly every full run, including on a build with the editor fix removed. Until that is fixed, only a focused re-run is evidence, and a full-suite red is not.
