# The screen lock's PIN field takes no typing and a test lock has no exit

Status: raised by the owner on 2026-10-15, the day v0.106.0 shipped, from the settings' Test action on a workspace with a PIN set. Written down and verified at source: the key path read in `App.svelte`, `ScreensaverOverlay.svelte` and `store.svelte.ts`, and a throwaway jsdom probe run on the real App mount and on the overlay alone (readings in "What was seen", not kept). Built on 2026-10-15 as option one of "Desired contract" (a Test stays the real lock, the typing is repaired, no Esc exit), pending the owner's decision on the test exit; see "Repair 2026-10-15". Not shipped; owner the frontend seat.

## What was seen

The owner's report, in the owner's words:

> Workspace screen lock
>
> Bug: cannot type PIN on the test screen lock
>
> Repro:
>
> 1. Open the settings window
> 2. Click "This workspace"
> 3. Enable "Screen lock" at the bottom
> 4. Click "Set PIN" then set the PIN and the same value for Confirm and click "Save"
> 5. Then click "Test" to test the screen lock
>
> When you move the mouse and the PIN dialog comes up, you cannot type on it. And there's no way to ESC or stop the test either; The workaround is to use Cmd+R to reload the workspace window and the test screen lock goes away.

The path as the code takes it. Settings is an overlay inside the workspace window (`SettingsOverlay` mounted in `web/packages/workspace-app/src/App.svelte`, an `OverlayShell` at z-index 25000 plus its depth), so the Test locks the window the settings are in. The Test button in `components/settings/workspace/ScreenLockControl.svelte` (`testScreenLock`) reloads the server-side state and calls `lockNow()` in `state/screensaver.svelte.ts`, which sets `screensaver.locked = true`; the launcher command `app.screensaver.test` ("Screen lock: test") in `state/commands/global.ts` makes the same call. `components/ScreensaverOverlay.svelte`, mounted last in `App.svelte` at z-index 39000, paints the backdrop over the settings and focuses it; the first keydown or click on the backdrop wakes the unlock card (`onBackdropKey`, `onBackdropPointer`), and with `pin_set` the card's PIN `<input>` is focused and selected. The input's own `onkeydown` handles Tab (the focus trap) and Enter (`submit`); the Unlock button calls `submit` too; Esc and a click on the backdrop have no branch, by design. While locked the overlay registers `setCoverBlocking("screensaver", true)` in `state/store.svelte.ts`, and `appInputBlocked()` reads true.

`App.svelte` registers `onWindowKey` on `document` for `keydown` in the bubble phase (`onMount(() => document.addEventListener("keydown", onWindowKey))`). Its first branch, while `appInputBlocked()` is true, calls `e.preventDefault()` and `e.stopPropagation()` on every keydown whose `code` is not `Backquote`, with no modifier check and no target check. A character key's default action is the insertion into the focused field (the `beforeinput` and `input` pair), and the browser runs it only after the dispatch ends, so a document-level listener cancelling the keydown cancels the insertion: a digit typed into the PIN field never lands. The overlay's own handlers run earlier in the same dispatch (Svelte's delegated handler sits at the mount root, `#app` in `main.ts`, below `document`), which is why Enter still submits what the field holds, and the field holds nothing. The guard's comment says what the cover offers, "a Retry button, a PIN field", is a focused element and is unaffected; that is true of a button, which acts on a click, and false of a text field, which acts on the keydown's default. The guard shipped in `b765d8b04` (the closed item [full-window-covers-do-not-block-input](../done/full-window-covers-do-not-block-input.md), [v0.100.0](../../release/release-v0.100.0.md)), which generalized the reconnect overlay's `ui.disconnectBlocking` branch, written for a cover whose only control was that Retry button, to every cover in `FULL_WINDOW_COVERS`; the screensaver lock became "a real boundary" by the owner's ruling recorded there. That item's acceptance 2 (a synthetic Ctrl+D, Ctrl+Shift+T and a host command change nothing; Backquote passes) and acceptance 6 (focus cannot leave the PIN field; a native menu command changes nothing until the PIN is accepted) test chords, commands and focus; none of its six points types a character into the PIN field, so the lock was accepted as a boundary without a reading that the boundary can still be opened.

The probe, run on 2026-10-15 in jsdom with the real App mounted on the demo workspace (the cover contract test's fixture, `api.screensaverState` answering `pin_set: true` so the boot's load holds the PIN branch), the lock raised, the card woken by a click and the PIN field focused, each keydown dispatched on the field with `bubbles` and `cancelable`:

| keydown on the PIN field               | prevented | effect                  |
| --- | --- | --- |
| `1` (Digit1), App mounted              | true      | nothing lands           |
| Enter, empty field, App mounted        | true      | "Enter a PIN to unlock" |
| Enter, value set by an input event     | true      | `screensaverVerify` ran |
| Backquote with Meta, App mounted       | false     | passes                  |
| Ctrl+D, App mounted                    | true      | blocked                 |
| `1`, screensaver registration lowered  | false     | same App, same DOM      |
| `1`, registration raised again         | true      |                         |
| `1`, overlay mounted alone             | false     | no App listener         |

Outside the keyboard: a click on the Unlock button with the empty field runs `submit` and shows "Enter a PIN to unlock" (`screensaverVerify` not called); `mousemove` and `pointermove` on the backdrop leave the card hidden, a click shows it, and the field is then `document.activeElement`. jsdom inserts no text on a keydown, so the field's value is not a reading there; `defaultPrevented` on the digit is. The lowered-and-raised pair isolates the cause to the registration the guard reads: nothing else in the App changes between those two readings.

Why the suite is green. `components/ScreensaverOverlay.test.ts` ("the card takes the PIN, focused, and unlocks when the server verifies it") mounts the overlay alone, so `App.svelte`'s document listener is absent, and it fills the field by setting `input.value` and dispatching an `input` event rather than a keydown, so it would stay green with the guard present too: vacuous for this path twice over. `components/screensaverPinFocus.test.ts` mounts the overlay alone and dispatches Tab only; its header records that the App fixture's boot overwrites `pin_set`, which is why no App-mounted test holds a PIN today (the probe holds one by answering the boot's load). `components/fullWindowCoverContract.test.ts` mounts the real App: "the screensaver lock blocks it" and "the screensaver lock blocks the new-terminal chord" press Ctrl+D and Ctrl+Shift+T on `document` and read that the tab survives and no terminal spawns, and "Tab does not reach the lock's own dismissal" dispatches `a` and Tab on the backdrop with no PIN set. Those assert the blocking a repair must keep; none types into the PIN field. No browser check covers the screen lock: `scripts/e2e/browser-smoke/checks/` has no file naming the screensaver or the screen lock (a control search for "settings" finds seven).

The second symptom. With a PIN set, a Test is the real lock: `testScreenLock` makes the same `lockNow()` call as `Mod+L` and `app.screensaver.lock`, the overlay's one exit is a verified PIN (`unlockWithPin`), and with the field taking no typing there is no exit at all. Lock state is client-side only (`screensaver.locked`; `state/screensaver.svelte.ts` records that there is no server-side locked view), so a reload boots unlocked, which is why Cmd+R ends it. Without a PIN set a Test ends on the next key or click, so the owner's five steps are the one path with no way out.

Not established. Whether mouse movement alone woke the card: the overlay wakes it on a keydown or a click, `pointermove` is read only by the inactivity tracker (`installScreensaverTracker`), which returns early while locked, and the probe's `mousemove` and `pointermove` moved nothing; the report does not say whether a click or a key followed the movement. The owner's engine: Cmd+R names macOS; on the desktop the key bridge (`desktop/src-tauri/src/key_bridge.js`, a `window` capture listener) reloads the webview through IPC on Cmd+R ahead of the SPA's guard, and in a browser the guard cancels the Cmd+R keydown while macOS browsers reload from the menu accelerator regardless, so either reading matches the workaround and which one ran is not recorded. Whether the digit's insertion is also cancelled in WKWebView was not read; the keydown default is the same contract in every engine and the browser reading in the acceptance settles it.

## Desired contract

Behind the screen lock, a keystroke aimed at the lock's own surface reaches it: a digit typed into the PIN field lands, Enter submits it, and the Unlock button submits it; a wrong PIN shakes and clears as it does today. Everything that drives the app behind the cover stays blocked: Ctrl+D, Ctrl+Shift+T, the reload chord, the other chords and the host commands, with Backquote still passing to the window cycler and focus still trapped in the field. This is the floor for every cover: the reconnect, session-ended, missing-token and preflight surfaces hold buttons, so a target-scoped pass changes nothing for them.

What a Test lock is remains the owner's decision, with three options. One: a Test is the real lock, today's shape with the typing repaired; its exit is the PIN, and what the owner sees in a test is what a user meets at the timeout; the trade-off is that a PIN just set and then mistyped or forgotten makes the test a lockout ended only by a reload, which loses nothing (the lock state is client-only) but is not an exit a user can be expected to find. Two: a test lock carries an exit the real lock does not, Esc ending it or an "End test" control on the card, with the overlay told it is a test (a flag beside `locked`, set by `testScreenLock` and cleared by any unlock); the trade-off is that the test stops proving the boundary it exists to show, and the flag is one more state for the overlay and the cover contract test to carry. Three: Esc ends every lock; this makes the lock a cosmetic cover and reverses the owner's ruling of 2026-09-20 in the closed item, so it is out unless the owner reverses that ruling. The recommendation is option one: the repaired PIN field is the exit, the Test shows the lock as it is, and the owner's "no way to ESC or stop the test" was read while the one exit was broken. If the owner wants an exit anyway, option two with Esc on a test lock only, pinned so that Esc never ends a real lock.
