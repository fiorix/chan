# Session saves are not serialized against each other or against a peer's frame

Status: built on 2026-10-16 on the seat's branch; the section Build 2026-10-16 holds the evidence; it closes at the GA as shipped.

Record before the release: raised by the frontend seat on 2026-10-13 from its repair of the moved-terminal item ("Remaining paths" of `tasks/task-Frontend106-Lead106-25.md` in the round's bus); written down the same day by the lead as a row of its own, outside that item; owner the frontend seat; not reached in the v0.106.0 round

## What was seen

Read at source in `web/packages/workspace-app/src/state/store.svelte.ts`, not run. The moved-terminal item's repair makes `applyRemoteSessionBlob` await the flushed write before it re-arms the refetch. Three paths beside it remain: a failed flushed PUT stops the re-arm, so the removed terminal stays absent in this page, but the dedupe snapshot was advanced before the PUT, so an identical later save may not retry and a reload can read the old blob; a debounce PUT already in flight has no pending timer to flush, so a peer's frame arriving in that interval can still fetch without waiting for it; and two overlapping own PUTs can finish out of order, the older blob landing last.

## Desired contract

One window's session saves reach the server in the order they were made, a peer's frame never makes this window read back a blob older than a save of its own that is still in flight, and a save that failed is retried or reported, not forgotten behind a dedupe. Two writes stand outside the order: the exit write and a discard's DELETE are not ordered behind a write in flight, and the last writer wins between them and it (narrowed by the lead on 2026-10-16, with the review of the design as the evidence; the section Lead's rulings 2026-10-16).

## What to do

Construct each path as a store test with the PUT held (the moved-terminal item's test file has the fixture): the failed save with the dedupe, a peer frame during an in-flight debounce save, two overlapping saves released in the reverse order; read the outcomes. Then design, to the review seat before code: one in-flight save at a time with the latest state coalesced behind it, the refetch awaiting any in-flight save, the dedupe snapshot advanced only on success.

## Boundaries

`web/packages/workspace-app/src/state/store.svelte.ts` (the session save and the remote blob's application), `state/sessionSync` and their tests. Not changed: the server's session route and its last-writer rule.

## Lead's rulings 2026-10-16

The frontend seat's design (one session write in flight with later saves coalesced behind it, the dedupe on what the server is known to hold, a failed write retried, the co-view read waiting for the window's own write), designed with the dropped-tab row, was accepted in shape by the lead on 2026-10-16 and read by the review seat (`reports/design-Frontend107-sesser-tablos.md`, `reviews/review-Review107-29-sesser-tablos-design.md` in the round's bus). The lead's rulings that bear on this row, in its words:

1. "A failed save is retried with a back-off; after two failures in a row the status reports it; a later success clears the report."
2. "The three races that stay last-writer (two pages changing the layout inside one debounce window; the exit write beside a write in flight; a discard's keepalive DELETE beside a PUT in flight) need a versioned or conditional PUT, a server change the sesser row's boundary keeps out; they are stated in both rows' closing sections as the rule, with the session alive in each."
3. "Two commits, sesser first and tablos on it, one per item."
4. "The sesser contract's first clause is narrowed in the row: the exit write and a discard's DELETE are not ordered behind a write in flight; last-writer is the rule for those two. The client-side narrowing is taken: at a discard with a write in flight, the same DELETE with its `moved` and `session` query is sent again once that write settles if the page still lives (the server takes a repeat: a missing key answers 204; forget or unpersist run again); one pin (a discard during a write, then the write settles, then a second DELETE) and one mutant (no resend)."
5. "A save queued behind a write that then fails waits for the back-off, and the retry carries the latest layout; one write out at a time, the back-off belongs to the series; its failures count toward the report as the series' failures; a success resets. Pin: a save queued during a failing write sends no PUT before the back-off elapses, then one PUT with the latest layout; mutant: the queued save sent at once."
6. "line 3882's echo check stays as it is; no pin."
7. On the review seat's read of the build (`reviews/review-Review107-45-sesser-range.md` in the round's bus): "F1 (a product fix): every failure after the second sets the report again, so a persistent status set after the report is overwritten by the next failure and then cleared to null by the success. The report is set at the second failure and afterwards only while it still shows"; "G1 (a pin): Hybrid Nav's wait for a write in flight"; "G2 (a pin): the GET guard's `sessionSaveSeq !== asked` arm (a write that started and landed while the GET was out)"; "N1, taken: a seed during a back-off closes the series: the failure count resets and the report is cleared only while it still shows, since a seeded layout has nothing owed; one pin, one mutant."

## Build 2026-10-16

Built in `web/packages/workspace-app/src/state/store.svelte.ts`, the design read first by the lead and the review seat (the section above). A window has one session write out at a time: a save asked for while one is out waits for it and then serializes the layout as it is, so a burst reaches the server as one write after the first, in the order made, and it sends nothing when the server already holds its layout (`savedSessionSnapshot`, a successful answer or a seed, not the snapshot sent, which may not have landed). A failed write is retried after a back-off of 1 s doubling to 30 s, which a success resets; a save asked for during the back-off waits for the retry, which carries the layout as it is; the second failure in a row sets the persistent status `layout not saved: <reason>`, and a later failure updates it only while the status still shows it; the series ends at the next write to land, or at a seed of a layout during the back-off (an applied blob, a peer's DELETE), which leaves nothing owed: the count starts again and the report clears while the status still shows it. The co-view read (`applyRemoteSessionBlob`) never applies a blob older than the window's own save: it sends a save waiting in the debounce or the back-off first (a read that comes due during a back-off sends the retry at once, its failure counting as the next), waits for a write in flight whatever frame armed it, and re-arms behind the write; a waiting save that sends nothing lets the GET go out at once; a write that fails leaves the read owed to the next write that lands; a blob answered after a local write started, or after the layout changed, while its GET is out is dropped and the read taken again. A discard with a write in flight sends its DELETE again once that write settles. The workspace app's design text holds the rules (`src/design.md`, "A window's session saves").

What stays the last writer's, as the lead ruled, with the session alive in each: two pages that each change the layout inside one debounce window (the later write wins, and the other page's reconcile drops a terminal its layout lacks; the session stays alive and listed by `cs terminal list`); the exit write beside a write in flight (either can be stored last; the window's sessions stay as they are); and a discard's DELETE beside a PUT in flight (the PUT can be stored after the DELETE and write the blob back, so the window shows in `cs window list` until its next discard; the repeat closes it whenever the page outlives the write; the discard's reap of the window's sessions runs either way, and a moved session stays alive with the window it moved to).

The pins are `state/store.sessionSaves.test.ts`, 26 cases with every write held for the test to answer or fail, and two cases in `state/store.exitFlush.test.ts`: the overlapping-saves case there rewritten to the one-write form (a save asked for while another is out waits for it, and the exit flush sends it when the page goes first), and a failed save with the page going before its retry giving one keepalive PUT of the layout as it is.
