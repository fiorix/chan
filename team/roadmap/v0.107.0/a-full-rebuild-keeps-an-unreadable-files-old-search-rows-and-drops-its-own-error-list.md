# A full rebuild keeps an unreadable file's old search rows and drops its own error list

Status: built on 2026-10-16 on the seat's branch; the section Rebuild forgets and names an unreadable file holds the evidence; it closes at the GA as shipped.

Record before the release: raised on 2026-10-13 from the runtime seat's design note for the unreadable-file lock in the v0.106.0 round (`reports/design-Runtime106-idxlock.md` and its followup 47 in the round's bus); read at source by the seat and by the lead, not constructed, not run; written down, not designed, not accepted for build.

## What was seen

By source, at the round's integration branch (`4aed59d16`), two things about a full index rebuild that meets a file of the user's it cannot read or decode:

- **Old search rows survive.** On a fresh graph pass the file is left out and the graph is swapped without it (`crates/chan-workspace/src/workspace.rs` 3380 to 3383 and 3407). In the search index a failed read records an error and moves on without touching the file's rows (`index/facade.rs` 640 to 645); the cleanup after the walk deletes only paths that were not walked, and counts every walked name as visited (780 to 800); and a file's earlier chunks are deleted only on the way into a successful write (`index/bm25.rs` 152 to 161). So a file that was indexed, then became unreadable, and is still present keeps its earlier chunks and vectors through a warm rebuild: search can return text of a file that can no longer be read, while the graph no longer holds it. The watcher's per-file path forgets both (`workspace.rs` 3839 to 3844 and 4068 to 4080), so the two paths disagree.
- **The rebuild's error list is dropped.** `BuildSummary.errors` holds source read errors (`index/facade.rs` 643), BM25 write failures (647 to 649) and vector or embedding failures (660 to 665, 716 to 724) in one list, and the server maps a successful summary away (`crates/chan-server/src/indexer.rs` 785 to 787). Some failures do propagate, the graph's and the final BM25 commit's (`facade.rs` 810) among them. Nobody is told which files a rebuild could not index, and a caller cannot tell a user's unreadable file from a failed write of the index's own.

Not established: either case constructed or run; a rebuild that resumes staged graph work, which the fresh-pass reading does not cover; how often a warm rebuild meets such a file.

## Desired contract

A file the rebuild could not read leaves no stale row behind, as the watcher's path leaves none; and the rebuild says which files it skipped, apart from failures of the index's own state.

## What to do

Construct the warm case first: index a file, make it unreadable, rebuild, search for its old text. If it holds, forget a walked file whose read failed, as the per-file path does, and keep the two kinds of error apart in the summary so the rebuild can log the skipped files by name. Design before code: the rebuild's failure policy is shared by every caller of the facade.

Changed by the lead's rulings of 2026-10-16 on the runtime seat's design note (`reports/design-Runtime107-rbstale.md` in the round's bus): the log lives in chan-workspace's `reindex_with_aggression`, which every rebuild caller passes (the server's coordinator, the open-time recovery worker whose rebuilds a server process also runs, the metadata import's rescan and `chan index`) and where a test pins it on the calling thread. The server's coordinator, where it receives the summary, misses the open-time worker's rebuilds (`workspace.rs` 1162 drops that summary) and runs its pass under `spawn_blocking`, where a thread-local capture cannot see a warning. Per-file failures of the index's own writes are logged and the pass completes, as its policy is; `chan workspace index rebuild` names the skipped count beside the errors and drops its per-entry lines, which the rebuild's warnings carry.

## Boundaries

`crates/chan-workspace/src/index/facade.rs` (the build and its summary), `crates/chan-workspace/src/workspace.rs` (`reindex_with_aggression`, where the rebuild logs) and `crates/chan/src/index.rs` (the count line of `chan workspace index rebuild`), by the lead's rulings of 2026-10-16; `index/bm25.rs` is used, not changed, and `crates/chan-server/src/indexer.rs` is not changed. Not changed here: the watcher's per-file apply, which is the unreadable-file lock's item.

## Acceptance

1. The warm case constructed, with its expected values written first, and what search returns before and after the rebuild.
2. After a repair, a rebuild leaves no search row for a file it could not read, pinned, with a readable neighbour as the positive control.
3. The skipped files are named in the server's log, and a failure of the index's own state is not reported as one of them.

## Rebuild forgets and names an unreadable file 2026-10-16

Built by the runtime seat from its design note as the review seat read it (`reviews/review-Review107-55-rbstale-design.md` in the round's bus) and the lead ruled it. `Index::build_all` records a read of the user's file that fails in `BuildSummary.skipped`, with the read's `std::io::Error`, apart from `BuildSummary.errors`, which keeps per-file failures of the index's own writes. It forgets such a file's earlier rows in `Index::forget`'s order: the vector shard is removed first and the BM25 delete is queued only once the shard is gone, so no commit removes a document whose shard outlives it; when the shard cannot be removed, that failure goes to `errors` under the path and the document stays. The deletes are explicit rather than through the walk's `visited` set, whose BM25 enumeration is best-effort. `reindex_with_aggression` logs each skipped file at WARN (`reindex: skipped unreadable source file`, with `path` and `error`) and each per-file index failure at WARN (`reindex: failed to index file`) on the calling thread; a file that vanished during the walk is logged at DEBUG. The pass outcome, the graph rebuild, the server's coordinator and idxlock's watcher path are unchanged. `chan workspace index rebuild` prints `indexed N/M files, C chunks (S skipped, E errors)` and no per-entry lines. Stated costs, as the lead ruled: a transient read error counts as a skip, so the file's rows are gone until its next index; an undecodable non-Markdown text file has no graph stat row after a rebuild until the next reconcile reads it once and stamps it; a workspace with many unreadable files logs one warning per file per rebuild. The `chan-workspace` design states the summary, the delete order, the writer's queued writes after a cancel, the log and the convergence; the root design names the rebuild's warning.

Acceptance 1, the warm case, with the design note's predictions written before the run. At base `91465f512dcbb8016b41b55edd79884abf447fb7`, `bad.md` ("sourceoldtoken", linking `good.md`) and `good.md` ("neighbortoken") indexed by a full rebuild: BM25 search returns `["bad.md"]` and `["good.md"]`, and the graph holds both with one backlink to `good.md` (the positive controls passed). Then `bad.md` made undecodable (bytes `ff fe`), or mode 000 with the plain read by the non-root test user proved denied first, and rebuilt: search for "sourceoldtoken" returned `["bad.md"]`, the stale row (`cargo test -p chan-workspace --lib rebuild_skip_tests -- --test-threads=2` exit 101 at that assertion for both fixtures; the refused-graph-directory control passed). With vector shards seeded for both files, the shards after the rebuild read `["bad.md", "good.md"]` (exit 101 at that assertion). After the repair the same search returns `[]`, the shards read `["good.md"]`, and the neighbour's hit and graph row are intact.

Acceptance 2 is pinned by ten tests in `crates/chan-workspace/src/workspace_rebuild_skip_tests.rs`, `index/facade.rs`'s tests and `crates/chan/src/index.rs`'s tests: the stale BM25 row for an undecodable and a mode-000 file; the stale vector shard; the readable neighbour untouched; the skip named in `skipped` with `InvalidData` and `errors` empty; one WARN naming `bad.md` with the read's exact error, under a capture that holds a second registered dispatcher and rebuilds the interest cache so another thread cannot cache the callsite as disabled; a one-shot BM25 write fault on `good.md` reported in `errors` and its own warning, not as a skip; a file removed after the listing in `skipped` with `NotFound`, its rows gone and no warning; a graph directory at mode 500 an `Err` with no skip warning; the BM25 document kept, and the failure in both lists, when the embeddings directory at mode 500 refuses the shard's removal; the CLI's count line.
