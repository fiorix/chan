## Desired contract

A change the page has made reaches the server, by its own save or by the exit flush, whether or not the page is gone before the save's answer.

## What to do

A design choice of the store's owner: record the snapshot as saved when the write is answered, or keep the unanswered write and let the exit flush send again with keepalive while it is open. Design read before code; the pin a store row with the write held and the page unloaded.

## Owner's decision 2026-10-16

Put to the owner by survey on 2026-10-16 ("Exit flush: a save sent and not answered when the page goes") with four options: record the snapshot as saved only when the write is answered so the exit flush re-sends an unanswered save with keepalive (recommended); keep the unanswered write and let the exit flush send it again; leave it as is and close the row as a recorded cost; delegate the design choice to the frontend seat. The owner's answer, in the survey's words: "Mark saved only when answered; the exit flush re-sends (recommended)". Applied as: `commitSessionSave` records the last saved snapshot when its request is answered, not when it is sent, and the exit flush's comparison therefore sends a keepalive PUT for a change whose save is still in flight; a repeated PUT of the same blob is the accepted cost. ## Build 2026-10-16

Built as the owner decided, in `web/packages/workspace-app/src/state/store.svelte.ts`. The store keeps two records of the session snapshot. `lastSessionSnapshot` is what the page has sent or seeded, as before: the debounced save dedupes against it and the co-view read skips a blob equal to it, so neither path changes. `savedSessionSnapshot` is what the server is known to hold: set when a save's PUT or DELETE answers with success (`sendSessionSnapshot`), cleared to null when a save is sent, and set by every seed where no answer is due (`seedSessionSnapshot`: a clean or empty apply of a peer's blob, a diverged apply, a peer's DELETE frame, a local discard, the no-blob first save, and a web follower's empty view, whose DELETE is the leader's, so a page that stops being a follower before it goes does not delete the blob at exit). A sequence bumped by every send and every seed lets an answer record its snapshot only while its save is the latest, so a slow answer for an older save never stands for a newer one in flight, nor undoes a peer's DELETE recorded after it. The exit flush (`flushSessionSaveOnExit`) compares the current snapshot against `savedSessionSnapshot` instead of the sent one, so a change whose save is still in flight, or failed, goes out once more as the keepalive PUT (or DELETE for an emptied window); a repeated write of the same blob is the accepted cost. The design document gains the section "A session save at page exit" (`web/packages/workspace-app/src/design.md`), which names every skip of the flush. What stays: the server's announcement, the follower's suppressed DELETE, the no-blob first save's silence, and the in-page retry of a failed save, which is the session-save ordering row's.

The pin is `web/packages/workspace-app/src/state/store.exitFlush.test.ts`, eleven store cases over the module's own save and `pagehide` paths with the write held (`api.putSession` or `api.deleteSession` returning a promise the test answers or fails, `fetch` spied for the flush's keepalive request): a save unanswered at `pagehide` is sent again with keepalive and the same body; an answered save is not; a failed save is; an emptied window's unanswered DELETE is sent again; with layouts A, B, A sent and the first answered, the flush sends the last A; with A answered and B out, a layout back at A is sent; a peer's DELETE taken while a save is out keeps the flush from writing the blob back after the older save answers; a peer's layout applied cleanly is not written back; a peer's layout the page cannot attach, leaving it empty, is not deleted; a page whose load found no blob and that holds no layout sends no DELETE; and a follower's empty view sends no DELETE at exit after its role changes.
