# A second page loading into a window drops a tab the first page was just given

Status: built on 2026-10-16 on the seat's branch; the section Build 2026-10-16 holds the evidence; it closes at the GA as shipped.

Record before the release: raised by the review seat on 2026-10-13 from its runs of the terminal size instrument's two-page arm (the observation O1 of `reviews/review-Review106-termsz-design-1.md` in the round's bus); written down the same day by the lead as a row of its own, outside that item; owner the frontend seat; dispositioned at the candidate: a reading if reached, else recorded with the observation below.

## What was seen

In the review seat's guest, in three of five runs of the instrument's co-view arm (two pages of one window at different sizes, forced onto one window id by the URL), a terminal tab created through `cs terminal new` and shown on the first page was gone from both pages seconds after the second page of the same window loaded: never attached on the second page, its socket closed on the first, the first page's last sample holding the other two tabs with the probe shown again. In the two runs that completed, the second page attached all three tabs. The seat's own three final arms completed in its guest. The runs' records are under `evidence/Review106/termsz2-*` in the round's bus; the driver then looked for a tab that was gone and ended inconclusive (status 3, "timeout: tab selectable").

Not established: what the second page restores at load and what it writes back to the window's layout; whether the tab's session was ended or only dropped from the layout (a running terminal lost without a close, or a tab whose session survives unattached); whether one page reloading inside the same interval does the same; whether the arrangement (two pages on one window id) is one a user reaches outside the instrument, and whether a desktop window and a browser page on one workspace share it; the cause at source (the layout's restore and save on page load against a tab added by the control socket a moment before).

## Desired contract

A tab added to a window is not removed by another page's load of that window; a page that loads restores the window's layout as it is at that moment, a tab just added included, or the layout's rule says which writer wins and the losing tab is closed by a close, never dropped.

## What to do

Read the workspace app's layout restore and save on page load (`web/packages/workspace-app/src/state/store.svelte.ts`, the restore constructors and the layout hash's write) against the control socket's tab creation (`crates/chan-server/src/control_socket.rs`, `terminal new`) and say what a second page writes back; then reproduce in a guest's Chrome with the instrument's own arrangement and without it (one page reloaded right after a tab is added), reading whether the tab's session is ended or dropped, with the expected readings written first. The repair, if one is needed, is designed after the reading.

## Boundaries

`web/packages/workspace-app/src/state/store.svelte.ts` and `state/tabs.svelte.ts` (the restore and the layout's save), their tests, and a browser check if the reading asks for one. Not changed: the shared layout hash's content, the control socket's tab creation, the terminal size item's instrument.

## Acceptance

1. A reading of what a page load writes back to the window's layout and when, with line numbers, and a reproduction in a guest's Chrome in the instrument's arrangement and in a single page reloaded after a tab is added: the tab's fate (session ended, or dropped from the layout with its session alive), with the count of attempts.
2. If a repair: a pin red first on its own assertion that a tab added a moment before a page's load is in the layout after it, on both pages; `make web-check` green at the commit in the owning guest.
3. If the arrangement is the instrument's own: the item says so, with the reading that shows a user cannot reach it.

The lead's ruling: the tab's fate is established, dropped from the layout or re-homed on a new shell, with its session alive in both and no session ended. The cause is the one the row `sesser` names, a layout save that is not serialized against a peer's write: a page that saves its bootstrap layout over a newer peer layout, and a reload whose snapshot yields to a lagging layout. The repair the seat proposes, a versioned or conditional write of the shared layout with the reload snapshot's session ids taking priority while the layout lags, changes the store's save and restore, the most shared files of the round, with a design read before code; it is not built in this version, which freezes with this reading, and is the first case of that row's design in the next. Kept as a stated cost: a second page loaded into a window before the first page's save of the tab has landed (750 ms after the tab's last layout change plus the write's own time, 34 to 312 ms here; the three losing reads completed about 0.9 s after the addition) can drop the tab from the layout, and a reload in that interval can re-home it on a new shell, each leaving the original session live and listed by `cs terminal list`; the tab leaves the layout or comes back on a new shell, its session stays alive and listed, and the review found no way back to it in the page (the session roster feeds broadcast targets alone and the reattach helper has one caller, the cross-window drop; two callers read, not every surface).

Read by the review seat (`reviews/review-Review106-tablos-record-1.md` in the round's bus): the lines say what the record says of them, the counts and the ordering hold from the records, the reading accounts for its own earlier observation, and the deferral is sound; two sentences corrected above on its read (the overwriting write is the co-view read's early flush, not the 750 ms save; the interval is about a second, not half). A smaller guard in shape, not run by anyone and not for this freeze: the co-view loss is one write, so a bootstrap that recorded its restored layout as already sent (as the apply path does after a reconcile, 3606 to 3610) would send nothing at the flush and the read re-armed behind it would fetch the newer layout; it does nothing for the reload arm, and the write it withholds is one the server reads to mark the window persisted (`routes/sessions.rs` 160; `terminal_sessions.rs` 505, 2882), which keeps a window's detached terminals from being reaped, so whether a window that loads and never writes is marked by another path is the design read's first question. Not established: what closed a second socket in the review's own run; whether the leaving page's exit write was sent in reload attempts 4, 5 and 9; a native engine.

The server change (an attach key recorded at the tab's creation) is out of both rows' boundaries and is not built; the stated-cost alternative is not needed."
2. "The three races that stay last-writer (two pages changing the layout inside one debounce window; the exit write beside a write in flight; a discard's keepalive DELETE beside a PUT in flight) need a versioned or conditional PUT, a server change the sesser row's boundary keeps out; they are stated in both rows' closing sections as the rule, with the session alive in each."

"The two-page check is committed into `scripts/e2e/browser-smoke/` by Frontend107 on its base (the scope allows a lane to write a check on a base the lead names), read by Hygiene107 as the suite's owner in a short task before the tablos commit lands, and run alone and beside the base; the reading's driver at the fix tip, ten attempts per arm, is kept as evidence beside it."
4. "Two commits, sesser first and tablos on it, one per item."
5. "The reload graft is by name, not by position: a restored terminal takes the id its name holds in the page's own snapshot, else in the blob, else in this window's roster (the T3 reclaim), each id taken once, the position kept only between tabs of one name; one rule for T2 and T3, within `restoreLayout` and the row's boundary, replacing the design's leaves-and-titles match and its positional fallback. The case (a shorter blob in another order re-homes nothing) is a pin."
6. A page opened from a copied URL, ruled twice, the second refining the first. First: "A hash boot that is not the page's own reload and finds a blob takes T1's path: it seeds, writes nothing, and its first-ready read reconciles it to the window; "own" is a per-tab marker written at pagehide for every window kind (sessionStorage, which a copied link's new tab lacks). The hash's verbatim restore stays for a window with no blob and for the page's own reload; the hash's content is unchanged." Then, refining it: "option (b). A hash boot that is not the page's own reload (the per-tab marker absent) and finds a blob restores the blob as a blob boot does: T1's seed at the end of the try, no write, the first-ready read reconciling toward a newer peer layout; the hash's Search overlay still applies and the blob's tree-expansion sidecar is read. The hash's verbatim restore stays for a window with no blob and for the page's own reload, as before; no hash content changes." Its reason, in the row's words: under the first option a copied hash that names a terminal the window no longer has (closed, renamed or ended since the copy) restores a tab no source can graft, whose attach spawns a shell and schedules a save that the first read flushes before it reconciles, so the copy-time layout plus a new shell replaces the window's blob, and the spawned shell stays alive in a marked window, unshown and unreaped; the second reaches the first's end state, the window as it is, without the write, the spawn or the flicker. Its cost: the copier's view markers (the active tab, the focused pane) are those of the blob's last writer.

## Build 2026-10-16

Built in `web/packages/workspace-app/src/state/store.svelte.ts` and `state/tabs.svelte.ts`, the design read first by the lead and the review seat (the section above). A page that loads restores, from the first that applies (`restoreBootLayout`, one function for the workspace and the standalone boot): its URL hash, when the hash is the page's own or the window has no saved session; the window's saved session; the tab's all-terminal reload snapshot. The hash is the page's own when the tab carries the mark (`chan.layout.ownReload:<window>` in sessionStorage) that a page of the window leaves at `pagehide` in every window kind. A page that has heard of, or may have missed, a peer's save it has not read leaves no mark, since its hash can lack that save, so that page's next load opens the window as the server holds it. A peer's `session_changed` frame sets `sessionPeerSaveUnread`, and so does an open of the event socket after the page's first, since a save made while the socket was down sends no frame; a read that takes the blob in clears it only when no peer frame arrived while its GET was out (`sessionPeerFrames`). The boot consumes the mark, and so does a persisted `pageshow`, a restore from the back-forward cache, which runs no boot; a live page holds none, and a tab duplicated from it opens the window as it is. A copied URL, in a tab without the mark, opens the window as its saved session holds it, with the hash's Search overlay. A page that restored the saved session records the restored layout as held by the server at the end of the boot, after the tree-expansion snapshot, the transfers and the overlays (`seedRestoredSession`), so it writes nothing until it changes something, and its first ready's read, which goes to the GET at once when the save it finds pending has nothing to send, takes a newer peer layout instead of saving the older one over it; a restore that leaves nothing to save records nothing, so an emptied blob is still deleted. A restore from the hash or the reload snapshot can hold what the server lacks, and writes it.

The graft (`terminalGraftLenders`, `TerminalGraft`): a restored terminal without a session id takes the id its name holds in the tab's reload snapshot, else in the saved session, else among the live sessions the terminal roster binds to this window, read beside the session GET (its failure read as an empty roster), across every pane and both sides; each id once, a tab restored with its own id holding it; the k-th tab of a name takes the k-th entry still free; the entry that lends the id lends the session-only fields, and with no id anywhere the first entry of the name lends its fields. It applies to every restored terminal without its own id: a hash's, a reload snapshot's, and a saved session's terminal saved before its session frame. The positional graft is removed with `hydrateTerminalSessionsFromLayout`, which had no production caller. The workspace app's design text holds the rules (`src/design.md`, "A page's load of a window's layout").

The persisted-window mark, read at source, with what this build leaves to it: a page that loads and writes nothing leaves the mark as it is. The mark is set by a session PUT, by an fdstore restore of a session bound to a window and by minting a Terminal window, and cleared by a DELETE and by the host's window discard (`reap_discarded_window_state` in `crates/chan-library/src/host.rs`), which deletes the window's blobs too. A blob a page restores was written in this process, so its window is marked, or comes from an earlier process, whose sessions are either restored through the fdstore, each marking its window, or dead; a dead id is answered with a new session whose frame schedules a save, so the page writes and marks the window. The discard keeps the blob of a tenant held by a storage reset or a metadata import while the mark goes; a page that loads that blob meets reaped sessions, whose attach answers `Closed`, which removes the tab and schedules a save, so it writes too.

What stays, stated with the session's fate in each:

- A stale blob of window W across a restart that names a session the fdstore restored under another window W': the restore marks W', the loading page's attach re-homes the session to W under the same id, the layout is unchanged, nothing is written, and W stays unmarked, so the pruner reaps the session `terminal.idle_timeout_secs` (1800 s by default) after the page detaches. Closing it needs the blob stamped with the server instance, a server change outside this row.
- Two tabs of one name exist only before the session frame (a tab shows its requested name until the server settles a suffixed one); the second takes no id and spawns, and the suffixed session it would have had stays alive and unshown.
- A session moving out of this window stays bound here until the target window's attach re-binds it; a reload in that interval takes it by name, and both windows show it. Nothing is lost.
- Name reuse: a co-viewer that closes a tab and opens another under the same name before this page's snapshot follows (the snapshot follows within a save debounce) leaves the snapshot naming the closed session, which the reload takes first; its attach answers `Closed` and the tab is removed. Skipping snapshot and blob ids the roster does not list was not built, since a live session the roster lists under no window would then lose its reattach.
- A copied page reloaded before its own boot has finished leaves the mark at its `pagehide` and restores its hash on that reload.
- The copier's view markers (the active tab, the focused pane) are those of the blob's last writer.
- A page reloaded after hearing of a peer's save and before reading it opens the window as the server holds it, the peer's terminal included, with the view markers of the save's writer instead of its own. A reconnect arms no read, so after the event socket opens again the page counts a save as unread up to the next read that takes a blob in, which a peer's frame arms; a reload in that interval opens the blob, usually this page's own last save, with that save's view markers. A read that finds no blob, or whose blob Hybrid Nav defers until its transaction settles, leaves the page counting the save as unread until a later read takes a blob in; a reload in that state opens the window as the server holds it too. Nothing is dropped in either case.
- The three races the lead's rulings keep last-writer, as the session-saves row states them: two pages changing the layout inside one debounce window (the later write wins; the other page's reconcile drops a terminal its layout lacks, the session alive and listed by `cs terminal list`); the exit write beside a write in flight (either can be stored last; the sessions stay as they are); a discard's DELETE beside a PUT in flight (the blob can come back until the next discard; the reap runs either way).
