# The one-CPU test series helper refuses a guest outside the default sdme state directory

Status: carried into v0.106.0 at the v0.105.0 GA on 2026-10-11; the refusal reproduced and the decision taken on 2026-10-12 (see "Reproduction and the lead's decision"): the helper gains an option naming the sdme configuration, in design.

Record before the release: raised for v0.105.0 by the owner's word of 2026-10-09, from the v0.104.0 release report's known gaps; written down, not designed, not accepted for build.

## What was seen

`scripts/e2e/one-cpu-test-series.sh` was run once in the v0.104.0 round, on Linux on the development box, against the guest `chan-v0104-hygiene` after the lead had set that guest to one CPU (`dev/v0104-team/reports/report-Hygiene104-item7-L7-series.md`, "One-CPU instrument and limits"). It refused before any test ran, exit 2, with the one line `one-cpu-series: REFUSED: missing exact sdme state: /var/lib/sdme/state/chan-v0104-hygiene` (`dev/v0104-team/evidence/Hygiene104/item7-l7-repo-helper.log`; the status file beside it reads `rc=2`, with start and end both at 2026-10-08T10:21:20Z). The call was `sudo -n scripts/e2e/one-cpu-test-series.sh --container chan-v0104-hygiene --package chan-server a_superseded_mount_keeps_a_ 1 8` (`dev/v0104-team/evidence/Hygiene104/try-item7-l7-repo-helper.sh`).

The round's guests lived on a storage pool the team built, with its own sdme configuration (the [v0.104.0 report](../../release/release-v0.104.0.md), "Team and process"), and that configuration's first line is `datadir = "/var/lib/sdme-v0104"` (`dev/v0104-team/sdme.conf`). The helper fixes the state file's place: `STATE=/var/lib/sdme/state/$CONTAINER`, and a refusal when that is not a regular file (lines 140 and 141 in the released tree `af2af8ac0`); it takes no option and reads no variable that names another directory. From that file it reads the guest's name, backend and disk cap (lines 142 to 147). Past that point it also fixes the unit `sdme@$CONTAINER.service` (line 148), the host cgroup `/sys/fs/cgroup/machine.slice/sdme@$CONTAINER.service` (line 153), a bare `sdme exec` with no configuration argument (lines 69 and 82), root's home and a clean checkout at `/work/chan` in the guest (lines 69 to 78). `scripts/e2e/README.md` ("One-CPU test series") documents that fixed shape and creates its guest with a plain `sudo sdme create`.

The round ran a stand-in instead: 200 iterations of two guard tests under a host-verified `cpu.max` of `100000 100000`, all green. The same report says the stand-in "does not claim the repository helper's own state, disk and throttle-counter acceptance bar", and the v0.104.0 report's Known gaps repeat it: "that helper's full acceptance bar is not claimed".

Not established: whether the helper would have passed its later checks had the state path matched. Only its first refusal was reached, so the unit name, the cgroup path, the bare `sdme exec` and the `/work/chan` checkout were never tried against a guest under a second sdme configuration; the round's guest ran its jobs as the user `ubuntu` from a guest-private checkout (the report's "Hand-back" and "Method and raw evidence"), which the report does not place at `/work/chan`. How sdme names a guest's unit and cgroup under a non-default data directory was not read. No other host and no other sdme version was tried.

## Desired contract

The helper measures a guest wherever its sdme state lives and proves there what it proves today (a btrfs backend, a disk cap, a running guest, an exact one-CPU cap read from the host, the throttle counter, a clean and unmoving revision); or it refuses in a sentence that says it supports the default layout only, and its documentation says so. The item asks for a decision between the two.

## What to do

Reproduce the refusal with a constructed state directory (the helper's own test, `scripts/e2e/test-one-cpu-test-series.sh`, already sources its functions), then against a real guest created under a second sdme configuration. Read how the installed sdme exposes a configuration's data directory and how it names the guest's unit and cgroup there, and do not assume either. List each fixed assumption past line 141 and what it would have met under the round's layout. Then put the choice to the lead: an option that names the configuration or the state directory, with every later check derived from it; or the documented limit.

## Boundaries

`scripts/e2e/one-cpu-test-series.sh`, `scripts/e2e/test-one-cpu-test-series.sh` and the "One-CPU test series" section of `scripts/e2e/README.md`. The helper's proofs are not weakened: no path reports a rate without a host-verified one-CPU cap, a disk cap and a clean revision. `scripts/check-sdme-storage.py` and its inventory stay green. No host's sdme configuration is changed.

## Acceptance

1. Given the state of a guest under a non-default data directory, the helper either runs its series or refuses in a sentence that names the unsupported layout; pinned in the helper's test, red first against the behaviour of line 141 today.
2. If support is built: one real series of at least one run against a guest under a second configuration, whose final line reads the container, backend, disk cap, `cpu.max` and throttle delta from that guest's own state and cgroup, beside a control run showing that a guest in the default layout still passes.
3. If support is built: every refusal the helper has today (an absent or non-one-CPU cap, a non-btrfs or uncapped root, a dirty or moving revision, a selector that names no test) still refuses under the new option; pinned.
4. `scripts/e2e/README.md` says which layouts the helper supports.
5. `make shell-check` is green at the commit.

## Reproduction and the lead's decision 2026-10-12

Reproduced by the hygiene seat in two arms. Constructed, in its guest: a stand-in `sdme` on `PATH` whose configured `config get` named `/var/lib/sdme-v0106`, whose bare `ps --json` answered `[]` and whose configured `ps --json` named the running guest, with a regular state file under `/var/lib/sdme-v0106/state/` holding the guest's name, `STORAGE=btrfs` and `DISK=44G`; the unchanged helper, run as root with `--container chan-v0106-hygiene --package chan-server a_superseded_mount_keeps_a_ 1 8`, exited 2 with the one line `one-cpu-series: REFUSED: missing exact sdme state: /var/lib/sdme/state/chan-v0106-hygiene`. Real, on the host against this round's pool (`/var/lib/sdme-v0106`, its own configuration file, a capped btrfs guest running under `sdme@chan-v0106-hygiene.service` with `ControlGroup=/machine.slice/sdme@chan-v0106-hygiene.service`): the same exit and the identical line, before any guest operation, with the default pool's `ps --json` empty. Neither arm created a guest or ran a test selector. Records: `evidence/Hygiene106/onecpu-constructed-refusal.{sh,log,status}`, `onecpu-real-refusal.{log,status}` and `onecpu-layout.log` on the round's bus. Read past the refusal and not reached: the helper's unit and cgroup paths would match this host's live unit; its bare `sdme exec` would address the default pool, whose listing is empty, so it cannot reach the guest without the configuration; and its `/work/chan` checkout contract matches neither the round's read-only `/source` bind nor its private `/home/ubuntu/chan` checkout as `ubuntu`, so a configured exec would still need a guest of the helper's own shape or a changed checkout contract. `scripts/check-sdme-storage.py`, read and not run, counts ten container-creating sites and requires `--storage btrfs` at each, and `--disk` at six of them, the README's onecpu creation command among those; the helper creates no container and is not in the inventory.

Ruling: build the support. The helper gains one option that names the sdme configuration file (the form the cross-check driver already takes through its `SDME` variable is the model), and every later check is derived from it: the data directory read from `sdme config get` under that configuration rather than assumed, the state file under that directory, the guest's unit and cgroup named as the installed sdme names them there, and every `sdme` call carrying `--config`. Without the option the default layout stays the default and the refusal sentence names the state path it looked for, as today. The fixed assumptions past line 141, the `/work/chan` checkout contract among them, are listed in the design with what each would meet under this round's layout, and the design says how the real series of acceptance 2 gets a guest of the helper's shape under the second configuration. The default-layout control of acceptance 2 cannot run on this host, whose default pool refuses a disk cap; it is recorded as not run here with that reason, and the helper's own test pins the default path. The proofs are not weakened: no path reports a rate without the host-verified one-CPU cap, the disk cap and a clean revision. The review seat read the derivations against the installed sdme: the data directory and `--config` are what `sdme config get` and every command expose, and the unit is `sdme@NAME.service` with no data directory in its name; the `state/NAME` file and the cgroup path are this host's observed layout and systemd's `ControlGroup` of the unit, so the helper takes the `datadir` line alone from a `config get` whose other keys it never logs, proves that the unit is the guest whose state it read, and reads the cgroup from the unit's `ControlGroup`. The design goes to the review seat before the code.

## Lead's decision on the design 2026-10-12

The hygiene seat's design (`reports/design-Hygiene106-onecpu.md` in the round's bus: an optional `--sdme-config FILE`, the data directory read from `sdme config get` under that configuration as exactly one unquoted `datadir = /absolute/path` line with the output never printed, the state file derived from it, every sdme call through one command array with no fallback to the default pool, the running guest proved from systemd and `/proc`, the helper's fixed assumptions past line 141 kept as they are) is accepted with the review seat's seven amendments (`reviews/review-Review106-onecpu-design-1.md`), each adopted. The identity proof is that the unit is active, its main process carries the `--machine` and `--directory` arguments of the selected pool and sits in the unit's control group or under it, with every refusal naming the fact that failed and never the command line; a quoted `datadir` is refused; the stand-in prints a canary in the token key's form and the test proves it is never printed back; the helper's decisions are functions over values already read, tested without root with one mutant per guard, while the refusals that need a live unit are pinned in the real rig; acceptance 1's red is the configured case under the mutant that ignores the option; the README keeps one create command. Two rulings: the default path gets the identity proof as well, read from the same template and pinned by the constructed parser test only, since the default-layout control cannot run on this host, and the README and this item say so; acceptance 2 is met by one real run under the second configuration with its record (the helper's final line, the unit's cap and throttle before and after, the pool's quota beside the declared disk, the configuration and its data directory, the main process's directory, the tool versions, the clean detached revision, the toolchain, the create command, the result directory) and reads not run for the default-layout control, with the constructed default-path case named as what stands in. The real run's guest is granted at the code stage.
