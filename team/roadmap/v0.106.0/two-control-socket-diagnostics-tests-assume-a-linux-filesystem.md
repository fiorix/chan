# Two control-socket diagnostics tests assume a Linux filesystem

Status: raised by the lead on 2026-10-14 from the rc1 dry run (the `ci.yml` run 38608192090's `make ci-macos` job 116004419432, red on two tests by its failed-step log) and read at source the same day; written down the same day as a row of its own; owner the runtime seat; a test defect of the fallback-directory item's bind-report pins (`sockfb`; one of them also cited by the non-UTF-8 path row), the product unchanged.

## What was seen

The rc1 commit `1121267c8` carries the test-only repair of the `cs_alias` tests (`csbt`), so GitHub's macOS test step went past them for the first time in this version: `cargo test --all-targets` ran 21 workspace test binaries green on macOS (`tests/cs_alias.rs` among them, 21 of 21) and stopped, fail-fast, at the 22nd, `chan-server`'s unit tests, with `2197 passed; 2 failed; 1 ignored`. Both failures are in `crates/chan-server/src/control_socket_diagnostics_tests.rs`, written on 2026-10-13 in `211f8dcef` for the fallback-directory item's bind reports; each runs as an isolated child, and the parent's first panic at line 52 (`socket diagnostic child failed`) is the harness reporting the child's.

1. `foreign_directory_tenant_exports_the_owner_refusal` (line 475, `assertion left == right failed: original refused-directory reason`): the `RefusedDirectory::ForeignOwner` arm of `refused_directory_case` names `/tmp` as the directory another user owns (line 383). On macOS `/tmp` is a symbolic link to `/private/tmp`; `validate_control_socket_dir_for` in `crates/chan-shell/src/control_dir.rs` reads `symlink_metadata` of the directory node and refuses "is a symbolic link" (line 30) before it compares the owner, so the event read `control socket bind failed at /tmp/chan-control-s70a8b9a997908ace.sock: control socket directory /tmp is a symbolic link; this tenant's terminals get no CHAN_CONTROL_SOCKET; cs cannot reach this server` where the test expected the owner refusal. The validator's order is the product's rule on every platform, and the real fallback directory `chan-control-<uid>` is a directory node under it, not a link; the fixture's choice of `/tmp` is what does not hold on macOS.
2. `non_utf8_bound_path_has_no_failure_report` (line 539, `called Result::unwrap() on an Err value: Os { code: 92, kind: Uncategorized, message: "Illegal byte sequence" }`): `std::fs::create_dir` of a directory named by the byte `0xff` is refused by macOS's filesystem, so the constructed input cannot exist there and the product never meets it; the case is Linux-only by construction.

The step is fail-fast, so the 22 test binaries after `chan-server`'s in the root workspace's order (its `echo-extension` example, `chan-shell`, `chan-systemd`, the three tunnel crates with `substream_pool`, `listener_e2e` and `pat_lifetime`, `chan-workspace`'s lib and eleven test files, and `fetch-models`; the gateway workspace is a separate step) have still not run on macOS in this round. Of those, `chan-shell` (`cli.rs`, `control.rs`, `help.rs`) carries this round's changes and the `chan-server` example is built against the changed library (its own source unchanged); the other crates are unchanged since v0.105.0 by the diff from `4507fe5a0`. On Linux every guest gate of the round and the rc1 run's `make ci-linux` job pass the file whole. The logs are `evidence/Lead106/rc/rc1-runs/ci-run-38608192090.job-116004419432.ci-macos.{failed,full}.log` in the round's bus.

## Desired contract

A test that constructs a filesystem arrangement names it by what the platform guarantees (a real directory owned by another user; a name the filesystem accepts), or says on which platform it applies, so its verdict is the same in a guest, on a workstation and in a GitHub macOS job; a case that cannot be constructed on a platform does not pass there by silence.

## What to do

In `crates/chan-server/src/control_socket_diagnostics_tests.rs` alone: the foreign-owner case uses the real directory behind `/tmp` (`std::fs::canonicalize("/tmp")`, `/private/tmp` on macOS and `/tmp` on Linux) consistently, so the owner refusal is the one expected on both platforms; the non-UTF-8 case either is gated to Linux with one comment naming the refusal, or asserts the platform's refusal of the byte sequence and says it does not apply there. Green on Linux in the owning guest (the two tests alone, the sibling `Symlink` case as the control of the validator's order, fmt, clippy, the whole `chan-server` suite); the macOS proof is the next GitHub run on a commit holding the repair, an outward step on the owner's word.

## Boundaries

The one test file; `control_dir.rs` and the server are not touched, and the validator's order (link, directory, owner, mode) stays as it is on every platform.
