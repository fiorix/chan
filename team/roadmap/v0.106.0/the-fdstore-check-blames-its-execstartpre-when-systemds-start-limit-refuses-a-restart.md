# The fdstore check blames its ExecStartPre when systemd's start limit refuses a restart

Status: carried into v0.106.0 at the v0.105.0 GA on 2026-10-11; reproduced and ruled on 2026-10-12 (see "Lead's decision"), the repair built, reviewed and integrated the same day (see "Build record"), with one follow-up range for a measured timing read (see "Review and follow-up").

Record before the release: raised for v0.105.0 by the owner's word of 2026-10-09, from the v0.104.0 release report's follow-ups; written down, not designed, not accepted for build.

## Desired contract

When systemd refuses a restart of the check's unit by its start limit, the check's failure line says so, from the unit's own result, and does not point at its `ExecStartPre` drop-in; a refusal by that drop-in is still named as one. The record raises a second question and does not answer it, so the item also asks for a decision: whether the check, run unchanged in a guest with the manager's defaults, should pass by setting or resetting the start limit of its own disposable unit, or the override stays the runner's and is written where the check's run instructions are.

## What to do

Reproduce first: run the unchanged script in a guest whose user manager has the default limit, keep the unit's journal whole, and count the starts with their times up to the refusal, which shows whether the script's own pace meets the limit and at which case. Read the other restarts and failure lines of the script, and the sibling replay check, for the same exposure and the same guess. Then construct the two causes apart before any real run: a start limit made certain on the disposable unit by a burst of one, and an `ExecStartPre` helper that exits non-zero; the script's existing self-test modes (`CHAN_FDSTORE_E2E_SELFTEST`) are the form a constructed case can take. Put the second question to the lead with the reproduction.

## Acceptance

## Lead's decision 2026-10-12

Reproduced by the hygiene seat on 2026-10-12 in a guest (Ubuntu 24.04.4, 2 CPUs by `cpu.max=200000 100000`, systemd 255, a user manager for `ubuntu` with `DefaultStartLimitBurst=5` and `DefaultStartLimitIntervalUSec=10s`, the inactive unit inheriting both), with the unchanged script at `4507fe5a0` and a debug `chan` built at two jobs: cases 1 to 4 passed; five starts succeeded inside the ten-second interval (`Started` at 22:30:26.210, 27.526, 27.854, 33.341 and 34.365 by the guest's clock), and the sixth request, case 5's restart, was refused at 22:30:35.027, 8.8 seconds after the first start, with `Start request repeated too quickly` and `Result=start-limit-hit`; the script printed its `ExecStartPre` line and exited 1 after ten seconds. So the script's own pace meets the limit at case 5 on a manager with the defaults, and the one earlier failure was not a slow machine's. The script's other restarts (the first start at 598, case 2 at 648, case 8 at 820 and 825 through `restart_devserver`, case 1's bare restart at 633, the watchdog and crash paths through `wait_restarted`) do not read the unit's `Result` either, and `scripts/e2e/devserver-terminal-replay.sh` drives the same fixed unit under the same default with generic failure wording and no wrong guess.

Ruling on the second question: the check owns its disposable unit, so the limit is the check's. The script sets `StartLimitBurst` and `StartLimitIntervalSec` on the unit it writes, with the reason beside them, at a value bounded so that a crash loop still fails closed, and passes unchanged on a manager with the defaults; no manager default outside that unit changes, and the unit `chan devserver` writes is untouched. The failure line reads the unit's `Result` through the script's own `unit_prop` and names a start-limit refusal as such, keeping the `ExecStartPre` reading for an exec failure of the pre step. The replay script gets the same unit setting only if a count of its restarts from its text shows its pace can exceed the limit; its wording gets no change. The run instructions say the check owns its unit's limit. The design goes to the review seat before the code, with the two constructed causes in the script's self-test form, each red once against the old line. Amended the same day on the review seat's reading: the classifier reads the pre-step's recorded exit before `Result`, since the product's unit restarts itself on a failed pre-step toward the start limit and `Result` alone could be a race; a third constructed arm settles the order; the restart helper is used at every restart site; the self-test splits into a table test beside the stub modes and live arms behind the container refusal with a status of their own for a guest that cannot run them; the replay check is run unchanged once under the default manager before its limit is set. The third arm, run the same day under systemd 255 with `Restart=on-failure` and a failing pre-step, found the unit retrying twice, logging `Start request repeated too quickly`, and retaining `Result=exit-code` with the pre-step status, on an automatic retry and on an explicit restart alike; so on this host the race does not occur, the arm asserts that measured pair, the table test keeps the synthetic `start-limit-hit` pair for a systemd that reports it, and the pre-step-first order stands as right on both.

## Review and follow-up 2026-10-12

The review seat measured one thing the frozen arms cannot see (`evidence/Review106/fdlim-read-timing-probe.{sh,log,status}`): on the product's unit, with `Restart=on-failure` and no `RestartSec`, a restart refused because the pre-step failed is retried about every 250 ms, and each attempt clears the unit's result and the pre-step's recorded status until the pre-step ends again; the classifier's one read of the two properties names the step when it lands within the first 100 ms (ten of ten at 0 and 60 ms) and prints `unit Result=success` when it lands later (ten of ten at 120 ms, nine of ten at 200 ms, five of ten at 500 ms). On a quiet guest the `systemctl` method's read lands early; a throttled guest or the slower `cli` method lands late. The line names no wrong step, so the item's fault is repaired, and it is not yet the line acceptance 3 means at the product unit's pace. The lead's ruling: integrated now, since the host-release item's runs need the script, with the follow-up as its own small range by the hygiene seat: the classifier's input becomes a short bounded poll that returns at the first sample carrying a nonzero pre-step status or `start-limit-hit` and otherwise, at a two-second bound, classifies the last sample whose result is not `success`; a fourth live arm (the default `RestartSec`, a 50 ms failing pre-step, read 150 ms after the failed start) red at this tip and green after, with the poll reduced to one read as its mutant; a comment on arm C naming its values as systemd 255's; the mutant runner exported. Acceptance 3 is met in the constructed harness and at the end state, and at the product unit's pace it waits on that range. That range was built the same day on the hygiene branch (`a26a7bdde`, the one script): `unit_failure_reason` reads both properties in one `systemctl show` call per sample, returns at the first sample carrying a nonzero pre-step status or `start-limit-hit`, and otherwise polls at 50 ms until a two-second deadline before classifying the last non-success sample; arm D (the product unit's default retry interval, a 50 ms failing pre-step, a read 150 ms after the failed start) was red with the old reader on its rendered line, `unit Result=success`, and green with the poll, and its mutant, the poll reduced to one read, red; arms A to C keep their mutants red; arm C's comment names its systemd 255 pair and the table's alternate; the mutant runner and generator are exported beside the logs; the nine-case check and the replay check passed whole under the default manager; both lints green at the tip. Integration waits on the review seat's reading of that range.
