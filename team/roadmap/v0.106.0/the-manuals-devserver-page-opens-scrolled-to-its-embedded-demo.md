# The manual's Devserver page opens scrolled to its embedded demo

Status: raised by the owner on 2026-10-12 from the public site, the day after the manual was split into one page per guide (`f0901774a`, on `main` since `4507fe5a0`); written down, not reproduced by a team, not designed. Accepted into v0.106.0 on 2026-10-12 by the owner asking for it, at the round launch of that day: its first step (the reproduction named below) is accepted, and nothing past the decision it names. Reproduced on 2026-10-12 (see "Reproduction"); the repair was read by the review seat and built the same day (see "Build record"), with the review seat before integration; its shape was decided by four keyboard readings taken first on 2026-10-12: both halves, the helper's option for every caller and a mount option by which the embedded demo takes no initial focus, since with the option alone focus stayed in the frame after load, Space did not scroll the manual, and one Tab moved the page 2,103 px into the dialog and never left it (`reports/mscroll-keyboard-Frontend106.md` on the round's bus).

## What was seen

The owner's words: "on the public website when i click manual -> devserver, it scrolls the page to the place where we have a js widget injected there, instead of just opening the manual at the top of the devserver page".

Read at source on `main` at `4507fe5a0`: `web/packages/marketing/src/pages/manual/devserver.html` embeds the interactive Add devserver demo at line 69 as `<iframe class="launcher-demo-embed" src="/manual/demo/devserver/" loading="lazy">`, well below the top of the page. The framed page is built from `src/templates/demo-embed.html` with `data-variant="devserver"` and mounts the launcher's form through `src/launcher-demo.ts`. The launcher's `Modal.svelte` mounts `createModalFocus` from `@chan/web-shared/modal-focus` on its panel. No scroll or focus call for this page exists in `src/site.js`: the only scroll there keeps the active chapter visible in the mobile navigation strip, horizontally.

Hypothesis, not confirmed in a browser: the demo opens the form as a modal, the modal takes focus when it mounts, and a focus taken inside a frame scrolls the outer page to bring the frame into view. Not established: which browsers and viewport sizes show it; whether the Install page, whose demo is mounted in the page itself and not in a frame, does the same; whether the lazy loading changes when it happens.

## Desired contract

Following a link to a manual page with no fragment opens it at its top, whatever the page embeds. A link with a fragment opens at that heading. The demo still takes focus for its own keyboard handling once the reader interacts with it.

## What to do

Reproduce it first against a built `dist` in a headless browser at a desktop and a phone viewport: load `/manual/devserver/`, wait for the frame to mount, read `window.scrollY`. Find the call that moves the page. Then repair it where it is caused (a mount focus that does not scroll, or no focus until the reader's first interaction with the frame), not by scrolling back afterwards. Check the Install page and the Animations page by the same reading.

## Boundaries

`web/packages/marketing/src/` (the demo embed template, `launcher-demo.ts`, the manual pages), `web/packages/marketing/scripts/smoke-dist.mjs` or a sibling for the check; the launcher's demo mount options if the repair is a mount option. Not changed for the product: the launcher's modal focus behaviour in the desktop app and the workspace window, unless the reproduction shows the same fault there.

## Acceptance

1. The fault reproduced with a number: the scroll offset after load on `/manual/devserver/` with no fragment, per viewport, before the repair.
2. After the repair the offset is zero on every manual page and on `/animations/` with no fragment; the browser check lists the manual pages from the built `dist` and reads each with no fragment as a control, so a page that later embeds a demo is covered. The proof is in two parts, by the lead's ruling of 2026-10-12 on the review seat's reading: the package's smoke reads the built pages with no layout and the gate carries no browser, so the pins that run in the gate are the shared helper's unit test that a dialog mounted with initial focus disabled calls no focus and leaves `document.activeElement` where it was, red on the base, and a launcher test that the `devserver` demo opens its dialog with `document.activeElement` unchanged, red on the base the same way (the helper's pin first asserted that the mount focus carries `preventScroll`; the lead's ruling of 2026-10-12 on the review seat's range reading, below, drops that half and returns the pin to this form); the browser check lives under `scripts/e2e/` beside the browser suite's helpers, serves the built `dist`, is run by hand like the other suites, exits 2 and not 1 without a browser, and holds the desktop and fragment arms as pins red on the base, the Install, Animations and phone no-fragment arms as controls (at the base in Chrome 155 the lazy frame did not load at the phone viewport with no fragment, so that arm read 0 and proves nothing about the repair), and a scroll-toward-the-demo arm for the phone's real case, a pin only if it is red at the base; and, from the same ruling, a reader-open arm on the Install and Devserver pages (the opener 24 px above the viewport's bottom edge, a real pointer click, the dialog wholly in view within 2 px), red at `549bf15cb`.
3. A link with a fragment still lands on its heading.
4. The demo's form is reachable and usable by keyboard after the reader moves focus into it.
5. The repaired site is what the owner reads at `chan.app` after the next deploy of the marketing site, which is the owner's to authorize.

## Reproduction 2026-10-12

By the frontend seat, against the marketing package's production build at `4507fe5a0`, served statically on a guest loopback port and driven by headless Chrome 155 through the browser harness's locked puppeteer, with a constructed control first (an iframe whose focus call scrolled its parent from 0 to 1,824 px). `/manual/devserver/` with no fragment at 1280x800: the parent's `scrollY` went from 0 to 2,370 during the embedded dialog's `DIV.modal.focus()` call 108 ms after the navigation started and 79 ms after the frame's document was created (the run was contended, 13 to 22 throttled periods, so its times are ordering evidence), and the parent's active element was the iframe. With the fragment `#remote-workspaces` the landing moved too: 3,155 to 2,370 at 1280x800 and 4,499 to 3,626 at 390x844, leaving the heading 854 and 897 px down, below both viewports. At 390x844 with no fragment the lazy frame stayed 3,658 px below the viewport, never loaded and never mounted the dialog, so `scrollY` read 0 after a bounded 12 s wait: that arm has no focus result and is not a pass. The Install page (the `empty` launcher variant mounted in the page) and the Animations page stayed at 0 on both viewports with no focus call. The moving call is `createModalFocus.mount()` calling `panel.focus()` with no options (`web/packages/web-shared/src/modalFocus.ts` line 21), reached from the launcher demo's new-workspace dialog opened on mount for the `devserver` variant (`LauncherDemo.svelte` line 69); the same helper's restore passes `preventScroll`. The helper is shared with the launcher's and the workspace app's own modals, whose window scroll was read from source only, not measured. Record: `reports/mscroll-measure-Frontend106.md` and `evidence/Frontend106/mscroll-probe.log` on the round's bus.
