# `cs terminal status` returns at once, so a reported state cannot be watched on its tab

Status: raised by the owner on 2026-10-12, after v0.105.0 shipped the OSC 7501 program status item; written down, not designed. The owner asked for the flag by name. Accepted into v0.106.0 on 2026-10-12 by the owner asking for it, at the round launch of that day: its first step (the reproduction named below) is accepted, and nothing past the decision it names. Reproduced on 2026-10-12 (see "Reproduction"); the flag's design accepted by the lead and read by the review seat the same day, accepted for build (see "Lead's decision").

## What was seen

The owner tried to validate the tab marks of v0.105.0 by hand with `cs terminal status` from a shell prompt and could not: the command writes its report and exits, and the tab's state is gone before it can be read. The owner's words: "the cs terminal status commands could use a --sleep flag so that we can actually validate the states because otherwise they run too fast and we can't see the tab state because when the program exists the state is reset; i was able to run cs tunnel to validate, but that was it". `cs tunnel` works for this only because it stays in the foreground while it reports.

Read at source on `main` at `4507fe5a0`: `cs terminal status` takes a state and six options and no way to stay alive (`crates/chan-shell/src/cli.rs`, `TerminalAction::Status`, dispatched to `program_status::emit`). The library tags a report that sets `working`, `blocked` or `idle` with the process group that holds the PTY's foreground when the report is read, and stores `done` and `error` without one (`crates/chan-library/src/terminal_sessions/program_status.rs`, `apply`); the shipped item says a killed job takes its tagged records with it and that `working`, `blocked` and `idle` are also dropped at `OSC 133 ; A`. A report written by a command that has already exited is therefore the short-lived case by design.

Not established: which of the two rules removed the record in the owner's reading (the foreground group's end or the shell's next prompt mark); whether `done` and `error`, which both rules spare, were also lost in the owner's shell; whether the command's help line "A control report stays after this command returns, like a PTY report" is true of a PTY report of `working` from an interactive prompt.

## Desired contract

A person at a shell prompt can put a tab into each of the six states and look at it for as long as they ask. `cs terminal status <STATE> ... --sleep <SECONDS>` writes the report exactly as today and then stays in the foreground for that long before it exits, so the record lives under the rules that already exist; without the flag nothing changes.

## What to do

Read the two removal rules at source and reproduce the owner's reading first, so the flag is built against the rule that applies and the help text says what a user will see. Then settle, before the code: the unit and form of the value (whole or fractional seconds) and its bound; what an interrupt during the wait does (exit at once, nothing more written); whether the command writes anything when the wait ends (the default taken here: nothing, the existing rules end the record); what the flag means with `clear` and on the control-socket route (accepted and waited, or refused with a reason); the control route samples the subject session's foreground group as the PTY route does (`crates/chan-library/src/terminal_sessions/program_status.rs`, `apply_control`, lines 918 to 931 at `4507fe5a0`), so a waiting control sender keeps only itself alive and the record stays under the subject's own rules (read by the runtime seat on 2026-10-12, correcting the first draft's phrase that no foreground group is involved there). Add the flag, its help with an example a user can paste for each state, and the user manual's program status section.

## Boundaries

`crates/chan-shell/src/cli.rs` (the `Status` arguments and dispatch), `crates/chan-shell/src/program_status.rs`, `crates/chan-shell/src/help.rs`, their tests; `web/packages/marketing/src/pages/manual/terminal.html` if the manual names the command. Not changed: the report's bytes, the library's record rules, the wire.

## Acceptance

1. The owner's reading reproduced, and the rule that removed the record named with its source lines.
2. With `--sleep N` from an interactive prompt, the record for `working`, `blocked` and `idle` is on the session for the wait and gone after it, read through `cs terminal list --json` from a second terminal during and after; `done` and `error` behave as they do without the flag.
3. An interrupt during the wait ends the command at once with no second report written.
4. A refused value (negative, not a number, over the bound) writes no report byte.
5. The help's pasted examples each produce the state they name, and the corrected sentence about what stays after the command returns is true as written.

## Reproduction 2026-10-12

By the runtime seat, on the unchanged base `4507fe5a0` in a Linux guest (Ubuntu 24.04.4, Bash 5.2.21), through the product's PTY path: an interactive Bash created through the server's terminal API, `cs terminal status <state>` typed at its prompt, `cs terminal list --json` read by a second shell across each call and after its return (no reading fell wholly inside an unflagged call; that a held report is visible is the control's, a foreground subshell that reported `working` and waited on a FIFO), 35 cases and 1,519 list readings with present and absent controls. With a shell that emits no `OSC 133 ; A`, `working`, `blocked` and `idle` were gone in nine of nine cases, first seen absent 20 to 158 ms after `cs` returned; with the next prompt held behind a FIFO they were gone before the prompt could emit its mark. So the rule that removed the record is the foreground group's end: the drainer's 150 ms tick (`terminal_sessions.rs` 125 and 3588 to 3606) prunes a tagged record whose group has gone (6161 to 6210; `program_status.rs` 1006 to 1021). `done` and `error` stayed in all fourteen cases, through the prompt mark included (stored untagged at 1061 to 1066, spared by `drop_transient` at 960 to 976). Of the draft's three open points: the removing rule is the foreground group's end, not the prompt mark, in this configuration (the owner's own shell stream was not available, so which rule won in his session is not identified); `done` and `error` are not lost as records in the list (no rendered tab was read, and a completion report read while its session is focused is stored seen, which the tab strip leaves out, so on the tab in front `done`, `error` and `idle` show no mark; the help says how to see the mark for the two completions, by reporting while another tab is in front or by reading the list); and the help's sentence "A control report stays after this command returns, like a PTY report" (`help.rs` 1066) is misleading for the transient states on either route. One known limit of the heuristic stands: a writer that exits before the server samples the foreground receives no tag, and such a record would then end only at the next prompt mark; it was not seen in these cases. The run is recorded as contended (the guest met its cap during the build); its timings are observation bounds. Record: `reports/sleep-reproduction-Runtime106.md` and `evidence/Runtime106/sleep-base-1/` on the round's bus.

## Lead's decision 2026-10-12

The runtime seat's proposal, accepted by the lead and read by the review seat: `--sleep <SECONDS>` takes whole decimal seconds 0 to 86400 inclusive, validated before any byte so a refused value writes no report; omitted or 0 keeps today's return; one emission by the existing route, then a wait that writes nothing at expiry and exits 0; an interrupt ends the process with nothing more written (no handler is added on this path); `clear` and the control-socket route accept the flag and wait the same way, the control wait keeping only the sender alive. The help's persistence sentence gives way to the lifetime rules true on every build: completions stay until replaced or cleared and show no mark on the tab in front once seen; the transient states end with the foreground job that held the terminal when the report was read or at the next prompt mark; a report read with no such job, or on a non-Unix build, takes no tag and stays until the next prompt mark or a clear. The review seat's amendments on the proof: the arms own their order (a long wait, present across two drain periods with the writer alive, an interrupt, absence by bounded poll; an expiry arm with a lower bound only; no fixed sleep), four named mutants (a report at expiry, a clear on interrupt, the wait removed, the bound raised), the committed pins in the existing PTY fixture of the `chan` crate, the manual's four pasteable calls in scope, the help's examples parsed by a unit test; acceptance 5's reading names for each state what it read, the list or the mark.
