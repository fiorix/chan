# Root rows of the file tree fall outside the selected directory's refresh scope

Status: carried into v0.106.0 at the v0.105.0 GA on 2026-10-11, still raised for a decision.

Record before the release: raised for v0.105.0 by the owner's word of 2026-10-09, from the v0.104.0 release report's follow-ups; written down, not designed, not accepted for build.

## What was seen

A source inference after two development observations; no dedicated reproducer was run. In two development runs of browser check 132 a file written on disk at the workspace root did not appear in the File Browser's tree: `dev3-132` and `dev4-132` each ended "timed out waiting for the file smoke-attach-<stamp>-root.md in the tree" (`dev/v0104-team/evidence/Frontend104/drafts-web/dev3-132.log` and `dev4-132.log`, each with status 1, on Chrome for Testing 155.0.8059.39 in a guest), and the second log lists the tree's rows at the failure: the folder, the document inside it, the image uploaded into the folder in the same interval and the other root entries, without the new root file. The author recorded it as an observation with the cause not established, seen while the File Browser tab was not the active tab, within 20 seconds of the tab coming forward again (`dev/v0104-team/reports/validation-Frontend104-drafts-web.md`, section "Outside the item, for the lead"). The two runs were of two uncommitted development versions of the check, whose file's hash differs between the two logs; the committed check seeds both of its documents before the tree is first shown (the same report, section "The development runs, kept").

The review then read a cause at source and did not run it (`dev/v0104-team/reviews/review-Review104-drafts-web-range-1.md`, section "Notes, none holding the range", entry B3): a File Browser's refresh scope is its selection's directory, and a watch event refreshes the tree only when its path is inside some scope; in both runs the selection was the document inside the folder, so the scope was that folder and the file written at the root was outside it, while the image uploaded into the folder showed. The review holds the cause to be the scope rule as written, whether or not the tab is in front, and gives a reproducer by reading: select a file inside a folder in the File Browser, create a file at the workspace root from outside chan, and the root's rows do not gain it. It found the three scope functions and the filesystem tail of `onWatchEvent` byte-identical at the drafts range's base `1392c6012` and tip `728e66e8c`, so the drafts work is not the cause.

The functions are in the released tree as described, read again at the v0.104.0 commit: `web/packages/workspace-app/src/state/store.svelte.ts`, `fbScopeForSelection` (line 2996: no selection is the root scope, a selected directory is its own scope, a selected file gives its parent directory), `activeFbScopes` (line 3006: the dock's browser and every browser tab contribute one scope each), `pathInAnyScope` (line 3022), and the tail of `onWatchEvent` (lines 1182 to 1188), which calls `refreshTreeForPath` only when a watched path is inside some scope. The comment above the three functions states the rule and its reason: an event refreshes the tree if and only if at least one scope contains its path, the gain being no flicker when the scope and the event path do not intersect.

Not established: that the scope rule is the cause, since nothing was run to separate it from the inactive tab the author observed; the lead's dispositions say the explanation is read at source, not a separately run reproducer (`dev/v0104-team/reports/held-observation-dispositions-Lead104.md`, the paragraph after the table), and the candidate report claims no dedicated reproducer and no inactive-tab cause (`dev/v0104-team/reports/candidate-report-Lead104.md`, section "Held observations and limits"). Also not established: whether and when the stale root rows catch up (a later event inside the scope, a change of selection, a collapse and expand, a reload); the dock's browser as against a browser tab; any engine other than headless Chrome 155. Whether root rows that go stale while a folder's file is selected are wanted is recorded as a product question, the owner's to decide (the dispositions' same paragraph; the review's entry B3).

## Desired contract

The choices: a file created at the workspace root appears in the tree within the watcher's ordinary delay whatever the File Browser's selection is; or the scope rule stands as written, and what goes stale and what brings it up to date are stated where a user and a check author can read them.

## Reproduction and the owner's decision 2026-10-13

Acceptance 1 and 2, by the frontend seat in its guest at `31513a64f` on its branch, no product change (`tasks/task-Frontend106-Lead106-28.md` in the round's bus; the development check `evidence/Frontend106/fbroot-probe.mjs`, the expected readings written first in `fbroot-expected.md`, one log per arm): headless Chrome for Testing 155.0.8059.39 against a debug build of that tip, a 2 CPU / 6 GiB guest, each arm a fresh workspace, server and browser context, the root file written with Node's filesystem API outside chan. With the tab in front and a file inside a folder selected the root row was absent for the whole 20.2 s observation, while a file then created inside the selected folder appeared in 253 ms; clearing the selection did not bring the root row, at once or two seconds later; a second write at the root brought both root rows in 252 ms. The cause is shown: the scope rule, whether the tab is in front or not. The inactive tab alone is not a cause, since its control with no selection had the row on return. What clears the stale root rows, as observed: a later event at the root; not a change of selection. Not observed: an upper bound on the stale interval without a later root event (at least 20.2 s in front and 40.2 s across the hidden and visible phases); a collapse and expand or a reload; the dock's browser as against a browser tab; a rename or a removal at the root; any engine other than headless Chrome 155.

## The design read and the lead's rulings 2026-10-13

The frontend seat's note (`reports/design-Frontend106-fbroot.md` in the round's bus), read by the review seat before code (`reviews/review-Review106-fbroot-design-1.md`): for each distinct exact parent of a watch path or a rename's destination, relist it if the store marks it loaded, whatever is selected and whichever browser is in front; a parent never loaded gets no request and no change of the tree; the nearest-loaded-ancestor climb stays for the direct file operations and leaves the watch path. Accepted. The key is exact state: `tree.loadedDirs` has three writers and nothing removes a key, and it means "listed since the last full refresh", not "shown by a browser", which is the right meaning because the tree trusts a loaded directory when it is expanded again; so the rule's invariant is that every directory marked loaded is kept current by its own events. The owner's second half holds by the rule as written, and it is a reduction against today, where with nothing selected an event anywhere below an unopened directory relists the root. Two alternatives declined: the root joined to every scope leaves the same miss one level down and with no browser open; a relist at a selection change is not within the watcher's delay, and the reproduction showed that clearing the selection brings nothing.

What a relist costs, read at source: one directory's direct children replaced, every other row the same object, the rows keyed by path so a row still listed keeps its element; expansion, selection and scroll held apart. The rule's old "flicker" is work, not a visible reset; what does blink at this tip is the full tree refresh, which the design does not call and which the browser check uses as its detector's red.

Rulings on the review's four amendments. Taken as needed: the three scope functions and both comments go with the rule, the new comment stating the rule, its invariant and its limits; and the browser check's flicker detector runs in the arm where a relist happens (a root file created while a nested file is selected; an existing root file modified from outside, which must leave no mutation record), is shown red once against a bundle that calls the full refresh, reads an absence only after the page has received the watch frame naming the path, and asserts no tight time bound (the reproduction's 253 ms readings are one step of the probe's 250 ms poll, an upper bound and not a delay of the watcher, which has none). Not taken into this range, each a cost the product has today whenever nothing is selected and each given a row of its own with the review's proposal: an event for a parent whose first listing is in flight is skipped, and watch relists of one directory are neither limited to one in flight nor ordered ([watch-relists-of-one-directory-are-not-serialized-and-skip-a-listing-in-flight](watch-relists-of-one-directory-are-not-serialized-and-skip-a-listing-in-flight.md)); the new comment says the cost as it is, one listing per frame and two frames per event. Also outside the item and real at the base: a removed or renamed loaded directory keeps showing with its cached rows ([a-removed-or-renamed-loaded-directory-keeps-showing-in-the-file-tree-with-its-cached-rows](a-removed-or-renamed-loaded-directory-keeps-showing-in-the-file-tree-with-its-cached-rows.md)); under this change a rename with a file selected elsewhere shows both names where today it shows the old one alone.

What clears a stale root row today, added to the reproduction's record from the review's reading of the source, not observed: a socket's reopening and a lagged receiver's resync both run the full refresh. The standalone window has the same selection gate on its `fs` frames and the design repairs it there too: read, not run.

The code is the frontend seat's (the store, its watch-frame tests and browser check 163), with the pins as the review shapes them: the root creation red first in its dock, tab and no-browser forms and with each frame type; "refreshes nothing" read after the frame's own scheduled workspace refresh is seen and not after a sleep, with one mutant for the restored climb and one for the dropped loaded test; a rename across two loaded parents with one assertion per side; the draft bail kept on the watch path.
