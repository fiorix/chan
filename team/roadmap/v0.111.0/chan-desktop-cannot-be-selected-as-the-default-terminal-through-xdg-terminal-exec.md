# chan-desktop cannot be selected as the default terminal through xdg-terminal-exec

Status: raised on 2026-10-25 by the owner after the v0.110.0 release; accepted for v0.111.0; built on `v0111/xdgtex` on 2026-10-25 (the section below); the Omarchy VM checks and the merge into `main` remain.

## What was seen

The owner's ask of 2026-10-25, from a study of Omarchy (Arch + Hyprland, branch `quattro`): make `chan-desktop` selectable as the default terminal on Linux desktops that launch terminals through `xdg-terminal-exec`. Omarchy's picker offers foot, kitty, ghostty and alacritty; chan cannot stand in for them because it has neither the command-line contract nor the desktop entry keys a default terminal needs.

Read at `b2dbbf270`. Paths under `desktop/src-tauri/src/` unless named.

- `xdg-terminal-exec` picks the first entry in `~/.config/xdg-terminals.list` that carries the `TerminalEmulator` category and passes Desktop Entry validation, maps its own options onto the terminal's flags through the entry's `X-TerminalArg*` keys (a key ending in `=` appends the value to the same argv item; an option with no key is dropped), and execs the terminal without forking: `<Exec minus field codes> [mapped options] [X-TerminalArgExec value] command args...`. Reference: https://github.com/Vladimir-csp/xdg-terminal-exec.
- `packaging/distros/shared/chan-desktop.desktop` is the one entry the distro packages install (AUR, Debian, Fedora, Nix; each runs `desktop-file-validate` on it). It has `Categories=Office;TextEditor;`, no `X-TerminalArg*` key, and a `MimeType=x-scheme-handler/chan;` line left from the `chan://` handler that `5e46eb896` removed.
- `main.rs` `fn main()` reads argv only in its pre-GUI probes (`__mcp-proxy`, the `cs` and `chan` argv[0] stems, `--version`); nothing consumes a positional argument, so `chan-desktop -e cmd` today opens the launcher and ignores the flag. There is no single-instance plugin: every launch is its own process, and a second full boot would unlink the first instance's handoff socket, reopen its `~/.chan/windows.json` windows and rerun shims, gateway autoconnect and the update check.
- The terminal pipeline carries one command string: `CreateOptions.command: Option<String>` runs as `$SHELL -lc <string>` (`crates/chan-library/src/terminal_sessions/platform.rs`), the tenant default is `Registry::default_command` applied in `create()` with a `{command}\r\n` banner, and every terminal-tenant PTY starts in the home directory (`crates/chan-server/src/lib.rs`, the `TenantKind::Terminal` root). `-e bash -c "<script>"` cannot reach a PTY as three argv items.
- On Linux the Wayland `app_id` and X11 class come from GLib's program name: tauri passes no GTK application id (`app.enableGTKAppId` is unset), tao creates `gtk::Application::new(None, ..)`, and GTK3 falls back to `g_get_prgname()`, which GLib derives from argv[0] only when nothing set it first. That is why windows read `chan-desktop` today and why `StartupWMClass=chan-desktop` matches.
- What Omarchy sends, after the entry's key mapping: Super+Return `chan-desktop --dir=<cwd of the focused terminal, else $HOME>`; TUIs `chan-desktop --app-id=org.omarchy.btop -e btop`; package install `chan-desktop --app-id=org.omarchy.terminal -e omarchy-pkg-install`; floating installers `chan-desktop --app-id=org.omarchy.terminal --title=Omarchy -e bash -c "<script>"`. Hyprland rules float and tag windows by `org.omarchy.*` and `TUI.*` classes and by the title `Omarchy`; `omarchy-launch-or-focus-tui` finds an existing window by class; `omarchy-cmd-terminal-cwd` reads the cwd of the newest child of the focused window's pid when that child's executable is in `/etc/shells`.

## Desired contract

`chan-desktop [--dir=PATH] [--app-id=ID] [--title=TITLE] [--hold] [-e CMD ARGS... | -- CMD ARGS...]` opens one terminal-only window in its own process, with no workspace, launcher, registry writes or indexing. Everything after `-e` or `--` is the command's argv, exec'd as given (never joined into a string or re-split by a shell); `-e` with nothing after it is a usage error. With no command the window runs the user's shell (`$SHELL`, falling back to the passwd entry). The shell or command starts in `--dir` (a stale directory falls back to the home directory with a warning). The window and the process exit when the command exits, with the command's exit code, unless `--hold` keeps the window open until the user closes it. `--app-id` becomes the Wayland `app_id` and X11 class on Linux and is ignored elsewhere; `--title` is the fixed OS window title. Closing the window ends the command and the process with no prompt. New Window in such a window starts a sibling process with the same `--dir` and `--app-id`. Plain `chan-desktop` and `chan-desktop <positional>` keep today's GUI exactly. The shared desktop entry carries `System;TerminalEmulator;` beside its existing categories and the keys `X-TerminalArgExec=-e`, `X-TerminalArgDir=--dir=`, `X-TerminalArgAppId=--app-id=`, `X-TerminalArgTitle=--title=`, `X-TerminalArgHold=--hold`, and no `chan://` scheme handler.

## What to do

1. chan-library and chan-server: a terminal tenant's program is either a shell command line (today's path, through the login shell, with its banner) or an argv exec'd directly with no banner (`TenantProgram`), stored on the session so a restart re-execs it; a terminal tenant can be mounted with a cwd that becomes its root, so the spawn cwd, the inside-root cwd report and `CHAN_WORKSPACE_PATH` follow one value; a host front `open_terminal_session_with_program(config, program, cwd)` beside the existing command front, with the shared-tenant classification made explicit rather than inferred from "no command". Tests red first: argv with a space, a `;`, a `$HOME` and quotes reaches the child intact; no banner; the cwd is the root; the exit code reaches `last_exit`; a restart re-execs; a command override replaces an exec program; the host front refuses an empty argv and a relative cwd.
2. desktop: a `terminal_mode` module with the pure argv parser and its helpers (working-directory resolution, exit code mapping, default title, sibling argv, a PATH preflight for the command), a branch in `main()` after the GUI-stack preference and before the shims, a slim `EmbeddedServer` constructor that opens the library and binds an ephemeral loopback port with no registries, overlay, launcher root or extension processes, a `/exec` tenant front, a window of the `control` kind under the label `terminal-exec` with the capability globs that label needs, a real-close arm for that label in the close handler, an exit watcher that ends the process with the command's code unless `--hold`, a sibling spawn for New Window, and `g_set_prgname` before GTK initialises for `--app-id`.
3. packaging: the entry's categories and keys, the stale scheme-handler line removed, and `packaging/distros/README.md` saying what the entry is.
4. docs: `desktop/design.md` (the window class, the sibling New Window, the terminal-emulator contract, the AppImage entry limitation), `crates/chan-library/design.md` (the terminal tenant root and program).

2. `desktop-file-validate packaging/distros/shared/chan-desktop.desktop` exits 0; with the entry on `XDG_DATA_DIRS` and named in `xdg-terminals.list`, `xdg-terminal-exec --print-id` prints `chan-desktop.desktop` and `--print-cmd --app-id=TUI.float --dir=/tmp -e btop` prints the binary, `--app-id=TUI.float`, `--dir=/tmp`, `-e`, `btop`, one item per line.
3. `chan-desktop --dir=/tmp` opens a shell in `/tmp` and `exit` closes the window and the process; `chan-desktop -e bash -c 'echo hi; sleep 2'` shows `hi` and exits 0 after two seconds; `chan-desktop -e sh -c 'exit 3'` exits 3; `--hold` keeps the window until Ctrl+D; a missing program exits 127 with no window; the command is a direct child of the window's process with no shell wrapper; plain `chan-desktop` still opens the launcher; a GUI instance running beside a terminal launch keeps its windows, handoff socket and saved port.
4. With `--app-id=X`, the compositor reads class `X` (KWin `resourceClass` on the build host, `hyprctl clients` class in an Omarchy VM); without it, `chan-desktop`.
5. In an Omarchy VM: `xdg-terminal-exec --app-id=TUI.float -e btop` floats; the menu's Install, Package opens a floating chan window and the install runs; Super+Return from a focused chan window opens in its cwd.

## Built and verified 2026-10-25

Built on `v0111/xdgtex` from `b2dbbf270`, on the host `geekom` (CachyOS, Rust 1.95.0). What landed follows the plan above: `TenantProgram` and the tenant cwd in chan-library and chan-server, the `terminal_mode` module and the slim host in the desktop, the entry and its keys in packaging, and the design documents.

Rulings made while building:

- `--dir V` is accepted beside `--dir=V` (the entry only ever sends the `=` form); a `--dir` that is not a directory falls back to the home directory with a logged warning rather than refusing, since a launcher passing a stale directory must still get a window; `--` with nothing after it is the same usage error as `-e`.
- The program named by `-e` is resolved through `PATH` before any window opens, so a missing program exits 127 with no window instead of a window sitting on a spawn error.
- New Window in a default-terminal window starts a sibling process through `sh -c '"$0" "$@" &'`, so it is reparented away from the window's process and Omarchy's cwd lookup, which reads the focused window's newest child, still finds the shell; the argv rides as positional parameters.
- The shared terminal tenant is declared by its caller, not inferred from "no command": a `--dir`-only launch is a program-less single-purpose tenant and must not take the shared tenant's window-reap hook.
- `cargo doc` reads `argv[0]` in a doc comment as a link; such mentions are code spans.
