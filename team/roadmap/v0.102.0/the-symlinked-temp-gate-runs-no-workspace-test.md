# The symlinked-temp gate runs no workspace test

Status: raised on 2026-10-05 by the dry run of the release workflow on the version's first release candidate, whose macOS validation job was red at one test of the workspace crate, at an assertion of the test's own fixture; read that day as a fault of the fixture and a gap in what the Linux gate runs, reproduced on Linux, ordered by the lead as a repair of both and built on the v0.102.0 integration branch. A discovery: the item itself was not put to the owner, who answered the red job with a second candidate, as recorded below. `accepted | cut`: both halves are built and proven, on Linux and on a macOS runner, and the row was added at cut.

## Owner ruling

Not put to the owner as an item. On 2026-10-05 the owner was told in writing of the red job, of its reading and its reproduction on Linux, of the gap in the gate and that both were being repaired, and was given three choices on the red job: a second release candidate cut once the repair was gated, which the lead recommended; the first candidate tested as it was, the repair going into a later one; or one dry run of the release workflow on a branch that holds the repair, with no new candidate. The owner's answer was "cut rc1".

## What was seen

The dry run of the release workflow at `adf953f6c`, the commit of the release candidate `0.102.0-rc0` (run 37312660124, dispatched with `publish=false`), failed in its macOS validation job, in the step `make ci-macos`. `cargo test --all-targets` stopped at the workspace crate's unit tests, 942 passed and 1 failed: `library::tests::a_reset_keeps_a_row_registered_under_its_match_since_its_lookup`, at `crates/chan-workspace/src/library.rs:1876`, with `fixture: the registration's alias probe never reached the stall`. That is an assertion of the test's own fixture, ahead of every assertion on the product. The test is of this version, written on 2026-10-03 and compiled on Unix alone; by the lead's record of that day, no commit of this version had been built on macOS before that candidate.

What the red stopped: the workspace crate's integration tests, `make casefold-test-verdict` and `make ci-macos-build` did not run in that job, so the verdict that [the-casefold-pins-run-in-no-gate](the-casefold-pins-run-in-no-gate.md) waited for was not printed by it. By the lead's record of that day it did not stop the candidate's packages, which a dry run builds beside validation; a publishing run would have stopped on it.

What it was, read in the code at `adf953f6c` with nothing run: the fixture, and not the product. The test registers a workspace under a parent directory, moves the parent away and leaves a link in its place, and from inside a reset of the moved directory registers that directory again, with the second registration's probe of the first row's root held by a stall. The stall is keyed on the first row's stored root, in its canonical spelling, and lets one call through (`stall_after(&self.stored, 1)` in `RegisterDuringTheWipe::on_progress`, `library.rs:1870`). The one pass is meant for the registration's own lookup of its root, so that the probe after it is the call that is held. But the fixture handed the registration a path built from the temporary directory as the process spells it (`library.rs:1887-1890`), and the stall matches a path as it was asked, before anything is resolved (`stall_point`, `crates/chan-workspace/src/paths.rs:748-760`, called at the top of `canonicalize_normalized`, `paths.rs:426-429`). Where the temporary directory's path is already canonical, the lookup is spelled under the stall's key and uses up the pass, and the probe is held. Where it is not, the lookup matches no key and is not counted, the probe takes the pass and answers, nothing is ever held, and the fixture's assertion gives up after ten seconds. A temporary directory on macOS is spelled through a link, `/var/folders` for `/private/var/folders`; that the runner's path in that job was spelled so is inferred, since the job's log prints no such path. No line of the product stands on that difference: the reset matches its root once and removes the one row it wiped, by that row's own stored root and key, and resolves nothing more (`reset_workspace_with` and `reset_row`, `library.rs`; `remove_stored`, `crates/chan-workspace/src/registry.rs`). The reading went through every stall that lets a counted number of calls through and every test that relinks a root under a temporary directory, and found this test the only one exposed.

Reproduced on Linux at that commit the same day, in the gate's worktree. With the temporary directory set through a symlink the one test fails at `library.rs:1876:17` with the same sentence after 10.00 s, and with it plain the same test passes in 0.05 s. The whole test set of the workspace crate, run through the symlink with every test run whatever failed, has that one failure and no other: 961 unit tests passed and 1 failed, and each of the eleven integration-test files is green. So the tests of that crate which the macOS job never reached were green on Linux under the condition that reds the one test; that is a run on Linux and not on macOS.

Why no gate on Linux showed it. `make test-symlink-tmpdir`, the step of `make ci-linux` that runs Rust suites with the temporary directory spelled through a symlink, ran `-p chan -p chan-library -p chan-server` (`Makefile:423` at `adf953f6c`) and no test of the workspace crate. The item that added the step in v0.101.0 says so itself: [the-linux-gate-runs-tests-under-a-canonical-tmpdir](../done/the-linux-gate-runs-tests-under-a-canonical-tmpdir.md) has `not run` for that crate under the symlink. So for that crate a macOS runner was the only place where a test met a temporary path that is not canonical. In the integration gate on `adf953f6c` this test passed where the temporary directory is plain and was not in the symlinked step at all.

## Desired contract

A test of the workspace crate that holds only under a canonical temporary path goes red on the Linux gate, and not first on a macOS runner: `make test-symlink-tmpdir` runs that crate's unit and integration tests beside the other crates', and the gate skill says which arm runs which crate. The reset's test builds its race whatever the spelling of the temporary directory.

## What to do

Of the two repairs the reading names for the fixture, the smaller: resolve the moved directory before it is handed to the registration and to the reset, as the sibling fixture `relinked_row` does, so that the registration's lookup is spelled under the stall's key on every host. The other, moving the test onto the helper that derives the number of passes from the two spellings (`register_beside_a_held_probe`), was not taken. Keeping the test off macOS is not a repair: the fixture is wrong wherever the temporary path is not canonical, Linux included, and the reset's half of the behaviour would be left with no test on macOS. Then add `-p chan-workspace` to `make test-symlink-tmpdir`, with the gate skill's lines.

## Boundaries

The fixture of the one test in `crates/chan-workspace/src/library.rs`; the target `test-symlink-tmpdir` in `Makefile`; `.agents/skills/gate/SKILL.md`. No production line.

## Acceptance

1. The reset's test is red at its fixture's assertion under a symlinked temporary directory before the repair and green after it, under a symlinked and under a plain one; a mutation of what the test pins still reds it both ways.
2. `make test-symlink-tmpdir` runs the workspace crate's unit and integration tests and `.agents/skills/gate/SKILL.md` says so; shown by a gate run whose symlinked step has that test `ok`.
3. The macOS validation job of a run of the release workflow is green with that test `ok`.
