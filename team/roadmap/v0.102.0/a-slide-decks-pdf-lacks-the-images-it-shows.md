# A slide deck's PDF lacks the images the deck shows

Read in code at `4c4ada0a1`. The causes below were a reading when the item was written; on 2026-10-03 the owner's own exports of the deck were read back pixel by pixel, and the section "What the exports show" records which of them that measurement settles. Ruled on 2026-10-03: see Owner ruling.

## Owner ruling

Accepted on 2026-09-29 for the next version: the owner reported the defect and asked in the same sentence to "add to next roadmap for fixing". It is not part of v0.101.0. The shape of the fix is not ruled.

## What was seen

The owner's words, of the export that the UI completes: "it fails to export images which are displayed on a chan's slide deck resulting in missing the image in the final pdf". The first half of that sentence, `cs export` hanging, is [cs-export-hangs-where-the-ui-export-completes](cs-export-hangs-where-the-ui-export-completes.md). Not recorded: which app wrote the PDF, chan-desktop or a browser; where the deck showed the image, in the editor, the preview or play, and at what window size; the image's type and size and what else its slide holds; and whether the image was absent or cut.

Read, not run. Lines at `4c4ada0a1`, under `web/packages/workspace-app/src/` where no other path is named.

**An image's way to the screen and to the PDF.** The preview renders a slide's markdown and rewrites each image's `src` to the workspace's file route with the window's token, and the page loads it (`show`, `state/slidePreview.ts:236-264`; `prepareSlideImages`, `editor/slide_dom.ts:393-433`; `resolveImageSrc`, `editor/extensions/image.ts:98-116`). The export builds the same elements with the same two functions, in a tree that is never attached (`buildSlidePageDom`, `editor/pdf_pages.ts:280-335`), waits for each image to load or fail, ten seconds at most (`editor/slide_dom.ts:435-469`), and then, for each slide, fetches every image and writes it into its `src` as a `data:` URI (`inlineImages`, `editor/pdf_snapshot.ts:165-180`), refuses the page while any reference is still external (`auditSelfContained`, `:216-252`), serializes the page into an `<svg><foreignObject>`, loads that as an image, draws it on a canvas and encodes a PNG (`:257-322`), which becomes one A4 landscape page (`editor/pdf_export.ts:238-266`). An image the export cannot fetch fails the export by name. So a PDF that was written without an image means that the image was inlined and not painted, or painted where the page does not reach.

**1. The page is drawn as soon as its SVG has loaded.** `loadSvgPageImage` resolves at the page image's `load` and `rasterizePage` draws at once (`editor/pdf_snapshot.ts:266-277`, `:296-302`); nothing waits for the images nested in that SVG to be decoded. Whether they are decoded by then is the engine's choice. chan-desktop runs WebKit on Linux and macOS (`desktop/design.md:271`, `:225`), and WebKit is known, from other projects that rasterize a page this way and not from this tree, to fire that `load` before the nested images are decoded, so that a first draw has the text and not the images. Every check of the export ran in headless Chrome (`scripts/e2e/browser-smoke/README.md:3`). If the owner's PDF came from chan-desktop this is the first cause to test, and it would take a document's images as well as a deck's.

**2. The export cuts a slide that the screen scrolls, in a box smaller than a large screen's.** On screen a slide's page scrolls (`overflow:auto`, `state/slidePreview.ts:510`) and is sized from the window, 86 percent of it in the preview and all of it in play (`:506-509`). In the export the slide is a fixed box that hides what overflows (`slidePageBoxStyle`, `editor/slide_dom.ts:640-642`; the page's root, `editor/pdf_pages.ts:296`), laid out as the preview at a screen of 1920 by 1080 (`deckSlideLayoutBox`, `editor/pdf_pages.ts:198-220`). Text and an image's width in pixels do not grow with the screen, and the content is zoomed by 2 unless the deck says otherwise (`editor/slides.ts:25`; `contentStyle`, `editor/slide_dom.ts:601-610`). For a 16:9 deck that leaves the content about 410 pixels of height in the export, against 486 in play at 1920 by 1080, 565 in the preview at 2560 by 1440 and 666 in play there, and an image keeps its width and takes the height that follows (`editor/slide_dom.ts:771-776`). So a slide that fits the owner's screen, or that the owner scrolls, loses in the PDF what lies below the box, and an image under a heading and some text is what lies there. The fix that set the export's box recorded this as out of scope, "preview-vs-play drift and non-reference viewports", and no item took it up ([bug-fixes](../done/bug-fixes.md), "Slides: PDF export diagram sizing").

**3. The audit takes any `data:` URI for an image.** `fetchAsDataUrl` keeps whatever body and type a 200 carried (`editor/pdf_snapshot.ts:67-85`), and the audit asks only whether a `src` starts with `data:` (`isInlineUrl`, `:89-91`, `:219-222`). A body that is not an image passes and paints nothing. The server has no media type for `.webp`, which the editor counts as an image, nor for `.avif` or `.bmp`, and serves them as `application/octet-stream` (`content_type_for`, `crates/chan-server/src/static_assets.rs:399-431`; `IMAGE_EXTS`, `editor/extensions/image.ts:13`); whether an engine paints such a `data:` URI inside the page's SVG was not established.

**4. An image's `srcset` is not inlined and not audited.** `inlineImages` and the audit read `src` alone (`editor/pdf_snapshot.ts:165-180`, `:219-222`). Only an `<img>` written as HTML carries one.

**What the reading rules out.** The sanitizer is the same on the preview and in the export and admits `img` and its `src` (`api/markdown.ts:58-80`). The export's fetch is of the same origin as the image the page loads and carries the same token in its address (`api/transport.ts:109-114`). An image marked lazy is made eager before it is waited for (`editor/slide_dom.ts:454-457`). No content security policy was found on the workspace app's page, and the desktop's own (`desktop/src-tauri/tauri.conf.json:17`) was not shown to reach a workspace window.

**What checks it.** The browser smoke exports a deck whose first slide holds an image (`scripts/e2e/browser-smoke/seed/deck-169.md:12`) and asserts each PDF's page count and orientation and that each page holds some ink (`scripts/e2e/browser-smoke/checks/20-pdf-inspector.mjs:53-66`; `scripts/e2e/browser-smoke/lib/pdf.mjs:228-237`), which a slide with its text and without its image passes. No check reads an image's pixels in a PDF, in any engine.

**Two statements that one engine cannot both satisfy.** A comment says that WebKit taints a canvas drawn from an SVG that holds a `foreignObject`, so that chan-desktop cannot read such a canvas back (`editor/mermaid_render.ts:57-62`), and the export reads back exactly such a canvas for every page while the desktop's design says the export works on every surface (`desktop/design.md:331`). Which holds in the desktop's engine today was not established; the owner's PDF was written, so where the owner exported, the canvas was read.

No cause shared with the hang of `cs export` was found. The two share the render engine. Slides that carry images are the slowest pages, so an image-heavy deck is the one most likely to outlast that command's wait; that link is possible and not established.

## What the exports show

Measured on 2026-10-03 against the owner's own exports of `dev/asg/presentation.md` in the `sdme` workspace, a 46-slide 16:9 deck at `zoom_factor: 2.5` whose seven image slides each hold a heading and one PNG screenshot sized with `#w=`. Each export is 46 pages, one 2246x1588 PNG per page. The pages were decompressed out of the PDF and scanned for ink.

**The image is absent, not cut, and the loss is deterministic.** In the export chan-desktop wrote on 2026-10-02, the `footlose` page carries exactly one band of ink, rows 255 to 315 at x 74 to 366, which is the heading; every other pixel is the slide background. The seven image pages are the smallest in the file, 17 to 25 KB against a 110 KB mean, and they are byte-identical to the export of 2026-09-30, so this is not a race that sometimes loses.

**The images did reach the raster.** `auditSelfContained` fails the export by name while any `img src` is still external, and the server serves `.png` as `image/png` (`crates/chan-server/src/static_assets.rs:415`), so a 46-page PDF existing at all proves every image was fetched and inlined as a `data:` URI. The loss is at the single draw in `rasterizePage`, which paints the moment the outer SVG image fires `load` and waits for nothing nested inside the `foreignObject`. This is cause 1, measured.

**The engine is the variable.** The same deck exported from Chrome against the same devserver on 2026-10-03 carries the images. chan-desktop runs WKWebView on macOS. So the nested `data:` images are subresources of the SVG-image document that Chromium blocks the outer `load` on and WebKit does not, and every check in this repo runs headless Chrome, which is why none of them sees it.

**Cause 3 is ruled out for this deck.** Every image is a `.png` and every `data:` URI it was inlined as is an image's.

**The export's box is the preview's, in both axes.** The geometry read back from the Chrome raster matches `deckPageLayout` to the pixel: the slide content box runs x 73.4 to 2171.4 raster px against measured ink at 73 to 2171, and the `footlose` image's computed right edge of 2031.7 against measured 2031. That box is `deckSlideLayoutBox`, which mirrors the preview's `width:min(86vw, ...)` at a 1920x1080 reference and so fixes the slide at 1651.2 px, while play is `width:100vw` (`state/slidePreview.ts:498`). The two agree only at a 1651 px wide window. The body size the raster measures is 16px, from a heading ink height of 61 raster px.

- Height, which is cause 2 measured: the content box is 328.32 px tall at this zoom, the heading block takes 43.4 and the image's top margin 11.2, leaving 273.7 for images whose seven instances are 307 to 332 px tall, 11 to 18 percent over. On the `footlose` page the image's ink runs to y 1424 against a content bottom at 1351.9 and the slide's own edge at 1425.3: the screenshot is cut at the padding edge, silently.
- Width, which cause 2 did not name: on `How the isolate binary works` the first two bullets are one line when the deck plays and two in the PDF. On `Other root filesystems` the `sh` block's longest line overflows the box by about 1.3 percent, and because `slidePreviewCss` gives `pre` `overflow: auto` (`editor/slide_dom.ts:779`) the engine paints a scrollbar thumb into the raster, rows 1035 to 1044 at x 77 to 2148 inside a 73 to 2171 track. A PDF has no scrolling, so no overflow of any size may paint one.

One reading is not settled: the export of 2026-09-30 00:26 has those same seven pages byte-identical to each other and of a single color, fully blank with no heading either. The deck most likely had no headings on those slides then, and that was not established.

## Desired contract

The PDF of a slide shows every image that the slide shows on screen, whole, in the same place and at the same share of the slide, in each engine chan ships in: the desktop's on Linux, macOS and Windows, and a browser. An image that the export cannot paint fails the export and names the image, as one it cannot fetch does. A slide whose content does not fit its page is not cut in silence. The PDF breaks a slide's lines where the deck breaks them when it plays, so an author who composes in play gets the deck they composed. The raster carries no interactive affordance: a page that overflows never paints a scrollbar, whatever the engine would show on screen. A document's export holds the same.

## What to do

Reproduce first, with the owner's deck, in the app the owner used and in a Chromium browser, and read which of the causes above it is; more than one can hold. Then, as suggestions: decode every inlined image before the page is serialized and hold the draw until the page image's own images are decoded, or paint the page by a way that needs no SVG image; refuse a `data:` URI whose type is not an image's, and give the server the media types of the images the editor names; give the preview, play and the export one design box, which the earlier fix named as the principled one, and rule what the export does with a slide that overflows it, scale it, refuse it by name or warn; and teach the smoke's PDF helper to read a region's color.

## Boundaries

`web/packages/workspace-app/src/editor/pdf_snapshot.ts`, `pdf_pages.ts`, `pdf_export.ts` and `slide_dom.ts`, `state/slidePreview.ts` if the box becomes one, and their tests; `crates/chan-server/src/static_assets.rs` if media types are added; `scripts/e2e/browser-smoke/lib/pdf.mjs`, `checks/20-pdf-inspector.mjs` and `seed/`; the sentence of `crates/chan-shell/src/help.rs:179-181` that says images render into the PDF the way the editor shows them, and `desktop/design.md:331`. The audit stays as strict as it is or becomes stricter. The token that an image's address carries stays out of the PDF, as it does today once the image is inlined. `pdf_export.ts` is shared with the item on the hang of `cs export`, so the two are built one after the other.

## Acceptance

1. A page one of whose images was inlined as a `data:` URI of a type that is not an image's is refused and the image named; pinned in jsdom with a fetch that answers 200 and `text/html`, red first.
2. The page is not drawn before each of its inlined images reports that it is decoded, and an image that does not decode fails the export by name; pinned in jsdom with a stand-in image whose decode is held, red first.
3. An `<img>` that carries a `srcset`, and a `<picture>`, are inlined or refused by name; pinned.
4. The browser smoke's deck holds an image of one known color, and the check reads that color from the PDF page where the preview shows the image; red first in an engine that loses the image, and where the image is painted today the check is a pin whose mutation is the draw made before the decode.
5. A slide whose image lies below the height of the export's box comes out as the ruling on an overflowing slide says, whole at a smaller scale, refused by name or warned by name, and never cut in silence; pinned in the browser smoke, red first, since by this reading the image is cut today.
6. A document that holds the same image passes checks 2 and 4.
7. On a display, by a person: the owner's deck exported from chan-desktop on Linux and on macOS and from a browser, each PDF opened beside the deck in the preview and in play on the owner's screen: every image is there, whole, where its slide shows it.
8. A slide whose `pre` is wider than the export's box rasterizes with no scrollbar pixel in it; pinned on the raster of `Other root filesystems`, red first.
9. A slide line that fits on one line at the play box fits on one line in the PDF; pinned in the browser smoke on the two bullets of `How the isolate binary works`, red first.

## What shipped

Built on 2026-10-03 on the v0.102.0 integration branch and not on `main`, in a range the lead accepted on its reports, the status files of its gate and of its two Chrome checks at its tip, and an independent review of each of its repairs. This record was written that day from those. The row stays at build: acceptance 7 is a reading on the owner's display, no check ran in WebKit, the engine of chan-desktop and of the owner's report, and the last review read three kinds of export the range gets wrong (under "Left"), none of them run.

**The image.** A page's images are no longer left to the SVG the page is drawn from. Each image a page shows is fetched, checked to be an image, decoded, and painted from its decoded bitmap at the box and size its page composed for it, and a page is drawn only after its images decode (`web/packages/workspace-app/src/editor/pdf_snapshot.ts`). An image with no size of its own, one shaped by `object-fit` and one cut by a clipping parent are placed as the page shows them. An image the lift cannot place exactly (a box cut by the page's edge or by the last page's window, a transform, a clip path, a mask) keeps its prepared `data:` source in the page's own document, which draws it. An image hidden by CSS, by a closed `details` or, once loaded, by an empty composed box is skipped; an `<img>` with a `srcset` is prepared from the candidate the page shows; an ancestor with `content-visibility:auto` is revealed before the image is measured.

**The refusals.** An image the snapshot cannot stand behind fails the export by name and is never left out in silence: a fetch that fails, a body whose type is not an image's, an image that does not decode, a `<picture>` that carries a `<source>`. The first such image in document order is the one named, by its address without the query string, so the window's token is not in the message. A document's images are prepared in batches inside a bound of five minutes that stops the work left.

**The deck.** A deck's page is laid out in play's reference box, 1920 by 1080, and a slide that overflows it is scaled down whole (`fitSlideContent`, `web/packages/workspace-app/src/editor/pdf_pages.ts`). No scrollbar is painted into a page's raster. The sentence of `cs export`'s help that says so is true with this range.

**The checks.** Acceptance 1 to 3 are pinned in jsdom beside the snapshot. The browser smoke reads the PDF itself: `scripts/e2e/browser-smoke/checks/20-pdf-inspector.mjs` exports seeded documents and decks and reads image pixels, composed boxes, page fit, line breaks and scrollbar bands out of the pages (acceptance 4 to 6, 8 and 9), and check 30 exports through `cs`. Acceptance 8 and 9 are pinned on seeded slides of the shape the owner's deck showed, not on that deck, which is not in the repository. Both checks were green in Chrome at the range's tip.

**The four rows were repaired on 2026-10-04**, in a range the lead accepted on its report, its status files and an independent review of its whole diff, which found nothing above low, each shown red first: an image turned or mirrored by the `rotate` or `scale` property, or on an `offset-path`, on itself or an ancestor, is left to the page's document (Chrome shows the rotation and the mirror with their pixels; `offset-path` has a unit pin with a fed value and no engine was asked); a marker shorter than the image is a page's cut only at that page's edge, so an image cut from above on a page that is not the last is painted by the document (Chrome shows it); `currentSrc` is read only where a `srcset` is present; and check 20 pins which painter each seed's images took. The owner ruled on 2026-10-04: no cut goes out while the turned image was open, which this closes; a WebKitGTK run of a seeded deck's export, in the shape of `scripts/e2e/webview-flip-render.py`, covers Linux's engine and is a row for the Clients seat; macOS and acceptance 7 are the owner's reading.

**The WebKitGTK reading.** On 2026-10-04, in a range the lead accepted on its report, its status files and an independent review of its whole diff, a bare WebKit2 4.1 view under Xvfb exported `deck-box.md`, `layout-rotate.md` and `layout-page-edge.md` through `chan shell export` from a seeded `chan serve` window (`scripts/e2e/webview-deck-export.py`), and `scripts/e2e/webview-deck-export-read.mjs` applied check 20's page counts, A4 orientation, raster ink and color assertions to the PDFs: all three passed, the rotated image painted by its page document and the image cut at the page edge among them, and the deck's first page showed a 422 by 421 teal image below its heading. A halved image and a removed rotation each failed the run at its pixel assertion, and a missing GI stack is a refusal, never a pass. This covers Linux's WebKit engine in a bare view with software rendering, not chan-desktop's wrapped view, macOS WebKit or Windows WebView2; it reads pixels and page geometry, not the paint counts check 20 records.

**Left.** A first image part whose marker spans both the page's top and bottom is taken as a cut from below even when the image began above the window. A document-painted `srcset` candidate chosen by density can reflow at its intrinsic size. No PDF run was made in Firefox, macOS WebKit, Windows WebView2 or chan-desktop's wrapped view.
