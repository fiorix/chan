# A window's first save can swallow a peer's unsent split

Status: raised on 2026-10-04 from a reading of a browser smoke check's failures; read in the code and not run; the owner's ruling is recorded below. On 2026-10-04 the owner accepted the smallest shape for a build in v0.102.0; the structural comparison remains a cost. On 2026-10-04 the smallest shape was built; the row stays at build for the browser proof.

## Owner ruling

On 2026-10-04 the owner accepted the smallest shape for a build in v0.102.0: a window that never held a saved layout and found no blob on load sends no DELETE for its empty layout, at its first save or on exit. The alternative structural comparison remains a cost: a peer's delete for a real reason can still seed over a pending split. The rarer missed frame before hydration or subscription remains a separate cost.

## What was seen

Two windows on one window id, two browser tabs or two views, share one session blob, and each sends its layout through a 750 ms save delay. In `web/packages/workspace-app/src/state/store.svelte.ts` at c8f9c8ec5, `scheduleSessionSave` (3295-3302, `SESSION_DEBOUNCE_MS` at 3172) arms `commitSessionSave` (3307-3325), which skips a payload equal to `lastSessionSnapshot` (3314) and otherwise sends a PUT (3323) or, for a layout that serializes to nothing, a DELETE (3321). The server broadcasts `session_changed` after each, with `deleted:true` after a DELETE, and answers 204 to a DELETE of a blob that does not exist (`crates/chan-server/src/routes/sessions.rs`, `broadcast_session_changed` 91-100, `api_delete_session` 184-195). The other window takes the frame in `onSessionChangedFrame` (3349-3374) and reads the blob back 250 ms later (`scheduleSessionSyncRefetch` 3378-3386, `applyRemoteSessionBlob` 3388-3416).

The routine DELETE of an empty window. A window whose layout is one empty pane serializes to nothing (`serializeSession` 3214-3257; `serializeLayout` in `web/packages/workspace-app/src/state/tabs.svelte.ts` 7114-7128), and `lastSessionSnapshot` starts null (3174). So its first save, armed once the app is bootstrapped (`web/packages/workspace-app/src/App.svelte`, the layout effect 202-277 with the save at 271-277; `bootstrapped` set at 433), sends a DELETE 750 ms later, even when the window never held a saved layout and found no blob when it loaded (`bootstrap` 2593-2635). The comment in `onSessionChangedFrame` at 3361-3368 names it: the routine empty-window DELETE both co-viewers fire at boot.

The first way the split is lost. Window B splits, and its PUT waits in the 750 ms delay. Window A's routine DELETE lands first, and B's `onSessionChangedFrame` takes the `deleted` case (3359-3371), which seeds `lastSessionSnapshot` with B's current serialization; that serialization already holds the split. When B's delay ends, `commitSessionSave` finds the payload equal to the snapshot (3314) and sends nothing. The split never leaves B, and A never hears of it.

The second way. B's PUT lands, then A's routine DELETE lands before A's 250 ms refetch reads the blob. A's GET answers nothing and `applyRemoteSessionBlob` returns at 3402 with the split unseen. B, seeded by A's `deleted` frame, does not send it again. The blob is gone too, so a reload of either window loses the split.

The window of the race and where it was met. The loss needs A's first save to fall between B's change and A's refetch: with both delays at 750 ms, a layout change made within about 750 ms of the other window finishing its boot. Browser smoke check 123 (`scripts/e2e/browser-smoke/checks/123-hybrid-nav-stale.mjs`) opens two pages on one window and commits B's split under a second after the first page loads. It then waits at line 259 for A's stale-layout warning (`web/packages/workspace-app/src/components/Pane.svelte` 1805-1806), and it timed out there in six of its seven recorded runs, with the check and this code unchanged across those runs. No run recorded A's state; the reading rests on the code and the run timings. A rarer variant leaves the same trace: A is not yet hydrated, or not yet subscribed, when B's frame goes out (3356), and `onWatchReady` (2229-2248) reads no session back to catch up.

## Desired contract

A layout change that a window has not yet sent is never marked saved by another window's save or delete: the change reaches the server and the other windows on that id. A layout another window saved is never removed by a routine first save: a window that never held a saved layout, and found no blob when it loaded, sends no DELETE for its empty layout, neither at its first save nor when its page goes away. A deliberate discard keeps its present meaning, including that an echo of the discarded state from a co-viewer does not bring the blob back.

## What to do

The smallest shape: in `commitSessionSave` (3307-3325) and in `flushSessionSaveOnExit` (3558-3594), when the payload is empty, the window has neither sent nor applied a layout since it loaded (`lastSessionSnapshot` still null), and its load found no blob, record the empty snapshot and send no DELETE. That takes one flag, set where `bootstrap` reads the blob (`api.getSession` at 2595 for a workspace window and at 2445 in `bootstrapStandalone`). It removes the `deleted` frame that both losses start from in the boot window, which is the case met, and it covers both ways.

The alternative, for the first clause in general: in the `deleted` case of `onSessionChangedFrame` (3359-3371), do not seed over a pending save whose layout structure differs from the structure this window last sent or applied, and keep the seed for a pending save of view state only (carets, active markers), which is the echo that case exists for. A real layout change a peer never saw is then sent, last writer wins, as the comment at 3364-3366 already promises for a new mutation. Its costs: the window keeps the structure of what it last sent or applied (the structure-only form `serializeLayout({ terminalSessions: false })` is at hand) and compares it on each `deleted` frame. The existing pin "a peer delete stops the echo save from re-persisting the discarded blob" (`web/packages/workspace-app/src/state/sessionSync.test.ts` 285-300) also needs a new setup: its pending save holds a layout the window never sent (the snapshot is the empty string from `discardWindowSessionLocal`, 3529-3538), which is the same shape as the lost split, so its setup must first send the layout and then leave only a view-state change pending. The alternative alone does not cover the second way, since a routine DELETE after B's PUT still removes the blob. The owner chose the smallest shape for this build; the structural comparison remains a cost.

## Boundaries

The change stays in the page's session save and its handling of `session_changed` frames in `store.svelte.ts`. The server route, its 204 for a missing blob and its `deleted:true` broadcast stay as they are. A deliberate discard stays as it is: `discardWindowSessionLocal` (3529-3538) and its DELETE, the exit DELETE of a window that held a layout and was emptied, and the follower rule (`followerSuppressesSessionDelete`, 3291-3293). The server's DELETE also reaps the window's terminal sessions (`delete_session_response` in `sessions.rs`, 197-244, `forget_window` at 222), so a window that skips its routine first DELETE also skips that reap. Such a window owns no layout of its own; whether today's routine DELETE reaps anything a co-viewer on the same id holds was not read, and this item does not rely on it. Hybrid Nav's stale rule (`paneModeDeferRemoteLayout`, `tabs.svelte.ts` 6753-6765) and its warning are out of scope; they work once the frame arrives. The rarer variant, a frame missed before hydration or subscription, would need a read-back of the session on each socket (re)connect in `onWatchReady`; it is named here and left to its own item.

## Acceptance

Pins in vitest that need no browser, in `web/packages/workspace-app/src/state/sessionSync.test.ts` with its fake timers and `api` spies, plus a test hook for the load flag beside `__testSetBootstrapHydrated` (3540-3542). A window whose load found no blob and that holds one empty pane sends no DELETE at its first save, and none from `flushSessionSaveOnExit`. A window that loaded a blob, or that sent or applied a layout, and is then emptied still sends its DELETE. Under the alternative, a pending save that holds a structural change, followed by a `deleted` frame from a peer, still sends one PUT when the delay ends, while a pending save of view state only sends nothing. The existing pins keep passing: "a deleted frame never refetches or tears down live tabs" (113-123), "an inbound frame racing a pending local save flushes the save and refetches after" (261-283) and "a peer delete never latches: syncs and new local saves continue" (302-326); "a peer delete stops the echo save from re-persisting the discarded blob" (285-300) passes unchanged under the smallest shape and with the new setup under the alternative. The browser proof is smoke check 123 with its barrier before the stale step: B commits one split and A, outside Hybrid Nav, waits until it shows two panes, and the later writes expect three and four panes. With the fix, the check passes five of five runs alone and in the whole suite; without it, the barrier is where the race shows.
