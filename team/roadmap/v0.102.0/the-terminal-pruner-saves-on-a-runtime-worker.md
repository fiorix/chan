# The terminal pruner saves the window registry under the chan home on a runtime worker

Status: accepted by the owner on 2026-09-27 for a later version than v0.101.0, so it is held under v0.102.0; raised during v0.101.0 on 2026-09-27 by the independent review of the Files watch bound ([a-quit-can-hang-on-a-standalone-files-watch](../done/a-quit-can-hang-on-a-standalone-files-watch.md); `dev/v0101-team/reviews/review-Services-10.md` in the development tree, finding 4), which read the code at `24731ad21`; read again in code at `b1ef073ae`, where the path holds. ## Owner ruling

## What was seen

The shared terminal tenant's pruner is a runtime task with a minute tick that reaps exited sessions (`spawn_pruner`, `crates/chan-library/src/terminal_sessions.rs:3318-3336`). Reaping a detached session whose shell exited fires the tenant's window reaper (`reap_exited`, `:3216-3254`, the call at `:3248-3250`), which removes the standalone terminal's row from the window registry (`crates/chan-library/src/host.rs:1711-1729`), and the removal saves the registry inline, an atomic write of the whole store (`remove_terminal`, `crates/chan-library/src/windows.rs:560-579`; `save_best_effort`, `:652-681`). The store is a file under the chan home: `windows.json` beside the devserver's configuration (`crates/chan-server/src/devserver.rs:2112-2119`, under `devserver_state_dir`, `:309-321`), and the same file under the desktop's chan home (the comment at `desktop/src-tauri/src/embedded.rs:101`).

So with the chan home on a mount that stopped answering, a tick can block inside that save on a runtime worker. At a quit, the task owner gives the pruner its five-second grace and then aborts it, but an abort takes effect only at the task's next yield, as the review read tokio, so it cannot interrupt a tick inside that save, and the await after the abort (`crates/chan-library/src/tenant.rs:266-277`) then waits, and with it the terminal tenant's shutdown and the drain, until the mount answers. The owner's contract for the quit is about a mounted root, so this is outside it unless the chan home shares the mount with a workspace. The review did not check whether another write under the chan home on the quit path would block first.

## Desired contract

No wait of the quit drain depends on the chan home's filesystem: a save the drain can meet runs off the runtime worker or within a bound.

## What to do

Move the registry's save off the runtime worker, onto the blocking pool or a writer thread of the registry's own, or bound it, and read the other writes under the chan home that the quit path can meet for the same shape. Pin it with the save held while the host drains. Red first: with the save held, the drain does not return.

## Boundaries

`crates/chan-library/src/terminal_sessions.rs` (the pruner), `crates/chan-library/src/host.rs` (the window reaper), `crates/chan-library/src/windows.rs` (the save), and their tests. The design documents say what the drain waits for if that changes.

## Acceptance

1. With the registry's save held inside the pruner's tick, the host's drain returns within its bound, pinned by state and not by time alone.
2. A reap in a healthy home still saves the registry, and the row is gone from it.

The pruner's part of the contract is built. Each tick, the reap of exited sessions and the prune of idle ones, runs on the blocking pool, and the pruner awaits it beside the tenant's stop signal, so no second tick starts beside one still running (`spawn_pruner`, `crates/chan-library/src/terminal_sessions.rs`). A stop that arrives while a tick is inside the window registry's save closes every live session and ends the pruner. The task owner's shutdown awaits the pruner's own handle and nothing of the tick, so the terminal tenant's shutdown and the host's drain go on, where the await after the abort waited for the mount: the wait is removed and not moved. A held save keeps one blocking thread, and with it the terminal registry and the window registry, until the chan home answers; the tick then finishes that save, finds its other sessions gone and ends. No session is closed twice, since every closer removes a session from the map under one mutex before it closes it, and a dead session the tick had listed and the stop closed first is closed as a shutdown and keeps its window row, as when a stop comes before a tick. The window reaper and the save itself are unchanged, and `crates/chan-library/design.md` says that the pruner awaits its window save beside the stop signal.

Pinned red first (`pruner_shutdown_closes_live_sessions_while_reaper_is_held`): the window reaper's callback, from which the host saves, is held once a dead detached session has entered the first tick, and the task owner's shutdown is asked beside it. Before the fix the shutdown had not returned after seven seconds; with it the shutdown returns while the reaper is still held and with the live session closed, so the pin holds by state and not by time alone. The pin holds the reaper's callback in place of the save and asks the task owner in place of the host: that the tenant's teardown and the host's drain await nothing else of the pruner is read in the code and not run. Acceptance 2 is held by a guard the earlier code passes (`terminal_pruner_persists_a_reaped_window`, `crates/chan-library/src/host.rs`): in a healthy home the pruner's reap empties the registry, and `windows.json`, read back from disk, no longer lists the window. The two writes of the restart manifest that the paragraph above leaves on the way to a devserver's quit hold it for five seconds at most since 2026-10-05, in a range the lead accepted on its report, its status files (both reds at their own labels at their committed shas with a clean tree, four mutations restored by hash, two series of 200 runs of the two stall pins in parallel and on one CPU with no red, the closing gate green over twelve steps at the tip with the symlinked-temp suite and both Windows clippy lines) and an independent review of its whole diff, which found nothing above medium: two mediums, sent to the next range, and eleven lows. The seal at the head of a graceful shutdown stops the kept sessions' readers, takes its snapshot of the kept set and hands the final write to a thread of its own; the shutdown waits at most five seconds for that thread, counted from its start, so the thread's wait for the parker's phase lock is inside them, and then detaches the kept sessions and goes on to its tenants (`seal_flush_detach_bounded`, `SEAL_WRITE_WAIT`, `crates/chan-server/src/devserver/fdstore.rs`). The debounced writer runs each rewrite on a thread of its own and its task only awaits that thread's signal, so the abort at a stop ends the task while a rewrite is still inside the chan home. From the seal's first line a flag refuses every new park, adoption and rewrite, so a park beside a held write returns at once where it waited for the phase lock.

What a write cut off at its bound can and cannot do afterwards, as the review read the code; nothing of it was run. It runs on, inside the filesystem call with the phase lock held or waiting for that lock, and it can land at any time until the process ends, after the shutdown has detached and gone on: what lands is the snapshot taken before the detach, marked sealed, and the mark is true of it, since it was taken after the readers stopped. It cannot tear the manifest: the file is written as a temporary of its own, synced, renamed over the target and its directory synced, so a reader sees the whole earlier file or the whole new one; a write cut inside that sequence can leave its temporary beside the manifest, and nothing was found that sweeps it. It cannot replace a newer manifest of its own process, since every other writer reads the flag first and a rewrite or a park already inside its write publishes before the seal's does. And it cannot land after the process, whose end ends the thread. Nothing waits for it past the five seconds, so whether the next start finds the sealed manifest is a race the shutdown does not control.

What the next start then reads is the sealed manifest, the one written before it, or none. It reads the file once, as its first step and with no bound, so a chan home that still does not answer holds the start where it no longer holds the quit. With the sealed manifest it restores as after any graceful restart. With the earlier one, which is not sealed: a session it names whose descriptor systemd's store kept is restored, whole when it has a ring file and perhaps behind its last output when it has none, with the placement, names and size that write recorded; a session it names with no descriptor, one closed after that write, is skipped, and its standalone terminal window is removed with every session of that window, restored ones too, while workspace windows are kept; and a descriptor it does not name, a park whose commit never landed, is removed from the store, so its shell hangs up. With descriptors inherited and no readable manifest all of them are removed, and every standalone terminal window with them. For a chan home that never answers none of this is worse than before this build: that quit ended at systemd's stop timeout with a kill, and the next start read the same earlier manifest.

The five seconds are ruled to stand, by the lead on 2026-10-05, as this item's contract at its cost: no wait of the quit depends on the chan home's filesystem, and nothing waits for a final write that outlives its bound. So a chan home that answers, at the seal, is one that answers within five seconds of the write thread's start, the wait for the phase lock included, which a park inside its manager barrier can hold for as long. A chan home that answers after six seconds had a clean restart before this build, after a quit six seconds longer; it now restarts from the earlier manifest unless the tenants' shutdown happens to outlast the write.
