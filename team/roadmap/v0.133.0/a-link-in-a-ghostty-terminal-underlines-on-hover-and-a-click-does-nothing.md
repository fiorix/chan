# A link in a ghostty terminal underlines on hover and a click does nothing

Status: accepted for v0.133.0 by the owner on 2026-11-20 ("the ghostty terminal can highlight (underline) URLs when we hover the mouse over them., but there's no click action; i want to treat URLs on the terminal similarly to how we do in the editor: we open a dropdown with the option to 'open in browser'; i also noticed how ghostty highlight *files* the same way, e.g. ./dev/path-to-file-md; in this case i'd like to be able to open in our own editor with `cs open` from the dropdown 'open in editor'"); not started.

Record: the owner's report of 2026-11-20, from his own use of the ghostty backend with Claude Code running in the terminal.

## What is there now

Read at `793d86522`.

- The ghostty widget detects links through two providers registered in `web/packages/ghostty-web-ng/lib/terminal.ts` (lines 473 to 480): OSC 8 hyperlinks first (`lib/providers/osc8-link-provider.ts`), then a URL regex (`lib/providers/url-regex-provider.ts`). Hover underlines a link and sets a pointer cursor (`processMouseMove`, line 1258 on). A click looks the link up again at the click's cell and calls its `activate` (`handleClick`, line 1420 on). Both providers' `activate` act only with Ctrl or Cmd held, through `window.open(uri, '_blank', 'noopener,noreferrer')` (`url-regex-provider.ts:82-85`, `osc8-link-provider.ts:102-105`). A plain click does nothing; the modified click takes the path that, under WKWebView, "either no-ops or opens inside the app shell" by the comment where the xterm.js backend replaces it (`web/packages/workspace-app/src/components/TerminalTab.svelte`, lines 1390 to 1401).
- The OSC 8 provider hands over the target exactly as the program wrote it (`getHyperlinkUri`), with no scheme check. It scans one row: a link the program wrapped onto the next row is two links with the same target.
- chan's app does not touch the widget's links: nothing under `web/packages/workspace-app/src` reads the link detector or registers a provider.
- The URL regex excludes paths by design (its header and pattern: `https?://`, `mailto:`, `ftp://`, `ssh://`, `git://`, `tel:`, `magnet:`, `gemini://`, `gopher://`, `news:`). A path the terminal underlines is therefore an OSC 8 hyperlink the program printed.
- What Claude Code prints for such a path (read from the installed build's bundled JavaScript, `/opt/claude-code/bin/claude`, on 2026-11-20; not captured from a live session): its Markdown renderer prints a link `[text](href)` as `ESC ] 8 ; ; <href> BEL <text> ESC ] 8 ; ; BEL` when it judges the terminal to support hyperlinks. The href goes through a filter that passes a target with a scheme (`/^[a-z][a-z0-9+.-]*:/i`) as written and returns null (no hyperlink) for a `file:` target; a target with no scheme passes as written unless further checks refuse it, which this reading did not resolve. So the owner's `./dev/path-to-file-md` was, by inference, a Markdown link whose target is a path relative to the directory Claude Code runs in, and a `file://` target does not come from Claude Code. Other programs (`ls --hyperlink`, `ripgrep --hyperlink-format`, `gcc`) print `file://<host><absolute path>`.
- Mouse tracking on ghostty: `lib/input-handler.ts` (lines 816 to 900) reports every press, release and tracked motion to the program whenever tracking is on, Shift included (the modifier is encoded into the report). The xterm.js backend forces a native selection on Shift and so does not report it (`terminal/selectionBypass.ts`). On ghostty, a Shift press is reported today.
- The xterm.js backend opens a URL on a plain click with no menu: `WebLinksAddon` routed to `openExternalUrl` (`TerminalTab.svelte:1398`). It installs no `linkHandler`, so an OSC 8 link takes xterm.js's default handler.
- The editor's side: `editor/external_links.ts` (`openExternalUrl`, with the scheme gate `isOpenableExternalUrl` over `http`, `https`, `mailto`, `tel`, the desktop opener and its copy-and-notify fallback), the editor's link picker (`editor/bubbles/wiki.ts`, its OPEN row and copy button) and its context menu's "Open link" and "Copy link" (`FileEditorTab.svelte`, around line 1340). A plain click on a URL in the editor opens nothing; Cmd or Ctrl with a click opens it at once (`team/roadmap/done/a-click-on-a-url-in-the-editor-opens-it-instead-of-editing-the-link.md`).
- `cs open` runs in the shell, so a relative path resolves against the shell's directory. `POST /api/open` (`crates/chan-server/src/routes/open.rs`) resolves a relative target against the workspace root instead (lines 86 to 93), routes a path outside the workspace through `route_open_if_outside_workspace`, and opens an in-workspace path through `control_socket::open_path`, which creates a missing file and opens it. A standalone terminal window mounts no `/api/open`. The app can ask a terminal for its directory: the `cwd` frame (`TerminalTab.svelte`, `requestTerminalCwd`, line 2910) answers the PTY child's directory from procfs (`chan-library/src/terminal_sessions.rs`, `cwd`, line 1955), the shell's and not a program's under it.

## Desired contract

1. A click on a link the ghostty terminal underlines opens a small menu at the pointer, in the app's menu style. A web link offers "Open in browser" and "Copy link"; a file link offers "Open in editor" and "Copy path". A press that ends a drag or a double click is not a link click.
2. "Open in browser" goes through `openExternalUrl` with its scheme gate: a new tab in a browser, the system browser in the desktop app. A target the gate refuses shows the entry disabled.
3. "Open in editor" opens the file where `cs open <path>` typed in that terminal's shell would put it: a relative target resolves against the shell's current directory at the click (the server's `cwd` frame), an absolute one and a `file://` one with an empty, `localhost` or the server's host name are taken as they are. A `file:` target naming another host, a missing file, or a target the open path refuses shows the entry disabled with the reason ("not found" for a missing file), and is never opened somewhere else or created. The open path gains a must-exist mode for this; `cs open` and the launcher's Open keep creating a missing file.
4. The menu shows the link's real target, not only the text on screen: OSC 8 text can name one place and point at another, and terminal output is not trusted.
5. A program that asked for mouse reporting keeps its clicks: under mouse tracking a plain click goes to the program and opens no menu. On both backends Shift bypasses mouse reporting: no Shift press, release or drag is reported to the program, Shift with a click on a link opens the menu and Shift with a drag selects. On ghostty this is new (it reports Shift today); on xterm.js it is what `terminal/selectionBypass.ts` already does.
6. Ctrl or Cmd with a click opens the link directly, by the same two paths, with no menu.
7. The menu is a keyboard owner like the app's other menus: Escape closes it and the keyboard returns to the terminal; it closes when the terminal's content under it changes or scrolls away; it adds no hole under the screen lock or a cover (`state/keyboardOwner.svelte.ts`).
8. The xterm.js backend shows the same menu for the links it detects: a plain click no longer opens a URL at once. If its existing hooks (`WebLinksAddon`'s handler, the `linkHandler` option for OSC 8) cannot carry it, that is this row's second stage, put to the owner.

The owner's rulings on 2026-11-20, asked in four questions with a recommendation each, all taken: a relative target resolves against the terminal's directory ("Terminal's directory"); a missing file is refused, not created ("Refuse"); Shift bypasses all mouse reporting on ghostty ("Shift bypasses all"); xterm.js gets the same menu ("Same menu").

## Boundaries

- The widget gets one public hook for link activation (the link's target, its kind, its cell range and the pointer event), and its providers stop calling `window.open`. The menu, the two actions and every rule above live in chan's app, which reads no private field of the widget for it. That is the direction of the widget's fork row (`chan-drives-ghostty-web-from-outside-through-its-private-internals.md`, part 4), parked with an unmerged branch stack that rewrites the widget's pointer handling (`v0132/ghosttyng-p4t2` and three more). The widget's diff stays small, and the closing section names what that stack must carry when it is rebased.
- The server change is the open path's must-exist mode alone (`crates/chan-server/src/routes/open.rs` and what it calls), classified in `route_authority.rs` if a route is added; nothing else under `crates/`.
- The widget's Shift rule lives in `lib/input-handler.ts`, beside the reports it withholds.
- Detection is not widened: what the terminal underlines today gets the menu. A detector for bare paths no program marked is a separate question for the owner.

## What the parked widget stack carries when it is rebased

The parked stack (`v0132/ghosttyng-p4t2`, `-p4t2b`, `-p4t3`, `-p4t4`) moves the widget's pointer handling to pointer events (`handlePointerDown`, `pointerup`, pointer capture on the scrollbar thumb and in the selection manager). Rebased onto this row, it keeps three things, each pinned by a test it must keep green:

- The hook. `Terminal.onLinkActivate` fires `TerminalLinkActivation` (`target`, `kind`, `range`, `event`; `lib/interfaces.ts`, exported from `lib/index.ts`) from `handleClick`. The providers describe a link with `target` and `kind` in place of an `activate` callback (`ILink` in `lib/types.ts`), and nothing in the widget calls `window.open`. Pinned by `lib/terminal.links.test.ts` and the link cases of the app's `terminal/ghosttyWidget.keptContracts.test.ts`.
- The click rule. The press a click ends is noted by a capture listener of its own on the terminal's element (`handleLinkPress`, on `mousedown` here), not by the scrollbar's listener, which the app replaces (`gateGhosttyScrollbarClicks`). Under pointer events it listens to `pointerdown`. `handleClick` reports nothing for a button other than the primary, a click whose `detail` is above 1, a click with no noted press, a press that was reported to a program tracking the mouse (no Shift held while tracking), or a press that moved at least the selection manager's drag threshold, half a cell width; the two thresholds stay equal. The test drives the listeners by name, so a renamed listener renames there, and the kept contracts dispatch the press and then the click as a pointer makes them.
- The Shift rule, in `lib/input-handler.ts` beside the reports it withholds: while a program tracks the mouse, a press with Shift marks its button bypassed (`mouseButtonsBypassed`) and is not reported, nor is that button's release, motion with Shift or during a bypassed press, or a wheel with Shift; a release whose press was reported is reported. If the stack moves the input handler's reports to pointer events, the rule moves with them. Pinned by the `Shift keeps a gesture from the program while it tracks the mouse` case in `lib/input-handler.test.ts`.

## xterm.js limits

Two things the xterm.js backend does not carry, both from xterm.js itself, with no public seam to change them:

- It underlines no OSC 8 target that does not parse as an absolute URL: its OSC 8 provider drops it (`OscLinkProvider.provideLinks`, the `new URL(text)` check, in `@xterm/xterm` 6.0.0). Claude Code's `./dev/foo.md` and a `~/` target get the menu on ghostty only. The owner kept `allowNonHttpProtocols` on (2026-11-20), so `file:` targets get it on both.
- It reads a row's links anew only when the pointer enters that row (`Linkifier._handleHover`: a fresh `_askForLink` only when `_activeLine !== position.y`, else the row's cached replies; the re-read after a render is registered only while a link is under the pointer, in `_handleNewLink`). A link printed into the row under a pointer resting there is neither underlined nor clickable until the pointer leaves the row and comes back. Clearing that cache from outside takes xterm.js's private Linkifier; ghostty looks the link up at the click.
