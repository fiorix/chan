## What is there now

Read at `342dbe791`, and the same at v0.128.0 (`8ded1bda9`); not run.

- **Server.** A session pushes each PTY read into its replay ring and broadcasts it as one `SessionEvent::Output` on a tokio broadcast channel of 1,024 events (`BROADCAST_CAP`, `record_output`, `crates/chan-library/src/terminal_sessions.rs`); the event carries the bytes and no position. Each terminal socket forwards events one WebSocket message at a time, awaiting each send (the `session.rx.recv()` arm of the socket loop, `crates/chan-server/src/routes/terminal.rs`). Nothing slows the PTY for a socket. A socket more than 1,024 events behind loses the oldest: its next receive is `RecvError::Lagged`, and the loop sends an `error` frame, "terminal output lagged; reconnect to replay retained scrollback", and goes on from the oldest event still held. The skipped events never reach that socket, output or otherwise.
- **The ring.** A bounded buffer of numbered chunks, 2 MiB by default (`ring_bytes`, `default_terminal_ring_bytes` in `crates/chan-library/src/config.rs`). An attach subscribes and snapshots it under one lock and resumes from the client's cursor, with a missed count when the cursor is older than the ring (`attach_resuming`; `crates/chan-library/design.md`). A lag re-reads nothing from it. Under a writer running flat out a Linux PTY read is about 4 KiB (the `PTY_READ_BYTES` comment), so 1,024 events are about 4 MiB, twice the default ring: when a socket lags, the bytes it skipped are mostly gone from the ring too. Read sizes on macOS were not read.
- **Client.** The workspace app writes the frame into the terminal as `terminal error: ...` and does not redial (`ws.onmessage`, `web/packages/workspace-app/src/components/TerminalTab.svelte`). Its cursor `receivedSeq` adds the length of each live binary frame, so after a lag it is short by the skipped bytes, by reading: a later redial resumes from it, and an xterm.js snapshot captured after the lag records it, so the replay shows that many bytes a second time while the skipped ones stay missing.
- The owner's run was on the ghostty backend, whose writes parse synchronously inside `ws.onmessage` (through the viewport controller); xterm.js queues writes in its own buffer. Whether the xterm.js backend lags as readily is not established by reading.

## Desired contract

1. A view that falls behind a fast stream loses none of it: when the stream ends the view holds every byte the program wrote, once and in order, and the terminal prints no lag line. The R9 commands above are the reference load.
2. A view that stops reading (a hung page, a socket nobody drains) holds neither the program nor the other views beyond a bound, and the server's memory per session stays bounded. When it reads again it resumes as a reattach does: from the ring, with the count of what it missed.
3. Wherever bytes are lost the terminal says how many, as a replay that missed bytes does, and the client's cursor stays equal to the server's, so a redial or a snapshot resume neither repeats bytes nor skips more.

## Boundaries

- The session's output fan-out and the terminal socket's loop (`terminal_sessions.rs`, `routes/terminal.rs`), and the client's cursor and error handling (`TerminalTab.svelte`). How the server keeps a slow view whole was put to the owner as two shapes: pacing the PTY read by the views that read, which is what a full PTY buffer does to a writer under a native terminal, or a window of bytes the client acknowledges (the watermark scheme of xterm.js's flow-control guide). He took the integrator's recommendation ("i will take your recommendation here"), the first: the PTY read waits for the views still reading, the socket's own send backpressure telling the server how far a view is, with no new client protocol; a view that stays behind past the bound of contract 2 stops holding the program and resumes from the ring with the count it missed. The measurement of acceptance 1 still comes first, and if it shows the first shape cannot meet the contract, the choice goes back to him. Re-reading the ring at a lag cannot meet contract 1 under the reference load alone, by the sizes above.
- Not here: the ring's size and the scrollback setting; the `/ws` watcher socket's lag handling; program status and title frames, which already read their latest value independently of output lag (`crates/chan-server/design.md`).

## Acceptance

1. A measurement in a guest before the design is chosen: the reference load on the ghostty backend in a browser against the guest's devserver, recording read sizes, the point where the socket lags, and how far behind it is then.
2. Server tests: a socket that reads slower than the PTY writes, past what the broadcast holds, receives every byte once and in order and no `error` frame; a socket that stops reading holds the session no longer than the bound and does not slow another socket; each red on today's code where it applies.
3. A workspace app test: after a loss the server reports, the cursor equals the server's and a redial replays no byte twice; red on today's code.
4. In the guest, on both backends: `seq 1 400000` read back from the terminal's buffer is the whole sequence, and no lag line is printed. On the owner's Mac, on chan-desktop: the R9 commands print no lag line, and `seq 1 400000` scrolled back at a few points shows consecutive numbers.

## Rulings for v0.131.0, 2026-11-14

The owner answered the decisions document for v0.131.0 (`dev/v0131/decisions.md`, point 5) on 2026-11-14: "taking your recommendation; i want to make sure this won't introduce new unexpected side effects and am willing to even defer the landing if we are not 100% sure this is working well".

- The bound: a view stops holding the program after 5 s without progress, where progress is its sent position advancing. The reader starts waiting when the slowest holding view is half the ring behind, or 512 events behind, whichever comes first.
- On resume the terminal shows nothing when the ring still holds the view's position, and the existing "terminal replay missed N bytes" line when it does not; the lag error line goes.
- The measurement comes first, at the base in a rig guest with a release devserver and a measurement-only patch that is never merged: the R9 loads and `seq 1 400000`; the same under a CPU throttle of 4x and 20x; the page's main thread paused 30 s under an unbounded `yes`; two views of one session, one throttled; a 200 MB stream on xterm.js against its discard watermark; Ctrl+C to prompt under the flood. Five runs an arm on ghostty and xterm.js in headless Chrome, the paused-page arm also on WebKitGTK in the desktop guest. What each outcome means is point 5's table: a WebKit engine whose sends never block while its page is stalled goes back to the owner with the numbers; xterm.js alone losing bytes past its buffer is accepted on that backend and documented.
- Folded in from v0.130.0's follow-ups: a lagging socket also skips `Resize`, `Activity`, `QueueDepth` and `PromptDelivered`, and a lost `PromptDelivered` leaves a Rich Prompt untraced. A paced view does not lag, and a view cut loose and re-attached gets the size, the queue depth and the queued prompt ids again through the prelude.
- The build must keep: the pacing wait wakes on a stop request and on exit, the exit drain runs unpaced, and input frames from a paced socket are still read.
- Landing: it merges only when both reviewers accept, the terminal regression suite is green on both backends, and a reading in a guest shows an interactive shell and a second view of the same session unaffected while one view is held back. On any doubt that remains, the landing moves to the next release, with the evidence, as the owner allowed.

## Ruling on tmux panes, 2026-11-14

Found while preparing the build: output of a terminal pane backed by tmux reaches the server through tmux's control connection (`crates/chan-library/src/terminal_sessions/tmux_connection.rs`, which calls `record_output` from the connection's processing path) and never runs that pane's PTY reader, so pacing the PTY reader does not pace tmux panes, and blocking `record_output` there would stall the connection. The owner, asked by survey on 2026-11-14 whether tmux panes get counted loss now and lossless pacing in v0.132.0, or pacing in this row: "Pace tmux panes in this row too (a separate design; streamlag lands later)". So the contract stays terminal-wide: tmux panes are paced in this row by a mechanism of their own (tmux's control-mode flow control is the candidate), with their own tests in a guest, and the row lands when both mechanisms meet the landing condition.

## Second ruling on tmux panes, 2026-11-14

The build then read tmux's source (3.2 and 3.6, the version in the guests): control mode's flow control (`pause-after`) discards a paused pane's buffered output and continues from current output (`control.c`, `control_pause_pane` and `control_continue_pane`; tmux's control-mode guide tells clients to redraw the pane after it), and tmux keeps producing whenever any ordinary client is attached to the session (`server-client.c`). So stock tmux offers no lossless stop of a pane's producer that chan can drive. Asked again by survey with that evidence, the owner chose: "tmux panes: bounded with a missed-bytes count now; lossless only for chan PTYs (recommended)". Contract 1 holds for chan's own PTY sessions; for a tmux pane, contracts 2 and 3 hold (a stalled view is bounded, resumes and says how many bytes it missed, and the cursor stays equal). A note for tmux upstream (a producer-credit or retention mechanism) is a candidate for the owner.
