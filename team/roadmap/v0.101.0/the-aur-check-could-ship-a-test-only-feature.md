# Nothing pins the one packaging recipe whose shape could ship a test-only feature

Status: landed again on 2026-09-28, with the fix the owner accepted and a package built by the recipe to prove it ("Opened again", below); opened again on 2026-09-27, when its contract was found broken on the integration branch (below), and accepted as build work again the same day; landed on 2026-09-26 in one lane with [a-service-spawned-extension-gets-a-bare-path](a-service-spawned-extension-gets-a-bare-path.md), whose second round answered an independent review of its first and was checked by the lead; accepted for v0.101.0 by the owner on 2026-09-25; raised for v0.101.0 from the v0.99.0 fix loop's follow-ups, where gating a startup hook behind a test-only feature surfaced the question and it was parked. A source reading of the recipes and the manifests against `main` at `d3de0180b`; no package was built until the landing of 2026-09-28.

## Owner ruling

On 2026-09-27, with the item open again, the lead ruled the fix from a code map of what each shipping recipe builds and installs (`dev/v0101-team/int28-docs/codemaps/test-hooks-in-a-shipped-binary.md` in the development tree), and the owner accepted that ruling as the lead recommended the same day, answering it by its number. The fix is in the recipe: in both AUR recipes `build()` sets its binary aside and `package()` installs that copy, and the pin asserts that the installed file is written by `build()` and by nothing after it. It holds whatever a test build resolves, so the tests keep their seam. Nothing of the fix is at `37e9d23dd`.

## What was seen

chan-workspace has a `test-hooks` feature and chan-library a `test-util` feature. `test-util` is enabled only from chan-server's dev-dependencies (`crates/chan-server/Cargo.toml:100`). `test-hooks` is enabled from chan-server's (`:91`) and, since 2026-09-26, from the dev-dependencies of `chan` and of `chan-desktop` too (`crates/chan/Cargo.toml:93-95`, `desktop/src-tauri/Cargo.toml:130-133`), so a build of either shipped package with dev units has it, and one shipping recipe installs a binary such a build wrote ("Opened again", below). This paragraph was corrected on 2026-09-27: it said that both features were enabled only from chan-server's dev-dependencies and so reached a build only when an invocation selected chan-server with dev units, which no shipping recipe did.

One recipe is close to the line. `packaging/distros/arch/aur/chan/PKGBUILD.in` runs `cargo test --frozen --release -p chan` in `check()`, between `build()` and the install of `target/release/chan`, and that test run relinks the binary the package then installs. It stayed clean only while no dev-dependency of `chan` enabled a test-only feature, which has not held since 2026-09-26; this sentence was corrected on 2026-09-27, as it said that `-p chan` not selecting chan-server was enough. Nothing in the tree pins that selection: a later widening of `check()` to the workspace would enable both features in a shipped binary silently, and a stripped release binary makes it undetectable afterwards. The desktop recipe beside it has the same shape to keep honest.

## Desired contract

A shipped binary cannot carry a test-only feature, and the packaging recipes' package selection is pinned by a check that fails when it widens, rather than by the memory of why it is narrow.

## What shipped

- **The check.** `check_aur_check_selection_contract` in `scripts/check-build-matrix.py` reads both recipes (`AUR_RECIPES`); for each, `check_aur_recipe` takes the package from `pkgname=`, requires `package()` to install `target/release/<pkgname>`, and reads `check()` command by command. Every building cargo call must select that package alone with `-p`, where `$pkgname` and `${pkgname}` resolve to it. Words after `--` belong to the test binaries and are not read, and a subcommand that builds nothing (`fetch`, `metadata`, `tree` and the like) is skipped.
- **The refusals.** A building cargo call is refused for `--workspace` or `--all`, `--manifest-path`, no `-p`, a package other than the recipe's (as `-p X`, `-pX`, `--package X`, `--package=X` or a `p` in a short-flag cluster), any feature flag (`--features`, `-F`, `--all-features`), or a shell expansion before `--` other than `$pkgname`. Any other command is refused when its program is a variable or one of `bash`, `eval`, `gmake`, `just`, `make`, `sh` and `xargs`, or when it names cargo anywhere but as its program (behind `timeout`, `env` or `sudo`, in a brace group, an `if` or a `for`, or in a command substitution). A `check()` with no building cargo call left is refused too, so the contract cannot outlive the shape it pins. A refused command is named with its line in the recipe.
- **Where it runs.** `scripts/test-check-build-matrix.py` writes a throwaway recipe per shape, 49 of them, runs each through the checker's `aur-recipe` entry point and requires it to pass or be refused as the contract says, a refusal naming the line its shape starts on (except a `check()` with no cargo call, which is refused by file), then runs the real recipes. `make build-matrix-check` runs the checker and then that self-test, and `check_make_contract` pins the self-test's line in the target. `pre-push` runs `build-matrix-check`, and so does CI: `make ci-linux` through `pre-push`, and `make ci-macos` and `make ci-windows` directly.
- **The recorded reading.** The contract's docstring carries the command, `cargo tree --locked -p <package> --target x86_64-unknown-linux-gnu -e normal,build,dev --prefix none --format '{p} [{f}]'`, and its result: `-e dev` resolves features with dev units the way `cargo test` does, and neither the `chan` nor the `chan-desktop` tree enables `test-hooks` or `test-util`, while `chan-server`, the control, enables both, as do the widened selections the contract refuses. The lane's run for x86_64 and aarch64 is `dev/v0101-tasks/evidence/extp/aurc-3-feature-reading.log`. That result held at the lane's sha and is false at `37e9d23dd`: both trees enable `test-hooks` with dev units ("Opened again", below), and the docstring still gives the old result (`scripts/check-build-matrix.py:1274-1279`). This sentence was added on 2026-09-27 to correct the one before it.
- The item's premise holds for `chan`, whose integration tests make `check()` relink the binary `package()` installs. `chan-desktop` has no integration test today, so its `check()` leaves the `build()` binary in place; its recipe is pinned all the same. `.agents/skills/gate/SKILL.md` lists the contract under `build-matrix-check`.

One gap stays open: this contract reads the recipes and not the manifests, so it would not catch a dev-dependency in `crates/chan/Cargo.toml` that enabled a test-only feature under `-p chan`.

### Landed again

Landed on 2026-09-28, the owner's ruling as built, in six commits; lines at `7957bccef`. The builder's report is `dev/v0101-team/reports/report-Services-28.md` in the development tree, to the lead's rulings in `dev/v0101-team/followups/followup-Lead-Services-19.md`, `-20.md` and `-21.md`; the lead read the production diff whole and verified it at the blob, with no independent review (`dev/v0101-team/journals/journal-Lead.md`, the entries of 2026-09-28 07:33Z and 08:28Z).

- **The recipes.** In both AUR recipes `build()` ends by copying its release binary out of cargo's target directory, `install -Dm755 target/release/<pkgname> package-bin/<pkgname>`, after its one cargo build, with a comment that says why (`packaging/distros/arch/aur/chan/PKGBUILD.in:37-47`, the copy at `:46`; `packaging/distros/arch/aur/chan-desktop/PKGBUILD.in:49-59`, the copy at `:58`). `check()` runs the same tests in the same target directory as before (`chan/PKGBUILD.in:49-55`; `chan-desktop/PKGBUILD.in:61-68`), and `package()` installs the saved copy (`chan/PKGBUILD.in:59`; `chan-desktop/PKGBUILD.in:72`). The tests keep their seam, and the recipes keep makepkg's own processing of what they install, strip and debug included, as the lead ruled (`options=(!lto)`, `chan/PKGBUILD.in:23`; `followup-Lead-Services-20.md`, ruling 1).
- **What the checker pins.** `check_aur_artifact`, which `check_aur_recipe` runs for each recipe (`scripts/check-build-matrix.py:1359`, `:1362-1470`), requires the literal copy from `target/release/<pkgname>` to `package-bin/<pkgname>` once, after the last cargo build of `build()` (`:1370-1371`, `:1404-1413`, `:1464-1468`), and the install of the saved copy in `package()` (`:1372`, `:1432-1438`, `:1469-1470`). It reads the three functions in a small grammar and refuses any command it cannot show leaves the saved binary alone: a writer it cannot read, a redirect, a path it cannot expand, a metadata install outside `$pkgdir/usr/share` or `$pkgdir/usr/lib`, or a link that is not one of the other entry points (`:1394-1463`). Its docstring says what it does not prove: it trusts cargo, make and the tests, reads no manifest and runs no resolver, so a package build must prove the installed file's contents (`:1252-1277`, `:1363-1369`). By the report, its self-test runs 76 cases, with 36 mutations of the checker each shown to fail its case.
- **The proof, as it was run.** One package build of both recipes at the range's tip, in the Arch wrapper's container, with its compilers bound to three CPUs, which changes no input of the binary (`report-Services-28.md`, "Package run and four hashes"). Four SHA-256 hashes for each package: (a) the file `build()` set aside, (b) `target/release/<pkgname>` after `check()`, (c) the file as `package()` installed it, before makepkg's own processing, and (d) the installed file, beside the same stock processing applied to a copy of (a). For `chan`: (a) and (c) are equal (`725c585e`), (b) differs (`12947d8c`), and (d) equals the processing of (a) (`f42e39a1`): the first proof by a run that the test build writes the file, and that the package installs the file `build()` made. For `chan-desktop`: (a), (b) and (c) are equal (`390a6f70`), and (d) equals the processing of (a) (`a14e3b8a`): the desktop package's test build did not write its binary in this run, as its manifest has one binary and no integration test leads one to expect (`desktop/src-tauri/Cargo.toml:15-17`, and no `desktop/src-tauri/tests` directory); its recipe saves the binary all the same, against an integration test added later. The report gives the whole hashes; the test groups passed, 337 with one ignored for `chan` and 431 for `chan-desktop`.
- **The wrapper's fault.** The Arch wrapper handed its container a source snapshot whose root only the invoking user can enter, while the container's build runs as another user, so the unchanged wrapper failed before cargo with "Permission denied" (`report-Services-28.md`). It is fixed in the wrapper alone, which makes the snapshot's root traversable and says why (`packaging/distros/arch/build-with-sdme.sh:68-70`), and the one package build above ran through the committed wrapper with nothing changed by hand.
- **The words.** The test-only feature's comment now says that a packaged binary must come from a build without dev units, since cargo test can turn the feature on while it relinks an executable (`crates/chan-workspace/Cargo.toml:175-181`), where it said that production builds compile none of its seams (the first bullet above); both packaging guides describe the saved copy (`packaging/distros/README.md:23`; `packaging/distros/arch/README.md:73`), and the changelog records the fix (`CHANGELOG.md:21`).

**Not shown, and written as such:** whether CI's Docker path meets the wrapper's fault. By the report's reading it cannot: `build-in-ci.sh` binds the checkout itself into the container and makes no such snapshot (`packaging/distros/arch/build-in-ci.sh:55-62`, the bind at `:60`). No CI run of this recipe exists before the landing.

Acceptance 3 is met by the checker and acceptance 4 by the run. The gap named above is closed in effect: an edge in a manifest can still turn a test-only feature on in `check()`'s test build, but the file a recipe installs is the one `build()` made. At `7957bccef` the checker's docstring records no reading of cargo's resolver; the bullet on the recorded reading above holds for the shas it names. This paragraph was added on 2026-09-28.

## Boundaries

## Acceptance

1. A check reads both recipes and fails when `check()` selects anything beyond the package the recipe installs; it is red against a copy widened to the workspace and green against the recipes as they stand.
2. The check runs in the pre-push gate and in CI, so a recipe edit cannot land without it.
3. The file a recipe installs as its binary is the one its `build()` set aside: a check reads both AUR recipes and fails when `package()` installs from the target directory, when the copy is set aside before the build's last cargo call, or when `check()` or `package()` writes the copy. This point was replaced on 2026-09-27 under the owner's ruling: it asked for a dependency-tree reading of the shipped packages that shows neither test-only feature, which a test dependency of a shipped package breaks and which the ruled fix does not need, since the tests keep their seam.
4. A package built with the `chan` recipe shows it by a run: the file the package installs is the file `build()` set aside, as the packager's own processing after `package()` leaves it, and the target directory's file after `check()` is another.
