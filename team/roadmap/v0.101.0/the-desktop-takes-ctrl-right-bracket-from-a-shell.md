# The desktop takes Ctrl+] from a focused shell

Status: accepted for v0.101.0 by the owner on 2026-09-27; raised during v0.101.0 on 2026-09-27 by the owner, who pressed Ctrl+] three times in a chan terminal on the macOS desktop to leave a container session (`Connected to machine ... Press ^] three times within 1s to exit session`) and saw nothing happen. The mechanism is read in code at `7504a5f9c` and not reproduced: the box the code was read on has no display.

## Owner ruling

Accepted on 2026-09-27 with the contract in the owner's words, a terminal's behaviour as iTerm2 has it: Ctrl+] sends the Group Separator, 0x1D, and three presses that leave a container session are the test. Ctrl+] and Ctrl+/ are released to a focused terminal on every desktop, and Command+] and Command+/ keep their claims on macOS. Off macOS the workspace app's own shortcut rule also takes Ctrl+[, Ctrl+] and Ctrl+/ from a focused terminal, which the clients lane found first for Ctrl+[; the three stay with the terminal there too. The terminal library has no encoding for Ctrl+/, so the owner accepted the same day, as the lead recommended, that the terminal sends 0x1F for it on every client, the browser included. Off macOS this takes the native chords of Next Pane and Split Right from a focused terminal, as the owner was told; with focus anywhere else they keep them. The wider rule, the bridge claiming only the Command forms on macOS, is decided with the platform-modifier pattern of the frontend review's remainder. The clients lane's.

Ctrl+Q joined the item on 2026-09-27, when the owner, asked about that wider rule, answered "free up ctrl+q as well". The lead reads it, for the owner to correct, as: on macOS the desktop's key bridge no longer claims Ctrl+Q, whatever has focus, so a focused terminal and the page receive it, and Command+Q stays Quit; off macOS Ctrl+Q stays Quit, as the bridge claims it on purpose there. The wider rule itself, whether on macOS the bridge claims only the Command form of every chord, the tab digits and zoom among them, is not decided by that answer and stays open. The clients lane's, with the rest of this item.

## What was seen

Two things take the key from the shell: the desktop's key bridge on every desktop, and the workspace app's own shortcut rule off macOS.

The desktop's key bridge admits a key event when either the Command key or the Control key is down (`const meta = e.metaKey || e.ctrlKey`, `desktop/src-tauri/src/key_bridge.js:103-104`), and a chord it claims is stopped before the page sees it (`fire`, `:3-5`: `preventDefault` and `stopImmediatePropagation`). In its unshifted branch the right bracket is claimed with no condition: `case 'BracketRight': fire(e, 'app.pane.next'); return;` (`:233`). So Ctrl+] typed into a focused terminal becomes Next Pane, which does nothing visible in a window with one pane, and the byte the shell reads for it, 0x1D, is never sent.

The case above it is the same chord's pair and has the release this one lacks: `BracketLeft` returns without claiming when the Command key is up and a terminal has focus (`:229-232`, with `terminalHasFocus` at `:42-47`), with the comment "Ctrl+[ is ESC to a focused shell, so the Ctrl form is released there" (`:227-228`). That release, and those of Find and Find Next, came with [terminal-chords-run-twice-or-not-at-all](../done/terminal-chords-run-twice-or-not-at-all.md) in v0.100.0, on the owner's ruling of 2026-09-20 that the shell keeps its Ctrl keys. Its acceptance names Ctrl+F, Ctrl+G and Ctrl+[ and no other key, and the finding it answered did not name Ctrl+] either. A Rust test reads the bridge's script as text and pins the release set at those three chords, counting the uses of `terminalHasFocus()` (`key_bridge_releases_a_focused_terminals_chords`, `desktop/src-tauri/src/serve.rs:2486-2560`, the count at `:2551-2559`).

Read in the same handler, and claimed under Control alone with a terminal focused in the same way:

- Ctrl+/ splits the pane right (`:240`). Terminals send 0x1F for it, which readline binds to undo. The terminal library chan ships does not: the installed `@xterm/xterm` 6.0.0 maps Control with the two brackets to ESC and the Group Separator and has no arm for the slash (`src/common/input/Keyboard.ts:308-323` of that package), so a released Ctrl+/ is handed to the terminal and nothing is sent. The frontend review's finding that the fix answered named this chord; the fix did not release it.
- Ctrl+1 to Ctrl+9 jump to a tab (`:242-246`).
- Ctrl+=, Ctrl+- and Ctrl+0 zoom (`:139-152`).

Ctrl+Q is claimed as Quit on macOS as well as off it (read again at `f55f7f509`, where the bridge is unchanged since `7504a5f9c`). The arm is `case 'KeyQ': if (!e.metaKey) invokeIpc(e, 'request_app_quit'); return;` (`:163`), which tests only that the Command key is up and not which platform it runs on. So a Control+Q keydown, which the handler admits because Control is down (`:103-104`), is stopped before the page sees it whenever the desktop's IPC is present (`invokeIpc`, `:19-29`) and starts the desktop's quit, which asks first while any of the workspace app's windows is open (`request_app_quit` and `request_quit`, `desktop/src-tauri/src/main.rs:4146-4149`, `:6776-6800`), whatever has focus, a terminal included. The comments give the claim as the Quit of the Linux and Windows windows, which have no menu bar, and say that it costs a focused terminal its XON chord (`:94-97`, `:155-162`). On macOS Command+Q is the app menu's Quit Chan item (`CmdOrCtrl+Q` in the macOS menu, `main.rs:5725-5726`, `:5859-5862`), which the arm leaves alone. A Rust test pins the arm's text (`key_bridge_serves_the_retired_menu_chords_off_mac`, `desktop/src-tauri/src/serve.rs:2385-2408`, the arm at `:2395-2397`). The bridge already knows its platform from the user agent (`MAC`, `:64`) and uses it today only to leave an AltGraph keydown alone off macOS (`:72`). The workspace app's shortcut registry has no chord on Q (`web/packages/workspace-app/src/state/shortcuts.ts`).

Off macOS the workspace app takes the three chords as well. The shortcut registry gives Previous Pane, Next Pane and Split Right the native chords `Mod+[`, `Mod+]` and `Mod+/` with `escapeTerminal: true` (`web/packages/workspace-app/src/state/shortcuts.ts:199-228`). Off macOS an event's Control is read as `Mod` (`eventCandidates`, `:702-706`; `canonicalChordTokens`, `:856-859`), so `shouldEscapeTerminal` answers true for Ctrl+[, Ctrl+] and Ctrl+/ (`:783-788`, through `registryCommandId`, `:809-832`), and the terminal's key handler then returns `false` (`handleTerminalKeyEvent`, `web/packages/workspace-app/src/components/TerminalTab.svelte:2465`), which lets the key out of xterm for the app's own keymap (the flag's comment, `shortcuts.ts:73-80`). So on the Linux and Windows desktop a release in the bridge alone leaves the shell without these keys: Ctrl+[, which the bridge already releases, does not reach it there either. On macOS an event's `Mod` is Command and its Control is read as `Ctrl`, so this rule does not take the Control forms there.

In a browser no bridge is injected, and the three commands have other chords (`Alt+[`, `Alt+]`, `Ctrl+Alt+/`, `shortcuts.ts:202`, `:210`, `:224`), so the rule does not take Ctrl+] there; what the browser itself does with the key was not read.

## Desired contract

Ctrl+[, Ctrl+] and Ctrl+/ typed into a focused terminal reach the shell as 0x1B, 0x1D and 0x1F on every desktop platform, and Ctrl+/ sends its byte in a browser as well, where the key reaches the terminal today and nothing is sent. Command+] and Command+/ stay Next Pane and Split Right on macOS, and every form keeps its command with focus anywhere else.

On macOS the desktop's key bridge does not claim Ctrl+Q, whatever has focus, so the key reaches the page and a focused terminal, and Command+Q stays Quit. Off macOS Ctrl+Q stays Quit.

## What to do

Give `BracketRight` the release `BracketLeft` has. Give `Slash` the same together with an encoding in the terminal tab, which sends the one byte 0x1F when it is handed Control with the slash and no other modifier, behind the override and registry checks: without the encoding the release would turn a chord that splits the pane into a key that does nothing. Move the Rust pin of the release set to five chords. Off macOS, keep the three chords with a focused terminal in the workspace app's shortcut rule, said in one place: the registry's entries, `registryCommandId` or `shouldEscapeTerminal`. Pin the bridge in the test that runs its script (`web/packages/workspace-app/src/state/desktopBridgeLayout.test.ts`): with a terminal focused the Control form is not claimed and the Command form is; with focus elsewhere both are. Pin the rule with mounted terminal tests on native macOS, Linux and Windows clients. Correct the comment above the bridge's handler, which lists the chords released (`key_bridge.js:98-101`).

For Ctrl+Q, gate the Quit arm on the platform as well as on the Command key, so that on macOS it claims nothing; the bridge's `MAC` (`key_bridge.js:64`) already says which platform it runs on. Move the Rust pin of the arm's text (`serve.rs:2395-2397`) to the new arm, pin the arm under a macOS and a Linux user agent in the test that runs the bridge's script, which can already run it under either (`desktopBridgeLayout.test.ts:25`, `:68`), and keep the comments above the handler and the arm (`key_bridge.js:94-97`, `:155-162`) true of the new gate.

Ctrl+Q is decided on its own. Whether the bridge should claim only the Command forms on macOS, so that every Control chord reaches the focused surface there, is a wider ruling: it also frees the digits and the zoom chords, and it changes pane navigation for a user who presses Ctrl+] in an editor on macOS. The frontend review's remainder carries that pattern (the platform modifier re-derived by hand in three places) and it is decided there.

## Boundaries

`desktop/src-tauri/src/key_bridge.js` and the Rust tests that read it in `desktop/src-tauri/src/serve.rs`; the workspace app's shortcut rule (`web/packages/workspace-app/src/state/shortcuts.ts`) and the terminal's key handling in `TerminalTab.svelte`; and the tests that run them. In a browser the three commands keep their own chords, and a chord the user assigned still leaves the terminal (`shouldEscapeTerminal`'s override arm, `shortcuts.ts:786`).

## Acceptance

1. With a terminal focused, the bridge claims neither Ctrl+] nor Ctrl+/, on macOS and off it, pinned by a test that runs the bridge's script.
2. On the native macOS, Linux and Windows clients, a Ctrl+[, Ctrl+] or Ctrl+/ keydown on a focused terminal stays with the terminal, pinned by mounted tests.
3. A Control and slash keydown on a focused terminal sends exactly one 0x1F to the session's input and is not also encoded by xterm, on the native clients and in a browser, pinned by mounted tests.
4. Command+] and Command+/ keep their claims on macOS with a terminal focused, every form keeps its command with focus anywhere else, and the browser's chords and a chord the user assigned still leave the terminal; each is pinned.
5. On macOS the bridge claims no Control+Q keydown, with a terminal focused or not, and leaves Command+Q to the app menu's Quit; off macOS it still claims Control+Q as Quit. Pinned by the test that runs the bridge's script under each platform's user agent, and by the Rust test that reads the arm's text.
6. On the macOS desktop, Ctrl+] pressed three times leaves a container session. This is a reading on a display host.

## What shipped

Landed on 2026-09-27 in two ranges, the three chords with the byte for Ctrl+/ and then Ctrl+Q on macOS. The lead verified both ranges, and they had no independent review. Lines are cited at `b1ef073ae`.

- **The three chords stay with a focused terminal on every desktop.** The bridge's `BracketRight` and `Slash` arms now return without claiming when the Command key is up and a terminal has focus, as `BracketLeft` does (`desktop/src-tauri/src/key_bridge.js:224-247`), so Command+] and Command+/ keep Next Pane and Split Right, and both forms keep their commands with focus anywhere else. Off macOS the workspace app's shortcut rule leaves the three Control chords with the terminal too: on a native client `shouldEscapeTerminal` answers false for Ctrl+[, Ctrl+] and Ctrl+/ unless the user assigned the chord, whose check comes first, and before the registry is asked (`web/packages/workspace-app/src/state/shortcuts.ts:785-798`, the user's chord at `:788`), so the terminal's key handler no longer lets them out to the app's keymap (`components/TerminalTab.svelte:2467`). The comment above the bridge's handler names the five chords a focused terminal takes back (`key_bridge.js:99-102`), and the Rust pin of the release set checks each of the four Control-only arms and counts one definition and five uses of `terminalHasFocus()` (`key_bridge_releases_a_focused_terminals_chords`, `desktop/src-tauri/src/serve.rs:2485-2562`).
- **Ctrl+/ sends 0x1F on every client.** The terminal tab sends the one byte 0x1F through its user-input path when a keydown carries Control and a slash as the layout resolves it, with no Command, Option or Shift, then consumes the event and tells xterm not to encode it (`TerminalTab.svelte:2473-2488`). It runs after the escape check and after the opt-in Ghostty renderer's early return (`:2467-2472`), so it serves the default xterm renderer in a desktop window and in a browser alike. Ghostty keeps its own encoder, which the lane's report ran directly and saw send 0x1F for Ctrl+/ (`dev/v0101-team/reports/report-Clients-18.md` in the development tree).
- **Ctrl+Q stays with the page on macOS.** The Quit arm claims Control+Q only off macOS (`case 'KeyQ': if (!MAC && !e.metaKey) invokeIpc(e, 'request_app_quit'); return;`, `key_bridge.js:160`, its comment at `:156-159`), so on macOS a Control+Q keydown reaches the page and a focused terminal whatever has focus, and Command+Q stays the app menu's Quit Chan (`CmdOrCtrl+Q`, `desktop/src-tauri/src/main.rs:5859-5862`). Off macOS Ctrl+Q still asks to quit. The Rust test that reads the arm's text reads the new arm (`serve.rs:2395-2396`), and `desktop/design.md` says who owns each of these chords (`:175`).

Pinned:

- The bridge's script, run under a macOS and a Linux user agent: with a terminal focused, Ctrl+[, Ctrl+] and Ctrl+/ are neither claimed nor prevented and the Command forms keep their commands; with focus in an editor or in a terminal tab that is not the active one, both forms keep them; the shifted forms keep theirs (`web/packages/workspace-app/src/state/desktopBridgeLayout.test.ts:78-137`). Control+Q is left to the page on macOS with a terminal or an editor focused, Command+Q is left to the menubar, and Control+Q requests Quit under a Linux and a Windows user agent (`:139-171`).
- Mounted terminal tests under macOS, Linux and Windows user agents (`state/desktopBridgeTerminal.test.ts:37-173`): a native Control bracket reaches xterm unprevented and outside the escape rule (`:76-84`); the shifted platform form, the macOS Command form, the browser's chords and a Control chord the user assigned still leave the terminal (`:86-121`); Control and slash send exactly one 0x1F on a native client and in a browser, also with the slash on another physical key, and xterm does not encode it (`:130-141`); other keys, modifiers and event types send nothing (`:143-162`); a Control and slash the user assigned leaves a browser terminal and sends nothing (`:164-172`).

The lane's reports show each pin failing before its fix and a mutation of each rule failing its own pins (`dev/v0101-team/reports/report-Clients-18.md` and `report-Clients-19.md` in the development tree).

What is not shown: no desktop window and no browser was driven. The bridge's claims rest on its script run in tests, the terminal's on mounted tests with a stand-in for xterm, and the bytes of the installed encoders on the lane's direct runs of them. Acceptance 6, Ctrl+] pressed three times leaving a container session on the macOS desktop, is owed on a display host, with the other presses the two reports list: the bytes 1b, 1d and 1f read raw in a shell on each desktop, Ctrl+/ undoing an edit in a readline shell, Ctrl+Q read as 11 in a macOS terminal with no Quit dialog, and Command+Q still asking to quit.

The wider rule stays open. On macOS the bridge still claims chords under Control alone: the tab digits (`key_bridge.js:249-253`), the zoom chords (`:140-153`), and the Option and shifted forms (`:111-133`, `:254-308`). The second report tables every Control chord the bridge still claims on macOS, with its command, what a focused terminal would receive if it were released, and the Command form that keeps the command (`dev/v0101-team/reports/report-Clients-19.md` in the development tree, "macOS Control claims after the Quit change"). The wider ruling waits on that table, with the frontend review remainder's platform-modifier pattern.
