# A relinked root's handoff window nests outside its launcher row

Status: raised during v0.101.0 on 2026-09-26 by the independent review of a test-only order (`dev/v0101-team/reviews/review-Services-1.md`, finding 3, in the development tree), which found it older than that order's range. A source reading against `main` at `1566b06d0`; not reproduced.

## Owner ruling

Accepted on 2026-09-26 as the lead recommended, with the smaller shape: every mint site stores the registry row's root, the handoff and desktop sites looking the row up by the key they already hold; red first with a relinked root minted through the devserver handoff. The services lane's, paired with the absent-root handoff item since both touch the desktop's handoff mint.

On 2026-09-27 the owner accepted, as the lead recommended, a widening of the item. A code map of the lane's next orders (`dev/v0101-team/int24-docs/codemaps/services-next.md` in the development tree, headline 5 and its section on this item, read at `4139f8656`, nothing run) found a second place where the two spellings part. The devserver keys a new mount's record by the canonical key of the path it was given (`begin_registered_mount`, `crates/chan-server/src/devserver.rs:1092`, the key from `register_workspace_keyed` and `mount_at`, `:968-974`, `:986-991`), while its management list joins records to registry rows by the row's stored root (`workspace_entries`, `:1634-1646`), lists a row with no record as off (`:1644-1645`) and lists a record with no row only while it is on (`:1653-1657`). So after a relinked root is mounted, a desktop connected to the devserver would list the workspace twice, an off row at the stored root and an on row at the canonical path, and a fix of the window's path alone would nest the window under the off row. That is inferred from the code, and no test asserts it. Revised: the item widens from the window's path to one row per workspace, joined by the canonical key, and a code map comes before its order.

## What was seen

The window feed matches a record's stored root against either of two keys the runtime holds, its canonical root or the registry row's root it was opened at (`found_by`, `crates/chan-library/src/host.rs:589-590`), so a record minted with either spelling is in the feed. The launcher nests a window under its workspace row by string equality with the row's `root_path` (`web/packages/launcher/src/lib/machineTree.ts:52-55`, `:106`; the row's path comes from the registry at `crates/chan-server/src/routes/library.rs:704-707`). Two mint sites store the canonical key of the caller's path rather than the row's root: the devserver handoff (`crates/chan-server/src/devserver.rs:2610-2611`, keyed at `:854-859`) and the desktop's window paths (`desktop/src-tauri/src/window_ops.rs:163-170`, `main.rs:2889`, `:2904`, `serve.rs:112`). For a root whose spelling has been relinked since the row was stored (a row at `/home/u/proj` after `/home/u` became a symlink to `/data/u`), those sites store `/data/u/proj`: the window is in the feed and sits outside its workspace row. The window route and the command action store the row's root and nest correctly. `crates/chan-library/design.md`'s sentence that a record's path is the one the launcher nests it under holds only for those two.

## Desired contract

A window minted for a registered root nests under that root's launcher row whichever spelling the minting site resolved, and the design text says which spelling a record stores.

## What to do

Either have every mint site store the registry row's root (the handoff and desktop sites would look the row up by the key they already hold), or have the launcher nest by the same two-key match the feed uses. The first keeps one spelling in every record and is the smaller change; the second keeps a lexical launcher. Red first: a test that relinks a registered root, mints through the devserver handoff, and asserts the launcher tree nests the window under the row; today it is a top-level window.

Under the owner's revised ruling of 2026-09-27 the item also asks for one row per workspace: the devserver's list joins a relinked root's record to its registry row by the canonical key, so the root lists once, and the window nests under that one row. The code map that the ruling asked for was made the same day (`dev/v0101-team/int28-docs/codemaps/relinked-root-one-row.md` in the development tree, read at `91cdd462e`, nothing run), and from it the lead ruled how the join reads the key: a record joins the registry row whose stored root or whose cached canonical path is the record's root, the match `canonical_root_status` already makes (`crates/chan-library/src/host.rs:3718-3728` at `37e9d23dd`), which resolves nothing and touches no filesystem; and every mint of a workspace window stores the root its runtime was opened at. Windows that an earlier build stored under the canonical path are not rewritten. Red first for this half: the same relinked root mounted through the devserver, and its management list read for one row. This paragraph was added on 2026-09-27 to bring this section to the revised ruling.

## Boundaries

The mint sites named above, `machineTree.ts` if the second shape is taken, and the design sentence. The feed match itself and the root locks are not part of this item.

It came in two parts, a range and its fix round: the range (`dev/v0101-team/reports/report-Runtime-29.md` in the development tree, to the order `dev/v0101-team/tasks/task-Lead-Services-28.md`), whose independent review asked for a fix round (`dev/v0101-team/reviews/review-Runtime-17.md`, with the lead's notes), and that round (`dev/v0101-team/reports/report-Runtime-31.md`, to `dev/v0101-team/tasks/task-Lead-Runtime-29.md`), whose production diff the lead read whole and verified at the blob (`dev/v0101-team/journals/journal-Lead.md`, the entry of 2026-09-28 13:04Z). The shapes of both orders are the lead's rulings, the owner's to overrule. `crates/chan-library/design.md:48` and `crates/chan-server/design.md:28` are the builders' account; what follows is the code's.

- **A workspace window stores the root its runtime was opened at.** `WorkspaceHost::mint_workspace_window` stores the root that the workspace runtime the caller's key names was opened at, the registry row's stored root, whichever of the runtime's two keys the caller holds (`crates/chan-library/src/host.rs:2522-2554`; `mounted_root`, `:3816-3825`; `found_by`, `:612-619`). With no runtime by that key, as when a mount is still pending, it stores the stored root of the registry row that goes by the key, found without asking any filesystem, and the key itself only when no row does (`:2539-2548`). The devserver's serve handoff (`handle_discovery_request`, `crates/chan-server/src/devserver.rs:2895-2897`), the launcher's window route (`handle_create_library_window`, `crates/chan-server/src/routes/library.rs:1179-1182`) and its command action (`handle_library_command_action`, `:828-830`) mint through it. chan-desktop does not: its handoff and `cs window new` mint through `mint_window` with the key they computed (`host.rs:2471-2481`), which is the desktop's half, below.
- **The keys a registry row goes by are named by one function,** `registry_row_keys`: the root the row stores and the canonical path it last resolved to, read with no filesystem (`host.rs:4543-4553`). A registry load primes that path to the stored root, and a registration that finds the row refreshes it (`cached_canonical_path`, `crates/chan-workspace/src/registry.rs:232-239`). The host's status by key (`canonical_root_status`, `host.rs:3874-3884`), the mint's arm with no runtime, the devserver's set of registered keys (`registered_root_keys`, `devserver.rs:3243-3254`) and its list's join all ask a row through it.
- **The devserver's list joins a record to the registry row that goes by its root** (`WorkspaceRecord::joins`, `devserver.rs:599-604`) and lists one row per registry row, at the row's stored root and with its label (`workspace_entries`, `:1704-1738`; `registry_row_entry`, `:1740-1763`). A mount still keys a new record by the canonical path (`begin_registered_mount`, `:1143`); the join is what lists a relinked root once. **When two records join one row, the row shows** the one whose prefix the host serves, then the one desired on, then the one keyed by the row's stored root, then the one whose prefix sorts first, and the others are not listed (`Listing::shown`, `:634-650`). The served prefixes are read from the host's map while the record map is held, as the save reads them, so the list asks no filesystem (`Listing::read`, `:614-632`; `mounted_prefixes`, `host.rs:3728-3737`). A row that no record joins is listed off at the prefix derived from its stored root, and a record that joins no row is listed only while it is on (`devserver.rs:1756-1762`, `:1721-1735`).
- **The list's row and the on route's answer are one function.** `entry_for`, which answers the on route, finds the record at the prefix and the registry row that record joins, and answers `registry_row_entry` for that row, read in the same lock window as the record, so the answer can be another record's row and is what the next list shows; a record that joins no row is answered at its own root (`devserver.rs:1435-1461`; the on route's answer, `:1429-1432`).

Pinned, each new pin that changes behaviour red first at its own assertion in the two reports: the handed-off window stores the row's root (`a_relinked_roots_handed_off_window_stores_its_registry_rows_root`, `devserver.rs:8698`); one row after a handoff, after the on route, beside an off record and between two records alike (`:8776`, `:8797`, `:8828`, `:8871`); the served record beside a failed restore, with the on route's answer for either prefix equal to the row (`:8953`); the served prefix after an on route, a handoff and two saves, whichever prefix sorts first (`:9134`); a restore from an overlay row keyed by the canonical path, listed once (`:9025`); a root whose last component became a symlink to another name, listed with its stored root's label and its mount's error (`:9069`); the method's stored root for either key, the row's root with no runtime, and the origin its caller names (`host.rs:6305`, `:6343`, `:6390`); the command action's window (`crates/chan-server/src/routes/library_command_capability_tests.rs:571`); a workspace mint gated on its leader by either path (`:939`); and the window route's existing pin, its body unchanged (`routes/library.rs:3168`). **What is left, by the code at the tip and by the records:**

- **The devserver can still hold two records for one relinked workspace** (the review's first finding). The on route of its row and a handoff of its directory each key a record by the canonical path, one at the stored root's prefix and one at the canonical path's (`set_workspace_on`, `devserver.rs:1374-1382`; `register_workspace_keyed`, `:1019-1026`; `begin_registered_mount`, `:1128-1154`), and a save folds the overlay row of either into both, since it matches overlay rows to records by the record's root (`:1603-1607`, `:1632-1641`). After an on route, a handoff and two saves the row lists the prefix the host serves, which is pinned; that it then reads off while the host serves it is the report's inference and was not observed at the tip, and that a restart then restores nothing is the review's reading, not run (`reports/report-Runtime-31.md`, "The review's findings"). One record per workspace is an order of its own (`dev/v0101-team/tasks/task-Lead-Runtime-30.md`), handed back on 2026-09-28 and under independent review (`dev/v0101-team/reports/report-Runtime-32.md`); it is not in this landing.
- **A relinked root's public path can change across a restart.** Turned on through the on route, it is served at the prefix derived from its stored root (`set_workspace_on`, `devserver.rs:1376-1382`) by a record keyed by its canonical path (`:1143`), whose overlay row the save writes under that path (`WorkspaceRecord::persisted`, `:588-597`); a restart derives each restored record's prefix from its overlay row's path (`prepare_restore_rows`, `:1908-1927`), so the workspace is then served at the canonical path's prefix. Read at the tip and not run; the review saw it on the way, and the lead's notes raise it here.
- **The shape the lead ruled for that order on 2026-09-28, the owner's to overrule, is not at this tip** (`dev/v0101-team/followups/followup-Lead-Runtime-37.md`): every record is keyed by its registry row's stored root and served at the prefix derived from it. It replaces the lead's earlier ruling that a record keeps its canonical key (ruling 6 of `tasks/task-Lead-Services-28.md`), and **it changes what a user sees, so it is written here before it lands:** a workspace served through an alias whose last component differs from its registered root's is then served at its registered prefix. Today the devserver takes a mount's slug from the path its request names (`workspace_prefix_for`, `crates/chan-library/src/prefix.rs:36-44`, called at `devserver.rs:1024`; the open route passes its path as sent, `:3039-3043`), so a request that names such an alias as typed is answered at the alias's name. The shipped `chan serve` resolves its path before it hands it off (`absolutize_serve_root`, `crates/chan/src/lib.rs:3349-3354`, called at `:3814`), so a handoff from it names the resolved path already. The lead accepted the change as one workspace having one prefix, with a pin and its words in the design document and the changelog.
- **The desktop's half is not ordered yet.** chan-desktop's handoff, whose running arm mints at once and whose other arm mints in `serve::start`, and `cs window new` store the canonical key they computed (`desktop/src-tauri/src/main.rs:2960`, `:2975`; `serve.rs:113`; `window_ops.rs:163-170`), so a relinked root's window opened through the desktop is in the feed and outside its row (`crates/chan-library/design.md:48`). It meets [the-desktop-handoff-keys-an-absent-root](the-desktop-handoff-keys-an-absent-root.md) in the same handoff.
- **Windows that an earlier build stored under the canonical path are not rewritten**, as the lead ruled on 2026-09-27. The window registry sets a record's path only when it creates the record (`create_with_origin`, `crates/chan-library/src/windows.rs:473-497`), the feed keeps such a record while a runtime goes by that path (`window_in_live_feed`, `host.rs:2357-2364`; `found_by`, `:617-619`), and the launcher nests a window under a row by the equality of the two paths (`samePath`, `web/packages/launcher/src/lib/machineTree.ts:52-55`, `:103-112`), so such a window stays outside its row until it is closed; the changelog says so (`CHANGELOG.md:23`).
- **A root relinked while it is mounted cannot be handed off**, read at the tip and not run. A mounted runtime keeps the two keys it had at its mount, the stored root and the canonical path it resolved to then (`host.rs:1645-1679`), so a handoff of the new canonical path finds no runtime (`found_by`, `:617-619`; `open_or_get_registered_workspace`, `:1452-1466`) and opens the workspace again. The library's own check for a handle it still holds keys by the canonical path as it resolves now and misses the handle it keeps under the old one (`Library::open_workspace`, `crates/chan-workspace/src/library.rs:303-329`); the writer lock, which this process holds under the same metadata key, compares the holder's record, which names the old path, with the new one and reads the holder as another process (`WorkspaceLock::acquire` and `try_steal`, `crates/chan-workspace/src/lock.rs:217-227`, `:236-271`; the record's path, `:510-513`, `:538-544`). The open then answers `workspace is locked by another process` at once, since the host waits out a held lock only after an in-process conflict (`host.rs:1389-1405`), and the handoff answers with that error. The code map of 2026-09-27 had inferred `WorkspaceAlreadyOpen` after the one-second release budget; the comparison of paths in the lock is what it had not read.
