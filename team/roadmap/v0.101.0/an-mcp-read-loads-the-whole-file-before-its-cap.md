# An MCP tool reads a whole file before its size cap applies

Status: accepted for v0.101.0 by the owner on 2026-09-27; raised for a decision on 2026-09-27 by the plan for the cancellation of a started MCP tool ([a-started-mcp-tool-cannot-be-cancelled](a-started-mcp-tool-cannot-be-cancelled.md); `dev/v0101-team/followups/followup-Runtime-Lead-16.md` in the development tree, section 6), which read `read_media`'s read and its cap at `836d2508a` and took `read_file`'s from a code map, and ran nothing; read again in code at `d1fe06c86`, where both hold, and not run.

## Owner ruling

Accepted on 2026-09-27 for v0.101.0, as the lead recommended, in the owner's answer to it by its number: a stat before the read, which bounds the read and does not cancel it. The owner added that the documents say so: the tool's documentation and the design document say what a read of a file over its cap answers, and that the file is not read to learn its size. In the same answer the owner asked for an investigation, for the next version, of how other MCP servers handle a read of a file over their cap; that is [how-mcp-servers-cap-a-read-is-unsurveyed](../v0.102.0/how-mcp-servers-cap-a-read-is-unsurveyed.md).

## What was seen

`read_media` reads the file whole and only then compares its length with its cap. `read_media_content_sync` in `crates/chan-llm/src/mcp.rs` calls `Workspace::read` (`:682-685`), which reads the regular file to its end into memory (`crates/chan-workspace/src/workspace.rs:1752-1754`; `crates/chan-workspace/src/rooted_fs.rs:557-566`), and then refuses it with `media too large` when its length passes `max_media_bytes` (`mcp.rs:686-695`), whose default the tool's description gives as 10 MiB (`:555-558`).

`read_file` has the same shape against its own cap, which cuts the text rather than refusing it: the tool reads the whole text with its stat (`exec_read_file`, `crates/chan-llm/src/tools.rs:267-272`; `read_text_with_stat`, `rooted_fs.rs:615-634`) and then truncates it to `READ_FILE_CAP_BYTES`, 256 KiB (`tools.rs:273-285`, the constant at `:31-38`).

Both run on the blocking pool with the workspace in the tool's context for the whole call (`run_tool`, `mcp.rs:621-646`; `read_media_content`, `:648-668`), and a workspace holds its root's writer lock until it is dropped (`_lock`, `workspace.rs:864-865`). So a file of several gigabytes is read to its end, into memory, holding its workspace, and with it the root's writer lock, for the whole read, and only then refused or cut. A close of the root waits for the last handle and the lock to go, up to a 5 s deadline, and then logs that the writer lock is still held (`shutdown_with_budget`, `crates/chan-library/src/host.rs:626-662`; `wait_for_workspace_release`, `:4503-4523`; `WORKSPACE_SHUTDOWN_RELEASE_TIMEOUT`, `:49`), so the lock outlives the close until the read returns. The request's cancellation is checked twice before the read and not during it (`mcp.rs:656-663`), and `crates/chan-llm/design.md:67` says that a body already executing can retain the workspace until it returns.

The cancellation [a-started-mcp-tool-cannot-be-cancelled](a-started-mcp-tool-cannot-be-cancelled.md) builds stops a tool body at a boundary inside a walk, a search or a report scan. A single read is one call with no such boundary, so, as the record reads it, a cancel flag cannot shorten it; that item leaves `read_media` with the checks it has.

## Desired contract

A tool that reads one file reads no more of it than its cap needs: `read_media` refuses a file over its cap without reading it, and `read_file` reads at most its cap and still reports the file's size and that it was cut. A read then holds its workspace, and a close of its root waits on it, for a time bounded by the cap and not by the file.

## What to do

Stat the file before the read: `read_media` refuses a file whose size passes its cap before it reads a byte, and `read_file` reads at most its cap, taking the size it reports from the stat. A suggestion beyond the record: bound the read itself as well, since a file can grow between the stat and the read. It is a bound and not a cancel: a read within the cap still runs to its end, and a single read that blocks on a root that stopped answering is not shortened. Red first: a test with a file over each cap that observes how much of the file the tool read; today it reads the whole file.

## Boundaries

`crates/chan-llm/src/mcp.rs` (`read_media_content_sync`), `crates/chan-llm/src/tools.rs` (`exec_read_file`), the chan-workspace reads they call if a bounded read needs one (`Workspace::read`, `read_text_with_stat`), the cancellation paragraph of `crates/chan-llm/design.md`, and their tests. The cancellation of a running tool body is [a-started-mcp-tool-cannot-be-cancelled](a-started-mcp-tool-cannot-be-cancelled.md).

## Acceptance

1. `read_media` of a file over its cap answers `media too large` having read none of the file; pinned red first.
2. `read_file` of a file over its cap reads at most its cap and answers the file's size, the truncated text and its note, as now; pinned red first.
3. A file within each cap reads as it does now.
4. `crates/chan-llm/design.md` says that a tool's read of one file is bounded by its cap.
5. The tools' own descriptions and `crates/chan-llm/design.md` say what a read of a file over its cap answers, and that the file is not read to learn its size: `read_media` reads none of such a file, and `read_file` no more than its cap. Added on 2026-09-27 with the owner's ruling.

## What shipped

Landed on 2026-09-28, in the shape the owner accepted, a stat before the read; lines at `b39274a1a`. The builder's report is `dev/v0101-team/reports/report-Runtime-30.md` in the development tree, to the order `dev/v0101-team/tasks/task-Lead-Runtime-27.md` and its six rulings, with `dev/v0101-team/followups/followup-Lead-Runtime-35.md`; the lead read the production diff whole and verified it at the blob, with no independent review (`dev/v0101-team/journals/journal-Lead.md`, the entry headed 2026-09-28 11:40Z, which its own correction says was written at 11:36Z).

- **`read_media` reads none of a file over its cap.** It opens the file through `Workspace::read_bytes_bounded`, which takes the file's stat from the open handle and freezes the byte window at that size (`read_media_content_sync`, `crates/chan-llm/src/mcp.rs:733-741`; `read_bytes_bounded_slice`, `crates/chan-workspace/src/rooted_fs.rs:529-555`), and refuses a file whose size passes `max_media_bytes` with `media too large` and the two numbers before it reads a chunk (`mcp.rs:741-747`). A file within the cap is read in chunks of at most 64 KiB into one buffer of its size (`:748-751`; `BoundedFileReader`, `crates/chan-workspace/src/workspace.rs:202-239`); bytes it gains after the open are not read, and a file that shrinks under the read is an error (`workspace.rs:215-227`).
- **`read_file` reads at most its cap.** It calls a new bounded text read with `READ_FILE_CAP_BYTES`, 256 KiB (`exec_read_file`, `crates/chan-llm/src/tools.rs:290-316`; the constant at `:32-40`), and answers the stat's size, with `truncated` and its note when that size passes the cap (`:299-314`). The read (`Workspace::read_text_with_stat_bounded`, `workspace.rs:1784-1802`, over `rooted_fs.rs:636-676`) applies the editable-text gate that `read_text_with_stat` applies, takes the stat from the open handle, reads no more than the bound or the stat's size, whichever is smaller, cuts a character that the bound splits back to its first byte, and validates only the bytes it read, with the error `read_text_with_stat` gives (`rooted_fs.rs:644-675`). For a path the extension classifier does not type as text, the gate's content sniff reads up to 8 KiB of the file's start first, as it does for every text read (`sniff_is_text`, `rooted_fs.rs:568-599`; `TEXT_SNIFF_BYTES`, `crates/chan-workspace/src/fs_ops.rs:439`).
- **A file within each cap** is answered as before, with one difference for both tools: bytes a file gains after it is opened are not read. `read_file` reads such a file whole and validates it as before, and its `size` now comes from the stat and not from the text's length, the same number for a file not written during the read (the report, "Acceptance 3").
- **The words.** Both tools' descriptions say what a read of a file over the cap answers and that its size comes from the file's metadata (`mcp.rs:433-443`, `:551-562`, and their copies in `crates/chan-llm/src/prompts.rs:7-17`, `:89-100`); `crates/chan-llm/design.md` says that a tool's read of one file is bounded by its cap and not by the file's size, and that neither read is cancelled while it runs (`:71`, `:94`); `crates/chan-workspace/design.md:105` describes the bounded text read; and the changelog records it (`CHANGELOG.md:29`).

**A change of behaviour that the lead ruled and the owner has not answered**, ruling 3 of the order, the owner's to overrule: a text file over the cap whose bytes past the cap are not UTF-8 is answered where it was refused. At the tip `read_file` answers such a file, when its bytes up to the cap are UTF-8, with its text up to the cap, a character the cap splits cut back to its first byte, `truncated: true`, `size` the whole file's, and the note `file truncated to 262144 bytes; full size <size>` (`rooted_fs.rs:659-675`; `tools.rs:299-314`); before, the whole read was refused with the error of a text that is not UTF-8 (the report, "Red first"). A byte that is not UTF-8 within the first 256 KiB is still refused with that error, and so is a file whose own last character is cut short by its end rather than by the cap (`rooted_fs.rs:662-674`). The owner's acceptance of a stat before the read, on 2026-09-27, did not name this; the design document and the changelog say it (`crates/chan-llm/design.md:94`; `CHANGELOG.md:29`).

Pinned: `read_file` over 256 KiB of text followed by 1,024 bytes of `0xff`, answered with the text, `truncated`, the size and the note (`read_file_answers_a_file_whose_bytes_past_the_cap_are_not_utf8`, `tools.rs:666`), red first at the base, where the tool refused the file; a character that straddles the cap, cut at its first byte (`:691`), which held at the base after a whole read; the bounded read's four tests in chan-workspace: a file within the bound returned as `read_text_with_stat` returns it, a cut at the bound or the character before it with bytes past the bound neither read nor validated, the same errors for an invalid byte and for a short last character, and the text gate (`workspace.rs:8199`, `:8214`, `:8240`, `:8256`); and `read_media` in a test binary of its own, built only on Linux with chan-llm's `mcp` feature (`read_media_reads_none_of_a_file_over_its_cap`, `crates/chan-llm/tests/mcp_read_bound.rs:80`, the gate at `:12`). That pin counts `rchar` in `/proc/self/io`, every byte any thread of the process read through a read-like system call, around one call over an in-memory MCP session, with the workspace's startup recovery stopped first, and leaves the counter's own read of `/proc/self/io` out of each count (`:1-11`, `:30-38`, `:66-74`, `:86`, `:96-97`). It asks a file of a quarter of the cap to count its size and less than 256 bytes more, and a sparse file eight times the cap to count less than 256 bytes (`:20`, `:25`, `:87-94`, `:127-142`). The 256 bytes are room for a read the tool does not make: glibc's malloc reads the list of online CPUs, 4 bytes on the builder's box, once per process the first time a thread finds its arena held, which pinned to one CPU landed inside a call in 181 of 200 runs of an exact count; it is far below the 64 KiB a bounded read takes at a time, so a read of one chunk before the refusal reds the pin (the report, "The read_media pin's instrument"). At the base the pin counted the file's 8,388,608 bytes and 102 more, the counter's own read. In the report ten mutations red the pins at their own assertions, the `read_media` pin passes 200 runs as it is and 200 on one CPU, and the own gate was green with chan-llm's `mcp` feature on in its test, doc and Windows-target clippy steps.
