# An extension spawned by the installed devserver gets a bare PATH, and the warning hides why it failed

Status: landed in one lane with [the-aur-check-could-ship-a-test-only-feature](the-aur-check-could-ship-a-test-only-feature.md), whose second round answered an independent review of its first and was checked by the lead; accepted for v0.101.0 by the owner on 2026-09-25; raised for v0.101.0 from a field investigation of an extension that never appeared in the catalog on a machine running the devserver as a systemd user service. The cause was established there by reproducing the spawn under the service's exact environment; the code claims below are a source reading against `main` at `d3de0180b`.

## What was seen

chan spawns an extension with `Command::new` and no shell (`crates/chan-server/src/extensions.rs`), so the child inherits the server's environment verbatim and nothing sources a shell profile the way a chan terminal does. The unit chan renders (`crates/chan-systemd/src/lib.rs`) emits only the `Environment=` assignments it holds and never a `PATH=`, so a devserver started by that unit runs with systemd's own default PATH. An administrator cannot simply add one: `classify_installed` in the same file accepts only `CHAN_HOME`, `CHAN_TUNNEL_TOKEN`, `CHAN_TUNNEL_URL` and `CHAN_TUNNEL_DEVSERVER_NAME` as chan-owned keys, and any other key makes chan refuse to manage its own unit ("refusing to overwrite foreign or administrator-edited systemd unit", `crates/chan/src/lib.rs`). The declaration cannot carry one either: `ExtensionFile` is `deny_unknown_fields` over name, command, args and capabilities.

An extension that resolves a helper on PATH therefore exits before printing its handshake line, and the operator is told almost nothing. `ExtensionRuntime::start_in` logs `extension ignored` with the error's `Display`, which renders only the outermost context, so the journal says the handshake could not be read and never says the child closed its stdout without the marker. In the field case that opacity was most of the investigation: the extension failed at every devserver start, and the working fix was a systemd drop-in adding the user's own bin directory to PATH.

## Desired contract

An extension spawned by a chan-installed devserver resolves the helpers a user would reasonably expect it to, or, where chan will not promise that, the failure names its own cause in one log line and the documentation says plainly that a service-spawned extension inherits no shell PATH.

## What shipped

The owner asked for the failure fixed rather than only documented, so the PATH question is settled the first way acceptance 2 names: the service definition records a PATH.

- **The logged cause.** `ExtensionRuntime::start_in` (`crates/chan-server/src/extensions.rs`) logs `extension ignored` with the whole context chain (`{error:#}`), and `start_extension` adds the child's exit status to the handshake read's context, from the wait `terminate_child` already did and now returns. A helper missing from PATH logs `reading handshake (child exit status: 127): extension stdout closed before the handshake marker` on Linux, and a bare `command` missing from PATH logs the spawn error after `spawning <command>`. `a_closed_stdout_is_logged_with_its_cause_and_exit_status` pins the first.
- **The systemd unit.** `DevserverUnit::with_search_path` (`crates/chan-systemd/src/lib.rs`) renders `Environment="PATH=..."` from the installing process's own PATH through the shared filter `service_search_path`: absolute entries only, the first occurrence of a repeat, no entry holding `"`, `\`, a control character or bytes that are not UTF-8, and `%` written `%%` for systemd's specifiers; no line when nothing survives. `write_devserver_unit` (`crates/chan/src/lib.rs`) renders it; on the systemd backend `chan devserver restart` always reaches that function, and `start` and `join` reach it when the service is not running. `classify_installed` accepts one `PATH` as chan-owned, so a unit with another PATH or none (an older chan's) is rewritten as `KnownLegacy`, and a second `PATH` line or any other added key is still refused as foreign.
- **The launchd plist.** `write_devserver_launch_agent` records the PATH in the plist's `EnvironmentVariables` beside `CHAN_HOME`, XML-escaped and after `ProgramArguments`, chosen by `launch_agent_search_path` with the same filter.
- **A render without a terminal.** `keeps_recorded_service_path` decides for both: a render whose standard input is not a terminal (a desktop connect script, any script) keeps the PATH the installed definition records (`DevserverUnit::recorded_search_path`, `recorded_launch_agent_search_path`), and so does a terminal render whose PATH has no usable entry; with nothing recorded, every render records its own. `a_render_without_a_terminal_keeps_the_recorded_search_path` and `launch_agent_search_path_follows_the_unit_rule` pin the rule.
- **Persisted flags.** `persisted_flag_value` reads `--bind=`, `--port=` and `--tunnel-url=` only from the command a definition runs, the unit's `ExecStart=` line or the plist's `ProgramArguments` array (`persisted_command_line`), so a PATH entry holding the same text is never read as a flag; `persisted_flags_come_from_the_command_line_only` pins it.
- **A service's environment.** `a_service_environment_is_what_an_extension_resolves_through` re-runs its own test binary as the chan process with the environment cleared to one PATH. Under a service's default PATH the catalog is empty and both failures log their causes; with the user's bin directory first on PATH, both extensions start. The tests that capture the warning run alone in a child process, because tracing's process-wide callsite cache let an in-process capture miss the warning in 10 of 60 parallel runs.
- **Docs.** `docs/extensions.md` has a section, "The environment", on the inherited environment, which runs record the PATH and which keep it, the entries dropped, the PATH also being where every terminal the service opens starts, the two definitions chan does not write (the distro packages' static unit and the sdme provisioner's) with the drop-in for them, and the two log lines. `docs/config-reference.md`'s `command` row and inheritance sentence point at it, and `crates/chan-systemd/design.md` lists the accepted keys and the new functions.

Two points are open. Whether the desktop's `limactl shell` connect flow gives the remote chan a terminal is unverified: the desktop runs connect scripts in a control-terminal PTY (`desktop/src-tauri/src/main.rs`), so if `limactl shell` passes a terminal through, a `chan devserver join` there counts as a terminal render and records the remote shell's PATH, and if it does not, the render keeps the PATH already recorded. The launchd path has not been exercised on a real Mac: only tests have built and read back the plist it writes.

## Boundaries

`crates/chan-server/src/extensions.rs` (the spawn, `read_handshake` and the ignored-extension warning), `crates/chan-systemd/src/lib.rs` (the rendered unit and its accepted environment keys), `crates/chan/src/lib.rs` (the foreign-unit refusal) and the extension authoring documentation under `docs/`.

## Acceptance

1. A test in which the child closes stdout without the marker shows the logged error naming that cause, not only the outer context.
2. The PATH question is settled one way and the choice is implemented: the rendered unit sets a PATH, or the declaration may carry an environment, or the documentation states the bare-PATH behaviour and the drop-in remedy.
3. A test starts an extension under a minimal environment and asserts the documented behaviour, so the case a service produces is covered without a service.
