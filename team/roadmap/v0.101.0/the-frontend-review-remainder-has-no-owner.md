# The rest of the frontend review has no owner

Status: accepted for v0.101.0 by the owner on 2026-09-25; raised for v0.101.0. v0.100.0 took 52 of the frontend review's 166 high and medium findings, and four sibling items here take the ones that are one piece of work each (source-text tests, repeated shapes, comments and dead code, mirrored contracts). This item is the ledger for what is left, so it does not become a second parked list. The mediums were re-verified against `main` at `d3de0180b` and all still apply; the lows were not.

## Owner ruling

Accepted on 2026-09-25 as the lead recommended, after [frontend-comments-narrate-history](frontend-comments-narrate-history.md) in the frontend rounds. It starts with a reading lane like the one over the Rust side-effect and error-handling lows ([the-side-effect-and-error-lows-are-unread](the-side-effect-and-error-lows-are-unread.md)): a disposition for each medium finding and each bug or side-effect low, with the ruling each one waits on. Fix lanes by area follow, highest consequence first. Of the five rulings this item needs, the workspace demo is settled by [frontend-comments-narrate-history](frontend-comments-narrate-history.md)'s ruling (it stays); the owner gives the other four (graph filesystem mode, non-markdown surfaces rewriting files, how snippets cross the wire, and what a multi-selection means for destructive actions) when the reading lane reports, with its evidence in hand.

On 2026-09-26, with the reading lane's evidence in hand, the owner gave the four rulings: graph filesystem mode stays supported and its four lows are fixed; no non-markdown surface writes a file without a user edit, and the first real edit may normalize; search snippets cross the wire as raw text with bare `<b>` markers, fixed on the Rust side, with no client change; destructive file-browser verbs act on the whole selection behind one confirm naming the count, report partial failures and clear the selection. The reading is done: the 47 mediums and the 116 lows filed as bugs or side effects (the item's 88 and 28) each have a disposition in the round's ledger, `dev/v0101-team/ferem-ledger.md` in the development tree, with the fix lanes by area in its two reports; the fix lanes follow.

Two of the editor's defects landed on 2026-09-27. In `web/packages/workspace-app`:

- **A `.json5` file opens as source text.** The strict JSON test (`isJson` in `src/state/fileTypes.ts`) no longer claims `.json5`, so such a file no longer opens in the JSON tree, which could not parse it, and the strict JSON save check, which refused its comments and unquoted keys, no longer runs on it: it saves through the plain write with its text as it is. `.json5` stays editable text.
- **A pasted inline image is named from its mime type** (`dataUriImageMetadata` in `src/editor/paste_html.ts`, used by both naming sites and the decoder). The extension is the mime's subtype, `svg` for `image/svg+xml` and `jpg` for `image/jpeg`, whose subtypes are not the extension, and `png` when the mime has none. It was the subtype of whatever preceded the data URI's first semicolon, so an SVG with no parameters was named with part of its payload, a base64 SVG `svg+xml`, and a JPEG `jpeg`.

Pinned by a state-level test that a `.json5` buffer with a comment and an unquoted key saves through the plain write with its bytes unchanged (`src/state/tabs.test.ts`), and by four rich-paste cases, a parameterless SVG, an SVG whose payload holds a semicolon, a base64 SVG and a JPEG, that dispatch a paste into a real CodeMirror view and read the name and type of the file handed to a mocked upload (`src/editor/paste_chan_html.test.ts`). Four more of the editor's defects were fixed later on 2026-09-27, in `web/packages/workspace-app` (lines at `7504a5f9c`):

- **A failed or oversized image upload is named, and the batch goes on.** An image over 50 MiB was skipped with no message, and a failed upload was logged to the console only and abandoned every image after it. Each now puts "Image NAME exceeds the 50 MiB upload limit; skipped" or "Image upload failed for NAME; skipped" on the status line (`notify`, `src/state/notify.svelte.ts:1-7`) and the batch continues with the next image; only the upload itself sits inside the catch, so a failure to insert is not reported as a failed upload (`uploadAndInsertAll` in `src/editor/bubbles/image_drop.ts:246-307`, the notices at `:265` and `:287`).
- **The images of a multi-image drop land where they were dropped.** The batch moved its insert position only by its own inserts, so an edit typed or received while an upload was pending put the images still uploading at stale offsets. Each batch's position is now mapped through every change to the document, its own inserts included, by a view plugin kept outside the editor's writable compartment, so a read-only toggle during the upload does not drop it (`uploadPositions`, `image_drop.ts:235-244`, installed at `:254-259`).
- **A file picked into an existing link keeps a working destination.** Picking `My Photo.md` into a `[label](...)` slot wrote the path with its raw space, which a Markdown parser does not read as a link; only the inline-code slot encoded it. Pinned in `src/editor/bubbles/image_drop.test.ts` (both notices with the batch continuing, and an edit between two uploads), `src/editor/Wysiwyg.imageDrop.test.ts` (a pending upload across read-only toggles in a mounted editor), `src/editor/bubbles/wiki.test.ts` (a name with a space in either slot) and `src/components/FileEditorTab.test.ts` (an indented heading skipped by the outline, in both modes).
