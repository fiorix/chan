# The desktop waits on every registered root to close a workspace, open a window or quit

Status: accepted for v0.101.0 by the owner on 2026-09-26; raised during v0.101.0 on 2026-09-26 from the independent review of the root locks lane (`dev/v0101-tasks/reviews/review-rlock-2.md`, finding 3). It follows from [one-root-blocks-every-other-mount](one-root-blocks-every-other-mount.md): the review notes that the lane's brief named the desktop's close, and the lane changed nothing under `desktop/`. A source reading against the root locks lane at `3746c268f`, which had not landed on the integration branch when this was raised, so every line cited is as it is at that sha; read in code, not reproduced.

## Owner ruling

Accepted on 2026-09-26 on the owner's word that nothing is deferred, in the services lane's hung-root orders with [a-late-http-mount-escapes-the-shutdown-sweep](a-late-http-mount-escapes-the-shutdown-sweep.md). The lead's ruling: the stored-key answers the item suggests (`is_canonical_root_mounted` through the embedded wrapper, `registered_workspace_prefix` re-exported beside `allocate_workspace_prefix`), with a red test at the host level for the helpers the desktop calls unless the `test-hooks` feature can enter the desktop's dev-dependencies without a `Cargo.lock` change.

## What was seen

Three desktop paths resolve every registered root on the way to acting on one, so one hung root C stalls them for every other root.

- **Close.** `close_workspace_from_handoff` in `desktop/src-tauri/src/main.rs` (`:2964-2995`) closes the root through the embedded host and then calls `persist_workspaces` (`:2989`). That filters every registered row by `embedded.is_root_mounted(&ws.root_path)` (`:1153-1161`), which goes through `WorkspaceHost::is_root_mounted`, `live_workspace` and `canonical_key` and canonicalizes each root (`crates/chan-library/src/host.rs:3425-3427`, `:3406-3408`, `:4105-4109`). It runs on the Tauri runtime worker that serves the handoff connection (the listener's dispatch, `main.rs:5282-5345`). With C hung, `chan close B` closes B but the `Closed` reply is never written: the CLI gives up after its 3 s read timeout (`crates/chan-server/src/handoff.rs:965`, `:1285-1287`) and falls through to the control-socket path (`crates/chan/src/lib.rs:2503-2519`), the desktop never emits `SERVES_CHANGED` (`main.rs:2990`), and each such close parks one more runtime worker until C answers.
- **New window.** `create_library_window` (`main.rs:4335-4357`) resolves a local workspace id in `local_workspace_path` (`:4284-4305`), which calls `chan_server::allocate_workspace_prefix` on each registered root in list order until one matches (`:4291-4302`), and that canonicalizes the root (`crates/chan-library/src/prefix.rs:32-34`). A hung root listed before the wanted one stalls the command. The lane added `registered_workspace_prefix` (`prefix.rs:51-55`), which hashes the stored root instead, but chan-server re-exports only `allocate_workspace_prefix` (`crates/chan-server/src/lib.rs:198`).
- **Quit.** `begin_normal_shutdown` runs `persist_workspaces` synchronously before it spawns the drain (`main.rs:6642-6655`). Its callers are the run-event callback's `ExitRequested` arm (`:5621-5638`), `request_quit` (`:6700-6733`), and the restart and update-install paths (`:3134`, `:3154`, `:3242`, `:3441`, `:3465`); the `RunEvent::Exit` arm calls `persist_workspaces` itself when no drain started (`:5646-5651`). The run-event callback (`app.run`, `:5611`) runs on the event loop's thread, so a quit from it waits there on C, and the drain that stops the tenants never starts.

## Desired contract

Closing a workspace, opening a window of a workspace and quitting never wait on the filesystem of a root the operation does not act on: the on-set snapshot and the id resolution go by the keys the registry and the host store.

## What to do

The review gives no fix beyond raising the item. A suggestion: have `persist_workspaces` ask by stored key through `WorkspaceHost::is_canonical_root_mounted` (`host.rs:3434-3436`), which answers from the runtimes' stored keys (the embedded wrapper exposes only `is_root_mounted`, `desktop/src-tauri/src/embedded.rs:328-333`), and have `local_workspace_path` hash the stored root with `registered_workspace_prefix`, re-exported next to `allocate_workspace_prefix`. Both compare stored keys with canonical ones, which is where the lane's relinked-root regression lives (review finding 1, fixed in the lane before it lands), so build on that fix. The stall seam is behind `test-hooks`, which no desktop build enables (review Q5, and `desktop/src-tauri/Cargo.toml` at the sha), so a red test in the desktop needs that feature in its dev-dependencies; the alternative is a test at the host level for the helpers the desktop calls.

## Boundaries

`desktop/src-tauri/src/main.rs` (`persist_workspaces`, `close_workspace_from_handoff`, `local_workspace_path`, `begin_normal_shutdown`), `desktop/src-tauri/src/embedded.rs` (the host wrappers), `crates/chan-server/src/lib.rs` (the re-export), and, for a red test, the dev-dependencies in `desktop/src-tauri/Cargo.toml`. The desktop's leaked handoff listener (`main.rs:5255-5282`, leaked at `:5480`), which the review lists as causing no stall, is not part of this item.

## What shipped

Landed on 2026-09-27, with [a-late-http-mount-escapes-the-shutdown-sweep](a-late-http-mount-escapes-the-shutdown-sweep.md) and with [a-save-after-the-shutdown-sweeps-turns-every-workspace-off](a-save-after-the-shutdown-sweeps-turns-every-workspace-off.md), which was found while this was built. The contract's checks, as the code now meets them:

- **Close.** `close_workspace_from_handoff` resolves only the root it closes. The on-set snapshot it writes afterwards matches each registry row by the root the row stores against the keys the host's workspace tenants store (`WorkspaceHost::is_workspace_mounted_by_key`, through the embedded wrapper), and resolves no root. It asks that query rather than `is_canonical_root_mounted`, which the item suggested, because only a tenant holding a workspace counts there, so the shared terminal tenant, which goes by the home directory, never reads as a home workspace being on. `chan close` of one workspace answers within the CLI's reply budget while another registered root hangs, pinned with the other root held by the `root_stall` seam.
- **Forget.** A removal finds its registry row by the rows' cached paths first and re-resolves the other rows only when no cached path matches (`Library::match_root` in `crates/chan-workspace/src/library.rs`). `chan workspace forget` of one workspace answers within the same budget and asks the hung root nothing, pinned. A row whose own cached path is stale still waits on the hung root at each lookup: [forgetting-a-relinked-root-waits-four-lookups](../v0.102.0/forgetting-a-relinked-root-waits-four-lookups.md).
- **New window.** `local_workspace_path` hashes the root each row stores with `registered_workspace_prefix`, which chan-server now re-exports beside `allocate_workspace_prefix`, so a workspace id resolves past a hung root listed before it; pinned.
- **Quit.** `begin_normal_shutdown` writes the stop's snapshot through the same stored-key match before it spawns the drain, and the snapshot is pinned to answer beside a hung root. The drain can still wait on a mounted root's recovery pass: [the-quit-drain-can-hang-on-a-recovery-pass](the-quit-drain-can-hang-on-a-recovery-pass.md).

The desktop's dev-dependency on chan-workspace enables `test-hooks`, so these pins run in the desktop's own tests, with no `Cargo.lock` change.

A quit that answers made reachable a loss the hang had hidden: a quit while the boot restore waited on a hung root wrote off every row the restore had not finished. The boot restore now keeps a pending set (`AppState::restore_pending`), the overlay's on rows, filled by `queue_boot_restore` before the shared terminal tenant mounts, so a quit or a close during that mount finds it filled. Only the restore takes a row out: once the row's mount has published or failed, or when its turn comes and the overlay no longer has it on. `snapshot_workspaces` reads the pending set before the mounted set, since a row leaves the set only after its mount has published, and writes a pending row on while the overlay still has it on. `restore_on_workspaces` reads the overlay again at each row's turn and skips a row turned off or forgotten while it waited. For both to see a user's intent on a root that moved under a symlink after it was registered, the host records an off or a forget under the key it resolved and, where that differs, under the root the registry row stores, which is where the on-row is kept, under one lock and one save (`overlay_spellings` in `crates/chan-library/src/host.rs`, `WorkspaceOverlay::set_each` and `forget_each`). Pinned with a boot restore held on a hung root: a quit keeps on the row mounted before it, the row it waits on and the row behind it; a relinked row queued behind it and closed through the handoff, turned off as the launcher turns it off, or forgotten, reads off after the quit; and a row turned off while it waited is not mounted when the restore reaches it.

Not fixed, or not pinned:

- The snapshot reads the pending set, the mounted set and the overlay's on rows, then replaces the overlay. A close or a forget that lands between those reads and the write is lost: the replace writes a row that differs from the stored one at the stored generation plus one. The snapshot's log line now follows the write, so no write to stderr sits inside that window.
- The order of the two boot calls, the pending set filled before the terminal tenant mounts, is pinned by a test that reads `main.rs`'s source (`boot_restore_requests_no_window_mint` in `serve.rs`): the terminal tenant's mount cannot be held in a test without a new seam.
- The Windows arm runs the desktop's tests (`make ci-windows`), and the tests beside a hung root and the on-set tests, apart from the relinked-root ones, which need a symlink and are Unix-only, have not run on Windows yet; Windows CI after this change is their first run.
- One hung root still holds the boot restore of every row behind it: [one-hung-root-holds-up-the-whole-restore](one-hung-root-holds-up-the-whole-restore.md).
