# Host programs started from the AppImage get the bundle's environment and its CLI searches the current directory for libraries

Status: accepted for v0.130.0 by the owner on 2026-11-13 and moved by him to v0.131.0 on 2026-11-14, when he took v0.130.0 to its release with the rows built by then; not started.

Record: found by reading in the last fix round of the `chan-term` work before v0.129.0, the same in v0.128.0, and left open for the owner (`dev/v0129/row-notes.md`, the sections "AppImage: host programs started by the desktop get the bundle's environment" and "chan-term: follow-ups from the round 7 review"; the review `dev/v0129/reviews/review-termfix-7.md`, finding 2 and "Found sound"). On 2026-11-13 the integrator named it, with the Windows claim, as one of the two items with a security angle: the CLI started from an AppImage keeps an empty `LD_LIBRARY_PATH` entry, which puts the current directory on the library search path. The owner: "sure, let's include them". The two behaviours are one row because both come from what a chan process of the AppImage keeps and passes on of AppRun's environment, which one module reads and one medium shows. A fix of the CLI's search path alone would still leave its extensions with the bundle's environment.

## What is there now

Read at `342dbe791`, the Linux AppImage only.

- AppRun builds an AppImage process's environment. Each search path it prepends to (`APPRUN_SEARCH_PATHS`, `crates/chan-library/src/terminal_sessions/platform.rs`) holds the mount's block, a separator, then the user's value, so a path the user had no value for ends in an empty entry. `PYTHONHOME` names the mount, linuxdeploy's GTK hook points the GTK, GIO and theme variables at the bundle, and the runtime sets `APPDIR`, `APPIMAGE`, `ARGV0` and `OWD`.
- chan gives two kinds of child the user's environment back: a terminal (`clear_appimage_env`, the full scrub) and chan's own AppImage started again (`hand_appimage_host_env`: a New Window sibling, a desktop a command starts, the devserver daemon, the relaunch after an update). Every other child inherits the process's environment.
- Among those children are host programs. The desktop opens links through tauri-plugin-opener 2.7.2's `open_url`, which runs `open` 5.3.4's `that_detached`: `xdg-open`, found on the bundle-first `PATH`. Four sites do this: the editor's external links (`web/packages/workspace-app/src/editor/external_links.ts`, `plugin:opener|open_url`), Open in Browser (`open_window_in_browser`, `desktop/src-tauri/src/main.rs:7315`), the launcher's links (`open_externally`, `desktop/src-tauri/src/launcher_panel.rs:1108`) and the gateway sign-in URL (`open_authorize_url`, `desktop/src-tauri/src/auth.rs:674`). Every chan server starts its extensions the same way (`start_extension`, `crates/chan-server/src/extensions.rs:460`): the desktop's embedded server, `chan serve` and the devserver, so an AppImage CLI does too. By the scrub's own reasoning (`clear_appimage_env`), a browser started this way searches the bundle's library directories, and a Python extension starts with a `PYTHONHOME` that holds no standard library.
- `main` (`desktop/src-tauri/src/main.rs`) runs the CLI personalities and returns before the boot's cleanup. Three dispatches do this: the MCP proxy (`:5614`), `cs` (`:5624`), and `chan` with `chan-files`, `chan-edit` and a `chan-term` that only runs the shell (`:5635`). All return before `linux_gui_stack::prefer_system_gui_stack` (`:5657`), the one place that drops AppRun's trailing empty entry and an older chan's blocks from the search paths (`clean_apprun_search_paths`, through `own_apprun_value`, `platform.rs`) and removes the re-exec marker's names.
- The `~/.local/bin` shims run `exec -a <name> "$APPIMAGE"` (`desktop/src-tauri/src/cs_install.rs`), so each of those commands typed in a shell runs under AppRun's environment. With no `LD_LIBRARY_PATH` of the user's, the value ends in the empty entry; the review measured `O*10 E` (the mount's ten entries, then the empty one), and `O*10 H X*10 E` under an older parent. The loader reads an empty entry as the current directory: for `chan serve .` that is the workspace (`restore_caller_cwd`), for the devserver daemon its chan home. By reading, not shown: a `dlopen` of a library the bundle lacks, such as an NSS module, looks in that directory before the system's. Children the CLI starts outside the hand-down and the scrub inherit the value.
- The loader (glibc's `ld.so`) reads `LD_LIBRARY_PATH` once, when a process starts. The desktop's `set_var` cleanup therefore reaches its children and the image its GUI-stack re-exec starts, but not the process that runs it.

## Desired contract

1. The links the desktop opens (the four sites above) and every extension a chan server of the AppImage starts get the environment a terminal's shell gets there (`clear_appimage_env`). No search-path entry, `PYTHONHOME`, GTK, GIO or theme variable names the mount; `APPDIR`, `APPIMAGE`, `ARGV0` and `OWD` are gone; and `LD_LIBRARY_PATH` is unset when the user had none.
2. No CLI personality of the AppImage (`chan`, `cs`, `chan-files`, `chan-edit`, a shell-only `chan-term`, the MCP proxy) has its current directory on its library search path, neither for its own lookups nor for any child's. AppRun's lone trailing empty entry is gone before the personality runs, a user's own empty entry or value stays as they wrote it, and the re-exec marker's names reach no child.
3. Unchanged: chan's own AppImage started again keeps the hand-down, a terminal keeps its scrub, the desktop keeps what its GUI stack needs, and off an AppImage nothing changes.

## Boundaries

- In scope: the AppImage environment readers in `platform.rs` and one way to start a host program under the scrub; its callers at the link sites and in `start_extension`; and the start of the CLI personalities in `main`. The editor's links reach that way through a chan command, or through the plugin's call routed through it; the build chooses.
- Since the loader reads `LD_LIBRARY_PATH` at the process's start, contract 2's own-lookups half needs the value clean before the personality's image starts. The desktop's GUI-stack re-exec already hands its new image a clean value that way. A cleanup inside `main` covers only the children. The build says which it does, and what it costs per CLI command.
- Not here: FUSE mode. The readings below run in extract-and-run mode, since the guests have no `/dev/fuse`. Under FUSE each chan process has a mount of its own, and the scrub tells this mount's entries by `$APPDIR`. So these readings join the list of [the AppImage's environment fixes are unread in FUSE mode](../v0.131.0/the-appimages-environment-fixes-are-unread-in-fuse-mode.md) (v0.131.0).
- Not here: other host programs a CLI of the AppImage starts with its environment, such as the systemd tools the devserver commands run (`systemctl`, `systemd-run`, `journalctl`, `crates/chan-systemd/src/linux.rs`). Read, not measured.

## Acceptance

1. Tests, red on the code without the change: an extension started from an AppImage process's environment (`start_extension` taking the parent environment), and the link opener's command built from one, get neither the mount's entries nor `PYTHONHOME`, and no `LD_LIBRARY_PATH` when the user had none. Over the review's shapes (`O*10 E`, `O*10 H X*10 E`), each CLI personality's start leaves no trailing empty entry in what a child gets, nor in the value a re-exec'd image starts with if the build re-execs; a user's own empty entry stays.
2. In an sdme guest, in extract-and-run mode, with the AppImage under test and no `LD_LIBRARY_PATH` of the user's: a link from the editor, Open in Browser, a launcher link and the sign-in URL each start an `xdg-open` stand-in that records its environment, with none of the mount's entries and no `PYTHONHOME`. A Python extension starts and answers its handshake under the desktop and under `chan serve` run through the shim. The search path the loader reports (`LD_DEBUG=libs`) for the serving `chan serve .` and devserver daemon processes, started through the shims, holds no current-directory entry. At the base, each of these readings shows the bundle's entries or the empty entry (the red).
3. The same readings on a host with FUSE, through the FUSE row's list.
