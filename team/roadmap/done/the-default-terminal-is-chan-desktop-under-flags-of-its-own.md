# The default terminal is chan-desktop under flags of its own

Status: shipped in [v0.129.0](../../release/release-v0.129.0.md): `chan-term` as a name of the `chan` binary with its own desktop entry and chan-desktop without the terminal flags, the AppImage's environment for the windows, desktops, devservers and shells it starts, and the macOS cold start through the desktop's links. The owner's Mac walk on 2026-11-13 (a build of `8a44e110e`) passed every step it ran from T0 to T6, the cold start by the `open` path in 7 s. Not shipped: the reading in FUSE mode (the last section), which the owner moved to the next version ("appimage: move to next version yes") and which is [a v0.130.0 row](../v0.131.0/the-appimages-environment-fixes-are-unread-in-fuse-mode.md); and a warm launch on macOS opens its window with Chan left behind, [a v0.130.0 row](../v0.131.0/a-warm-chan-term-launch-opens-its-window-without-chan-coming-forward-on-macos.md) on his word ("let's add a follow up item for this, no need to fix in this version").

Record before the release: built on `feat/chan-term` on 2026-11-12 (the section Built) and taken into the integration branch as `151515fee` the same day, with fix rounds since, the last merged as `997c53be7` on 2026-11-13 (the sections after it). It waits on the owner's Mac walk, and on a reading in FUSE mode before the release (the last section).

Record: raised by the owner on 2026-11-12, right after v0.128.0's `chan-files` and `chan-edit`, and accepted for v0.129.0 in the same words: "making chan-term like we just did chan-edit, and chan-files", "move all of the XDG wiring we did in chan-desktop over to the chan-term command, and the XDG instructions should point to chan-term.desktop, chan-edit.desktop, chan-files.desktop", "the chan-desktop binary no longer needs those flags and subcommands, our manuals must be updated as well".

## What is there now

- **The default terminal is the desktop app's own entry and flags.** `packaging/distros/shared/chan-desktop.desktop`, the app's menu entry, also carries `TerminalEmulator` and the `X-TerminalArg*` keys, and `chan-desktop [--dir=PATH] [--app-id=ID] [--title=TITLE] [--hold] [-e CMD ARGS... | -- CMD ARGS...]` is the launch xdg-terminal-exec runs (`desktop/src-tauri/src/terminal_mode.rs`, since v0.111.0). The grammar shares argv with the GUI launch: before a terminal flag an unknown option or a positional falls through to the GUI, and a bare `chan-desktop` is either a terminal (handed to a running desktop as a throwaway shell window, since v0.116.0) or the GUI boot.
- **The openers are names of the binary.** v0.128.0 made `chan-files` and `chan-edit` names of the `chan` binary, dispatched on the program name, each with its own usage, its own desktop entry, a link in every package and a shim the desktop writes; the standalone CLI's openers hand their paths to a running desktop.

## Desired contract

1. `chan-term` is a name of the `chan` binary, dispatched on the program name as `cs`, `chan-files` and `chan-edit` are, with the xdg-terminal-exec grammar as its whole usage: no argument runs the shell in the current directory, `-e` or `--` ends the grammar, a positional or an unknown option is a usage error (exit 2), and `--help` and `--version` answer.
2. A launch that only runs the shell works as the openers do: it opens a terminal window of the running chan-desktop, and with none running chan-desktop's own `chan-term` starts the desktop, whose first window is that terminal, so later launches hand off to it; there is no other standalone terminal (owner, 2026-11-12: "if chan-term is invoked when there's no chan running, it should spawn one up and subsequent calls to chan-term should work just normally handing off to the main chan-desktop process; i dont want to have yet another standalone terminal in the same app", replacing his first ruling of the same day, a cold launch's own window). A launch with a command, `--hold`, `--app-id` or `--title` keeps a `terminal-exec` window in a process of its own, for the command's exit status, the held window, the app id and the fixed title (owner, 2026-11-12), with a New Window sibling of the same name.
3. The standalone CLI's `chan-term` hands a shell-only launch to a running desktop and refuses, with the reason and exit 1, a launch that needs a window of its own and every case the openers refuse (no desktop, the opt-out, no display) (owner, 2026-11-12).
4. `chan-term.desktop` carries `TerminalEmulator` and the `X-TerminalArg*` keys, out of the application menu; `chan-desktop.desktop` carries neither, and `chan-desktop` takes none of the terminal flags. Every package links `chan-term` and every desktop package installs and validates its entry, as the openers'.
5. The manuals' XDG instructions name `chan-term.desktop`, `chan-edit.desktop` and `chan-files.desktop`.

## Boundaries

`crates/chan` (the grammar in `term.rs`, the dispatch, the help), `crates/chan-server/src/handoff.rs` (an `open_terminal` that reports its outcome), `desktop/src-tauri/src/{terminal_mode,main,launch_paths,cs_install}.rs`, the shared entries, every package recipe and container smoke, the entry and build-matrix checkers, the manual's install and terminal pages, and the design and contributor documents. Not changed: the terminal-only host, the `/exec` tenant, the throwaway window and the handoff protocol; Windows gets no `chan-term` shim, as it gets no opener.

## Built

## For the release notes

- A `~/.config/xdg-terminals.list` that names `chan-desktop.desktop` no longer selects chan, since that entry is no longer a terminal: name `chan-term.desktop` in its place. With the old list xdg-terminal-exec skips the entry and takes the next terminal it finds, which is `chan-term.desktop` only when no other terminal entry comes first.
- A script or key binding that runs `chan-desktop -e`, `--dir`, `--hold`, `--app-id` or `--title` gets a usage error that points at `chan-term`. Windows installs no `chan-term`, so there `chan-desktop.exe -e` and the other options, which opened a terminal window of their own before, exit 2 and open nothing; the error, which names `chan-term`, reaches only a redirected stderr, since a release `chan-desktop.exe` has no console.
- A bare `chan-desktop` beside a running desktop asks it to come forward instead of opening a new terminal window; `chan-term` opens one.
- A `chan-term` that only runs the shell, bare or with `--dir` (Omarchy's Super+Return sends `--dir=<cwd>`), with no desktop running starts Chan Desktop, whose first window is that terminal in the launch's directory, beside the windows it restores; before, a bare `chan-desktop` started it with the restored windows alone and a `--dir` launch opened a window of its own.
- `CHAN_NO_DESKTOP_HANDOFF`, and a session read as headless (an SSH login, which `SSH_CONNECTION`, `SSH_TTY` or `SSH_CLIENT` marks, `ssh -X` with a working `DISPLAY` included), make Chan Desktop's `chan-term` refuse a launch that only runs the shell, as the standalone CLI's does: it exits 1 with the reason and opens nothing. Before, a bare `chan-desktop` there brought the running desktop forward or started one, and a `--dir` launch opened a window of its own.
- On Linux, a Chan Desktop AppImage's New Window windows, a desktop such a window starts, and a `chan-term -e` typed in its terminals use the system GTK and WebKit, as the first launch does. Before, they ran the bundled ones, and the typed `chan-term -e` exited 127.
- The AppImage finds `ldconfig` in `/sbin` or `/usr/sbin` when `PATH` lacks them. Before, it ran on the bundled GTK and WebKit without saying so.
- On Linux, a terminal of the Chan Desktop AppImage gets back the `LD_LIBRARY_PATH` and `XDG_DATA_DIRS` you had. Before, a user who had none got `LD_LIBRARY_PATH=/usr/lib/x86_64-linux-gnu:`, so commands searched the host library directory and then the current directory for libraries, and got `XDG_DATA_DIRS=/usr/share:`.
- On Linux, a terminal of the Chan Desktop AppImage gets back the `PYTHONPATH`, `PERLLIB` and `QT_PLUGIN_PATH` you had and no `PYTHONDONTWRITEBYTECODE`, so Python there writes its bytecode caches again. Before, the three were dropped, and the AppImage's `PYTHONDONTWRITEBYTECODE=1` reached every shell.
- On Linux, a desktop, a New Window window or a devserver that the Chan Desktop AppImage starts, and the desktop it relaunches after an update, start from the environment you had and carry the AppImage's own search paths once. Before, each such process added the AppImage's paths ahead of its parent's, and in FUSE mode it and its terminals kept the parent's mount, directories under `/tmp` gone once the parent exited (the FUSE case read from the code, not run).
- On Linux, the Chan Desktop AppImage and its WebKit processes no longer search the current directory for libraries when you had no `LD_LIBRARY_PATH`.
- A `chan devserver start` run from the Chan Desktop AppImage records your `PATH` in the devserver's systemd unit, without the AppImage's directories, and a unit an earlier release wrote from the AppImage loses them at its next start. Before, the service searched directories under `/tmp` first that were gone once the AppImage exited, and that another local user could create.
- On macOS, a cold `chan-term`, `chan-files` or `chan-edit` run through the desktop's `~/.local/bin` links starts Chan Desktop, and so do `chan serve` and `chan upgrade` through the `chan` link. Before, the first three could start a chain of processes that never opened the app, and the last two timed out after 20 s (read from the code and the standard library, where `current_exe` returns a symlink's own path on macOS; not observed on a Mac before the fix).
- A Chan Desktop binary copied or hard-linked under a command name refuses to start the desktop and says why. On macOS the headless refusal names only an SSH login.

## Readings after the merge, 2026-11-12

An independent review of the merged branch found no high-severity defect (`dev/v0129/reviews/review-chan-term-intake.md`); its confirmed findings were fixed in two rounds, each reviewed or read (`dev/v0129/reviews/review-termfix-1.md`). Four guest readings it asked for (`dev/v0129/reviews/chan-term-runs-1.md`):

With a list that still names `chan-desktop.desktop`, which terminal wins depends on the filesystem's directory order: on btrfs the entry created last, on tmpfs the one created first.
- Wayland: under headless sway a `chan-term` window's `app_id` is `TUI.float` with `--app-id=TUI.float` and `chan-desktop` without.

Still not read: macOS (the shim and the window), a FUSE-mounted AppImage, other xdg-terminal-exec implementations and the KDE and GLib terminal pickers.

The macOS cold start was read while its walk was drafted (`dev/v0129/owner/owner-mac-checks-v0129-2-chan-term.md`): through a shim symlink the start climbed an unresolved path, found no `.app` and re-ran the shim under the same name. `desktop_start` (`crates/chan/src/desktop.rs`) now decides from the resolved path and refuses a target named as a command; the `open` command carries no `ARGV0`. ## An older release starting this one, 2026-11-13

A further fix round answered both causes and the empty entries, merged as `997c53be7`:

## Not read: FUSE mode

Nothing in this round has run chan's AppImage in FUSE mode.
