## What is there now

Read at `aabb9d039`, by reading, except the measurement named.

- `send_attach_prelude` (`crates/chan-server/src/routes/terminal.rs:1675-1740`) sends the session frame, then the replay (`:1707-1718`), then the `mode_reassert` suffix (`:1733-1740`), which after actual loss also disables the modes whose reset bytes were lost and reconciles the alternate screen. The live socket's in-band recovery calls it with `recovering` set (`:1439-1440`). The base `3a34491ce` sends the replay before the suffix too (D126 item 4); the redial row brought the redial onto that path.
- So after a loss whose span holds the program's exit from the alternate screen, the retained normal-screen tail is drawn on the stale alternate screen, and the suffix's exit then drops it (the Mac finding's mechanism, for the redial; Core-38 for both).
- Core-38's measurement, run once at `7e7618972` and not committed: on the lag-recovery rig, a blocked 1 MiB send and a flood past a 16 KiB ring, with the exit from the alternate screen in the lost span; the test fails with "the retained tail is drawn on the normal screen: before 0 bytes, the normal screen ends `"$ probe\r\n"`" (`dev/v0135-scratch/Core135/c38/live-recovery-measurement.log` and `.patch`).
- A page that is stopped while the server keeps its socket recovers over that live socket: the owner's first check 2 run, with the page and its network process both stopped, recovered that way (no `connected_at` changed) (`owner-mac-results-v0135.md`, check 2, "Method").
- Why the redial's fix does not carry over, per Core-38: on a new socket it sends the screen switch ahead of the session frame, where the tab counts nothing. On a live socket the tab counts binary bytes ahead of a session frame as live output, so the recovery's continued position would run ahead by the switch's length, and for a loss shorter than the switch (9 or 20 bytes) the tab would skip that many bytes, less the loss, from the replay's start (Core-38 decision 1, citing `TerminalTab.svelte:1718`, `:1722`, `:1732` at `08b5a96d1`).
- A replay that itself switches screens gets no switch ahead of it, because the session keeps no screen for the replay's start. It is drawn on the view's own screen: right when the lost span holds no switch, wrong when the lost span enters the alternate screen and the retained span leaves it (Core-38 decision 2).

## Desired contract

1. After a live socket's lossy recovery whose lost span holds the program's exit from the alternate screen, the view shows the retained tail on the normal screen, and every mode the suffix resets reads reset.
2. A reconciling attach's session frame names the screen its replay starts on, in a new optional field that is absent otherwise. The tab writes the switch to that screen itself before the replay's first byte, outside its accounting, as it writes its tracked-mode reset, and omits it when it skips a replay prefix it already parsed. A page that does not know the field ignores it. Core-38: this covers both the live recovery and the redial.
3. A replay that itself switches screens takes as its start the opposite of its first switch. No new tracking; it is wrong only for a redundant switch.
4. A loss that crosses no screen switch, and a lossless recovery, behave as today.

## Boundaries

- The session frame's new field and the attach's choice of start screen (`crates/chan-library/src/terminal_sessions.rs`, `crates/chan-server/src/routes/terminal.rs`), and the tab's session-frame handling (`web/packages/workspace-app/src/components/TerminalTab.svelte`), with their tests. The tab half needs a client seat and a mounted test on the real core (Core-38's cost note).
- Not here: the redial's own fix at `7e7618972`, which stands on its own; whether the redial moves onto the frame field is decided at the build and recorded here.

## The options as drafted

Core-38's options, with the lead's recommendation (D126 item 4): 1A with (i).

- Decision 1, the live recovery: (A) the session frame names the replay's start screen and the tab writes the switch outside its accounting (recommended, contract 2); (B) server only: send the switch ahead of the live recovery's frame only when the missed bytes exceed the switch's length, which couples the server to the tab's accounting and leaves shorter losses as today.
- Decision 2, a replay that switches screens: (i) infer the start as the opposite of the replay's first switch (recommended, contract 3); (ii) track a screen bit per ring chunk at its start, which a ring rebuilt from the fd store does not have, so it falls back there. Both share a caveat: a re-ask whose tab skips past that switch needs A's tab-side omission.

The recovery suffix is unchanged.
