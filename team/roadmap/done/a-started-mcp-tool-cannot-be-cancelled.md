Status: shipped in [v0.101.0](../../release/release-v0.101.0.md).

Record before the release: accepted for v0.101.0 by the owner on 2026-09-26; raised during v0.101.0 on 2026-09-26 from the root locks lane, whose report and independent review (`dev/v0101-tasks/report-rlock.md` and `dev/v0101-tasks/reviews/review-rlock.md`, 2026-09-25) both confirmed by reading the second of the two clauses [one-root-blocks-every-other-mount](one-root-blocks-every-other-mount.md) reported without re-verifying: a tool body that is not cancelled at unmount. The lane did not fix it. A source reading against `main` at `426f06e33`; not reproduced.

## What was seen

`run_tool` in `crates/chan-llm/src/mcp.rs` runs a JSON tool inside `spawn_blocking` and reads the request's cancellation token there twice: before it resolves the workspace (`:631`) and after (`:636`). It then calls `tools::execute` (`:639`), and nothing reads the token again. `ToolContext` carries only the workspace (`crates/chan-llm/src/tools.rs:69-71`), so neither `tools::execute` nor the tool it dispatches to (`tools.rs:247-259`) can see a cancel. `read_media_content` has the same shape: its checks are at `:656` and `:661`, and `read_media_content_sync` (`:664`) then runs to its end. The test `mcp_cancelled_request_does_not_resolve_or_write` (`:933`) pins a cancel that arrives before the body starts, the only case the code handles.

A cancel therefore stops only a tool that has not started. A body already running, a `list_files` or a `workspace_search` over a large tree for example, whose loops run inside chan-workspace (`list_tree_unified` at `tools.rs:313`, `workspace_search` at `:358`), runs to completion and holds its `Arc<Workspace>` until it returns. That handle owns the root's writer lock (the `_lock` field of `Workspace`, `crates/chan-workspace/src/workspace.rs:846`). A close of the root clears the workspace cell and then waits for that lock's release (`HostedWorkspaceRuntime::shutdown`, `crates/chan-library/src/host.rs:572-600`), and `wait_for_workspace_release` gives up after 5 s with `close_workspace: workspace flock still held 5s after teardown` (`host.rs:3930-3946`), so the lock stays held past the close until the body returns. The reindex pass has the same shape and takes a cancel flag checked at file boundaries for exactly this reason (the comment in `shutdown`, `host.rs:573-582`); a tool body has none. `crates/chan-llm/design.md` and `crates/chan-library/design.md` already say that a running tool body is not interrupted and can keep its workspace.

The lines above were read at `426f06e33`, as the Status says, and each holds there; they describe the code before the fix below. Checked again on 2026-09-27, some have moved since: at `37e9d23dd` `HostedWorkspaceRuntime::shutdown` is `crates/chan-library/src/host.rs:622-624` with its body in `shutdown_with_budget` (`:626-662`), `wait_for_workspace_release` is `:4503-4523` and its warning now reads `workspace writer lock still held at the teardown deadline` (`:4518`), the `_lock` field is `crates/chan-workspace/src/workspace.rs:865`, and `mcp_cancelled_request_does_not_resolve_or_write` is `crates/chan-llm/src/mcp.rs:1075`. This paragraph was added on 2026-09-27.

## Desired contract

Once its request is cancelled or its root closes, a running tool body stops at its next file or result boundary, answers `request cancelled` and drops its workspace, so a close waits on a tool body for at most one filesystem call, as it does for the reindex pass. A single blocking call is still not interrupted.

## What to do

Carry the request's `CancellationToken` into `ToolContext` and poll it inside the loops that can run long. The review names the search, the tree walks and `repo_report`; those loops live in chan-workspace, so they need a cancellation seam of their own, the way the reindex pass takes its flag. `read_media` reads one file in one call and keeps the checks it has. Establish whether a root's close reaches the tokens of the requests still running against it, which this reading did not. Red first: a test that cancels a request while its tool body is inside a walk and shows the body return before the walk ends; today it runs to the end.

## Boundaries

`crates/chan-llm/src/mcp.rs` (`run_tool`, `read_media_content`), `crates/chan-llm/src/tools.rs` (`ToolContext` and the tools), the chan-workspace calls those tools make where a loop needs the seam, and the cancellation paragraph of `crates/chan-llm/design.md`. The root locks and the close path in `crates/chan-library/src/host.rs` belong to [one-root-blocks-every-other-mount](one-root-blocks-every-other-mount.md), as does that item's other clause, the over-cap handoff reply.

## What shipped

Landed on 2026-09-28, with a fix round. The build is `dev/v0101-team/reports/report-Runtime-26.md` in the development tree; the independent review, on another model than the seat's, found no defect that loses data and asked for a fix round (`dev/v0101-team/reviews/review-Runtime-14.md`, with the lead's notes and rulings); the fix round is `dev/v0101-team/reports/report-Services-27.md`, verified by the lead at the blob. Lines are cited at `37e9d23dd`.

- **What carries the cancel.** `ToolContext` holds a private flag beside the workspace (`crates/chan-llm/src/tools.rs:70-73`). `ToolContext::new` gives it a flag that nothing sets (`:203-205`); the constructor that takes one, `with_cancel`, is private to chan-llm (`:218`), and `run_tool` is its caller (`crates/chan-llm/src/mcp.rs:649`). `run_tool` makes a flag for each JSON tool call (`mcp.rs:631`) and sets it in two ways: when the request's token fires while the body runs, a biased `select!` stores it and then waits for the body (`:669-676`); and when the request's future is dropped, a guard stores it from its `Drop` (`CancelToolOnDrop`, `:632`, `:683-691`), since the blocking body outlives a dropped handler. The body still checks the token before and after it resolves the workspace (`:636-643`).
- **Who reads it.** Only the three long tools hand the flag on: `list_files` (`tools.rs:331-338`), `workspace_search` (`:382-384`) and `repo_report` in each of its three scopes (`:404-412`). The tree walk reads it at each walked entry (`tree_entries`, `crates/chan-workspace/src/fs_ops.rs:2013-2016`); a report scan at each walked entry and before each counted file (`crates/chan-report/src/walk.rs:215-218`, `crates/chan-report/src/lib.rs:182-187`), where a stopped scan becomes the workspace's `Cancelled` (`scan_error`, `crates/chan-workspace/src/report.rs:270-277`) and leaves a cached report as it was (`crates/chan-workspace/src/workspace.rs:4323-4327`); and the search in its catalog's walk (`crates/chan-workspace/src/workspace_search.rs:975`), in a warm report's rescan (`:1005`) and before each seed (`:682-685`).
- **The twins, and which calls delegate.** Each walk, scan and search has one body, reached through a twin that takes the flag. The calls that take none delegate to their twin with `None`: `fs_ops::list_tree`, `list_tree_scoped` and `list_tree_prefix` (`fs_ops.rs:1867-1869`, `:1890-1892`, `:1920-1922`), `Workspace::list_tree_prefix`, `list_tree_prefix_unified` and `list_tree_filtered_unified` (`workspace.rs:1994-1996`, `:2012-2014`, `:2033-2035`), `report`, `report_if_available`, `report_for_prefix` and `report_for_files` (`:4319-4321`, `:4336-4338`, `:4365-4367`, `:4384-4386`), `workspace_search` (`workspace_search.rs:563-568`) and chan-report's `Index::scan` (`lib.rs:162-164`). One does not: `Workspace::list_tree_unified` still calls `list_tree` (`workspace.rs:1964-1966`) and meets its twin (`:1970-1975`) in `fs_ops::list_tree_cancelable` (`fs_ops.rs:1873-1878`), so the unscoped listing has one walk body too. A twin is public only where another crate calls it: `list_tree_unified_cancelable`, `list_tree_prefix_unified_cancelable`, `report_cancelable`, `report_for_prefix_cancelable` and `report_for_files_cancelable` (`workspace.rs:1970`, `:2018`, `:4327`, `:4371`, `:4390`), `workspace_search_cancelable` (`workspace_search.rs:579`) and `Index::scan_cancelable` (`lib.rs:168`). The others are private to their crate (`fs_ops.rs:1873`, `:1896`, `:1926`; `workspace.rs:2000`, `:2039`, `:4342`, `:4429`).
- **What a stopped body answers.** A body that fails while its flag is set answers `request cancelled`, as a cancel before the body does (`mcp.rs:651-660`, `:636-643`), and has dropped its workspace by then, since its `ToolContext` is a temporary of the call (`:646-650`). A body that finished answers its result even when its request was cancelled, so a write that landed is reported as landed (the comment at `:652-654`; `crates/chan-llm/design.md:69`). The flag's answer replaces any other failure of a cancelled body, and chan-llm does not log the failure it replaces (`design.md:69`): the review found it, and the fix round added no log, since the crate logs no request's failure. `read_media` keeps its two checks and a context whose flag nothing sets (`mcp.rs:699-709`).
- **The owner's question, answered: a root's close does reach the bodies running against it.** The close's teardown cancels the reindex, waits for the tenant's tasks with a grace of up to five seconds (`shutdown_with_budget`, `crates/chan-library/src/host.rs:626-630`; `TENANT_TASK_SHUTDOWN_GRACE`, `crates/chan-library/src/tenant.rs:215`, `:249-279`), and then drops the tenant's keepalive (`host.rs:633-636`), which holds the MCP bridge's handle (`crates/chan-server/src/lib.rs:1539-1545`). The handle's drop aborts the bridge's accept loop (`crates/chan-server/src/mcp_bridge.rs:248-252`), whose `JoinSet` owns every session it spawned (`:276`, `:294-299`). An aborted session drops its rmcp service, which cancels the token of each of its requests, and `run_tool` stores the body's flag (`mcp.rs:672-673`); that rmcp step was read in rmcp's own source by the build, the review and the fix round, and a test runs it (below). Only then does the teardown clear the cell and wait for the workspace's release (`host.rs:637-647`). Two delays stand between a close and the flag, and the documents name both: up to five seconds of the tenant tasks' grace before the sessions are aborted, and, when a peer closes its transport without a cancel notification, up to five seconds that rmcp drains the session's responses before its service drops and the token fires (`crates/chan-llm/design.md:67`; `crates/chan-library/design.md:34`; `design.md:101`; `crates/chan-server/design.md:11`; the bridge's module comment, `mcp_bridge.rs:17-27`). The peer's drain was read in rmcp's source and not run.
- **Where the desired contract is met, and where it is not.** The contract above asks that a close wait on a tool body for at most one filesystem call. That holds for a tree walk (`list_files`) and for a report scan (`repo_report`, cold or after a scope change): each reads the flag at every walked entry or before every counted file, and a counted file is read up to the report's 16 MiB cap (`crates/chan-report/src/count.rs:41-43`). It does not hold for a workspace search. The search reads the flag once per seed (`workspace_search.rs:682-685`), and a seed then runs all its hops, up to ten (`MAX_DEPTH`, `:24`, applied at `:750`), and its closure work with no read (`traverse_seed`, `:2025-2109`; `traverse_directory`, `:2111-2146`). Between the catalog's walk and the first seed, only a warm report's rescan reads it: the catalog's graph queries (`:985-1001`), the report's load or snapshot (`:1005`, `workspace.rs:4342-4360`), content retrieval (`workspace_search.rs:658-662`), entity matching (`:663`) and seed resolution (`:668-674`) run to their end, as does the last relationship query after the seeds (`:690`). So a close can wait on a search for a whole seed and for the work before it; that is raised as [a-workspace-search-stops-only-between-seeds](a-workspace-search-stops-only-between-seeds.md). `read_file` and `read_media` each read one whole file with no read of the flag (`tools.rs:289-294`; `mcp.rs:699-709`, `:727-730`); that is [an-mcp-read-loads-the-whole-file-before-its-cap](an-mcp-read-loads-the-whole-file-before-its-cap.md), accepted for this version. A cell lock wait, the write serialization lock wait before a report rescan (`workspace.rs:4466`), a single filesystem call and a whole write also run to their end. `crates/chan-llm/design.md:71` says all of this, and the search's own comment and the constructor's say the search's part (`workspace_search.rs:570-578`; `tools.rs:207-217`).
- **What is pinned, and how.** Each pin was shown red first at its own assertion, before its fix; the fix round's four pins guard hand-offs that already worked, so their red witnesses are mutations. At the loops: a flag set while the loop runs stops the tree walk at its next entry (`fs_ops.rs:2377`), the report's walk and its count at the next entry or file (`crates/chan-report/src/walk.rs:345`, `crates/chan-report/src/lib.rs:698`) and the search at its next seed (`workspace_search.rs:2802`), and a cancelled rescan keeps the cached report (`workspace.rs:11640`). Through MCP, a call held after its checks, cancelled by the client's notification and then released: `list_files`, `workspace_search` and a cold `repo_report`, whole and scoped by a prefix or by paths, answer `request cancelled` with the workspace dropped (`mcp.rs:2015`, `:2029`, `:2045`, `:2059`), and a write answers its result (`mcp_cancel_reports_a_successful_write_result`, `:2085`). A request whose future is dropped sets its body's flag with its token left alone (`:1977`). The bridge's handle, dropped as the teardown drops it, reaches the running body's flag, and the workspace and its writer lock are released (`mcp_bridge.rs:527`). The fix round's hand-offs: a scan of directories alone stopped in its walk (`lib.rs:672`), a cancelled report that skips the descriptor pacing, on Linux (`workspace.rs:11482`), the refresh after a report's initialization (`:11573`), and a search's report rescan (`:11602`). The hold the MCP pins use is a seam compiled for tests alone, behind `cfg(any(test, feature = "test-hooks"))` (`mcp.rs:804-809`) and enabled by chan-server's dev-dependency (`crates/chan-server/Cargo.toml:101-104`). The build ran 16 mutations: 15 each turned red exactly the pins they target, and one died compiling and was replaced. The fix round ran 7, each red at its pin and no other. The race pins passed 200 of 200 runs free and 200 of 200 on one CPU in each round.
- **What the pins do not show.** The MCP pins hold the body before its tool runs and release it once the flag is set (`mcp.rs:1955-1969`), so no walk is in progress when the cancel arrives: that a walk reads the flag at each entry is pinned by the loop pins alone, and the bridge pin's name says more than it runs. No real MCP client was driven, so whether clients send a cancel notification or close the transport, which decides between a stop at once and the peer's drain, is not known. The standalone `chan-llm-mcp` binary's end of input was read and not run: its `main` returns once the service ends (`crates/chan-llm/src/bin/chan-llm-mcp.rs:97-101`), and the review read that the stopping runtime can drop the request's future, which the guard now turns into the flag (inferred). No Windows binary was executed: the Windows arm was checked with clippy for the Windows target, and the bridge's pins are for Unix alone (`mcp_bridge.rs:313-315`). How long a close waits on a body in a real walk of a large root was not measured.
