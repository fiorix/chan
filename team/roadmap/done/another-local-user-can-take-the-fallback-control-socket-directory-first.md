# Another local user can take the fallback control socket directory first

Status: shipped in [v0.106.0](../../release/release-v0.106.0.md).

Record before the release: carried into v0.106.0 at the v0.105.0 GA on 2026-10-11, still raised for a decision.

Record before the release: raised for v0.105.0 by the owner's word of 2026-10-09, from the v0.101.0 release report's known gaps; written down, not designed, not accepted for build.

## What was seen

The [v0.101.0 report](../../release/release-v0.101.0.md) ends its Known gaps with: "Open by design, each stated in its item: the server's bind still creates the private socket directory where there is no runtime directory; another local user who creates `/tmp/chan-control-<uid>` first denies that user a control socket on such a box; and where the sockets moved, a server restart and a new terminal are needed". The item it names is [the-control-sockets-directory-is-believed-as-found](the-control-sockets-directory-is-believed-as-found.md), shipped in v0.101.0. This item takes the first two clauses, which are one exposure: the fallback directory has a fixed name under `/tmp`, the server's bind creates it there, and whoever creates it first owns it. The third clause is [a-terminal-from-before-the-socket-directory-moved-cannot-reach-its-server](a-terminal-from-before-the-socket-directory-moved-cannot-reach-its-server.md). The reports of v0.102.0, v0.103.0 and v0.104.0 do not mention either again: a search of the three for the directory's name, for "socket directory" and for "runtime directory" finds nothing.

What the closed item records, in its "What shipped" and "What an upgrade costs": a runtime directory that is unset, empty or fails the owner rule falls back to `/tmp/chan-control-<uid>`, "created with the mode 0700 when it is missing and validated"; `chan`'s discovery validates the fallback and never creates it, while "the server's binds still create it"; and "on a machine without `XDG_RUNTIME_DIR`, another local user who creates `/tmp/chan-control-<uid>` first denies that user a control socket: the server logs the rejection and runs without one, and since no client connects in a directory that is not its user's own, that other user receives none of its requests".

The shape came from two rulings. The owner's, of 2026-09-29 (the closed item's "Owner ruling"): a per-user fallback directory that only its owner can use where `XDG_RUNTIME_DIR` is unset or fails the rule, "so that a devserver on a default macOS setup still starts". The lead's, of 2026-10-02 ("What shipped"), "made under the owner's standing word and left for the owner's review": a tenant whose fallback fails too "runs without a control socket, where the plan had recommended that the devserver refuse to start". No record read for this item shows the owner's review of that second ruling.

The released tree `af2af8ac0` still has that shape, read at source and not run. `unix_socket_dir_from` uses an `XDG_RUNTIME_DIR` that passes the rule and otherwise the fallback under `/tmp`, logging a rejected fallback and returning its path all the same (`crates/chan-server/src/mcp_bridge.rs` lines 66 to 91). `ensure_control_socket_dir` creates a missing directory with mode 0700 and then requires a real directory, owned by the effective user, with mode exactly 0700 (`crates/chan-shell/src/control_dir.rs` lines 18 to 75). `chan`'s discovery validates the fallback and passes over a missing one (`crates/chan/src/control.rs` lines 46 to 66). The comment above the endpoint picker says why the name is short and fixed: "macOS caps `sun_path` at 104 bytes, so the suffix and the fixed private `/tmp/chan-control-<uid>` fallback keep the full path short" (`mcp_bridge.rs` line 48). `crates/chan-server/design.md` (the entry "Local control sockets") says that when the fallback also fails, "binding logs `control socket bind failed at <path>: <reason>` and the tenant continues without a control socket or `$CHAN_CONTROL_SOCKET`; MCP bridge failure is also logged and that bridge is absent", and the changelog's v0.101.0 section says that `cs` then does not work in that server's terminals (`CHANGELOG.md`, the entry "The owner-only socket directory refuses two more cases").

Platform, and what is not established: the exposure needs a Unix machine with a second local user and no usable `XDG_RUNTIME_DIR`; the closed item's owner ruling says `/tmp` is the socket directory by default on macOS. It was never run. The closed item ends with what was "Not run on any machine", among it "a native macOS run with its socket path length budget and its moved directory, a second local user, and a hosted user unit", and the v0.101.0 report's Known gaps say the team made "no run as a second local user". So the denial, the log line and the missing socket are read from the code and the documents and were not observed with two users. Not established either: what the denied user sees in the product, since a log line is the only signal the records name; how that user recovers; and whether the first clause carries any harm of its own, since the record states the bind's creation of the directory as a fact and names no consequence beyond the second clause.

## Desired contract

On a machine with no usable runtime directory, another local user cannot silently keep a user from having a control socket. The item asks the owner for a decision among: keep the shipped shape (the server logs and runs without a control socket), now confirmed; keep it and tell the user in the product that the socket is absent and why; refuse to start, as the plan had recommended; or place the fallback where another user cannot create it first, which the closed item's "What to do" names as "a directory of its own under the user's home".

## What to do

Reproduce first, in a guest with two local users and `XDG_RUNTIME_DIR` unset: the second user creates the first user's fallback directory, the first starts a server; record the log line, the absent socket, what `cs` prints in a terminal of that server, and what the second user can and cannot receive. Repeat it on macOS if a machine is offered, since that is where the fallback is the default. Then put the choices to the owner with what each costs: a loss of `cs` and of the MCP bridge that only a log reports, a notice, a server that will not start, or a longer socket path measured against the 104-byte limit the code's comment names.

## Boundaries

`crates/chan-server/src/mcp_bridge.rs`, `crates/chan-server/src/control_socket.rs`, the control socket's start in `crates/chan-server/src/lib.rs`, `crates/chan-shell/src/control_dir.rs` and `control.rs`, `crates/chan/src/control.rs`, their tests, the two design documents, and the help texts that name the directory (`crates/chan/src/help.rs`, `crates/chan-shell/src/cli.rs`). The owner rule itself is not weakened: a real directory, the effective user's, mode 0700, on the bind and on the connect. The handoff's sockets and Windows' named pipes are outside. A change of the directory's place is a second move of the sockets and carries the cost the sibling item describes.

## Acceptance

1. A two-user reproduction on Linux, recorded: the directory made first by another user, the server's log line, the absent `$CHAN_CONTROL_SOCKET`, `cs`'s words, and a proof that the other user receives no request.
2. The owner's decision among the four choices is recorded in this item in the owner's words, with its date.
3. If a notice is chosen: the user is told in the product, and not only in a log, that the control socket is absent and why; pinned red first.
4. If the server refuses to start or the fallback moves: pinned red first with a directory another user owns; the socket path stays within macOS's limit, pinned with a long home directory; discovery, `cs` and the MCP proxy find the new place; the design documents, the help texts and the changelog say it.
5. The owner rule's existing pins stay green.
6. The owning guest's fmt, clippy and whole crate suites are green at each commit.

## The notice's design read 2026-10-13

The runtime seat's design (`dev/v0106-team/reports/design-Runtime106-sockfb-notice.md`): one optional spawn variable, `CHAN_CONTROL_SOCKET_ERROR`, set for newly spawned terminals when the control socket failed to bind, carrying the original bind refusal with the existing length hint, so the directory another user owns and the sibling item's over-long path share one shape; the key reserved in the spawn list, so an inherited value is scrubbed and a caller's override refused; `cs`, for `CHAN=1` with a missing or blank socket, printing `this chan terminal has no CHAN_CONTROL_SOCKET; its spawn environment reports a server bind failure: "<detail>"; see its start-up log`, the detail debug-quoted, and today's generic sentence when the variable is absent, blank or unreadable. Review106 (`reviews/review-Review106-sockfb-notice-design-1.md`) read it against the source: yes to the route (the one channel that exists exactly when the socket does not), to the attribution (a report of the spawn environment, never the server's present state, resting on the same trust as `CHAN=1`) and to the pins (the real validator's refusal against a directory another user owns, read back from a real PTY), with five amendments, all ruled in. A1: the diagnostics fixture's parent must see its child run (a child whose exact name matches no test exits 0 and the parent passes; found on the sibling range): after the status check the parent requires the child's output to hold one passed test, with the name changed in one caller as its mutant. A2: the test seam sits at the directory's choice, upstream of the validation the bind runs itself, under `cfg(test)` with its callers. A3, the lead's ruling: one path on every platform, as the review recommends; the server sets the variable wherever a bind failed and `cs` reads it wherever it runs, with no platform gate in the producer or the three readers; the item's "Windows' named pipes are outside" is about the fallback directory, which this does not touch; neither shape is run on Windows by this team and the documents say so. A4: the shell's design sentence keeps the two shipped statements the replacement dropped (the outside-caller sentence without the marker; a missing window id taking precedence) and says both long-lived cases (a shell spawned under a failed bind keeps printing its spawn report after the server later binds; a shell spawned with a socket prints the stale-socket words and no reason after a restarted server fails its bind). A5: the detail is built once where the socket starts and logged followed by the consequence, so the logged line and the terminal's text are one string by construction; one field of three states in place of two options is the author's choice. For the record of this item's boundaries: the reason travels through the terminal registry's configuration in `crates/chan-library/src/terminal_sessions.rs` (and that configuration's literals in the crates' tests), the necessary carrier, since the socket's own path reaches the PTY through it and the reserved-key list lives there; the Boundaries section above is read as including it.

## The notice built, reviewed and landed; its notes ruled 2026-10-13

The runtime seat built the notice the design read accepted, in three commits, and the review seat read them (`reviews/review-Review106-sockfb-notice-range-1.md` in the round's bus): they can land, with no finding against the code or the pins. What is built: when a tenant's control socket cannot bind, every terminal that server spawns afterwards gets `CHAN_CONTROL_SOCKET_ERROR` holding the bind failure's reason and no `CHAN_CONTROL_SOCKET`; `cs` in such a terminal answers "this chan terminal has no CHAN_CONTROL_SOCKET; its spawn environment reports a server bind failure: <the reason, quoted>; see its start-up log"; a blank or unreadable report keeps the older sentence, and a usable socket ignores a report. The server sets or removes the variable on every spawn after the caller's own entries, and the route refuses a request that names it, so at spawn no terminal holds both and none holds another server's report. A shell keeps what it was given, which is the limit the shell's design text states: the report is what the spawn environment said and is never certified as the server's present state. The server keeps serving.

Evidence.
