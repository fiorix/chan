# Basic flows break with no end-to-end check to catch them

Status: shipped in [v0.128.0](../../release/release-v0.128.0.md).

Record before the release: raised by the owner on 2026-11-11 and accepted for v0.128.0 the same day; built on 2026-11-11 (the audit, the Chrome arm and the WebKit arm; the suites run at each milestone, with two follow-ups named in the Built section). His words: "we will also need to run the browser smoke tests and end-to-end tests; perhaps we may even need new ones because we've recently broke very basic functionality such as pasting images into the rich prompt and into the editor".

## What is there now

- The breakage: v0.127.0 fixed an image paste into the editor and the Rich Prompt that was lost on chan-desktop (`898474c75`, fix(editor): recover empty WebKit image pastes natively). WKWebView advertised Files in the clipboard event but exposed no items and no files, so the paste did nothing, while Chrome exposed the image and pasted it. The fix reads the image through the desktop IPC and uploads it as PNG; its tests are mounted vitest cases (`web/packages/workspace-app/src/editor/bubbles/image_drop.clipboard.test.ts`, `components/RichPrompt.svelte.test.ts`). A release earlier the ghostty image paste ([done](../done/ghostty-drops-an-image-paste-and-swallows-control-v.md)) had the same shape: a basic flow broken on one backend, found by the owner on his Mac.
- The browser suite (`scripts/e2e/browser-smoke/`, 119 checks at `8e41a9264`) drives Chrome through puppeteer-core against a debug `chan serve`; it is outside the gate and runs by judgment in an isolated guest (`.agents/skills/gate/SKILL.md`, "The browser smokes are outside the gate, deliberately"). Which basic flows it covers, and which it covers in Chrome alone, has not been listed; the WebKit breakage above passes every Chrome check.
- The desktop guest (`dev/hn-tmux-rig/chan-e2e-desktop.sdme`, `guest-desktop.sh`) builds chan-desktop on WebKitGTK and was written for the WireGuard arms (`scripts/e2e/desktop-wireguard.sh`); as far as read, nothing drives a paste, a drop or typing into its webview today. The audit below confirms or corrects that reading.

## Desired contract

1. An audit lists the basic flows and what checks each end to end today, with the engine each check runs on: pasting and dropping an image into the Rich Prompt and into the editor, typing and saving in the editor, a terminal's input, output and paste on both backends, opening a file, the search, the panes. The audit's list is this item's scope and is recorded in this item.
2. Each flow the audit finds without an end-to-end check gets one that goes red on the broken code and green on the fix, in two arms: a browser arm under `scripts/e2e/browser-smoke/checks/` in Chrome, and a WebKit arm on chan-desktop (WebKitGTK) in the desktop guest. Each check names the engine it runs on in its header and in its output.
3. The image paste into the Rich Prompt and into the editor is covered in both arms. The WebKit arm's check is red at `898474c75^` and green at `898474c75`, or the item records why WebKitGTK does not reproduce WKWebView's clipboard shape and the check then drives the fix's path with the clipboard shape that failed.
4. The whole browser suite and the end-to-end suites run on `v0128/int` at each milestone of this release, not only the new checks, with the results on the bus and in the release record.

## Boundaries

- Checks and the guest runner. A product defect a new check finds gets its own row and is not fixed here.
- The browser suite stays outside the gate; its README's graduation rule stands.
- WebKitGTK stands in for WKWebView. What only WKWebView shows stays an owner check on macOS, batched per milestone.

## Acceptance

1. The audit's table in this item: flow, unit or mounted tests, browser check and engine, WebKit check, gap.
2. For each gap, the new check green at the integration tip and shown red once on a deliberate break (the fix reverted or a mutation), with the red's output kept with the round's evidence; `make e2e-check` and `make browser-smoke-lib-test` green.
3. The whole browser suite green in an isolated guest at the integration tip, and the WebKit arm green in the desktop guest, each with its results file on the bus.
4. `scripts/e2e/README.md` and the browser suite's README list the new checks and the WebKit arm's run recipe.

The checks this item adds, from the audit's recommendation:

- Browser arm, Chrome, one check per line beside 212: an image pasted into the Rich Prompt and into the editor from the browser's own clipboard (a trusted paste through the devtools protocol's paste command), asserting the embed, the file on disk and, for the Rich Prompt, the delivered path in the terminal's scrollback; an image file dropped into both (a trusted drop through the devtools protocol, a synthetic DragEvent as the named fallback), asserting the embed, the file and the page's URL unchanged; a text paste into a terminal on both backends by chord and by the menu's Paste row under bracketed paste; typing and saving in rich text and in source mode with a reload; a search whose hit opens its file. Chrome never produced the failing shape, so these are shown red by a mutation of the code they guard, not at `898474c75^`.
- WebKit arm, chan-desktop on WebKitGTK in the desktop guest: one `basic-flows` driver under `scripts/e2e/desktop-observations/` with that directory's exit contract (0 held, 1 fault, 2 unrunnable, 3 inconclusive), each verdict line naming the WebKitGTK version, and a `flows` arm in the guest runner; the guest's rootfs gains openbox, xdotool, x11-utils, imagemagick, xclip and the GTK typelib for a drag source. Its arms, in order: the X clipboard seeded with a PNG and the failing clipboard shape dispatched on the real page through the inspector, so the real IPC, capability grant, clipboard read and upload run, red at the SPA of `898474c75^` and green at `898474c75`, with a text-only clipboard as the control; the same paste by a trusted Ctrl+V through xdotool, recording the shape WebKitGTK hands the page; a drop from a GTK drag source and a synthetic drop; terminal input, output and text paste per backend; typing and saving in both editor modes; opening a file, a search hit and the panes.

Rulings taken on the audit's open questions (lead, 2026-11-11): the injected WKWebView shape on the real WebKitGTK engine is this item's WebKit red proof, as contract 3 allows, and the trusted-paste arm records the engine's own shape for the record; the Chrome arm is proven red by mutation only, with no leg that emulates the desktop bridge in Chrome; the rootfs change is made in the guest definition and the image rebuilt; the `basic-flows` driver joins the whole-suite run on the integration tip at each milestone; if WebKitGTK does not map Ctrl+Shift+V to a paste, terminal paste by chord on the Linux desktop is a defect that gets its own row; a WebView2 arm on the Windows VM is a follow-up, not this item; the Mac's own Cmd+V and a Finder drop of an image into the editor and the Rich Prompt, where the bug lived, go to the owner in the milestone's batch of Mac checks. The three devtools capabilities the Chrome arm relies on (a file in a dispatched drag, the paste command on a key event, an image on the clipboard reaching a paste as a File) are confirmed on the first run and the check adapts if one is absent.

## Built, 2026-11-11

The audit above is the item's first deliverable; the two arms it recommended are built and run at each milestone.

The browser arm closes the audit's Chrome gaps with five checks, each shown red by a mutation of the code it guards, since Chrome never produced the WebKit failure: 214 and 215 paste and drop an image as Chrome's own trusted input (the devtools paste command and drag events) into a workspace document, a draft and the Rich Prompt, and read the image on disk and the path the Rich Prompt delivers to a terminal; 216 pastes text into a terminal on xterm.js and on ghostty by Ctrl+Shift+V and by the body menu's Paste row and reads the PTY's bytes through the raw recorder, once and bracketed, with xterm.js sending a line break as CR and ghostty as LF; 217 types and saves a document in its rendered view and in source, on the live document session and on the classic autosave, and reads the file and both views after a reload; 218 opens a search's content hit with Enter and a tag hit with a double-click. Each names headless Chrome and returns its version, and each passed ten runs alone and in a selection with the checks it neighbours (94, 203, 207, 209, 54, 174, 110). Stage 0 repaired checks 155, 90 and 98 beside them. The editor's own menu Paste row has no browser check.

The WebKit arm is `scripts/e2e/desktop-observations/basic-flows.sh` with its page runner `basic-flows.mjs`, run on chan-desktop's WebKitGTK (2.52.6) under Xvfb in the desktop guest; every verdict line names the engine and the page's user agent. It drives nine groups by X input and the engine's inspector: `native` (the WKWebView empty-Files paste shape injected, the desktop's clipboard read and upload real), `trusted` (a real Ctrl+V under three clipboard owners), `drop` and `xdnd` (a synthetic and a real file drop, and a real drop outside every zone), `terminal` (typed input and output, and a text pasted by Ctrl+Shift+V and by the menu into a bracketed-paste reader, on xterm.js and on ghostty), `editor` (typing in a note's rendered and source modes until its file holds it, under document sessions and with them off, then a reload), `open` (a double-click on a Files row), `search` (a typed query and its hit opened by Enter) and `panes` (a split by chord, a focus by click, a tab drag and a close by chord). Each group was shown red by a web-only mutation of the code it guards (the native read, the drop branch, the paste chord, the menu paste, the session push, the autosave, the row open, the hit open, the split) with its controls held, and green at the tip; `native,drop,terminal,editor,open,search,panes` passed five consecutive runs and is the green selection. Its readings settled two questions and found two faults: WebKitGTK fires a paste for Ctrl+Shift+V on both terminal backends, so terminal paste by chord works on Linux; chan binds no Ctrl+S by design; a real Ctrl+V of an image hands the page an empty clipboard, so image paste by chord lands nothing on the Linux desktop (its own row, drafted); and a real file drop hands the page a URI rather than a file and, outside a zone, navigates the window to it (its own row, drafted), which is why `trusted` and `xdnd` stay red until those rows land.

At the milestone 2 tip de11ad173 (acceptance 3): the whole browser suite ran 123 checks, 118 green; the five failures fell inside an eleven-minute window of another guest's test load and four passed alone (177, 181 and 214 environment; 213 a check defect, its root found by the card colour, which a pending directory's grey disc shares when the workspace is shared across checks: a repair follows), while 198 (Hybrid Nav tmux) failed a third time at the split after a window resize on unchanged code and is under investigation. The desktop flows' green selection held 24 of 24 with 6 controls, and the all-groups run showed only the nine faults of the two drafted Linux rows. Both READMEs list the checks and the WebKit arm's run recipe (acceptance 4). The suites run again at each later milestone.
