# cs session lists the clients of a library and detaches one

Status: shipped in [v0.109.0](../../release/release-v0.109.0.md).

Record before the release: built on 2026-10-23 on the owner's branch; the section Built 2026-10-23 holds the evidence; it closes at the GA as shipped.

## What was asked

The owner's word of 2026-10-23, bringing the build to the round: "done with both patches, 1 for the pty resize, 1 for the `cs session` and being able to identify a client to detach other clients when needed". A library served to several frontends (desktop processes, browser tabs) has no command that names the clients attached to its windows or disconnects one of them, and the workspace's `session` commands act on the window-based leadership roster only.

## Desired contract

- `cs session list [--json]` lists the frontend clients across every workspace and standalone terminal tenant of the serving library: a stable client id, the holder, a display name, live, disconnected or detached status, connection times, and each connection's tenant, window, transport, PTY id and last requested grid. `cs session info ID [--json]` shows one client's connections in full.
- A client is a holder claim (`h` on a socket, `x-chan-holder` on HTTP) grouping its connections; a desktop process uses one holder across its windows, browser windows opened together share their opener's, a direct browser tab keeps one through reloads, and an untagged socket caller is a client of its own. The holder is an operational claim and no authentication authority.
- `cs session self [--name NAME|--reset]` resolves the clients attached to `$CHAN_WINDOW_ID`: one resolves at once; with several, an interactive invocation shows an Identify this client card in the frontends, and a script passes `--id ID`. The identification is bounded, exits 124 on timeout and is dismissed by the caller's EOF.
- `cs session detach ID` revokes that holder's event, terminal, document and drawing connections across the library without removing a window, a layout, a PTY or a running program; later socket admissions close with code 4001, its HTTP requests to a workspace or terminal window's routes carrying the holder are refused with 409 after authentication, and its frontend stops retrying and offers Reconnect, which resumes the holder through `POST /api/session/resume` and reloads the view. Revocations and the roster live in memory for the server process's lifetime.
- `session handover` and `takeover` keep their window-based leadership meaning and stay workspace-only; `list`, `info`, `self` and `detach` run on both tenant kinds.

The owner's word of 2026-10-23 on naming, after the lead set out that the build left no command to show or set a window's participant name (the name on a collaborator's caret, given to extensions and in handover messages): "let's do the cs session self --name X part and leave the desktop setting alone, we can add that as an item in the roadmap for the next version". So:

- `cs session self --name X` sets one name: the calling client's and, in a workspace window, the calling window's participant name. `--reset` returns both to their defaults (the client to its generated name; the participant to its gateway identity, else its generated name). A bare `cs session self` shows the client (id, holder, name, status, connections) and, in a workspace window, the participant (window, name, role, leadership).
- A name is refused, with nothing renamed and a message naming the reason, when after trimming it is empty or longer than 64 characters, when it holds a control or format character (Unicode categories Cc and Cf, zero-width and bidirectional controls among them), or when it equals, ignoring case, the name of another live client of the library or of another participant of the window's tenant; the refusal names the client id or window holding that name. Generated default names are unique.
- A chan-desktop setting for the name is a later version's row.

The lead's rulings of 2026-10-23, on the review seat's reading of the build:

- **The roster's retention.** A client record whose holder is untagged leaves the roster when its last connection ends, unless it is detached. A tagged client whose connections have all ended stays listed as disconnected; when a new client is admitted at the bound of 4,096 records, the disconnected record with the oldest last activity that is not detached leaves the roster, and admission is refused only when every record is live or detached. A detached record never leaves the roster, so a detach holds for the server process's life. A holder whose record has left is a new client when it returns, with a new id and a generated name.
- **The detached holder's HTTP refusal.** On the protected workspace and terminal tenant routes (`/api` and `/ws`), an authenticated request carrying a valid detached `x-chan-holder` is refused with 409, except `/api/session/resume` and a WebSocket upgrade (`GET` with `Upgrade: websocket` and `Connection: upgrade`) on one of the event, terminal, document and drawing socket routes; those sockets refuse the holder themselves with close code 4001. A request carrying no holder is never refused for one.
- **The refusal's scope.** The 409 applies to the workspace and terminal tenants' routes, where a detached page's reads, writes and autosaves go. The library's own routes (the launcher, the window feed, library commands) do not consult the roster: a desktop client's launcher has no Reconnect cover and stays usable, and a window it opens is refused at its sockets. The design text states this scope.
- **A lost identification frame.** The server keeps, per window, the identification requests still pending (a `cs session self` waiting on its card), removed when the request ends by an answer, its timeout or the caller's EOF. The window's event socket sends `{"type":"session_identify_sync","request_ids":[...]}`, the window's pending request ids, empty included, on every attach of a socket that names its window and at every lag recovery, beside the survey snapshot. A socket forwards a request's start only while the server still holds that request, so a start broadcast before a sync and delivered after it never shows a request the sync no longer lists. The page keeps every pending identification of its window, in arrival order, and shows them one card at a time: a start adds its id, an end removes it, a sync replaces the set with its list, and the card shows the first pending id; each answer is keyed by its own request and sent once, so a card never outlives its request across a dropped or lagged socket, a live request survives a reconnect, and a second pending request shows when the first ends. An answer the server accepts keeps its card locked until the request's end frame or a sync that no longer lists it, the two points after which the socket carries no start for that request; an answer that fails releases its card and reports the error, and a later sync shows the card again while the server still holds the request.
- **The detached cover** says that a detach ends this client's connection and is not a sign-out (no credential is cleared), and makes no claim that a native desktop window never shows it.
- **Ignoring case.** Two names are equal ignoring case when their Unicode full case foldings are equal (the C and F mappings of Unicode 15.0.0, the version of the Cf table), applied per character with no normalization; a name keeps the spelling it was given.
- **Generated names.** A new client's generated name is drawn against every client record's generated and effective names, as a participant's is against every participant's. A reset passes the clash check of a rename on the name it restores, except a participant's gateway identity, which one person's windows share; a refused reset changes neither name.
- **A workspace window with no participant.** A client can be attached to a workspace window before its event socket joins or after the participant has left. A bare `cs session self` there shows the client and says the window has no joined participant; `--name` and `--reset` there refuse with nothing renamed. The reply names its tenant kind, `"tenant":"workspace"` or `"tenant":"terminal"`, beside `participant`, so a reader tells that absence from a standalone terminal's.

## Boundaries

Detach is an operational disconnect, not a credential revocation or a device ban: the detached client's own Reconnect resumes it. No persistence of the roster across a server restart. The leadership roster is unchanged.

## Acceptance

1. The registry's, the control session's and the routes' tests and the CLI output integration tests pass; each command behaves as the contract states on a workspace and on a standalone terminal tenant.
2. A detached client's sockets end and its retries stop, its tagged HTTP requests are refused, another client's PTY, program and layout survive and stay usable, and Reconnect resumes it.
3. The combined gate passes at the landed commit, `make web-check` included, and the browser suite passes whole and with every check alone at the frozen commit that ships.
4. Manual use on a desktop or over SSH is not exercised, by the owner's word of 2026-10-23: "there will be no rc and no manual testing in this round, we're going from here to ga, tag and release". An automated driver runs Acceptance 2 through an SSH forward to a devserver in a guest and on the Linux desktop under Xvfb.
