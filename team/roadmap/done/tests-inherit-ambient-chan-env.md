# Tests ignore ambient Chan terminal state

Status: SHIPPED in [v0.84.0](../../release/release-v0.84.0.md).

- `make pre-push` cannot pass from inside a chan terminal, because tests read the `CHAN_*` variables chan exports to its own terminals instead of a controlled environment. Two instances are confirmed by unsetting one variable at a time. `tests::devserver_tunnel_url_has_no_domain_default` (`crates/chan/src/lib.rs:8578`) asserts `tunnel_token == None` after `Cli::parse_from(["chan", "devserver"])`, but the arg is declared `#[arg(long, env = "CHAN_TUNNEL_TOKEN")]` (`:646`), so a tunnelled devserver's token is parsed in and the assertion fails; worse, the assertion message renders the received value, so a real `chan_pat_` credential is printed into the gate log, CI output, or any pasted capture. Separately, `close_remove_forgets_an_unserved_workspace` and `close_tears_down_the_separate_serve_process` (`crates/chan/tests/open_close.rs`) fail with "not registered" and a missing `writer.lock` record whenever ambient `CHAN_HOME` is set, and both pass with `CHAN_HOME` alone unset. Neither state is clean, which is what makes this more than a harness annoyance: with `CHAN_HOME` set the two `open_close` cases fail, and with it unset they pass but resolve the devserver home relative to the working directory, so a `cargo test` run writes a real `devserver/` home, complete with `config.toml` and per-workspace registry entries, into `crates/chan/` in the source tree. The likely shape is a shared test harness that clears the whole `CHAN_*` namespace and then points `CHAN_HOME` at a per-test throwaway, so neither the ambient environment nor the repository can be read or written, plus never rendering a secret-bearing value in an assertion. The gate is Linux-native and single-process, so this is the same family as the wall-clock hazards `timing-test-virtual-clock` closed, but the trigger is ambient environment rather than host load.
