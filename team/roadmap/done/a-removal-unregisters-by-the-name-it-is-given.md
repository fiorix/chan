## What was seen

- **The removal acts by the name it is given.** It resolves the name to a key, closes the workspace runtime whose canonical root is that key, and learns the root that runtime was opened at, or, with no runtime, the stored root of the registry row the name matches (`remove_workspace_for_root`, `crates/chan-library/src/host.rs:3434-3455`; `close_workspace_for_root_locked`, `:3357-3414`, the runtime's root at `:3371-3372`, the row's at `:3386-3392`). It forgets the overlay's rows under the key and that stored root (`:3465-3467`; `overlay_spellings`, `:4658-4664`), but purges the window records stored under the key or under the name (`:3472`; `workspace_window_ids`, `:4707-4721`) and unregisters by the name (`:3476-3491`; `unregister_registered_workspace`, `:4693-4697`).
- **The registry matches a name to a row by the row's cached canonical path, or by resolving the other rows' stored roots again** (`Library::unregister_workspace`, `crates/chan-workspace/src/library.rs:278-298`; `match_root`, `:556-565`; `alias_candidates` and `position_matched`, `crates/chan-workspace/src/registry.rs:345-374`). A load primes each row's cache to its stored root, and only a registration that finds the row refreshes it (`registry.rs:268-271`; `touch_matched`, `:384-391`).
- **So no name reaches a row that the boot restored and no registration has touched since, once its stored root resolves to another registered workspace's folder:** the folder the workspace was mounted from matches no row, and the stored root, resolved again, matches the other workspace's row. The desktop's forget names the runtime's canonical root in that case, by the lead's ruling, and the row stays registered and off with `NotFound` answered, which a pin holds as the code has it and which this item's fix turns red (`desktop/src-tauri/src/main.rs:9920`, the third assertion with its comment; `desktop/design.md:130`). At the fix round's base, where the forget named the stored root, the builder's probe showed the forget unregistering the other workspace, `Ok(Completed)` (`dev/v0101-team/evidence/Services/s37-f1-base.log`).
- **The launcher's delete names the row's stored root** (`handle_remove_workspace`, `crates/chan-server/src/routes/library.rs:2037-2062`, the root at `:2045`, from `resolve_workspace`, `:1756-1758`), so for the same row it hands the host a name that resolves to the other workspace's folder: by the lines above the removal would close that workspace's runtime if one is mounted, purge its windows and unregister its row. Read and not run; the review of the desktop's half named it as the host's older behaviour, shared with the launcher's delete (`dev/v0101-team/reviews/review-Services-17.md`, F1). `v0.100.0` has the same shape, a delete by the row's root and a removal by the name (`routes/library.rs:1931-1936` and `crates/chan-library/src/host.rs:2857-2894` at `v0.100.0`).
- **The purge by the name leaves windows.** A forget handed to the desktop of a relinked root that is not mounted names the resolved path, since no runtime goes by it, and the windows stored under the registered path, where the desktop stores them, stay in the window store (`main.rs:3048-3050`, `:3057-3058`); the removal holds that row's stored root there and forgets the overlay's rows by it, and does not purge by it (`host.rs:3386-3392`, `:3465-3472`).

## Desired contract

A removal unregisters the registry row of the workspace it closed or found, by that row and not by the name it was given, and purges the windows stored under that row's stored root as well as under the name; a name that resolves to another registered workspace's folder never forgets that workspace.

## What to do

As the lead recommends: the removal unregisters the row of the runtime that it closed, or of the row it found with no runtime, and purges by that runtime's or that row's stored root. The builder's reading is that this needs a call of chan-workspace that removes a row by its stored root without resolving it again (`followup-Services-Lead-22.md`, "Options", 1). Settle in the plan what the launcher's delete and the devserver's forget name, and whether a removal whose name and row disagree is refused; the plan reads [forgetting-a-relinked-root-waits-four-lookups](forgetting-a-relinked-root-waits-four-lookups.md), accepted for v0.102.0, which counts the registry lookups that the same removal makes for a relinked root. Red first: the desktop's pin of the forget of a restored root relinked onto another workspace (`main.rs:9920`), whose third assertion turns red, and a launcher delete of such a row leaving the other workspace registered and mounted, with the probe's patch as the shape (`dev/v0101-team/evidence/Services/s37-probe-f1/probe.patch`).

## Boundaries

`crates/chan-library/src/host.rs` (`remove_workspace_for_root`, `close_workspace_for_root_locked`, `workspace_window_ids`), the call of `crates/chan-workspace` that the plan settles, the desktop's pin that holds the cost, their tests, and `crates/chan-library/design.md` and `desktop/design.md` where they say what a removal names.

## Acceptance

1. A forget of a restored workspace whose stored root was pointed at another registered workspace's folder while it was mounted unregisters that workspace's row and leaves the other one whole, pinned red first.
2. A launcher delete of such a row does the same, pinned.
3. A removal purges the windows stored under the stored root of the row it removed, whether or not the workspace was mounted, pinned.
