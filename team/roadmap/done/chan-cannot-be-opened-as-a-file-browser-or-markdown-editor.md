# chan cannot be opened as a file browser or Markdown editor

Status: shipped in [v0.128.0](../../release/release-v0.128.0.md).

Record before the release: raised by the owner on 2026-11-09 and accepted for v0.128.0 the same day; in build since 2026-11-11 (the open-path request and the launch's arguments first; the verb's name chosen by the owner, below).

## What is there now

- **`cs open` already does the work, inside chan.** In a standalone window (a terminal window with no workspace behind it, `WindowKind::Terminal`, `crates/chan-library/src/windows.rs:4-5`), `cs open PATH` (`crates/chan-shell/src/cli.rs:1187-1216`, `ControlRequest::OpenPath`) reaches `open_path_standalone` (`crates/chan-server/src/control_socket.rs:5471-5483`): a directory opens the file browser, a text file the editor, any other file is revealed in its directory, and a missing path is created empty and opened in the editor (`standalone_open_target`, `:5360-5418`). From a workspace window a path outside the root goes to a standalone window that is reused or created and raised (`WorkspaceHost::open_outside_workspace`, `crates/chan-library/src/host.rs:4072-4168`). The standalone window's file surface is a mount rooted at `/` that starts in `$HOME`, and it exists on Unix only (`crates/chan-server/src/lib.rs:1111-1199`).
- **Nothing outside chan can ask for it.** `chan open` is a visible alias of `chan serve`, which serves a directory as a workspace (`crates/chan/src/cli.rs:56`, `crates/chan/src/help.rs:705`), and `--standalone` means a server that skips the desktop and devserver handoffs, not a standalone window (`cli.rs:547-554`). The desktop's handoff socket accepts `OpenWorkspace` and `OpenTerminal` and nothing that opens a path (`crates/chan-server/src/handoff.rs:82-90`, `:214-226`). `chan-desktop` reads no positional path: a `%U` argument boots the GUI and is ignored (`desktop/src-tauri/src/terminal_mode.rs:46-50`, `:310-325`), or, with a desktop already running, is dropped by a launch that asks that desktop to come forward and exits (`desktop/src-tauri/src/single_instance.rs`); there is no deep-link plugin.
- **Linux.** The packaged entry `packaging/distros/shared/chan-desktop.desktop` (installed by the deb, Fedora, AUR and Nix packages) has `Exec=chan-desktop %U` and the `TextEditor` category but no `MimeType=`; the AppImage uses Tauri's default template, `Exec=chan-desktop` with no field code. Nothing registers chan for `inode/directory` or `text/markdown`, so `xdg-open` never picks it, and a manual association would deliver a path the desktop ignores.
- **macOS.** The bundle declares no document types (`desktop/src-tauri/tauri.conf.json:42-45`, no `CFBundleDocumentTypes` or `fileAssociations`), and the desktop handles no open-file event (`RunEvent::Opened` is absent, `desktop/src-tauri/src/main.rs:6055-6118`), so chan cannot be chosen in Finder's Open With or set as the default app for Markdown.
- **Windows.** No file associations, and no standalone file surface to open into.
- **A second desktop process no longer runs beside the first; fixed in v0.127.0.** The owner met it on 2026-11-10 as a `tmux -CC` window on a devserver opening twice, mirrored: each desktop process runs its own window watcher, which counts only its own windows (`window_watcher_wiring.rs:871-880`), so both opened a native window for the same record (`window_watcher.rs:371`, `:386`). A GUI launch now claims the handoff endpoint before it touches anything, and one that finds it held sends the handoff socket's `Activate` (the running desktop raises its last focused window or opens a terminal) and exits, however it was launched, by path included; a desktop that predates `Activate` refuses it as unknown and the launch still exits (`desktop/src-tauri/src/single_instance.rs`, `crates/chan-server/src/handoff.rs`). That launch carries no path: its arguments are dropped, which contract 2 changes.

## Desired contract

1. The desktop's handoff socket takes an open-path request that does what `cs open` does in a standalone window: reuse or create a standalone window, raise it, and open the directory in the file browser or the file in the editor (or reveal it, or create it, by the same rules).
2. `chan-desktop PATH...` and `chan-desktop` given file URIs (`%U`) deliver each path to the running desktop through that request, launching the desktop first when it is not running; a second launch never starts a second desktop (true since v0.127.0): it hands its arguments to the running one and exits, however it was launched.
3. The CLI has a verb for the same thing, so `chan <verb> PATH` opens a directory or file in a standalone window of the running desktop or devserver. Naming it is hard, since `chan open` is a visible alias of `chan serve`: the item evaluates the options (a new verb, re-pointing `chan open`, or a flag) with what each breaks for existing users and scripts, and records the owner's choice before the verb is built (owner, 2026-11-09).
4. Linux: two desktop entries, packaged and in the AppImage, declare `inode/directory` (`chan-files.desktop`) and `text/markdown` (`chan-edit.desktop`) with a field code, so `xdg-open` and the desktop environment's Open With offer chan, and `xdg-mime default` makes it the default file browser or Markdown editor. Installing chan sets no default of its own, and a desktop that names an application for the exact type keeps it; where none names one, the first registered handler is used, which can be chan (GIO looks up `text/markdown` before its parent `text/plain`, all GNOME's text editors declare; generic `xdg-open` with no default for directories takes the first entry of `mimeinfo.cache`). Amended by the owner on 2026-11-12 from "installing chan does not make it the default by itself", which is not what Linux does with a declaration (the stage's reading and its review found both cases).
5. macOS: the bundle declares Markdown as a document type chan can edit, without claiming to be its default, so it shows in Open With and can be made the default Markdown app in Finder's Get Info; Finder's open, a double click once it is the default, and `open -a` deliver the file to a standalone window. Being the default file browser is not a goal on macOS.

## The shape, chosen 2026-11-11

Contract 3's spelling was first chosen as a new verb, `chan edit PATH`, from the team's note weighing a new verb, re-pointing `chan open` and a flag (the note stands in the round's coordination bus). The owner revised it the same evening to the busybox model: `chan-files` and `chan-edit` are names of the `chan` binary, links dispatched on the program name as `cs` already is, each with its own usage; `chan open` stays the alias of `chan serve`, the public spelling for opening a workspace since v0.112.0, and no subcommand is added. Both names reach the open-path request of contract 1 under the per-path rule of `cs open`: `chan-files PATH` opens a directory in the file browser and reveals a file in its directory; `chan-edit PATH` opens a text file in the editor and creates a missing one empty. On Linux each name has its own desktop entry with its MIME types (`chan-files` for `inode/directory`, `chan-edit` for `text/markdown`), the links installed by every package and written by the desktop's shim installer beside `chan` and `cs`; on macOS the bundle declares Markdown and the shims gain the two names.

## Boundaries

- Windows is out of scope (owner, 2026-11-09); a standalone window has no file surface there either.
- No change to what `cs open` decides per path; the new ways in reuse it.
- Plain-text and code files beyond Markdown may be declared later; this item declares directories (Linux) and Markdown.

## Acceptance

1. Tests of the handoff request: a directory, a Markdown file, a non-text file and a missing path each produce the window command `cs open` produces, into a reused or created standalone window.
2. Tests of `chan-desktop`'s argument handling for plain paths and `file://` URIs, with the desktop running and not running.
3. A packaging test that the desktop entry declares the MIME types and a field code and passes `desktop-file-validate`, for the shared entry and the AppImage's.
4. In an isolated Linux guest with the desktop under Xvfb: `xdg-open` of a directory and of a `.md` file, after `xdg-mime default`, opens each in a standalone window of the running desktop.
5. On macOS (owner): chan-desktop appears in a `.md` file's Open With, becomes its default through Get Info, and a double click opens the file in chan's editor.

## Built

### The open-path request and the launch's arguments (contracts 1 and 2), 2026-11-11

The desktop's handoff socket takes `open_path`, one absolute path per request, additive at protocol 1 as `activate` was: the desktop mounts its terminal tenant and opens the path in a standalone window it reuses or mints (native, so its watcher opens it) and raises, resolved by `cs open`'s own `standalone_open_target` and `standalone_open_command`, so a directory opens the file browser, a text file the editor, another file is revealed in its directory and a missing one is created empty. The answer `path_opened` carries the line `cs` prints; a refusal is a sentence, and a desktop that predates the request answers it as an unknown type, which the launch reads as a refusal rather than silence. A window minted for a path that cannot be resolved is discarded, which also fixed the `cs open` escape route that left such a window empty. The request and both answers are shown as JSON lines in `crates/chan-server/design.md`. `chan-desktop PATH...` and the `%U` file URIs: a path is made absolute against the launch's working directory, a `file://` URI is percent-decoded with its host checked on every platform, and options are left alone; an argument the desktop cannot open (another scheme or host, an encoded `/` or NUL, a relative name with no working directory, a non-UTF-8 path) is skipped with one log line and the rest delivered, while a terminal-mode option beside a path is a usage error with exit 2. With a desktop running each path goes over as `open_path` in order and the launch exits 0; the first path the holder leaves unanswered ends the run, a shutdown refusal on any path makes the launch wait and boot with all its paths, and a holder that opened none of them, an older desktop or one that cannot open them, is sent `activate` so it still comes forward; a second desktop is never started. With none running the launch boots and opens its paths after the boot restore, ahead of the first-open rule and the boot window, in a window of their own (a restored window takes an open only once connected); past sixteen commands into a window still opening a path is refused and logged, `cs open`'s park bound, now reachable by a multi-select Open With. An update relaunch carries the options and not the paths (the `tauri::Env` the GUI builder manages), so a relaunched desktop does not open them again. Acceptances 1 and 2: tests in chan-server (`control_socket`, `handoff`) and chan-desktop (`launch_paths`, `single_instance`, the relaunch pin), red at the base on the wire, the launch and the empty window and red at the first tip on the seven fix-round points, 23 mutations red; a Linux reading under Xvfb: a launch with no desktop booted and opened a directory, launches beside it handed over a `file://` URI with `%20`, a revealed image and a new relative `.md` into the same window, an `https://` URI was skipped and the desktop came forward, `smb://` beside a directory was skipped and the directory opened, and a terminal option beside a path exited 2. Reviewed before the merge (`dev/v0128-team/reviews/review-openwith-t1.md`); merged as 0c6e5f6b4 under fmt, clippy on four crates, the handoff, control socket, host, single-instance, terminal-mode and launch-path tests and the Windows target's lints. The CLI names (`chan-files`, `chan-edit`), the Linux desktop entries and the macOS document type follow in the next stages.

### The CLI names, the desktop entries and the shims (contracts 3 and 4), 2026-11-11

`chan-files` and `chan-edit` are names of the `chan` binary dispatched on the program name as `cs` is (`Opener::from_arg0`, the same file-stem rule, `$ARGV0` on an AppImage and a Windows shim; the opener's own name is put in argv[0] before clap parses, so an AppImage's usage line names it and not the inner binary); no `chan` subcommand spells them and `chan open` stays the alias of `chan serve`. Each parses its own usage (`PATH...`, defaulting to the current directory itself, and `-v`) into a clap-skipped `Command::OpenPaths`, and both follow `cs open`'s rule for every path, the names choosing only the usage and the desktop entry, as their help says. A `file://` argument is read by the handoff's `launch_arg_path`, the reader `chan-desktop PATH...` uses, moved to chan-server. In a chan terminal whose server answers an `Identify` each path is a `cs open`, so a desktop terminal's goes to the desktop and a devserver terminal's to that devserver; anywhere else, a stale control socket included, each path is an `open_path` on the desktop's endpoint after the `CHAN_NO_DESKTOP_HANDOFF` opt-out and the GUI-session check, each refusing with its own sentence. The endpoint is asked for up to 5 s per path (the single-instance guard's own bound), a listener that closes without an answer being asked again within it: a desktop that does not answer gets "chan-desktop did not answer for PATH" and exit 1, never a second desktop. Only when nothing listens is the desktop absent: chan-desktop's own openers (`run_invoked_as`, the name it read) start it with the paths, which its boot opens (on macOS through `open -n`, so an app already launching still runs the guard and forwards them), and read the process they started: exit 0 means it handed the paths to a desktop that was booting, which decides what to open; a failure means they were not taken, exit 1; and a served endpoint counts as the started desktop only once the process has outlived the guard's 5 s ask and a 2 s grace, since a booting desktop binds before it answers. The standalone CLI says no desktop is running and exits 1. Failures are reported in argument order and a refusal of every path follows them. The desktop's open-path reply names the absolute path, the surface root once. The desktop's shim installer writes both names beside `chan` and `cs` on Unix; Windows gets neither, a standalone window having no file surface there. Linux: `chan-files.desktop` (`inode/directory`, `Exec=chan-files %U`, System;FileTools;FileManager) and `chan-edit.desktop` (`text/markdown`, `Exec=chan-edit %U`, Utility;TextEditor), NoDisplay and without StartupWMClass, installed and validated by the deb, rpm, AUR and Nix desktop packages, linked by every package (CLI packages to `chan`), and carried by Tauri's deb, rpm and AppImage as bundle files; `scripts/check-desktop-entries.py` checks each entry's name, field code, MIME types and `desktop-file-validate` on the shared entries (`make desktop-entries-check`, Linux pre-push) and inside the built AppImage (`desktop/Makefile ci-linux`, exit 2 with a sentence when the image cannot be read), and the build-matrix contract requires every package's links and entries. The startup pin requires the opener check before the CLI probe in `run_as_chan_if_requested`, so the openers can never reach the single-instance guard unnoticed. Acceptance 3: the checker and its eight-case self-test, the build-matrix contract and its AUR cases. Acceptance 4, in a desktop guest under Xvfb with the entries installed as a package installs them beside a stand-in file manager and editor that a desktop defaults list names: before any choice gio keeps the stand-ins, `xdg-mime default` makes chan both defaults, `xdg-open` of a directory started chan-desktop with the path (its command line) and opened it in a standalone window's file browser, and `xdg-open` (generic and GNOME) and `gio open` of three Markdown files, one with a space delivered as a `%20` URI, opened in that window's editor. Tests red at the base on all ten end-to-end cases (the link parsed as `chan`) and the shim names; 35 mutations red, 17 of them on the fix rounds' rules. The manual's install page has the section, the terminal page the sentence, and the help heads read "`chan open` serves a workspace; `chan-files` and `chan-edit` open a path in a window, as `cs open` does inside chan". The root `design.md` and the chan, chan-server and desktop design docs count the two names among the CLI's. Reviewed independently before the merge (the round's review notes); the review's one contract finding is below.

Contract 4's "installing chan does not make it the default by itself" is not what Linux does with a declaration, in two cases the stage found: on GIO desktops `text/markdown` subclasses `text/plain`, GNOME's text editors declare only `text/plain`, and GIO looks up the exact type first, so a stock GNOME opens `.md` in chan once `chan-edit.desktop` is installed (reproduced with GLib 2.90 and a desktop defaults list naming `text/plain`); and generic `xdg-open` with no default for folders takes the first entry of `mimeinfo.cache`, where `chan-files` sorts before nautilus, dolphin, thunar and code, so a bare window manager without a folder default picks chan (xdg-utils 1.1 reads only the user's list; 1.2 also the system lists). A desktop that names a handler for the exact type keeps it either way, and `xdg-mime default` sets or unsets both. The owner was asked (keep both declarations and amend the contract to this truth, recommended; drop `inode/directory` only; drop both); the manual's paragraph and this contract's text follow his answer in the same round.

### The macOS document type and Finder's open (contract 5), 2026-11-11

The macOS bundle declares one document type, `.md` and `.markdown` by `net.daringfireball.markdown`, role Editor, rank Alternate, in `desktop/src-tauri/tauri.macos.conf.json` (a platform file, since `bundle.fileAssociations` also feeds the Linux entry's `MimeType=` and the Windows installers' associations, which stay out), and `Info.plist` imports the type (`UTImportedTypeDeclarations`, conforming to `public.plain-text`, tags `md`, `markdown`, `text/markdown`), an import rather than an export so a declaration by macOS or another app wins and chan does not claim to define Markdown; tauri-cli merges the plist on a macOS host only. Finder lists Chan in Open With and Get Info can make it the default; installing chan changes no default. Finder's open arrives as the run loop's `Opened` event, whose URLs go through the launch's URI reader (`launch_paths::from_urls`, reading each URL's text with the handoff's `launch_arg_path`, so an open-file event and `chan-desktop PATH...` read alike, a non-file URL logged with its reason and skipped) and then through the same open function as `cs open`, so Finder's open, a double click once chan is the default and `open -a Chan FILE` land in a standalone window, raised. AppKit hands a launch's documents before the app finishes launching, and tao passes them to the run callback with no buffering, so the queue on the app state starts held by the boot from the process's start and is opened right after the launch's paths, before the first-open rule and the boot window: a Finder launch on any library gets one window holding the file, not a boot terminal beside it. After the boot one task at a time drains the queue in event order, so two opens close together cannot each mint a window; the hold on the queue (`open_events::Opening`) is one type for the boot and each task, and its drop, at the end or in a panic's unwind, hands the queue to a new task when paths wait, so a panic loses the path being opened and no other. Linux and Windows drain an always-empty queue; the macOS arm is read, not built, on the Linux hosts here, and the owner's Mac reading (acceptance 5, the next owner batch) is its compile and its observation. Tests (chan-desktop): the eight-URI equivalence of the two readers plus a ninth case that only the `file://localhost` rewrite distinguishes, the queue's states, the embedded desktop opening two files asked for before the boot in one window and a later one beside them, a boot gone before its paths and a task that panics each handing the queue on, source pins of the macOS arm's one call and of the boot's order, the pinned emitter's plist on the macOS config, the imported type, and that only the macOS config declares a document type; 15 handler and declaration mutants red, each on its guarding test, and four more on the fix round. The manual's install page gains "Open Markdown files in Chan from Finder" with the two names beside it, and `desktop/design.md` describes the event path. Reviewed independently before the merge; the Windows-target clippy and test build are green in the seat's guest, the equivalence test's Windows run comes with the candidate check on the Windows VM.
