# A focus colour chosen just before a reload is lost

Status: shipped in [v0.109.0](../../release/release-v0.109.0.md).

Record before the release: built on 2026-10-23 on the seat's branch; the section Built 2026-10-23 holds the evidence; it closes at the GA as shipped.

## What was seen

Check `176-drag-focus-colour.mjs` failed in the whole browser run at `aa9dcd30d` (the hygiene guest, 2 CPUs, contended) at its reload arm: the window chose orange and reloaded about 0.2 s later, and the reloaded pane, drag strip and dock read blue, the layout's default. Alone in a 2-CPU guest at the same commit it was red once in five runs, and red every time with the session save's request held for 2 s. Read at source at `aa9dcd30d`: `applyNamedFocusColor` (`web/packages/workspace-app/src/state/paneColor.ts` 164) calls `setWindowFocusColor`, which only sets `layout.focusColor` (`state/tabs.svelte.ts` 3838); the layout persistence effect (`App.svelte` 209 to 288) does not read `layout.focusColor`, so a colour-only change schedules neither the 150 ms address write nor the 750 ms session save (`state/store.svelte.ts` 3685 to 3765, 4025 to 4031); a reload restores from the address and the server's blob, neither of which carries the choice, and `restoreLayout` falls back to blue (`state/tabs.svelte.ts` 1230). The exit flush's keepalive save can land after the reloaded page has read the blob. The path is older than this version (the effect and the setter predate `980864e24`); the paint and check 176 are focdnd's, the persistence is not. The reading is `dev/v0109-team/reports/reading-Frontend109-176.md`.

## Desired contract

A focus colour a person chooses for a window once the page writes its layout changes (its whole initial load done, the window's own requests, its saved layout's read and, in a workspace window, its extensions, whether the read found a saved layout, found none or failed: the moment from which the page's layout effect writes the address and the session for every other change), the default blue included, is the colour that window restores after a reload of the same page, however soon the reload follows the choice: the choice is a layout change like any other, written into the window's address at once with the session save scheduled. Before that moment the choice paints the window and itself writes no address and schedules no session save; the load's completion, the page-exit flush and the recovery keep their behaviour, and a choice made during the load gains no guarantee (a page exit during the load writes the address from the live layout, the chosen colour with it, as it does in v0.108.0). A window of a single empty blue pane has no serialized layout in the address or the session blob: a blue chosen there paints the window and carries no reload guarantee, and that layout's existing address, save and deletion rules apply unchanged. Nothing but the colour choice changes how a page loads, saves or recovers its layout.

Alex's word of 2026-10-23 (survey): "narrow the row: keep a colour chosen after the window has loaded; a choice during the load works as in v0.108.0". The row is narrowed to a choice made once the page writes its layout changes; a choice during the load works as in v0.108.0, and blue on a single empty pane is given no reload guarantee, as the option he chose sets them out.

The lead's ruling of 2026-10-23, on the reading of the narrowed text: the page writes its layout changes from the moment its layout effect does (App's bootstrap and, in a workspace window, its extensions load ended), not from the store's own load flag, which reads true before the load's first requests and before the extensions load; the choice itself writes nothing before that moment.

The lead's ruling of 2026-10-22: when the page has heard of a co-viewing page's save it has not taken in, its next load opens the window as the server holds it, for a colour choice as for every other layout change made in that interval; that precedence keeps the other page's change, and this row does not change it.

## What to do

Every choice a person makes goes through one store-owned function that sets the window's focus colour and, once the page writes layout changes (the readiness its layout effect reads), writes the layout into the window's address at once and schedules the session save; the pane menu (`components/Pane.svelte` 669) and the launcher command (`state/commands/panes.ts` 24) call it. A nonempty layout names blue explicitly, so a chosen blue outranks a stale saved colour. No state of its own beyond that readiness, set once where the layout effect's is: the choice path retains no pending colour for later application.

## Boundaries

The choice path in the store, its callers, the serialized blue, the pins, and the workspace app's `design.md` where it states what persists a window's layout. Not changed: the paint, the colour menu, the library's local colour and its live push, the initial load and its recovery, the layout effect's other triggers, the exit flush.
