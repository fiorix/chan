Three observe mutations survive because an earlier check refuses the same case, and a launch while an older desktop is still booting can boot a second desktop, the gap the owner accepted.

## What is there now

Read at `342dbe791`, by reading only. The claim is as v0.128.0 left it: v0.129.0 changed the guard's callers (the `chan-term` terminal a launch hands over, `check_terminal_at`, and the raise in `come_forward`, `desktop/src-tauri/src/single_instance.rs`) and nothing of the claim.

- On Windows the desktop's single-instance claim is the first and only instance of a named pipe, `\\.\pipe\chan-desktop-<SID>.claim` (`claim_endpoint_at` and `create_claim_pipe`, `crates/chan-server/src/handoff.rs`): owner-only through chan-winpipe, inbound, one instance at most, first instance. Pipe names are one namespace for the machine, so any local account can create a pipe of that name first, with whatever descriptor and limit it chooses.
- The claim reads what `CreateNamedPipe` answers: pipe busy is this account's holder (`ClaimError::Held`), access denied is another account's pipe (`ClaimError::Foreign`). The guard (`claim`, `single_instance.rs`) turns `Foreign` into `Lock::Unavailable`, so the launch boots without the handoff listener and holds no claim.
- Two shapes of a pipe another account creates first follow; `crates/chan-server/design.md` and `desktop/design.md` state both as limits.
  - A pipe that grants this account nothing, or grants it access with room for more instances (the first-instance flag then answers access denied too): every launch of this account boots a desktop with no listener and no claim, so a second launch boots a second desktop, whose window watcher opens a native window for every record the first shows. `chan serve` and the other handoff clients find no endpoint pipe and serve on their own, and as long as the pipe stays, the CLI says "chan-desktop is starting", since `desktop_is_starting` reads a claim pipe without an endpoint pipe as a desktop still booting.
  - A pipe of limit one that grants this account access: it answers busy like the account's own claim and reads as held. The launch waits `BOOT_BOUND` (30 s) for a listener that never comes and `ASK_BOUND` (5 s) for an answer, shows "Chan is not responding" about a copy the user cannot find, and exits 1. This account cannot start Chan while the pipe stays.
- Neither shape reaches what the desktop serves: the endpoint's pipe and every instance the listener arms grant this account alone, and every client reads the account of the pipe's server before it writes (`connect_endpoint_as`).
- The unix claim is a lock on a file beside the socket, in a directory checked as owner-controlled (`take_stable_lock`, `crates/chan-server/src/control_socket.rs`, `std::fs::File::try_lock`; `ensure_owner_dir_at`, `handoff.rs`). Another account can neither create that file nor lock it.

## Desired contract

1. On Windows only this account can hold its claim. The claim is a lock (`std::fs::File::try_lock`, the unix lock's twin) on a file under the account's own profile (`%LOCALAPPDATA%`), in a directory only the account can write. No pipe another account creates under this account's names, whatever it grants, keeps a launch of this account from claiming, or reads as a holder that is not this account's desktop.
2. The claim pipe stays only as the listing's sign of a desktop still booting (`endpoint_is_booting_at`, `desktop_is_starting`). Another account's pipe of that name can at most make the CLI's "starting" line wrong.
3. One desktop per account holds as today: two launches of this account end in one desktop; a desktop whose listener fails or stops keeps the claim; a relaunch releases it first.
4. Nothing splits at the release boundary. The endpoint keeps its name, so a CLI of either release reaches a desktop of the other as today, and a launch of this release beside a v0.129.0 desktop of this account, which holds the claim pipe and no lock, ends in one desktop, as does the reverse.

## Boundaries

- The Windows arm of the claim in `handoff.rs` (`EndpointClaim`, `claim_endpoint_at`, and `ClaimError::Foreign`, which then has no Windows source) and the guard's reading of it in `single_instance.rs`. chan-server keeps `#![forbid(unsafe_code)]`; a descriptor for the lock's directory, if one is needed, comes from chan-winpipe. The unix arms are unchanged.
- An elevated process of another account can write any profile and end any process. It is out of reach here, as it is for every per-account file.
- Not here: another account's pipe under the endpoint's own name, created first. The desktop then keeps its claim and runs without a listener: the CLI serves on its own, and a second launch cannot bring the desktop forward and exits 1 after the ask. The other pipe families keep their names and descriptors.

## Built, 2026-11-15: file claim and predecessor handling

Stage 1 implements the protected Windows file claim and keeps the named claim pipe only as an optional boot marker. The local profile's `chan/run` directory and the file are created owner-only, their descriptors are checked on every claim, reparse points are refused, and open handles prevent replacement until the claim drops. The listener handle owns the file claim even after its accept loop stops. The Unix claim remains the existing stable flock. Explicit test endpoints use independent hashed filenames; the well-known per-account endpoint uses `desktop.lock`.

Every freshly acquired Windows file claim, including one acquired after waiting, checks for a previous release's authenticated listener before booting. The new process retains its file claim through the check, hands over its paths or terminal as before, and releases the claim when the older desktop answers. It refreshes the boot marker before continuing a boot after the older desktop exits. An absent, foreign or unreadable server account is no predecessor. A busy pipe is retried within the ask bound, or the applicable release or drain bound after a refusal; if it remains busy for the whole bound, the launch boots rather than give an unauthenticated pipe a veto. The accepted compatibility gap therefore includes an older desktop whose endpoint stays busy for the whole bound at launch, alongside the older desktop still booting with only a marker. Both gaps end when no older desktop runs. The lead ruled this retry-then-boot outcome on 2026-11-15 in task 32 and records the owner's follow-up at integration.

Windows regression cases cover both squatted claim-pipe shapes, a marker without an endpoint, an unsafe existing directory, account-scoped lock filenames, an older listener without a file lock, permanent and transient busy endpoints, descriptor readbacks, lock lifetime, replacement, junctions and NUL rejection. The tests-first base patches and guard mutations are preserved for native execution under `dev/v0131-team/evidence/Desk131/winclaim-31`; they are not runtime red evidence until the VM runs them. Nine host-safe predecessor decisions passed; the Windows descriptor boundary cross-linted. The full Windows-target gate cannot run on this host because MinGW is absent. Stage 1 does not close acceptance: the committed scoped gates, Windows red/green and mutations, the two-account base/tip readings and both v0.130.0 compatibility directions remain recorded separately in the hand-back and Ops result. The manual's install page states the older-copy startup caveat. Elevated processes able to alter another profile, and reservation of the endpoint pipe's own name, remain outside this claim fix.

## Review correction and bounded marker retry, 2026-11-15

The predecessor-handling paragraph under "Built, 2026-11-15: file claim and predecessor handling", beginning "Every freshly acquired Windows file claim", is superseded by this dated correction and retained above as history. The retry-then-boot outcome applies only if no probe authenticated this account before the deadline. After an authenticated probe, a later busy reading retains the established unanswered, refusal or shutting-down outcome at the applicable ask, release or drain deadline and does not boot a second desktop.

At 2026-11-15T23:50:16Z the lead recorded: "the authenticated-then-busy narrowing (review 1a finding 2, task 66) is a lead ruling within the owner's 07:46:29Z ruling ("busy is retried within the bound then boots, never refuses")." The record says the owner's ruling "still holds for every unauthenticated busy reading" (`dev/v0131-team/reports/decisions-Lead131.md`). This is the lead's ruling, with confirmation asked of the owner in `dev/v0131-team/reports/owner-candidates-5.md`; the lead records that confirmation as "not a hold on the merge".

Before booting with its newly acquired file claim, the desktop retries creation of a missing optional marker every 20 ms for up to 200 ms while retaining the directory and file-lock handles. A squatted `<endpoint>.claim` name can add that bounded retry delay, including when the endpoint is absent; it cannot impose the thirty-second boot wait used when a desktop holds the file claim. If the marker stays unavailable, the launch still boots with its authoritative file claim. This marker retry is separate from the predecessor endpoint's ask, release and drain bounds. The authenticated-then-busy correction and marker retry remain subject to the final Windows-target gate and native Windows acceptance; this dated correction does not close the row.

Outside update mode, the uninstaller deletes `run\*.lock` and removes `run` only when `run` is a plain directory, preserving a junction or other reparse point and any non-directory entry.
