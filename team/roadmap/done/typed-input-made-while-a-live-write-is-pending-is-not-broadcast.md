## What was seen

Read at source, not run. `web/packages/workspace-app/src/terminal/connection.ts` 59 to 63 (the same blob at the round's base `4507fe5a0`): while a live write is pending, every chunk the terminal emits goes to the own-PTY sender alone, so that a terminal-generated reply reaches only the PTY that asked. `TerminalTab.svelte` 2021 pushes a live origin for every chunk of PTY output until xterm.js has parsed it, and ordinary typing reaches the router through the same `onData` path as the replies. So with broadcast on and the source terminal's output in flight when a key's data event fires (steady output in that terminal, or the echo of the key before), that key reaches the source PTY and no other member of the group, in this window or another: the group misses input the user typed. It is the focus report's "two routes by timing" with the opposite sign.

## Desired contract

A key the user types reaches every member of the broadcast group whatever the source terminal's output is doing at that instant; only terminal-generated replies take the own-PTY route.

## What to do

Capture before deciding, on the rig the frontend seat built for the focus-report item (`evidence/Frontend106/fbcast-browser-check.mjs` in the round's bus): two terminals of one broadcast group under xterm.js, the source program printing steadily while keys are typed into it, both PTYs' input recorded; count the keys each PTY received. If the group misses keys, read how the router can tell a reply from a key while a live write is pending (the reply's shape, the data event's source, or the pending write's own expectation) and put the choices to the lead. Design before code; the review seat reads the design.

## Boundaries

`web/packages/workspace-app/src/terminal/connection.ts`, `components/TerminalTab.svelte` and their tests. Not changed: the ghostty-web route; the focus report's own-PTY route; the server's fan-out.

## Acceptance

1. A written capture: with broadcast on and the source terminal printing steadily, what each member's PTY receives of the typed keys, with the engine named.
2. The decision recorded here with its reason.
3. If the route changes: a pin, red first on its own assertion, that a typed key made while a live write is pending reaches every member, and that a terminal-generated reply still reaches the own PTY alone.

## Built 2026-10-21

The route is by provenance, the seam the 2026-10-13 decision asked to investigate first. xterm.js marks the data the user made: in the locked 6.0.0, `CoreService.triggerDataEvent(data, wasUserInput)` fires its internal `onUserInput` event and then `onData`, in one call, for the keyboard, a paste, a composition, the `input` event, the wheel's cursor keys, an SGR mouse report, the alt-click cursor move and `Terminal.input`, and `onData` alone for every parser reply, the OSC colour replies, the focus reports and the pixel-size reports; each chunk is one call with one flag, so no chunk mixes a key and a reply. `terminal/xtermUserInput.ts` reads that mark from `term._core.coreService`, feature-detected as `terminal/selectionBypass.ts` reaches the selection service, and `TerminalTab.svelte` passes it with each chunk to `routeXtermData` (`terminal/connection.ts`): a marked chunk takes `sendUserInput` (this PTY, the same-window members and the server's `broadcast-input` fan-out) whatever the write origin, a live write or an attach replay; a lone focus report keeps its own-PTY rule ahead of the mark; an unmarked chunk takes today's rules (a live write: this PTY; a replay: the generated-reply drop). The kitty `u` final the review noted is a key here when the user types it, since xterm.js marks it, and the app's own encoded keys (`handleTerminalMetaKey`, Ctrl+/, ghostty's Shift+Enter) already call `sendUserInput` directly. Mouse reports in the SGR and SGR-pixels encodings (modes 1006 and 1016; xterm.js 6.0.0 has no UTF-8 or URXVT encoding) are marked and reach the group during a live write as outside one; X10's default encoding goes to `onBinary`, which the app does not subscribe (a row of its own, `x10mou`). Without the internal event (an xterm.js that drops it) the tracker is null and every chunk takes today's rules, with today's loss.

The ghostty backend keeps today's route, and with it the loss: ghostty is the default renderer on Linux (`crates/chan-library/src/config.rs` 268, `default_terminal_ghostty()` is `cfg!(target_os = "linux")`), and check 177's first run in the frontend guest mounted ghostty with no preference written (`dev/v0109-team/evidence/Frontend109/rpchrm/c177-work-1.log`). ghostty-web 0.4.0-next.20 marks no clean user-input boundary: the keyboard, a paste and `input()` set `awaitingEcho` before firing `onData` (`dist/ghostty-web.js` 2766, 2824, 2833), but `processTerminalResponses()` (3242 to 3250) fires the parser's replies from inside `write()` before `write()` clears the flag (2806), so a reply made right after a keypress carries it. The item's boundaries name the ghostty-web route as unchanged, and ghostty keeps the loss by the owner's word of 2026-10-21 ("make xterm.js the default on all platforms, this is a change to linux.. and from this change if ghostty loses functionality like the secret masking, it is fine"): xterm.js becomes the default renderer on every platform under the row `xtdflt`, and ghostty an opt-in one. Not exercised either: a member in another window (it takes the same `broadcast-input` route as any user chunk) and the server's fan-out.
