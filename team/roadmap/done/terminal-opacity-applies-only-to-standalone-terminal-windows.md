# Terminal opacity applies only to standalone terminal windows

Status: shipped in [v0.117.0](../../release/release-v0.117.0.md); the section Built, 2026-10-30 holds the Linux pixel reading. Not read by eye: macOS, the Settings slider's write on Linux, the light theme, the Hybrid side flip.

Record before the release: raised by the owner on 2026-10-30, after the v0.116.0 tag, with the decision made in the same words; accepted for v0.117.0; built on `v0117/terminal-opacity` the same day and read by pixel in the Linux rig (the section Built); the owner's macOS reading is pending.

## What was asked

The owner, reading the shipped v0.116.0 on the macOS desktop: the transparency setting does nothing for terminal tabs in workspace windows and for devserver terminals. Asked whether that is a bug, a matter of previously minted windows or a gap in the design, and told it is the design's scope, the owner ruled: "i want all terminal tabs, local or remote, to use the setting of the chan-desktop, because the windows are made by and controlled by chan-desktop; this shouldn't be a devserver feature, but the devserver terminal windows should still be transparent.. and so does the control terminals, and terminal tabs in workspace windows". And, to be crystal clear, in the owner's words: "i only want terminal tabs to be see-through, not all windows".

## Evidence

Read at `f46a812dc` (the v0.116.0 GA commit).

- `desktop/src-tauri/src/serve.rs`, `builds_transparent`: a window is built transparent and its URL carries `transparent=1` only for a local standalone terminal window (`library_id == "local"` and `kind == Some("terminal")`) and the default-terminal window (`terminal-exec`). Workspace windows (kind `None`), devserver windows (a `lib-<hex>` library) and control terminals (kind `control`) are built opaque. The flag is appended only when the window is not a connecting window (`connecting.is_none()`), and a devserver window starts on the connecting page and is navigated in place later (`retarget_watched_remote_window`), so the flag has to ride the retarget target as well as the build.
- The page paints see-through only in a window whose URL carries the flag (`windowIsTransparent` in `web/packages/workspace-app/src/terminal/backgroundOpacity.ts`): a see-through page in an opaque native window shows the window's own background, not the desktop.
- The value the page paints with is its tenant's preference: `currentPreferences()?.terminal?.background_opacity` in `App.svelte` and `TerminalTab.svelte`. In a devserver window that tenant is the devserver, so the slider in Settings > Terminal (`TerminalSection.svelte`, `commit` to the tenant's `PATCH /api/config`) writes the devserver's `server.toml`, and a devserver with the default 100 would paint a transparent window opaque whatever the desktop's own setting says.
- The desktop already pushes events to its pages (`app.emit` for the serves, the devserver control and the update prompt) and the pages reach the desktop through `tauriInvoke` (`web/packages/workspace-app/src/api/desktop.ts`); the desktop's embedded server runs one config watch for every local tenant (`crates/chan-server/src/config_watch.rs`), so a change of the desktop's `server.toml` is already an event inside the desktop process.
- The v0.116.0 item ([a-local-terminal-window-cannot-show-the-desktop-behind-it](a-local-terminal-window-cannot-show-the-desktop-behind-it.md)) scoped the feature to terminal-only windows; the config reference and the Settings hint say so.

## Desired contract

- Only terminal tabs are see-through. Below 100 the body of a terminal pane shows the desktop behind the window; every other surface of every window, the editor, graph, dashboard and file browser panes, the tab strips, the dock, the panels, the status bar, the overlays, the launcher and the connecting page, paints as it paints today, in every window kind. Nothing but a terminal body ever reads through, and at 100 every pixel of every window reads as it does in v0.116.0.
- `terminal.background_opacity` is chan-desktop's setting: the value in the desktop's own `server.toml` governs every terminal tab the desktop shows, in standalone terminal windows, the default-terminal window, workspace windows, devserver windows and control terminals alike. A devserver's own `terminal.background_opacity` plays no part in a desktop window; a browser tab stays opaque, as it has no desktop behind it.
- The native window is the means, not the effect: a window's transparency is fixed when it is built, so every window chan-desktop builds is built transparent and carries `transparent=1`, on the connecting page and on the navigated target alike, which is what lets a terminal tab in it read through and a later change of the setting apply live without reopening. The flag changes nothing the page paints outside a terminal body.
- In a desktop window the page takes the value from the desktop, not from its tenant's preferences: it asks the host once at load and follows a desktop event for every later change. The Settings slider in a desktop window, whatever tenant the window shows, writes the desktop's setting through the host; in a browser tab the row says the setting applies in chan-desktop and writes nothing the tab would paint.
- The backdrop mask with a hole behind each terminal pane card already keeps the pane layer opaque around terminals; every other surface that relies on the body background is audited and given its own, so the first bullet holds in a workspace window, a devserver window and a control terminal, not only in a terminal-only window.

## What to do

1. `desktop/src-tauri/src/serve.rs`: build every window transparent and drop `builds_transparent`; append the flag to the connecting URL and to the retarget target; on macOS keep the title bar layer for every window.
2. Desktop host: a Tauri command that answers the desktop's `terminal.background_opacity` (read from its `server.toml` through the embedded server's config) and one that writes it (the preferences route of the embedded local tenant, so the clamp and the config watch apply); an event the desktop emits to every window when the value changes, fed by the local config watch.
3. Page (`backgroundOpacity.ts`, `App.svelte`, `TerminalTab.svelte`, `TerminalSection.svelte`): in a desktop window the painted value comes from the host and its event, the slider reads and writes through the host; the tenant preference is used only to show the value in a browser tab's Settings with the note. Audit every surface of the workspace app that relies on the body background under `data-terminal-see-through` and give it its own background.
4. Docs: `docs/config-reference.md` (the key is chan-desktop's; a devserver's value has no effect on windows), the Settings hint, `desktop/design.md`, `crates/chan-server/design.md` if the key's row says otherwise.

## Boundaries

`desktop/src-tauri/src/serve.rs`, `main.rs` (the commands and the event), `desktop/src-tauri/capabilities/*.json` and `permissions/app.toml` for the new commands on every window kind; the workspace app files above and the surfaces the audit names; the docs above. Not changed: the handoff protocol, the devserver's config schema, the browser tab's behaviour.

Decisions the build makes: whether a devserver window keeps the `transparent=1` flag through a reconnect (the retarget path) or re-reads it from the host at load; whether the control terminal, which is a `control` kind on a devserver tenant, reads the flag from its URL or from the host.

## Acceptance

1. Unit: the build rule marks every window kind transparent; the connecting URL and the retarget target carry the flag; the host command answers the desktop's value and the event fires on a change of the desktop's `server.toml`; the page paints with the host's value over a tenant preference of 100, and the slider's write reaches the host.
2. By eye on macOS and by pixel in the Linux rig: in a workspace window a terminal tab is see-through at 80 while an editor pane beside it, the tab strips, the dock, the panels and the status bar read the same pixels as at 100; a devserver window's terminal is see-through at the desktop's 80 while the devserver's own key reads 100, and follows the desktop's slider live; a control terminal is see-through; a browser tab of the same devserver is opaque; at 100 a capture of every window kind equals a capture of the v0.116.0 build, so the native flag alone changes nothing visible.
3. `make web-check`, clippy with warnings denied for chan-desktop, and the browser checks that touch terminal appearance (105) green.

## Built, 2026-10-30

Built on `v0117/terminal-opacity` off `a7a46b0fe` by one lead with two building agents (host and page) and one read-only auditor of the page's surfaces.

- Host, chan-server: `ConfigWatch::with_server_config_hook` (`crates/chan-server/src/config_watch.rs`) starts the directory watch at construction and, after every tenant has reloaded a `server.toml` event, loads the file once more and hands it to the hook (`ServerConfigHook`, an `Arc<dyn Fn(&ServerConfig)>`); a `preferences.toml` event and a file that fails to load never reach it. `chan_server::route_builder_with_config_hook(runtime, hook)` builds the route layer with that watch, and the bounds `TERMINAL_BACKGROUND_OPACITY_MIN` and `MAX` are exported for the desktop's clamp.
- Host, chan-desktop (`desktop/src-tauri/src/terminal_opacity.rs`): `terminal_background_opacity` answers the clamped value of the desktop's own `server.toml` (a missing or unreadable file answers 100); `set_terminal_background_opacity { percent }` clamps, loads, sets and saves the file the way `chan config set` does (an unchanged value writes nothing, an unreadable file refuses the write) and announces the value. The announcement is the Tauri event `terminal-background-opacity` with `{ "percent": n }` to every window, deduped against the last announced value in `AppState`, so the config watch's hook, which fires for the desktop's own write too, sends nothing twice. The hook is installed through `RegistryDeps.server_config_hook` for the full desktop and for the default-terminal launch alike, so `chan config set` and a hand edit reach every window with no tenant mounted. The two commands are in the `workspace-window` and `gateway-window` permission sets and in `GATEWAY_WINDOW_COMMANDS`; `core:event:allow-listen` and `allow-unlisten` are in `capabilities/workspace.json` and in the runtime-minted exact-origin grant, so a remotely served devserver window reaches both like a loopback one.
- Host, windows (`desktop/src-tauri/src/serve.rs`): `builds_transparent` is gone. `mark_transparent_window` appends `transparent=1` once, on the URL every window is built with (before the connecting payload copies it as the navigate target) and on the retarget target a reconnected devserver window navigates to; a system-browser URL never carries it. Every window is built with `transparent(true)`, and on macOS every window's title bar container gets the opaque layer. The connecting page paints its own body (`desktop/src/styles.css`), so it reads as before in a transparent window.
- Page: `terminal/desktopTerminalOpacity.svelte.ts` follows the desktop's value. In a Tauri window it subscribes to the event first and then asks once, so a change between the two is not lost (an event that lands during the read wins); elsewhere, and before the first answer, it is `null`, which paints opaque. `App.svelte` and `TerminalTab.svelte` paint from it and never from the tenant preference. The Settings slider in a desktop window shows the desktop's value and writes it through the host (the buffer key is mutated so the field's status lights); in a browser tab it keeps writing the tenant's key with a hint that says the setting applies in chan-desktop. `api/desktop.ts` carries `onTauriEvent` and the two invokes.
- Page, surfaces: the auditor read every surface of the workspace app under `data-terminal-see-through` in a workspace, devserver and control window. The docked file browsers, the status bar, every modal and overlay shell, the command deck, menus and popovers, the pane frame, the pane tab strip (its own `var(--bg)`, inside the hole), every non-terminal pane body and the control-mode chrome paint their own background or sit over the masked backdrop, so nothing but a terminal body reads through at rest. One gap was fixed: a pane mid side flip kept its full hole while the card turned, so the desktop showed around it for the flip's 520 ms; `terminalHoles` cuts no hole for a face under `.pane.sideFlipActive`, and the class mutation at the flip's end rebuilds the mask.

Decisions the item left to the build: a devserver window keeps the flag through a reconnect because the retarget target carries it; the control terminal reads the flag from its URL like every window and the value from the host like every window; the desktop writes `server.toml` directly rather than through a tenant's PATCH, since the clamp is the same constant, the watch refreshes every tenant and calls the hook, and no tenant has to be mounted for a write.

Costs recorded, not fixed, each present in terminal-only windows before this item: the frame before a document's first paint shows the desktop (native, nothing a page can paint); the mask follows a layout change one frame late; a hairline seam is possible at fractional face edges; a `backdrop-filter` scrim over a see-through region (the deck's idle orbs, the 2 px blur of the disconnect, session-ended and close-confirm overlays) depends on the engine. On Linux every window now needs a compositor to paint as before, as the terminal windows already did; without one the page is opaque at 100 and the result is unread.

Checks, 2026-10-30, Linux (the CachyOS host under Hyprland 0.57.0 with a 3840x2160 output, WebKitGTK 2.54.2), with the debug build of `c239ef672` in an isolated rig (an own `CHAN_HOME` and `XDG_RUNTIME_DIR`, every `CHAN*` variable of the launching shell unset): `cargo fmt --check`; clippy and rustdoc with warnings denied for chan-library, chan-server and chan-desktop; chan-server `config_watch` 11 tests, chan-desktop 702, chan-library 763; `make web-check` (workspace app 610 files and 7913 tests, launcher 696, shared 234, profile 20, both production builds); browser check 105 alone, green in 13.6 s. The pixel reading: one desktop with four windows, a local workspace window holding a terminal tab beside the README editor, a devserver registered with a connect script that runs `chan devserver run` inside the control terminal (the desktop scraped the token from it), that devserver's workspace window in the same layout, opened through the connecting page, and a standalone terminal window, captured by `grim` at the default 100 and again after `chan config set terminal.background_opacity 80` with every window open, the devserver's own `server.toml` holding no key throughout. At 80 every terminal body shows the wallpaper: the per-channel standard deviation goes from 0.0 at 100 to (0.9, 6.8, 7.7) in the workspace window, (0.5, 2.5, 3.2) in the control terminal and (0.9, 5.0, 5.9) in the standalone window, and the devserver window's body, over a flat part of the wallpaper, reads the same 80 percent blend (a mean of 26.8 against 28.0). The editor bodies, the outline and details panels, the pane tab strips and the gutter between panes read byte-identical to the capture at 100 (a mean absolute difference of 0.0, a maximum of 1 on the anti-aliased strip text). A `chan devserver disconnect` and `connect` rebuilt the control terminal and the devserver window through the connecting page and the retarget, and the devserver window read the same at 80. `chan config set terminal.background_opacity 100` took every window back to flat bodies of (28, 28, 30) without reopening any. The same devserver window opened in headless Chrome as a browser tab reads an opaque body of (28, 28, 30) while the desktop sits at 80. The captures, the rig and the readers are kept under `releases/v0117/terminal-opacity-linux/` in the `chan-dev` repository.

Not read on Linux: the Settings slider's write (the host has no keyboard injection; the page test pins the slider's invoke and the host test the file write and the event); a capture of the v0.116.0 build at 100 for the equality, which stands on the 100 captures of this build reading every region at its theme colour and every non-terminal region identical between 80 and 100; the light theme; the Hybrid side flip.
