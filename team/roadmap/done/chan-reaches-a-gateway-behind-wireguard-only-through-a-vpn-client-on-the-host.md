# chan reaches a gateway behind WireGuard only through a VPN client on the host

Status: shipped in [v0.124.0](../../release/release-v0.124.0.md).

Record before the release: raised by the owner on 2026-10-30 as a feasibility question, whether chan-desktop could speak the WireGuard client protocol itself so the gateway's proxy and services can sit behind WireGuard with no VPN client installed (the brainstorm `chan-dev/brainstorm/wireguard-client-in-chan-desktop.md`, read at chan 0.115.0). The owner ruled out a dependency on boringtun, whose crate API changes between releases, and asked for the work as gradual commits on a branch of its own. The assessment that drove the shape is carried in [`crates/chan-wireguard/design.md`](../../../crates/chan-wireguard/design.md), "What is owned and what is depended on". Built on 2026-11-04 in another of the owner's sessions, with subagents, on `feat/chan-wireguard` off `main` at `b854ae252` and merged into `v0124/int` as `038d82f42`; its last commit, the macOS floor, is [its own item](chan-desktop-needs-macos-14-for-its-webview-proxy-and-its-updater-checks-no-floor.md).

Before the branch shipped, a reading of it found that the desktop resolved each gateway's endpoint once, inside a blocking start before the first window, with no retry and no timeout, and the owner asked on 2026-11-04 for the lookup to change: "when chan-desktop starts, the lookup of gateways dns should happen asynchronously, and not blocking the startup; i also dont think the dns should be cached once at start, it should be resolved on every attempt / respect the ttl". That work (`fix/wireguard-endpoint-resolution` off `d5ce4fbd1`, work order `dev/wireguard-endpoint-resolution.md` and its review addenda) merged as `c7e0f963f`. On 2026-11-05 the owner decided that a handshake with a known endpoint does not wait for its lookup. The Windows desktop suite (`test/desktop-wireguard-windows`, merged as `d797a1a2a`) and the documentation the branch left out (`docs/v0124-doc-gaps`, merged as `89acc216e`) belong here too.

## What was there

A devserver's tunnel dial (chan-tunnel-client) is TCP, TLS and h2 to a proxy node's public listener, so its ingress needs a public name, a certificate and an edge in front of it. chan-desktop's legs to a gateway (the SPA in the webview, the identity and tenant requests through reqwest, the window feed through tokio-tungstenite) dial directly. A gateway reachable only over WireGuard therefore needs WireGuard on every host that reaches it: `wg-quick`, wintun or a NetworkExtension, each extra software that needs administrator rights.

## Desired contract

1. **One peer in process.** A crate, chan-wireguard, runs one WireGuard peer and a TCP/IP stack over it inside the process: no interface, no route, no resolver change, no privilege; up to two UDP sockets on ephemeral ports (one per endpoint address family), the host resolver and the clock are all it takes from the operating system. The protocol core is boringtun 0.7.1's `noise` module, owned under BSD-3-Clause; the stack is smoltcp. Its peer is an ordinary kernel WireGuard interface.
2. **The configuration is a wg-quick file.** The subset an in-process client can honour: `[Interface]` with `PrivateKey`, `Address` (one or more; the stack holds at most two, one per family in practice) and an optional `MTU`; exactly one `[Peer]` with `PublicKey`, an optional `PresharedKey`, `Endpoint`, `AllowedIPs` and an optional `PersistentKeepalive`. `DNS`, `Table`, `FwMark`, the four hooks, `SaveConfig` and `ListenPort` are refused by name with the reason, as is a second `[Peer]`. CRLF and a leading UTF-8 byte order mark parse. On Unix a file the group or others can read is refused, naming `chmod 600`. No error and no `Debug` prints a key.
3. **The devserver.** `chan devserver run --tunnel-wireguard FILE` (`CHAN_TUNNEL_WIREGUARD`), on every verb that takes the devserver's serve arguments, reads and refuses the file at the command line before anything starts, dials the tunnel URL through the tunnel, and logs "WireGuard tunnel started from FILE" with the endpoint and the tunnel's public key for the peer's configuration. The URL may then be an `http://` address inside AllowedIPs, since the peer is pinned by its key; a URL host that resolves outside AllowedIPs is refused rather than dialed in the clear. The flag needs a tunnel token, `--no-tunnel` drops both, and only the path is recorded in a systemd unit's `ExecStart` or handed to the `--service=chan` daemon.
4. **chan-desktop.** A gateway row may name a wg-quick file (`wireguard`), set and cleared by a "WireGuard file" field in the launcher's Gateways form and read at add and update time, so a bad file is refused with the reader's message. At start, before any webview exists and without waiting for any lookup or handshake, the desktop starts one tunnel per enabled gateway with a file and one loopback proxy over them; every leg to a gateway goes through it (the reqwest clients with loopback destinations left direct, the window feed by a manual CONNECT, every webview including the launcher's). The proxy routes by destination: inside a tunnel's AllowedIPs through that tunnel, anything else directly. A file that fails at start disables that row alone with the reason as its `last_error`. The set is decided once per process, so a change takes effect at the next start, and the gateway badge says "Restart chan-desktop to apply the WireGuard change" until then. The Gateways screen shows each tunnel's state: connecting, up, or the lookup failure with ", retrying" or "; stalled, waiting for the system resolver", after "up; " while a live session carries traffic beside a failing lookup.
5. **The gateway builds without it.** chan-tunnel-client gains a `Connector` seam that chan-server implements over the tunnel (`WireguardConnector`); the gateway workspace builds chan-tunnel-client with no WireGuard edge.
6. **Endpoint resolution.** Creating a tunnel performs no lookup. The endpoint name is looked up on each handshake initiation (the first, each retry, each rekey and the attempts after an expiry) through the host's `getaddrinfo`, whose caching and TTLs apply, with no DNS crate and no cache of chan's own: one lookup in flight per tunnel, starts at least `REKEY_TIMEOUT` (5 s) apart and none while an endpoint is known and a lookup ended in the last 5 s, each bounded at 10 s, off the driver loop, so a hung lookup never stops the tunnel reading, sending or polling. With an endpoint known an initiation leaves at once; with none known it waits for the lookup's outcome. A lookup answer moves the endpoint only when no endpoint is known or the latest handshake is older than 135 s (`REKEY_AFTER_TIME` plus three `REKEY_TIMEOUT`s, the threshold wireguard-tools' `reresolve-dns.sh` uses); while a younger session lives, an answer that differs from the previous one gets one handshake initiation and the data stays on the address the peer last authenticated from, which roaming moves when the peer answers from the new one. A failed or timed-out lookup never disables a tunnel: the status names the failure or the stall, a failure warns when it starts or changes and its recovery warns once. A `connect` with no endpoint known waits for the next lookup outcome and fails with its reason, at once while a timed-out lookup still holds the OS call.

## Boundaries

New: `crates/chan-wireguard` (protocol core, configuration reader, stack and streams, driver and resolver, loopback HTTP proxy, two examples), `crates/chan-server/src/wireguard_connector.rs`, `desktop/src-tauri/src/wireguard.rs`, the e2e suites `wireguard-kernel.sh` (with `wireguard-dns.py` for its opt-in `dns` arm), `wireguard-freebsd.sh`, `wireguard-windows.sh`, `desktop-wireguard.sh` and `desktop-wireguard-windows.sh` (with `cdp.mjs` and `peer-http.py`). Changed: chan-tunnel-client's `ClientConfig` (`connector`), chan-server's devserver dial, the `chan` CLI, daemon and systemd paths, chan-systemd's flag recognition, chan-library's gateway row, the desktop's HTTP clients, window feed and webview builders, the launcher's Gateways form, badge and per-gateway state, the Nix `cargoHash`, the design documents (the crate's own, the root `design.md` and `README.md`, chan-server, chan, chan-tunnel-client, the desktop and the launcher), the configuration reference's `gateways[]` table and tunnel options, and the manual's devserver and gateway pages. Out of scope: key storage in the OS keyring and key enrollment through identity (the brainstorm's recommendation; the built form is a file the operator writes, and enrollment is the v0.125.0 item [`the-add-gateway-form-enrolls-a-wireguard-key-with-the-gateway-at-sign-in`](../v0.125.0/the-add-gateway-form-enrolls-a-wireguard-key-with-the-gateway-at-sign-in.md)), DNS inside the tunnel, UDP or ICMP through it, a TCP fallback, more than one peer per tunnel, a changed WireGuard file applied without a restart, and the gateway side, which stays an ordinary `wg` peer behind devserver-proxy's existing protected-overlay listener.

2. Against a kernel WireGuard peer on Linux 7.2.9: `wireguard-kernel.sh` (Linux client), `wireguard-freebsd.sh` (FreeBSD 15.1 client built natively) and `wireguard-windows.sh` (Windows 11 client cross-built for `x86_64-pc-windows-gnu`), each with wrong-key controls, a GET, an idle rekey, a keepalive hold and a real `chan devserver run --tunnel-wireguard` whose h2 preface reaches a raw listener on the peer; the kernel suite's `dns` arm serves the endpoint name from a private hosts file in an unprivileged mount namespace, absent at start, then added, then moved to a second forwarded port.
3. `desktop-wireguard.sh` under Xvfb: a debug chan-desktop with one gateway row behind a loopback peer starts its tunnel and proxy, reaches the peer by its discovery GET, by a plain forward and by CONNECT, loads a workspace window and the launcher through the proxied WebKitGTK webview with their sockets bridged, refuses nothing, and keeps the row across the config rewrite; with `--unresolved-endpoint` the first window does not wait for the gateway's lookup and the gateway comes up once the name resolves.
4. The webview legs through the proxy on Windows (WebView2's process-wide proxy argument) and on macOS (the data store proxy) reach a gateway inside the tunnel.
5. The full gate, `ci.yml` (the native Windows suites, the Nix job against the re-pinned `cargoHash`), Gateway CI and the `release.yml` dry run are green on the release commit.

Open: acceptance 4 on macOS was not read before the GA commit.
