# FreeBSD is not a published target

Status: accepted scope for v0.96.0. FreeBSD build support is merged at `13ca1ff7`; the static amd64 release arm, packaging, installer, updater metadata, and documentation are implemented at `455d6880`, `3125fb64`, and `5ca6aa89`. Integrated CI, stock-FreeBSD published-artifact acceptance, and three code-review findings remain open.

chan builds, tests, and runs on FreeBSD. The v0.96.0 release pipeline includes `chan-x86_64-unknown-freebsd.tar.gz`; `install.sh` selects that target and supports the base-system `fetch` command, and `chan upgrade` understands its release metadata. FreeBSD arm64 remains source-only because Rust does not distribute its standard library for `aarch64-unknown-freebsd`.

## Problem

The port itself was never the obstacle. A feasibility run on 2026-08-23 against FreeBSD 15.0-RELEASE arm64 (a `limactl` guest, 4 CPU, 8 GiB, ZFS) built `crates/chan` from `41fcf6880051` with no source changes at all: `pkg install rust` supplies 1.96.1 with rustfmt and clippy, the committed `Cargo.lock` resolves unchanged, and `cargo build --release -p chan` finished green with default features including candle embeddings. The reason it was that cheap is that the tree is already partitioned by platform rather than by "Linux and everything else": every `/proc` reader is `#[cfg(target_os = "linux")]`, `watch.rs` and `terminal_sessions/platform.rs` pair each Linux arm with a `not(linux)` arm, and `fs_ops.rs` already names `target_os = "freebsd"` in its xattr gate.

Running the tests found five defects fixed in the same change and described under Landed below. Two were not FreeBSD-specific: one breaks `cargo test` on every aarch64 Linux machine too, and the other is a false assumption about cap-std that the code had written down as fact.

The release implementation now builds and packages the amd64 target, exposes it through the installer and updater metadata, and documents the supported path. Shipping still depends on the integrated CI and host acceptance below.

## Landed

- **`fd_budget.rs`, `terminal_sessions/platform.rs`: the descriptor-pressure probe was reporting a constant.** Both count entries in `/dev/fd`. FreeBSD publishes that as a devfs stub holding `0`, `1`, `2` unless `fdescfs` is mounted over it, so the count is always 3 however many descriptors the process holds, and every consumer read permanent clear headroom. `nofile_limit` separately returned a hardcoded 4096 while the guest's real `RLIMIT_NOFILE` was 234981. Both now take the real rlimit through rustix, and the `/dev/fd` count is used only when a one-time probe proves the listing reflects this process's descriptors; otherwise the snapshot is `None`, which is an honest "no probe" rather than a confident wrong number.
- **`watch.rs`: the file watcher lost events.** `notify` selects its kqueue backend on FreeBSD, and that backend answers a write to a watched directory by reading the directory and taking the *first* entry it does not already watch (`.find(...)`, not `.filter(...)`). Measured directly against `notify` on the guest: four files created at once in a watched directory produced `d1.md`, `d1.md`, `d2.md` and never mentioned `d3.md`; a directory created with a file already inside announced only the directory. `notify` 8.2.0, the current stable, carries character-identical code, so the 6.1.1 pin is not the cause and a version bump is not the fix. FreeBSD now queues a rescan of the affected directory, coalesced on a 150 ms debounce, and synthesizes the `Created` events the backend swallowed. Rescans stay proportional to the change: the supervisor records each directory against its inode and follows only children it does not know. A same-name recreation is treated as new when its inode differs; inode reuse can match the stale identity and suppress nested descent, as recorded under Known gaps.
- **`fs_ops.rs`: `fsync` on a directory failed with `EBADF`.** `sync_dir_handle` documented the Linux `O_PATH` quirk and then asserted "Other unixes (macOS, BSDs) don't carry `O_PATH`, so the dup path is fine there." `target_o_path()` in cap-primitives lists freebsd alongside linux, so the ambient dir fd is `O_PATH` there too and every atomic write failed. FreeBSD has no procfs to reopen through, but it accepts an `O_PATH` descriptor as the `dirfd` of an `*at` call, so it reopens with `openat(dir, ".")`. The recorded suite moved from 374 failures before this fix point to 6 after it; the available evidence does not isolate how many failures this defect caused.
- **`fs_ops.rs`, `rooted_fs.rs`: a sandbox escape was refused but misclassified.** chan detects escapes by string-matching cap-std's message, which `rooted_fs.rs` called "the only portable signal we have". On FreeBSD cap-primitives resolves through the kernel's `O_RESOLVE_BENEATH`, so the kernel refuses with `ENOTCAPABLE` and no message is produced. The sandbox held throughout, and arguably harder since the kernel enforced it; what broke was the error class, so a caller branching on `SymlinkEscape` took the wrong branch and the user saw "Capabilities insufficient (os error 93)". Both mappers now match the errno first.
- **`Cargo.toml`: `cargo test` is broken on every aarch64 target whose baseline lacks fp16.** `gemm-common` reaches `fmla v0.8h` through `#[inline]` helpers called from `#[target_feature(enable = "fp16")]` code; at opt-level 0 those are emitted standalone without the feature and the assembler refuses them. `rustc --print cfg` reports `target_feature="fp16"` for `aarch64-apple-darwin` and not for `aarch64-unknown-linux-gnu`, `aarch64-unknown-linux-musl`, or `aarch64-unknown-freebsd`. Reproduced on an Ubuntu arm64 guest against a bare `gemm-f16 = "=0.19.0"` crate: dev fails with 11 errors, release is clean. So `cargo test` fails on any aarch64 Linux box today; it stayed invisible because the only aarch64 host running dev-profile tests is a developer Mac and CI's aarch64 work is release-only. `[profile.dev.package.gemm-f16] opt-level = 1` inlines the helpers back into their feature-carrying callers, and a dev-profile override moves no shipped artifact's instruction-set baseline.

## Release target

The release targets amd64 first. `x86_64-unknown-freebsd` is a Rust tier-2 target with rustup-distributed std, so the existing `ubuntu-latest` runners can cross-compile it against a sysroot unpacked from a checksum-pinned FreeBSD 15.0 `base.txz`. That toolchain support is sufficient reason to choose it as the first published architecture.

arm64 is a separate decision, not a follow-on commit. `aarch64-unknown-freebsd` is tier 3: rustup ships neither host tools nor std, and the ports toolchain that does exist only runs on FreeBSD itself. It needs a native FreeBSD arm64 builder or nightly `-Z build-std`, and the choice should be made on whether anyone is actually asking for it.

- **Static is the shipping format.** `-C target-feature=+crt-static` is respected on FreeBSD and produced a working binary: 58 MB, `ldd` reports "not a dynamic ELF executable", and it passed the full runtime smoke. The usual static casualty survives, verified through the real binary rather than inferred: `chan workspace index download-model` fetched bge-small from HuggingFace over HTTPS and exited 0, so DNS, rustls, and certificate verification all work. FreeBSD 15 carries the trust bundle at `/etc/ssl/cert.pem` in base with no `ca_root_nss` package needed.
- **Pass `--target` explicitly.** Without it, Cargo applies `RUSTFLAGS` to host artifacts and `+crt-static` breaks the proc-macro builds (`cannot produce proc-macro for async-trait`). A release pipeline passes `--target` anyway and `Makefile`'s `chan` target already threads `CHAN_TARGET` through, so this is a local-invocation trap rather than a packaging problem.
- **Packaging is target-specific.** `packaging/freebsd/Makefile` requires `x86_64-unknown-freebsd` and a FreeBSD sysroot, builds with the explicit target and static feature, and stages `chan`, `LICENSE`, and `README.md` in `chan-x86_64-unknown-freebsd.tar.gz`.
- **The installer and updater select only the published architecture.** `install.sh` maps FreeBSD amd64 to `x86_64-unknown-freebsd`, falls back to the base-system `fetch` command when curl and wget are absent, and refuses FreeBSD arm64. The updater target table uses the same mapping and refusal.
- **The release arm is build-only.** `freebsd-cli-artifacts` runs on Ubuntu, installs the pinned Rust target and clang/LLVM tools, verifies the checksum-pinned FreeBSD 15.0 sysroot, asserts that the result is a static FreeBSD amd64 ELF, and uploads `release-freebsd-cli`. Native FreeBSD behavior remains host acceptance because GitHub Actions has no FreeBSD runner.

## Known gaps to accept or close

- **Catch-up directory identity can miss a recreated subtree after inode reuse.** The queue retains known directories by path and inode. If a directory is deleted and recreated at the same path with the same reused inode, the stale identity can suppress descent into files already inside the replacement directory.
- **The FreeBSD directory reopen omits `CLOEXEC`.** `sync_dir_handle` calls raw `openat` with `RDONLY | DIRECTORY`, unlike the close-on-exec Linux arm, so a concurrent fork and exec can inherit the short-lived descriptor.
- **The debounced watcher scan root can be replaced by a symlink.** The candidate is checked with `symlink_metadata` before the 150 ms debounce and later scanned through ambient `read_dir`; replacement during that interval can make the watcher traverse outside the workspace before downstream capability reads refuse the synthesized paths.
- **Concurrent terminal creation intermittently fails with `Spawn(Operation not permitted (os error 1))`.** Reproduced deliberately: one failing round in eight running the two `terminal_sessions::tests::concurrent_*` tests at `--test-threads=8` on a loaded 4-vCPU guest; they pass three of three run serially. The anyhow backtrace puts the origin in `portable_pty::unix::PtyFd::spawn_command`, so it is the fork / pre_exec / exec path rather than anything chan owns. Two candidates are ruled out by C probes on the guest: `openpty` under contention (8 threads x 200 iterations, 1600 successes, no failures) and `setsid` / `ioctl(TIOCSCTTY)` under contention (6 threads x 60 forks, no `EPERM`). `kern.randompid` is 0 there, so the pid-collides-with-a-live-pgid theory has no amplifier either. Not attributed further. It wants instrumentation inside portable-pty's `pre_exec`, or a run on an unloaded FreeBSD box to see whether it survives off a contended guest. Worth noting that chan already carries a darwin-only transient-openpty retry whose comment asserts "only darwin's pty allocator refuses transiently", so a retry around `spawn_command` is the shape a fix would take. The same defect surfaces a third way: `control_socket::tests::spawn_team_brings_up_lead_first_and_pokes_only_agents` came up with `["@@Alice", "@@Shell"]` instead of `["@@Lead", "@@Alice", "@@Shell"]` in a loaded full-suite run and passes six of six in isolation, which is one terminal of a team failing to spawn rather than a distinct bug.
- **`spawn_time_backend_resolver_updates_new_children_and_keeps_last_good_value` breaks on any host whose login profile prints a banner.** chan spawns login shells and the test reads the child's first output; the guest's stock `~/.profile` runs `fortune freebsd-tips` and the test read a ZFS quota tip. Not a FreeBSD defect, but the test is asserting on an environment it does not control.
- **No rc.d integration.** `--service=systemd` and `--service=launchd` refuse off their platforms, so FreeBSD lands on `--service=chan`, chan's own supervision, which works. An rc.d script would be a feature, not a fix.

## Acceptance

- `install.sh` on a stock FreeBSD amd64 machine with neither curl nor wget installs a working `chan` and links `cs`, verified end to end rather than by reading the script.
- The release publishes a static `chan-x86_64-unknown-freebsd.tar.gz` whose SHA256 matches its `/dl/cli/latest.json` entry, and `chan upgrade --check` on FreeBSD reports the published version instead of refusing the target.
- A FreeBSD devserver serves a real workspace: `chan serve` binds, `/api/health` answers ok, an unauthenticated request is refused, the embedded SPA is served, and SIGINT exits cleanly. All of this already passes on the guest against both the dynamic and the static binary; the acceptance is that it passes against a *published* artifact.
- `cargo test --workspace --exclude chan-desktop` on FreeBSD is green apart from the intermittent terminal tests above, which are named rather than hidden.
- `crates/chan-workspace/tests/watch_completeness.rs` passes on every platform. It is not gated to FreeBSD: it states a contract every backend owes, and it fails on FreeBSD with the watcher fix reverted.

## Evidence

- Feasibility run 2026-08-23 on FreeBSD 15.0-RELEASE arm64 at `41fcf6880051`. Unpatched: `cargo check -p chan` green in 79 s with one `dead_code` warning; `cargo build --release -p chan` green; `chan --version` reported `chan 0.95.1 (build git-41fcf6880051)`, linked only against FreeBSD base (`libutil`, `libthr`, `libgcc_s`, `libc`, `libm`, `libsys`).
- Recorded suite transitions: 2398 passed / 374 failed before the directory `fsync` fix point, 2766 / 6 afterward, 2768 / 4 after the escape-classification fix, and the watcher and probe fixes close the remaining structural one. These aggregate transitions are established; no per-cause attribution was captured.
- The watcher fix is pinned adversarially: with `queue_catch_up` disabled on the guest, both `watch_completeness` tests fail; restored, they pass three of three, and `ignore_consistency` passes ten of ten where it previously failed three of three.
- The `O_PATH` mechanism was confirmed at the syscall level with a C probe on the guest: `fsync` on an `O_PATH` fd returns errno 9, `openat(o_path_fd, ".")` succeeds, and `fsync` on the reopened fd returns 0.
- The `/dev/fd` discriminator was confirmed by mounting and unmounting `fdescfs`: with the stub a process holding five extra descriptors still lists three entries; with `fdescfs` mounted the same process lists nine.
- The static binary and runtime smoke script were transient artifacts on the FreeBSD feasibility guest; neither is checked into this repository.
