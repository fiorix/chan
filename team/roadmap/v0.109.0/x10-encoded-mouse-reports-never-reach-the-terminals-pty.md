# X10-encoded mouse reports from the xterm.js renderer never reach the terminal's PTY

Status: built on 2026-10-22 on the runtime and frontend branches; the section Built 2026-10-22 holds the evidence; it closes at the GA as shipped.

## What was seen

The workspace app subscribes to xterm.js's `onData` only: `web/packages/workspace-app/src/components/TerminalTab.svelte` 1332 (`term.onData(handleXtermData)`), and `onBinary` appears nowhere in `src/` outside tests. xterm.js 6.0.0's `CoreMouseService` (`src/common/services/CoreMouseService.ts`, "always send DEFAULT as binary data") sends a mouse report in the `DEFAULT` encoding, the X10 form `ESC [ M` followed by three characters whose codes carry the button and the coordinates offset by 32 and can exceed 127, through `triggerBinaryEvent`, which fires `onBinary` and not `onData`; the SGR and SGR-pixels encodings (modes 1006 and 1016) go through `triggerDataEvent` and reach the PTY, and xterm.js 6.0.0 has no UTF-8 or URXVT encoding (modes 1005 and 1015 set nothing). So a program that enables mouse tracking without choosing SGR, with or without 1005 or 1015, gets no mouse report at all from a chan terminal on the xterm.js renderer, whether or not a live write is pending. The reading is the xterm.js renderer's: Ghostty, the renderer a person opts into (xterm.js is the default on every platform by the owner's word of 2026-10-21, carried by the default row; until it lands `crates/chan-library/src/config.rs` 268 keys ghostty on Linux), was not read for mouse reports. The terminal socket's `input` frame is a JSON string: `sendInput` sends `{ type: "input", data }` (`TerminalTab.svelte` 1925, `ws.send(JSON.stringify(frame))` at 1892) and the server writes `data.as_bytes()` (`crates/chan-server/src/routes/terminal.rs` 1027), so a byte-valued character above 127 pushed through that frame would reach the PTY as two UTF-8 bytes, not one. Read at source by the review seat and the lead; not measured in a terminal.

## Desired contract

A mouse report xterm.js emits in the X10 encoding reaches the PTY of the terminal it was made in, byte for byte: each character of the binary string becomes one byte. It is user input, so it takes the route a user-made chunk takes, including the typed-input broadcast item's group route once that lands.

## What to do

A short design first, since the wire shape is unnamed: how a byte-valued chunk crosses the terminal socket unchanged (a frame of its own carrying the bytes, or the `input` frame with an encoding the server undoes; the design names the frame, its server arm in `routes/terminal.rs` and its authority row if the route is new, and why the shape is the smallest). Then the build: subscribe `term.onBinary` beside `onData` in `TerminalTab.svelte`, convert the string to bytes by character code, and hand the chunk to the same route a user-made data chunk takes. Pins red first: a unit test of the route with a constructed X10 report whose coordinate characters exceed 127, asserting the bytes the socket carries equal the character codes, one byte each, and a mutant that encodes the string as UTF-8 red; a server test that the frame's bytes reach the PTY unchanged, red first. The mounted terminal test over the real xterm fixture (`__tests__/terminalReplay.ts`) drives a report through `triggerBinaryEvent` if the fixture allows it; the row says so if it does not.

## Boundaries

`web/packages/workspace-app/src/components/TerminalTab.svelte` at the subscription and the send, `web/packages/workspace-app/src/terminal/connection.ts` (the byte conversion and the route), `crates/chan-server/src/routes/terminal.rs` (the frame's server arm) and `route_authority.rs` only if the design adds a route, with the design documents of both. Lands after the typed-input broadcast item through `TerminalTab.svelte` and `connection.ts`. Not changed: xterm.js, the SGR path, ghostty's route.

## Built 2026-10-22

The terminal socket's `input` and `broadcast-input` frames take an optional `binary` boolean (`crates/chan-server/src/routes/terminal.rs`, one conversion both arms call; `crates/chan-server/design.md`): absent or false keeps UTF-8; true writes each character's code as one byte, and a frame holding a character above U+00FF is refused whole with an `error` frame while the socket stays open. No frame, route or authority row is added, and `web/packages/workspace-app/src/terminal/connection.ts` is unchanged, since the conversion is the server's. This is the server half, `2b315f1be` on the integration branch: decode pins for the absent, false and true forms on both frames and for the refused characters; a PTY pin that sends a refused frame and then the report on one socket and reads exactly `1b 5b 4d 20 bf e4` between markers; a two-window socket pin in which the group member's PTY reads the report and the source's its own sentinel. Seven mutants each fail a pin, among them the UTF-8 encoding of a binary frame, and the chan-server suite passed 2397 tests with one ignored (`dev/v0109-team/evidence/Runtime109/x10mou/` and its `broadcast23/`).

The client half: on the xterm.js renderer the terminal tab subscribes to `onBinary` beside `onData` (`web/packages/workspace-app/src/components/TerminalTab.svelte`), where xterm.js 6.0.0 hands the X10 report, `CSI M` and three characters of codes up to 255, with no user-input mark. `handleXtermBinary` sends it through `sendUserInput` with the binary flag, so it reaches this PTY and the broadcast group as user input whatever the terminal's output is doing; it bypasses `routeXtermData`, which holds an unmarked chunk to its own PTY during a live write. `sendInput` and the `broadcast-input` frame carry `binary: true` only when the flag is set, so text frames stay byte-identical, and `broadcastTerminalInput` (`state/tabs.svelte.ts`) hands the flag to each same-window member's sink, which puts it on that member's `input` frame. The workspace app's design text (`src/design.md`, a terminal's data and the broadcast group) says so. Ghostty's route is unchanged.

Acceptance 1, the page pins (`components/TerminalTab.binaryInput.test.ts`, new): the tab is mounted over a real xterm.js model of 220 columns whose mode 1000 the program's output sets, and the model's mouse service reports a left press in the zero-based cell (150, 3); the service moves the cell to one-based in place, so the report is `1b 5b 4d 20 b7 24`, with a character above 127. The `input` and `broadcast-input` frames carry the report with `binary: true` and a same-window member's sink receives the flag; the same holds for a press made while a live write is unparsed; a member's report reaches the tab's socket with the flag; text frames carry no field, read as the raw JSON. The shared xterm stand-in (`src/__tests__/xterm.ts`) gains an `onBinary` and `binary()` pair, and the five xterm stand-ins whose tests start the tab (`fullWindowCoverContract`, `keyboardLayoutDispatch`, `terminalChordContract`, `terminalCtrlDDoubleClose`, `TerminalTab.find`) gain `onBinary`: without it the tab's start raises `term.onBinary is not a function` (18 unhandled rejections, `dev-1`). With the two product modules as they are at the parent `4b2ebb901` and these tests (`redgreen-1`), the three report pins fail on their own assertions, no frame for either press and a member's report without the flag, while the report's byte pin and the text pin pass. The UTF-8 mutant is the server half's.
