# A command that exits before its terminal socket subscribes never reports its exit

Status: built on 2026-10-24 on the seat's branch; the section Built 2026-10-24 holds the evidence; it closes at the GA as shipped.

## What was seen

Browser check 164's exited arm (`scripts/e2e/browser-smoke/checks/164-cli-terminal-reload-notice.mjs` 467 to 524) creates a terminal through `cs terminal new --command "printf 'CLIRLD_164_EXITED\n'"` and waits for the page's terminal socket to carry an `exit` frame. At `a9fc42183` it was red once in the freeze's solo run and in 8 of 30 repetitions in a two-CPU guest (5 of 20 of the arm alone, 3 of 10 of the whole check), each with `session`, `ready`, the command's output and `program_status` on the socket and no `exit` within 30 s, while every green run carried `exit`; the recorded frames do not show when the exit was published relative to the subscription. At source, `Registry::create` (`crates/chan-library/src/terminal_sessions.rs` 2450 to 2487) starts the session and parks it before its first attach, and `Session::spawn` (4665 to 4798) starts the reader and the controller before it returns, so a short command can print and exit in that interval; `record_terminal_exit` stores the exit (6207 to 6218) and broadcasts it once (6221), a send with no receiver discarded (6354); `Session::attach_resuming` (5321 to 5376) subscribes at 5333 and replays the output ring and the program status under the output lock but neither reads nor replays the stored exit; `Registry::attach_resuming` (2638 to 2649) refuses only a closed session. A socket that attaches after the exit therefore sends `session`, the replayed bytes and `ready` (`crates/chan-server/src/routes/terminal.rs` 1414 to 1463) and then waits for an event published before it listened; the same prelude serves the `SessionEvent::Restarted` reattach (1296 to 1343). The path is unchanged since `759aac125` and older than this version. The page then keeps the tab connected to an ended process, with the CLI reload marker's pending bit retained, until another path clears the session.

## Desired contract

An attachment that acquires a retained session incarnation, and whose transport stays available, receives that incarnation's stored exit after its replay and `ready`, with the code `TerminalExit::wire_code()` gives, preceded by the final program status as the live exit path sends it; an attachment made before the exit keeps the live delivery path; each socket sends at most one `exit`. An unknown or closed id, an explicit client detachment and a transport failure keep their behaviour; exited ids are not retained longer than today, and the wire's code semantics do not change.

## What to do

Build: the attach result carries an optional captured exit, read with the exit lock taken before the output lock (the order the exit owner uses when it finalizes status, `terminal_sessions.rs` 6191 to 6207), while the subscription and the ring and status snapshot keep the output lock; no lock lives across a socket await. With a captured exit the socket finishes through one terminal path after `ready`: the final program status at the existing interval anchored on the session frame (`routes/terminal.rs` 867 to 905, 1422), the stored `exit`, the registry removal the live arm performs (1273), and termination without consuming the subscription's possible second copy. With none, the live `SessionEvent::Exit` arm (1271 to 1285) stands. Both `send_attach_prelude` callers, the first attach and the `Restarted` reattach, handle the result the same way, and an exited restarted incarnation ends its socket as an initially attached exited one does. The page needs no change: `TerminalTab.svelte` 1783 to 1798 handles `exit` after `ready` (the exited state with its code, the cleared prompt queue and sink, `clearTerminalSession(tab, true)`, the session save) and 1824 to 1831 does not reconnect after the close; `tabs.svelte.ts` 2671 to 2687 clears the session id and `cliCommandPending`, which check 164's marker read (lines 506 to 515) observes. Red first, with a real PTY child and a real terminal socket, the order owned by channels and a bounded receive for absence, no sleep: (1) the late attach held at the existing `AttachBeforeRingLock` seam while the child exits and an earlier observer consumes the broadcast, then released, requiring `session`, the replayed marker, `ready`, the final program status, then exactly one `exit` to socket termination; (2) the `ExitReadable` window, an attach between the store at 6218 and the broadcast at 6221, requiring exactly one `exit`; (3) an attach before the exit, a control requiring the live path's one `exit`; (4) the `Restarted` reattach to an exited incarnation. A status record that finalization changes is seeded so the final status is checked before the exit. One mutant per guard, each reaching its interleaving: the exit not replayed; the subscription's copy sent beside the replayed one; the lock order reversed. `crates/chan-library/design.md` and `crates/chan-server/design.md` state the rule where they describe the attach replay.

## Boundaries

Not changed: the client session registry and its detach cancellation (`crates/chan-server/src/client_connections.rs`), the page, check 164, the wire format.

## Built 2026-10-24

Built (Acceptance 1 and 3): `Session::attach_resuming` takes the session's exit lock, then the output lock, and under both subscribes, snapshots the ring, the cursor and the program status, and reads the recorded exit, which `AttachHandle::exit` carries; the exit owner takes the same two locks in the same order when it finalizes the status, so an exit not yet recorded is broadcast after the subscription and a recorded one comes with the finalized status. `recorded_exit` and the attach share one `lock_exit`, which fires the existing `RegistryBeforeSessionExit` seam. In `routes/terminal.rs` one `send_exit` ends a socket on an exit (the registry removal, the rest of the open status interval, the final status, `exit`); the live `SessionEvent::Exit` arm, the first attach and the `Restarted` reattach take it, the last two when the handle holds the exit, and the socket ends after it without reading its subscription, so a copy of the event broadcast after the record is not sent. `crates/chan-library/design.md` and `crates/chan-server/design.md` state the rule. The page, check 164, the wire format and `client_connections.rs` are unchanged. An attach that meets the exit owner's hold of the exit mutex, through its reader drain and status finalization, waits for it synchronously on the socket's task, as the registry's exit readers do; the reader drain's 500 ms deadline is the only timed wait inside that hold.
