# The Rust TLS clients ignore the system's CA store

Status: raised on 2026-11-07 from the v0.125.0 release's enrollment proof; accepted by the owner for v0.126.0 at the v0.125.0 cut; moved to v0.127.0 by the owner on 2026-11-08; moved to v0.128.0 by the owner on 2026-11-09; the verifier reading done and the verifier chosen on 2026-11-11 (platform policy); built the same day (see Built).

## What is there now

The root workspace selects reqwest with `rustls-tls` alone (`Cargo.toml`), which is `rustls-tls-webpki-roots`: the bundled Mozilla roots and nothing else. The desktop's reqwest clients (`desktop/src-tauri/src/wireguard.rs`, `client_builder`, which every gateway call shares) and its WebSocket feed (`tokio-tungstenite` with `rustls-tls-webpki-roots`) therefore verify a gateway against the bundled roots only, and so does the peer agent (`gateway/crates/wireguard-agent`, on the gateway workspace's reqwest with `rustls-tls`). A CA installed in the operating system's trust store, the shape of a corporate or self-signed gateway, is honoured by the system webviews and by `curl` and refused by chan's Rust clients with a certificate error; the release's enrollment proof ran without TLS for this reason. One client is the exception, in the other direction: the tunnel dial in `crates/chan-tunnel-client/src/dial.rs` (`build_tls_config`) loads the native certificates with `rustls-native-certs` beside the bundled roots, so the same gateway is trusted by the tunnel and refused by the sign-in that precedes it.

## Desired contract

1. Every Rust TLS client of the desktop and the peer agent trusts the platform's own store: on macOS and Windows the platform verifier decides (a root the system distrusts is distrusted, a public CA verifies as the system says), and on Linux the system bundle is read beside the bundled WebPKI roots, which stay the floor there, so a corporate or self-signed CA verifies once it is in the store and a public CA verifies on a Linux machine with an empty store. (Amended on 2026-11-11 by the owner's choice, survey 8, option A, platform policy: the first text promised the bundled floor on every platform and the platform verifier at once, and the reading found no crate that honours both, since a floor would re-trust a root the system distrusts; the floor is Linux-only.)
2. Verification is never weakened: no option disables it, no certificate is pinned by hand, and a CA absent from both stores still fails with the certificate error.
3. The tunnel dial and the HTTP and WebSocket clients agree: one trust decision per platform, built in one place, so a gateway trusted by one is trusted by all.

## Boundaries

- The clients' TLS configuration (reqwest's features or a shared rustls `ClientConfig`, tokio-tungstenite's connector, the agent's client); no change to what the clients send or to the gateway's certificates.
- The verifier is a dependency decision made with the owner, `rustls-platform-verifier` against `rustls-native-certs`, read on each platform before it is chosen.

## Acceptance

1. A throwaway CA installed in the system store and a gateway served under a leaf it signed: the desktop's sign-in, discovery and WebSocket feed and the peer agent's calls succeed on Linux, macOS and Windows, each read on that platform; with the CA absent from the store every client fails with the certificate error, and the same install at the base changes nothing (the red).
2. A gateway behind a public CA verifies unchanged on each platform with the bundled roots alone, read with an empty system store on Linux.
3. `cargo tree` at the tip shows one TLS backend for every client; `make pre-push` and the desktop package green.

## Built, 2026-11-11

One crate builds the trust decision for every Rust client of the desktop and the peer agent (`crates/chan-tls`, 692ddfcd3): `client_config()` returns a rustls `ClientConfig` with no ALPN, the ring provider, TLS 1.3 and 1.2 and one cached verifier per process; on macOS and Windows the platform verifier decides (`rustls-platform-verifier`, no extra roots), on Linux and the other Unixes a WebPKI verifier reads the system bundle (`rustls-native-certs`, `SSL_CERT_FILE` and `SSL_CERT_DIR` honoured there alone) beside the bundled roots, which stay the floor there (contract 1 as the owner chose, survey 8); no option disables verification and the only `dangerous()` call installs the real verifier (contract 2); the store's anchor count is logged at the first build and a store that gave none at warn (beaa0e5cc). Every client takes a clone with its own ALPN and keeps its proxy, timeouts and redirects (contract 3): the desktop's reqwest builder for discovery, the roster, the redeem, the revoke and the WireGuard calls, the window feed's WebSocket connector direct and through the CONNECT proxy, the reverse tunnel's connector for a gateway devserver (08bac020c), the tunnel dial with its h2 ALPN, which read the system store alone before and errored on an empty one and now has the floor (0c3aef276), the peer agent's identity client and the desktop's updater through reqwest 0.13's preconfigured backend (d85a41af1), and `chan metrics --url` (5d0dbfa6e); the CLI's self-update and the model download (ureq, bundled roots, inside the desktop through the embeddings feature) stay on bundled roots and are named in the crate's design as a follow-up; a failed discovery or roster request now names its cause (582f21251). The design documents, the tunnel and agent READMEs, the docker and e2e READMEs, the dev README's macOS and Windows steps for a private CA (`SSL_CERT_FILE` is not read there) and the manual's gateway page say so (b3d0d02d6, 94806d516); the Nix cargo hash re-pinned for the new lock.
