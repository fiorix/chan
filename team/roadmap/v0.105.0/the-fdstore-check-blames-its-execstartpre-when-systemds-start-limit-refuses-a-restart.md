# The fdstore check blames its ExecStartPre when systemd's start limit refuses a restart

Status: raised for v0.105.0 by the owner's word of 2026-10-09, from the v0.104.0 release report's follow-ups; written down, not designed, not accepted for build.

## What was seen

One failed run of an instrument, kept; nothing here is a fault of the product. The v0.104.0 report (`team/release/release-v0.104.0.md`, Follow-ups) asks to "Correct the fdstore fixture's start-limit diagnostic if that instrument is reused". The instrument is `scripts/e2e/devserver-fdstore.sh`, the nine-case check that drives a real `systemctl --user` unit through restarts, a watchdog kill and a crash and counts the fd store after each phase. The round's first run of it, unchanged, at the base commit `9108113357f00c77393fd41932d1a0df2b7a09a8`, failed (`dev/v0104-team/evidence/Runtime104/jobs/e2e-fdstore-base-01.log` and its `.status`: status 6, 2026-10-08T07:42:57Z to 07:44:51Z). Cases 1 to 4 passed; case 5 stopped at its restart with the script's line "FAIL: restart with the moved-prefix drop-in failed (its ExecStartPre refused?)" and the script's own status 1, while the unit's journal in the same log ends "Failed with result 'start-limit-hit'", 7.2 seconds by the journal's stamps after its first `Stopping` line. The author's hand-back reads it as systemd's default of five starts in ten seconds refusing the case's restart "after five rapid starts", with the script's diagnostic a guess at the wrong step (`dev/v0104-team/reports/handback-Runtime104-hold3.md`, "Scoped own-gate and job record" and "Real-unit check and its first failure"). The run was in the runtime seat's guest, at 2 CPUs by that hand-back and on Ubuntu 24.04.4 by `dev/v0104-team/reports/environment-Runtime104.md`.

What made the later runs pass: no code and no script changed. A drop-in on the check's disposable unit, in the guest only, raised its limit (`StartLimitBurst=30`, `StartLimitIntervalUSec=1min`); it was proved on a dummy inactive unit first and removed afterwards, and with it the unchanged script passed all nine cases at the base and at the hold's tip (the same two sections). The review read those jobs and wrote "The first real-unit base attempt remains failed", with the manager back at its "default burst 5 over 10 s" after the cleanup (`dev/v0104-team/reviews/review-Review104-item3-hold3-range-1.md`, "Evidence audited"). The same override was set before and removed after the real-unit runs of the other two holds (`dev/v0104-team/reports/handback-Runtime104-hold2.md`, "Real user-unit stop proof"; `dev/v0104-team/reports/handback-Runtime104-hold1.md`, "The real unit at the two-holds tip, appended 2026-10-08T16:49Z"). So the records named here hold one run of the check without the override, which failed at case 5, and five with it, each with status 0; none passed without it.

The lead held it "as a finding on the gate's own instrument for a roadmap home at the cut, not a change now" (`dev/v0104-team/reports/decisions-Lead104.md`, the entry of 2026-10-08T07:52:16Z; `dev/v0104-team/reports/held-observations-Lead104.md`, row 3 of the index) and disposed it as "Follow-up: fdstore fixture start-limit diagnostic, no repair here" (`dev/v0104-team/reports/held-observation-dispositions-Lead104.md`, row 3). The closed item says of the check that "its own diagnostic names the wrong step" (`team/roadmap/done/three-holds-keep-the-workspace-host-alive.md`, "Hold 3 landing 2026-10-08").

A reading of the released tree made for this item, at `af2af8ac0` and not run. Case 5 writes a drop-in whose `ExecStartPre` rewrites the parked manifest, reloads the manager and restarts the unit, and any failure of that restart goes to the one line quoted above (`scripts/e2e/devserver-fdstore.sh` 737 to 743). The script's `fail` prints its message and the kept work directory and exits 1 (46 to 50); it reads nothing of the unit, though the script has a helper that reads a unit's property (`unit_prop`, 284). A search of the script for `StartLimit` finds nothing, beside `ExecStartPre`, which the same search finds three times. The script's blob is the same at the base commit and at the released tree, its last commit being `c81038611` of 2026-10-03, so the released file is the one that ran. A search of the released `Makefile` and `.github/` for the script's name finds nothing, beside a control that finds the browser suite there: the check is run by hand in a container, as `scripts/e2e/README.md` describes.

Not established: more than one failure on one guest. Whether the unchanged script passes on a slower machine, and whether it met the limit in earlier versions, was not read. The starts were not counted with their times: "five rapid starts" is the hand-back's reading, and the log prints the unit's stop, failure and result lines and no line for a start. The systemd version is not in the records read here. Whether the sibling check `scripts/e2e/devserver-terminal-replay.sh`, which drives the same fixed unit, can meet the limit, and whether any other failure line of either script guesses its cause the same way, was not read. The fd store is Linux only, so nothing here concerns macOS or Windows.

## Desired contract

When systemd refuses a restart of the check's unit by its start limit, the check's failure line says so, from the unit's own result, and does not point at its `ExecStartPre` drop-in; a refusal by that drop-in is still named as one. The record raises a second question and does not answer it, so the item also asks for a decision: whether the check, run unchanged in a guest with the manager's defaults, should pass by setting or resetting the start limit of its own disposable unit, or the override stays the runner's and is written where the check's run instructions are.

## What to do

Reproduce first: run the unchanged script in a guest whose user manager has the default limit, keep the unit's journal whole, and count the starts with their times up to the refusal, which shows whether the script's own pace meets the limit and at which case. Read the other restarts and failure lines of the script, and the sibling replay check, for the same exposure and the same guess. Then construct the two causes apart before any real run: a start limit made certain on the disposable unit by a burst of one, and an `ExecStartPre` helper that exits non-zero; the script's existing self-test modes (`CHAN_FDSTORE_E2E_SELFTEST`) are the form a constructed case can take. Put the second question to the lead with the reproduction.

## Boundaries

`scripts/e2e/devserver-fdstore.sh`; `scripts/e2e/devserver-terminal-replay.sh` only if the reading shows the same line or the same exposure there; `scripts/e2e/README.md` and `scripts/e2e/scenarios/workspace-lifecycle.md` where they say how the check is run. Not changed: any product file, the unit that `chan devserver` writes among them; the nine cases and what each asserts; the snapshot and restore of a unit that existed before the run, and the masking of the token; a manager's defaults outside the check's own disposable unit. Not this item's: the host-release limits that the same sentence of the report names.

## Acceptance

1. A run record of the unchanged script in a guest with the manager's default start limit: the case it reached, the unit's result, each start with its journal time, the guest's CPUs and the systemd version; a pass is recorded as a pass, with the same times.
2. With the start limit met at a restart, the check's failure line names the start limit as the unit reports it and does not name `ExecStartPre`; shown by a constructed case that is red first on the present line.
3. With the `ExecStartPre` helper made to fail, the failure line names that step and not the start limit, in the same constructed harness.
4. The lead's decision on the second question is recorded here: the check sets or resets its own unit's limit, or the override stays with the runner and is written in the check's run instructions.
5. If the check changes its unit's limit: a run under an unchanged manager ends with the script's `PASS: all 9 cases` line and status 0, and afterwards no drop-in or unit of the check remains and the manager's limit reads as before.
6. `make shell-check` passes at the commit in the owning guest.
