# A gateway connection's windows across a devserver restart are unobserved

Status: raised for v0.105.0 by the owner's word of 2026-10-09, from the v0.104.0 release report's follow-ups; written down, not designed, not accepted for build.

## What was seen

v0.104.0 shipped the direct-connection half of [native-windows-across-a-devserver-restart-the-open-half](../done/native-windows-across-a-devserver-restart-the-open-half.md): a devserver withholds its window list and its window feed with a 503 until its start has settled, and a desktop that dialed it directly reads that 503 as a declined round. That item's status line names what did not ship: an observed guarantee on the gateway path, "where a gateway connection's 503 still counts as a dead round and a representative gateway stack could not be driven in a guest". The team observed nothing of the gateway path on any engine. The delayed arms that stand beside it ran on a direct connection, on Linux WebKitGTK 2.52.6 only (the item's sections "Repaired 2026-10-08" and "Post-repair window 2026-10-08").

Why no guest could drive it, as two source reads record. `dev/v0104-team/reports/gateway-Desktop104-stagea-source-1.md` ("Result", "Evidence chain" and "What follows, and what does not"): the stock desktop's HTTP and WebSocket clients verify servers against the compiled-in Mozilla root set only (`reqwest` and `tokio-tungstenite` linked with the bundled roots, no call site adding a root, the OS store read only by the tunnel dialer), so a gateway whose certificate chains to a guest-made authority fails verification before any HTTP. That is a reading of the compiled units and their dependency source in a Linux guest, not a runtime observation, and the macOS and Windows artifacts were not read. `dev/v0104-team/reports/gateway-Desktop104-cleartext-route-1.md` ("Result" and "The two rules"): a cleartext loopback stack cannot serve a desktop entry, because the proxy admits a cleartext public URL only for `localhost` or a loopback IP literal on a loopback listener (`require_secure_public_url` in `gateway/crates/devserver-proxy/src/config.rs`) while the identity service mints a tenant origin only one DNS label below the proxy apex (`validate_node_base` in `gateway/crates/identity/src/config.rs`). That is a reading of the checked-in source; nothing was built, configured or run.

What the desktop does on a gateway connection, read at the released tree and not run. In `desktop/src-tauri/src/window_watcher_wiring.rs` a feed error carries a `declined` flag that only `connect_raw_ws`, the direct dial, can set; the doc comment of `FeedError` says a gateway connection's error never reads as declined, because the gateway's proxy answers 503 of its own. `feed_round` therefore reads every gateway round without a frame as dead, and `FeedRounds::settle` marks the devserver unreachable at `FEED_UNREACHABLE_AFTER`, two dead rounds in a row. The review of the repair design read what that means while a start withholds its feed, at source and for the code before the repair (`dev/v0104-team/reviews/review-Review104-item4-repair-design-1.md`, the section "What holds at source" and the one headed "a restoring devserver will read as unreachable on the desktop"): after two refused rounds, about two to four seconds, the desktop shows a serving devserver as unreachable and raises its attention signal until the first admitted frame, and it keeps its windows meanwhile, since a refused round leaves the last set in place. The repair removed that for direct connections only.

What stands in for the path, by the cleartext report's section "What is left for acceptance 4": after entry, a gateway connection's windows reach the same feed, watch loop and reconcile as a direct one, and the server's gate is in the router both paths share.

Not established, and named so in that section and in the release report (`team/release/release-v0.104.0.md`, Desktop, Follow-ups and Known gaps): the cookie and Origin upgrade, the `wss` hop and its certificate chain, the tunnel's readmission after a devserver restart, the entry exchange, how the proxy relays the devserver's 503 beside the 503s it answers itself, and every engine but Linux WebKitGTK. Not named one by one in either, and unobserved with the rest of the path: whether a desktop connected through a gateway keeps, closes or replaces a window while the feed is withheld, and whether it shows the devserver unreachable for the length of a restore. The same section names what would observe it: a real deployment with a publicly trusted certificate, which only the owner has, or a desktop build that trusts one more root, which is a different binary from the stock one and was excluded in v0.104.0.

## Desired contract

With a devserver behind a gateway restarted while a desktop holds its windows, the desktop keeps those windows through the withheld feed and retargets each in place once the window set is whole, a workspace turned off and a discarded window still close, and the record says what the user is shown meanwhile; or the item says from an observation why the gateway path differs. The item asks first for a decision on how the path is observed: the owner's reading on a real tenant, a diagnostic desktop build that trusts one added root against a guest gateway and is named as not the stock binary, or the written form kept as a standing limit.

## What to do

Put the three routes to the owner with their costs. For a real tenant, write the steps beside reading 7 of the owner's checklist, which already asks for a devserver published through the real gateway and restarted with a workspace window and a terminal window open (`dev/v0104-team/reports/checklist-owner-readings-v0.104.0.md`, section 7; the readings themselves are [the-owners-ten-display-readings-are-not-taken-and-two-have-no-team-fixture](the-owners-ten-display-readings-are-not-taken-and-two-have-no-team-fixture.md)), and add what this item needs recorded: each window's fate through the gap, what the launcher shows for that devserver and for how long, and the desktop's log lines for its feed rounds. Before the observation, read at source which answers the proxy can give a feed upgrade while the tunnel is absent and while the devserver refuses, so the record can say which 503 the desktop received. Only an observation that shows a closed window or a misleading unreachable state opens a repair, designed and reviewed before code.

## Boundaries

Reading: `desktop/src-tauri/src/window_watcher_wiring.rs`, `window_watcher.rs` and `gateway/crates/devserver-proxy/src/proxy.rs`. Fixtures and run sheets: `scripts/e2e/desktop-observations/`. Not changed by this item: the desktop's trust in its compiled-in roots, the gateway's cleartext and tenant-origin rules, the settled-start gate and the direct-connection rule that v0.104.0 shipped. A diagnostic build that trusts another root is never shipped and never called the stock desktop. No product change before the observation.

## Acceptance

1. The route is decided and the decision recorded here with the words put to the owner.
2. One recorded restart of a devserver behind a gateway with a workspace window and a terminal window of it open on a desktop, naming the engine, the gateway used (a real tenant or a diagnostic build) and the binaries: each window's native identity before and after, and whether any window closed or was replaced.
3. The same record says what the launcher showed for that devserver through the gap, reachable or unreachable and for how long, and which answers the feed's upgrade received.
4. A workspace turned off and a discarded window close in the same arrangement, or the record says why that arm could not run.
5. If no arrangement can be had, the item closes as unobserved with the reason and with what stands in for the path, and not as passed.
