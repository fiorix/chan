# A program in a chan terminal cannot report its status (OSC 7501)

Status: raised for v0.105.0 by the owner's word of 2026-10-09 ("let's write an implementation plan for the `chan` and `cs` commands and chan's terminal to support OSC 7501"); assessed against the tree at `04b231515`, designed below, and reviewed twice by a second agent (see Review). The owner accepted its scope the same day, ("agree with the scope"), which with the end-to-end checks added at the owner's word is all seven stages, and settled the window's marks, chan's own reporters and what counts as seen (see Decisions). Every decision in it is settled; it waits to be cut for build.

## What was seen

The Program Status Protocol is a terminal escape sequence, OSC 7501, with which a program tells its terminal what it is doing: `idle`, `working`, `done`, `blocked` or `error`, with an optional reason. Its specification (`https://www.superlogical.com/rex/docs/build/program-status`) was first drafted on 2026-09-28 and announced on 2026-10-06 (`https://mitchellh.com/writing/program-status-osc7501`); it is read here at revision 0.3 of 2026-10-07, its third in ten days, and that text is kept as `dev/osc7501/spec-rev-0.3.txt`. A report is `OSC 7501 ; key=value(:key=value)* ST`; the terminal keeps one record per `id`, each report replaces its record whole, and `OSC 7501 ; ? ST` is a query the terminal answers with the same body.

What chan does with it today. Each point is a source reading at `04b231515` unless a run is named; the runs are in `dev/osc7501/`.

1. Nothing reads it. `git grep 7501` over `crates`, `desktop/src-tauri/src` and `web/packages` finds no line (the same search for OSC 52 finds 33). A chan terminal is one server-side PTY session (`crates/chan-library/src/terminal_sessions.rs`) with any number of web clients attached, each on its own WebSocket, under one of two engines. xterm.js 6.0.0 sends an OSC identifier it has no handler for to a fallback that only logs at debug level, and 7501 is not among the twelve it registers, so a report draws nothing and gets no reply. ghostty-web `0.4.0-next.20.g1858a59` entered this repository in `0d3926925`, authored 2026-07-24, two months before the specification's first draft, and its type declarations offer no way to register an OSC handler; what it does with a report or a query was not run.
2. The server already walks every byte a PTY prints. `Session::record_output` (line 5820) feeds each read to `VisibleScan` (`terminal_sessions/bytes.rs`, line 31), which carries its position from one read to the next and skips an OSC payload of up to 4096 bytes; the same function tracks the alternate screen and seven private modes, and notes a cursor-position query so that the library can answer it when no client did within 150 ms (`take_due_dsr_answer`, line 5909). `VisibleScan` is an approximation built for one question, whether visible text was printed: any ESC leaves a string, CAN and SUB cancel nothing, and its 4096 counts the payload alone. It is the place to hang a parser, not a parser.
3. Two things chan infers today are what the protocol states outright. The write queue behind `cs terminal write` delivers when "the agent is IDLE", and its only signal is 800 ms without visible output (lines 92 to 103); the manual names the case that misses. The tab strip's unseen-output dot (`terminalActivity`, `web/packages/workspace-app/src/state/tabs.svelte.ts`, line 456) says that something was printed, not whether the program wants the user.
4. `cs terminal list` reports name, agent, placement, window status, queue depth and working directory per session (`TerminalSessionSummary`, line 940; the payload in `crates/chan-server/src/control_socket.rs`, line 5029; the table in `crates/chan-shell/src/cli.rs`, line 2724). It has no word for what the program in a session is doing, and its table already has a column named `status`, which is the window's liveness.
5. Nothing in chan parses OSC 133 and chan installs no shell integration (`git grep` for `133;` and `OSC 133` in the same trees: no line). The specification ends `working` and `blocked` records at the shell prompt mark `OSC 133 ; A`.
6. A PTY's `TERM` defaults to the configured `default_term` (`crates/chan-library/src/config.rs`, line 57) and a spawn's own environment can replace it; chan ships no terminfo entry of its own to carry the specification's `Pst` capability.
7. Neither agent binary inspected here holds the sequence as a literal: Claude Code 2.1.284 and Codex 0.160.1 have no `]7501` and no `7501;`, with `]52;` found in both as the control. A program can build the sequence at run time, so this shows the literal's absence and no more. The specification's author reports proofs of concept for both, as plugins or forks.
8. A hook of Claude Code has no terminal of its own, and its parent's is within reach. A `SessionStart` hook run under Claude Code 2.1.284 in a chan terminal on Linux is its own session with no controlling terminal: none of its three standard descriptors is a terminal, read before any redirection and beside a control that reads yes on a PTY, and `/dev/tty` does not open. Its parent holds the terminal, and from the hook that device (`/dev/pts/N`, owned by the user) opens for write (run on 2026-10-09, `dev/osc7501/probe-hook.out`). The tool shell of a Claude Code session is in the same position, one process further from the terminal. One hook kind on one platform was measured. The environment contract carries no per-session identity: `CHAN_TAB_NAME` is a name two sessions can share, and there is no session id variable (`cs dump-skill --topic cs`).
9. A session ends with its process, and the end is not ordered after its last output. On the exit event the socket loop removes the session and closes (`crates/chan-server/src/routes/terminal.rs`, line 1110), and an exited session with no client is reaped (`reap_exited`, line 3266); the tab stays ("process exited; press Ctrl+D to close this tab") with its session identity cleared. The controller announces the exit as soon as `try_wait` sees it (line 4509) without waiting for the reader thread (line 4403), so what a program prints just before it exits can be recorded after the exit was announced.
10. The protocol's reply is byte-identical to its query, and a PTY can hand it back. Written as input to a PTY with echo on and `ECHOCTL` off, the reply returns as output unchanged, which is a new query; with the default line discipline it returns as `^[]7501;?^[\`, and with echo off not at all (run on 2026-10-09 on Linux, repeated by the reviewer, `dev/osc7501/probe-echo.out`). A terminal that always answers loops there at the speed of the PTY.
11. chan has no path that raises a notification outside its own window: no notification plugin in `desktop/src-tauri` and no use of the web Notification API in `web/packages`.
12. The reference implementation is a parser in libghostty-vt (ghostty pull request 14560, merged 2026-10-06, read at `a4aacd918`; its diff is `dev/osc7501/ghostty-pr-14560.diff`). It validates one report at a time, leaves the records to its embedder, and answers the query only while the embedder has registered a handler, "so programs don't send reports that nothing reads". The Ghostty application ignores the reports for now and answers no query. Where the specification leaves a case open, this is how its author's code reads it, and this item follows it except where it says otherwise: the body after `7501;` is limited to 4087 bytes, which is the 4096 of a sequence ended by `ESC \` and one byte less for BEL; leaving the string for any reason dispatches the report, an ESC followed by any byte and CAN and SUB included (xterm.js 6.0.0 does the same on ESC and abandons on CAN and SUB); every pair that holds an `=` is held to the key length limit, and every alphabet-valid pair to the value limits and every `id` among them to its grammar, also one that a later pair replaces, while a pair with a byte outside the value alphabet is skipped for its value, and only the winning `title` and `msg` are decoded; an `app` over 32 bytes discards the report and one outside its character set is absent; an empty `id` discards it and an empty `msg` or `title` is absent; the reply ends with BEL for a query that BEL ended and with `ESC \` otherwise. Its notes for embedders say to keep `done` and `error` "until the user has seen them, for example until they next focus the terminal". It answers every query it is given, with no bound, so the loop of point 10 is open to an embedder that registers.
13. Three `cs` commands hold their connection to the server open while they wait, and the server already knows when each begins and ends. A survey is parked until its answer, its timeout (600 seconds unless told otherwise) or, for a request flagged as `cs` flags it, the client's end of file (`TermSurvey`, `crates/chan-shell/src/wire.rs`, line 423); an export is a blocking round trip that can be cancelled the same way (`Export`, line 404); and for a tunnel "the connection's lifetime IS the tunnel's": the server acknowledges when the desktop's listener is up, reads the client's end of file as the command ending, and writes a second line "only if the tunnel dies before the client does" (`Tunnel`, line 185). None of the three requests names the terminal that sent it: they carry a target or a window, and the fourteen keys chan sets in a terminal's environment (`CHAN_SPAWN_ENV_KEYS`, `terminal_sessions.rs`, line 760) hold no session id. `cs tunnel` prints its acknowledgement on standard error and nothing while it runs, and a search of `crates/chan-revtunnel` for a count of bytes finds none.
14. What others do, read on 2026-10-09 in their own documents, kept under `dev/osc7501/prior-art/`. Three days after the announcement a search of GitHub for the sequence, capped at thirty results, returns thirty files in over twenty repositories, terminals and reporters both. Terminals that read the protocol keep the records with the pane and let `done` and `error` wait there for the user: cmux until "you focus that pane again", as the reference implementation's notes also say; con-terminal and tuios until input is typed in that pane; termy until replaced or cleared. None of them describes keeping a finished program's status once its pane is gone. For a reporter that does not own the terminal, the tools that host agents give it an id in the environment and a command or socket of their own: herdr sets `HERDR_PANE_ID` and takes `pane.report_agent` on its socket, cmux has hooks call `cmux notify` and `cmux set-status`, Harness passes `HARNESS_SURFACE` to `harness-cli notify`, fut defaults its command to `FUT_TERMINAL_ID`. The two reporter libraries read say as much of themselves: `osc-status` writes to standard error when that is a terminal unless told another stream, and `pi-osc7501` writes to its terminal and swallows a failed write; neither describes looking for an ancestor's terminal. Claude Code keeps its hooks away from the terminal on purpose. Its changelog for 2.1.139 reads "Fixed a bug where a hook writing to the terminal could corrupt an on-screen interactive prompt; hooks now run without terminal access", and its hooks reference says a hook and its children "can't open /dev/tty or send escape sequences directly to the Claude Code interface". What it offers in place, since 2.1.141, is a `terminalSequence` field in the hook's output that Claude Code writes itself, limited to a list (OSC 0, 1, 2, 9 with its 9;4 progress, 99, 777 and a bare BEL) outside which "the field is ignored"; 7501 is not on it. A request to give hooks the terminal's path (its issue 58343) was closed as not planned, and an earlier one (30910) describes hooks on macOS as orphaned, with a parent of process 1. A run here of a hook returning the field proved nothing either way: its control, a title, did not reach the PTY any more than the report did (`dev/osc7501/probe-termseq.out`). One more practice bears on a limit of this item: tuios notes which process group held the terminal's foreground when a report arrived and drops `working`, `blocked` and `idle` when that group is gone, because "A shell without OSC 133 marks does not tell tuios that a prompt started".

Not established: what ghostty-web does with a report or a query; whether a Windows ConPTY passes an OSC it does not know from the child to chan's reader, in order or at all; what a Codex hook, another kind of Claude Code hook, or any hook on macOS has for a terminal; any program the write queue targets that emits the protocol, so what the queue should do with a `blocked` record has nothing to be measured against.

## Desired contract

A chan terminal implements revision 0.3 as a terminal, on the server, for every session, with or without a client attached, with the limits named here and nowhere else:

1. A well-formed report updates the session's record set exactly as the specification's Syntax, Records and ids, States, Keys and Limits sections say, including every rule that discards a report whole, and a report split across PTY reads at any byte is read the same as one that is not.
2. No record ends because time passed, and none needs sending again to stay.
3. The query is answered by the library alone, with the same body and the terminator the query used, whether or not a client is attached, and ahead of any client's answer to a `CSI c` sent right after it. No engine answers it. Three limits, each a departure from the specification's MUST and each a bound on work: no answer while the PTY would echo it back unchanged (echo on, `ECHOCTL` off), no more than a fixed number of answers a second, and no more than a fixed number waiting to be written.
4. A program's records end where the specification says: `working`, `blocked` and `idle` are dropped when the session's process exits and at `OSC 133 ; A`, which chan sees only when the user's shell emits it; `done` and `error` survive both, for as long as decision 2 gives them a place to be; a full reset (`ESC c`) from the program and a restart of the session in place remove every one of the program's records; a soft reset and a switch of screen remove none. Beyond the specification, on Unix, `working`, `blocked` and `idle` are also dropped when the job that held the terminal's foreground as the report was read is gone, so that a script which is killed leaves no spinner behind under a shell that sends no prompt mark. That is a heuristic with the limits stage 1 names, and not a guarantee.
5. What a program reports just before it exits is read before the exit is announced.
6. Every window attached to a live session holds the same records for it: a window that attaches later, and one whose socket fell behind on output, hold the current records with no further report. What a page shows differs in one way, by decision 3: the page whose tab is in front hides an unseen mark for itself. One case stays as it is today and is not cured here: a socket that loses the restart event to lag stays on the old session. A graceful devserver restart on Linux carries the program's records of each session it carries; any other restore starts with none.
7. `cs terminal list` says what each session's program reports, and `cs` can send a report in band, in any terminal that implements the protocol, and inside a chan terminal also for a process that has no terminal of its own.
8. Everything a record carries is untrusted. Its text is shown as text, with direction overrides and invisible formatting disarmed, beside the name of the tab it came from; it reaches no log line, no error message and nothing written to a PTY; and a program that reports as fast as it can write costs bounded memory and bounded work, each bound named.
9. A chan command that waits shows on the terminal it was run in: `cs terminal survey` as blocked on a question for as long as it is parked, `cs export` as working while it renders, `cs tunnel` as working while the tunnel is up and as an error when the tunnel ends other than by the command's own end, and `chan upgrade` as working and then done or failed. None of them touches the record of the program that ran it. The three that wait on the server cannot leave a stale mark: the server sets it and the server removes it.

The protocol's own boundary holds: chan stores state and chooses presentation, and reads no meaning into `msg`. Nothing is readable through the PTY. Through `cs` a session's records are readable as its scrollback already is.

## What to do

One parser, on the server, is the design. A parser in the web client would be written twice, would lose its records with the page, would differ between two windows on one session, and would be invisible to `cs`. The server walk exists, carries state across reads, and has the precedent of the library answering a query itself.

Stage 1, the library (`crates/chan-library`). A module beside `bytes.rs` holds the record set and the report grammar.

- Framing has its own rules, stated, and does not borrow `VisibleScan`'s. An OSC whose identifier is exactly 7501 or 133 is buffered up to the body limit, 4087 bytes after `7501;`, and is applied when BEL or an ESC ends it, whatever byte follows that ESC, as both engines chan ships and the reference implementation end a string; that ESC then begins the escape sequence it belongs to. CAN and SUB abandon it and apply nothing, as xterm.js does and the reference implementation does not. One byte past the limit drops the capture, and the walk goes on as it does today. `ESC c` is a full reset wherever an escape sequence can begin, so one that ends an unfinished report applies the report and then clears every record.
- The visible-byte count does not change. The write queue's idle signal and the unseen-output dot rest on it: the tests in `bytes.rs` pass untouched, and a differential test holds the old and new counts equal over a corpus.
- Every pair of a report is checked before any record changes, as the reference implementation checks it. A key over 16 bytes in any pair that holds an `=`, whatever its value, a value limit broken by any alphabet-valid pair, or an `id` outside its grammar in one, discards the report, also where a later pair with the same key would have won, where the key is unknown, and where the state is `clear`; a pair whose value holds a byte outside the value alphabet is skipped for its value and its key is still measured. Only the winning `title` and `msg` are decoded: base64 that does not decode, bytes that are not UTF-8, a control character, or a decoded length over the limit discards the report. The two cases the specification's sections read differently are settled the same way: an `app` over 32 bytes breaks a limit and is not merely absent, and text that is not UTF-8 is text that does not decode. A replaced value is held to its encoded limit and is not decoded, as in the reference implementation, so one whose decoded length alone is over the limit does not discard the report; the specification's Limits can be read to ask for more, and this item does not.
- The set is published as a current value with a revision, on a `watch` channel, and not as events on the output channel. It is published under the lock that changed it and kept when no socket is attached. `record_output` publishes at most once per PTY read; a reader gets the latest value and never an older one after a newer; a socket that lags on the output channel keeps its status, where an event there would be lost for good (`routes/terminal.rs`, line 1172, prints an error and carries on); and no snapshot copies queue in the 1024-event channel. Reports, the focus word and a report handed over the control socket change the set under the one lock, and the seal's sample is taken after those already admitted: they move no position in the ring, so the position check of stage 2 cannot see one lost.
- The query's answer is enqueued on the session's input channel before the bytes of that read are pushed to the ring or broadcast, so no client can answer a following `CSI c` first. Both controllers serve that channel; the restored session's has no tick to ride. The controller makes the line-discipline check when it writes the answer, through the PTY handle it owns, so a change between the read and the write is seen; where the line discipline cannot be read, the two caps alone apply. An answer past either cap is dropped.
- The exit has one owner. It waits, with a bound, for the reader to drain what the process wrote, then drops `working`, `blocked` and `idle` once; output read after that changes nothing. The bound covers a descendant that keeps the PTY open. Fresh sessions, restored sessions and a read failure take the same path.
- A killed job takes its records with it, by a heuristic. The byte stream does not say who wrote a report, so a report that sets `working`, `blocked` or `idle` is tagged with the process group that holds the PTY's foreground when the report is read (`tcgetpgrp` on the master), unless that group is the session's own process's. The drainer that visits every session each 150 ms drops a tagged record once no process is left in its group (`rustix::process::test_kill_process_group`; `host.rs` already calls `test_kill_process`), on a path of its own and not behind the write queue's early returns; it drops only a record that is still the one it inspected, and takes only "no such process" for gone. Each record keeps its own group, so one job's end takes only that job's records, and a job stopped with Ctrl-Z still has its group and keeps them. `done` and `error` are never tagged. A report handed over the control socket (decision 4) is tagged the same way, by the foreground at its arrival. The reader needs a descriptor of the master to ask with: on Linux the session already keeps one (`master_fd`, line 3982), elsewhere on Unix it needs one of its own, and a restored session asks through `rustix::termios::tcgetpgrp`. This is chan's stand-in for the prompt mark, taken from tuios; the specification names the session's exit and the mark alone. What it promises is narrower than its name: a job that holds the foreground when its report is read loses its records when it ends. Its limits: none of it on Windows, which has no such groups; a job reached through ssh, tmux or screen shows chan the client's group, which outlives the job; a report from a background job is tagged by whatever holds the foreground then, which at a prompt is the shell and so no tag, and while another job runs is that job, whose end then takes it; a job that reports and is gone before chan reads its bytes is tagged the same wrong way, and its spinner can stay; a group id reused between two visits of the drainer is not noticed; and a restore keeps no tags, so restored records end by the other rules.
- `done` and `error` carry a seen mark, set as decision 3 says. Setting it changes the revision and not the record's place in the update order, which decides ties and eviction.

Stage 2, the wire and the read side (`crates/chan-server`, `crates/chan-shell`).

- The terminal socket's `session` frame carries the current set and its revision at attach, and a new `program-status` frame carries later ones (`ServerFrame`, `routes/terminal.rs`, line 232), paced per socket at no more than one per 150 ms and always the latest; the loop's select is biased, and the new branch must not starve under it. On exit the socket sends the current value before the `exit` frame. On a restart in place the socket takes the new session's value with its new generation. Status frames are not ordered against output bytes.
- A socket that loses the restart event to lag stays on the old session, as it does today. This item does not change that; it is named so that the status design is not read as curing it.
- `TerminalSessionSummary` gains the records and the list payload gains a `program_status` object per session. `cs terminal list` gains one column, `program`, since `status` is taken: the state of the most urgent record whether seen or not, by the order blocked, error, done, working, idle, the most recently updated winning a tie, with its `kind` or `progress` when present and `-` for none. `--json` carries every record with its decoded text, its seen mark and the revision. The order is chan's choice of presentation; the specification sets none.
- The free text is in the JSON alone, and the help says it is written by the program in that terminal. A `msg` in a markdown table an agent reads is another terminal's program writing into that agent's context, and it can hold a `|`.
- The restart manifest's per-session entry (`FdStoreSessionMeta`, line 1006) gains the records, their update order and seen marks, and the framing state with its unfinished string, all sampled with the entry's position under the ring lock, so a report cut by a graceful restart is still read. A restore carries them only from a sealed manifest (`sealed`, `crates/chan-server/src/devserver/fdstore.rs`, line 833) whose ring file is intact and ends at that position. Every other restore path, a stopped or missing ring among them, starts with none, and a session that was not parked does not survive the restart at all.

Stage 3, the window (`web/packages/workspace-app`).

- A server-owned, never persisted tab field holds the set, entered in both tab-field tables beside `queueDepth` (`tabs.svelte.ts`, lines 4285 and 7567) and in the fixture of `state/cloneTabFields.test.ts`.
- The tab strip (`components/Pane.svelte`, line 1580) gives a terminal tab two places, as the owner settled. The leading place is activity: the terminal icon becomes the spinner a loading file tab already shows (`.marker.spinner`) while any of the tab's records is `working`, and a ring filled to the percentage when the root record, or else the most recently updated working record, carries `progress`. The trailing place is attention, one mark by the order blocked, error, done, leaving out `done` and `error` once seen: for blocked a shape per `kind` (a shield for permission, a question mark for question, a key for auth, a pause when the kind is absent or unknown) in `--warn-text`; a check in `--info-text` for done; an exclamation in a circle in `--danger-text` for error. `idle` shows nothing. Only the spinner moves, and it stands still under reduced motion, which `.marker.spinner` does not do today and this stage adds. Shape carries the state and colour repeats it, and each mark has a title and an accessible label, as the dot has.
- The unseen-output dot keeps its meaning and its place, the trailing one. It shows when no attention mark does and no record is `working`: output from a program that says it is working is expected. A tab whose program reports nothing looks as it does today.
- Each place says its state to the DOM in a class or an attribute as well as in its accessible label, so that a check reads the state and never the pixels.
- The four models the owner chose among are drawn in chan's colours, both themes, in `dev/osc7501/tab-status-marks.html`.
- The mark's tooltip, and a list in a program status inspector that this stage adds (a "Program status" entry in the terminal tab's menu opening the shared inspector chrome; no terminal tab had an inspector before), give `app` (a record's own or its nearest ancestor's, resolved when shown), `title` and `msg` as text, shortened, with direction overrides and invisible formatting replaced, under the tab's own name.
- The xterm.js guard list (`terminal/xtermReports.ts`, line 11) registers 7501 as consumed with no reply. ghostty-web at the lock's pin, measured in Chrome 155 (`dev/osc7501-team/evidence/Web7501/ghostty-web-capture/`), rings its bell on a BEL-ended 7501 report or query and otherwise changes no cell and writes no input, and its declarations expose no OSC handler, so the page puts a byte-stream guard in front of its write path, live and replayed bytes alike, that consumes a 7501 sequence through its BEL and hands an ESC, CAN or SUB on, with the server's framing rules; an engine which learns the protocol later cannot become a second answerer. libghostty-vt answers only while its embedder registers a handler, so a later ghostty-web pin answers only if that package opts in; the check is made at each bump of the pin. This guard ships with whichever stage adds the library's reply.

Stage 4, the emitter (`crates/chan-shell`). `cs terminal status STATE` with `--kind`, `--progress`, `--app`, `--id`, `--title` and `--msg`.

- It builds one report by the specification's grammar, refuses an input the limits would have the terminal discard and writes nothing when it refuses, encodes the two text values, and writes the sequence in one write; a failed, short or unflushed write is a non-zero exit.
- It writes to standard output when that is a terminal, and to the controlling terminal otherwise. On Windows it writes to the console's output or refuses, as the Windows measurement decides.
- With neither, inside a chan terminal, it hands the report to the server in one new control request that names its session by `CHAN_SESSION_ID` (decision 4). The request carries one whole report body and nothing else: no query and no reset can be said through it. The server checks it with the validator that a report read from the PTY meets and applies it to the same program records, of that session's current incarnation, under the same lock. It never passes through the PTY's framing, the ring or the visible-byte count, so one that arrives between two halves of a report on the PTY disturbs neither. The record is the program's and stays after the request returns. A request that names no live session is refused and the command exits non-zero. Outside a chan terminal, with no terminal to write to, it refuses.
- In band it needs no control socket and no `CHAN` variable, so it also works over ssh and in any other terminal that implements the protocol, and `chan shell terminal status` is the same command. The sentence in `cs`'s own help that every action but the manual targets the window gains this second exception.
- Its help says that a program run by another program passes `--id`, since a report with none replaces the root record its parent may own, and that such a program ends with `done` or `error` when the result is worth leaving and with `clear` when it is not.
- The verb joins `cs terminal`, where `st` is free and no sibling loses a working prefix: on 0.104.0 `sc` is scrollback, `su` is survey and `s` is refused, and a verb beginning with `r` would have taken `r` from restart.

Stage 5, chan's own commands (`crates/chan-server`, `crates/chan-library`, `crates/chan-shell`, `crates/chan`). The owner's direction: the server marks what it already tracks, and `chan upgrade` reports in band.

- A terminal learns its own session. `CHAN_SESSION_ID` joins the keys chan sets at spawn (`CHAN_SPAWN_ENV_KEYS`, and the code that sets `CHAN_TAB_NAME` near line 4247). The id is the session's own, which a restart in place keeps. A terminal spawned before this change has no such variable until it is restarted.
- `TermSurvey`, `Export` and `Tunnel` gain an optional field carrying it. The server checks that it names a live session and otherwise marks nothing; the command itself behaves as it does today, so an older `cs`, and a `cs` run outside a session, lose nothing. A process can name another terminal's session, which gives it no power the control socket does not already give over that terminal.
- The server sets one record per open request, keyed by that request and held against the incarnation of the session that asked, and removes it when the request ends by any path, a dropped task included: blocked with kind question and the survey's title for a survey; working for an export; for a tunnel, working with the address its listener was acknowledged on from that moment, removed at the client's end of file, and replaced by an error when the tunnel ends from the far side or never comes up. That error stays until it is seen and is then removed, since nothing else will clear it; a program's seen error, by contrast, stays in the JSON. Two requests from one terminal hold two records, and the end of one leaves the other. A restart in place or a close of the terminal drops the records held against the old incarnation; the request itself goes on, and its later end touches nothing in the new one.
- These records are chan's own and are kept apart from what the program reports, in a set of their own: a report, a `clear`, `ESC c`, the prompt mark, the foreground rule and the 64-record cap do not touch them, they touch no reported record, and an id that reads the same in both sets names two records. The set holds 16 a session; past that a seen error goes first, and with none to drop the new mark is not set and the command runs as it would have. Their text is clipped to the protocol's limits for `title` and `msg` and meets the same rule on control characters, since a survey's title is an unbounded string on the wire. They take part in the marks, in the order of updates that decides ties, and in `cs terminal list`, whose JSON says which records are chan's. They are in no restart manifest: a devserver restart ends the requests they stand for.
- `chan upgrade` (`crates/chan/src/update.rs`) reports through stage 4's code, in band, under an id of its own and only when its output is a terminal: working while it runs, then done or error. That is the standalone CLI's replacement path (`run_upgrade`); the desktop route, which hands a background update to the desktop and returns, and a package-manager refusal before the upgrade starts are not marked, and the command's output is unchanged.
- No command reports traffic or any other running figure through a record.

## Decisions

Settled by the owner on 2026-10-09, in the conversation that followed the reviews:

- The marks: two places, activity leading and attention trailing; a shape per blocked kind; `working` hides the unseen-output dot; nothing moves but the spinner; a count of blocked terminals outside the strip is left for later. Each was the recommendation put to the owner, who answered "sure".
- chan's own commands report: "the option for having server side controls do make sense for survey and cs export; i think for chan upgrade inband is fine, and cs tunnel is the one i think we should emit 'working' when it's working, error when it fails". The tunnel takes the server's route as well, which the owner accepted together with the session id in the environment that all three need and with a spinner that turns for as long as the tunnel is up.
- A tunnel's traffic is not status: "it should just print tx/rx to the console not through this, let's not invent stuff".
- No spinner left behind: "i wouldnt like a script to leave a spinner behind". Stage 1 drops the records of a foreground job that is gone.
- Decision 1, scope: stages 1 to 6 in v0.105.0 ("agree with the scope"), and with them stage 7: "in the plan, we need to include the end-to-end tests that will validate this so we can get the agents to verify (on browser at least) as part of the feature complete", "we want all the states verified, and a few tests that will attempt to break it, like the case of a process leaving a spinner behind".
- Decision 3, what counts as seen ("taking your recommendation"): `done` and `error` become seen by the word the dot already uses (`set_focused`, line 5321), read also when the report arrives. That word is one value per session, the last any attached page sent; a page says yes when the tab is its active, visible tab in its active pane. It is not a count of viewers and not the operating system's focus: while one viewer looks, another page's no makes a `done` arrive unseen on the server. The page that is looking hides the mark for itself, as it hides the dot (`components/TerminalTab.svelte`, line 1645), and the other pages and `--json` show it unseen until a page says yes. With it the mark and the dot never disagree, and focus is the example the reference implementation gives its embedders. cmux does the same; con-terminal and tuios wait for typed input.

- Decision 2, records after a session's own process exits ("ok"): a record lives with its session, as everything else of a terminal does. When the process that exits is the session's own (an agent started with `--command`), `done` and `error` stay on the tabs attached at that moment until the tab closes, each page keeping its own seen mark since no server holds the session any more, and they leave `cs terminal list`, a later attach, a reload and a tab moved to another window with the session. A program that reports under a shell is not affected, since the session lives on. This is what the tools of point 14 do: the record belongs to the pane and ends with it. What chan lacks beside them is that its pane, for an exited session, exists in the pages and not on the server.
- Decision 4, a reporter with no terminal of its own ("yes control socket"), which is the measured position of a Claude Code hook: inside a chan terminal, `cs terminal status` with neither a terminal on standard output nor a controlling terminal hands its report to the server over the control socket, named by the session id that stage 5 adds, and the server checks it as it checks a report read from the PTY and applies it to the same records. It works the same on every platform and writes into no other process's terminal. This is what the agent hosts of point 14 do: an id in the environment and the host's own command. The first recommendation of this item, writing to the controlling terminal of the nearest ancestor process, was withdrawn before the ruling: it reaches past a separation Claude Code documents and declined to lift, and it has nothing to find where a hook is orphaned.
- The restart manifest's new fields are defaulted when absent ("correct"), as "What to do" records.

## Left out, each with its reason

- A terminfo entry with `Pst`. The specification makes it a SHOULD and the query authoritative; chan ships no entry.
- A notification outside the window. No plumbing exists for one. A separate item if wanted.
- The write queue reading a record. Holding a queued poke while its target is `blocked` on a permission prompt has the most to gain and the most to break, and no emitting target was found to measure it against.
- chan's other commands as reporters. Survey, export, tunnel and upgrade are in, as stage 5; no other command is shown to wait long enough to matter.
- A tunnel's traffic, or any running figure, in a record. The owner's word is that it belongs on the console. `cs tunnel` printing its rates needs a count of bytes the tunnel's path does not keep today, and is a change to that command of its own.
- A count of blocked terminals outside the tab strip, in the window's title or elsewhere. Left for later by the owner.
- Status in the other places that list terminals: the launcher's Terminals list (`web/packages/launcher/src/components/Library.svelte`, line 358), the command launcher's terminal rows and the cross-window roster stay as they are. A view across terminals (an inbox), a `cs` verb that waits for a state, and mapping OSC 9;4 onto the root record are each new surface.
- Holding an exited session on the server so that its last records stay listed and reach a later attach, the alternative of decision 2. It is the hold-on-exit other terminals offer as an option, with its own cap, names, close and restart rules: an item of its own size.
- Records across a crash. A restore that no seal wrote starts with none.
- tmux and screen inside a chan terminal, which pass an unknown OSC through or not by their own rules.

Tests that try to break it, in the browser:

14. A spinner left behind. In a shell with job control and no prompt mark, a script reports `working`, the record is seen while the script still holds the foreground, and then it is killed with SIGKILL; another is interrupted with Ctrl-C; a third exits without a word. 16. A flood. A program writes reports as fast as it can for some seconds, alternating states with the largest message allowed: the terminal's own output keeps arriving, the record at the end is the last state sent, and the status frames on the session's socket, counted on the wire, are no more than the pace allows for that time and one over.

20. The echo loop: with echo on and `ECHOCTL` off in the PTY, a query is written once, and no reply at all reaches the PTY, read from its input side; the caps alone would also quiet the ring, so the ring going quiet is not the test. Beside it, with the default line discipline, there is exactly one reply. A report sent afterwards is still applied.
21. A report sent while the page's terminal socket is cut: the cut is acknowledged, the redial is held back, a different state is confirmed on the server, and only then is the socket let in. The records the attach sends are the new ones, with no later report and no change of focus to repair them.
22. A reporter with no terminal: a process in a session of its own, its three descriptors redirected and shown not to be terminals and `/dev/tty` failing for it, which is what a Claude Code hook is, runs `cs terminal status` with an id in the subject terminal's environment. The mark follows and the record stays after the command returns; with the session id of a terminal that has closed it is refused and nothing changes.
