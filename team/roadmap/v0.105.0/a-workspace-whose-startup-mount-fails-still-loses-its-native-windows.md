# A workspace whose startup mount fails still loses its native windows

Status: raised for v0.105.0 by the owner's word of 2026-10-09, from the v0.104.0 release report's follow-ups; written down, not designed, not accepted for build.

## What was seen

The repair that v0.104.0 shipped for [native-windows-across-a-devserver-restart-the-open-half](../done/native-windows-across-a-devserver-restart-the-open-half.md) makes a devserver publish its window set only once its start has settled. A startup attempt that fails settles too: the workspace is left unmounted, the first admitted set lacks its windows, and a desktop that reconciles to that set closes them. The item states this as the repair's boundary in its section "Repaired 2026-10-08": a workspace whose startup mount fails (a root past the sixty-second bound, a lock, a missing root) "settles unmounted, is absent from the first admitted set and its windows close as before; pinned as decided behavior, and held as a note for a later version (a per-window restoration signal would be its repair)". Its status line ends "A workspace whose startup mount fails still loses its windows, as decided." The design document says the same at the released tree (`crates/chan-server/design.md`, the paragraph "Window snapshots while a devserver starts or stops"): "A row whose startup attempt fails settles too, so the first set lacks its windows and a client closes them, as it does for a workspace turned off."

What backs each half. The server half is pinned by `a_row_that_fails_its_startup_attempt_is_absent_from_the_first_set` in `crates/chan-server/src/devserver.rs`, a Rust test run in a Linux guest (`dev/v0104-team/reports/repair-Desktop104-item4-handback-1.md`, "Acceptance coverage"). The desktop half, the close of the omitted windows, is a source reading by the review of the repair design (`dev/v0104-team/reviews/review-Review104-item4-repair-design-1.md`, the section headed "a workspace whose startup mount fails still loses its windows when the gate opens"): `finish_failed_attempt` marks the root failed, mounts nothing and settles, the root then does not read mounted, the first admitted set omits that workspace's windows and the desktop's reconcile closes them; the window closes, its record stays, and a replacement opens when the workspace mounts later. The same close was observed natively for a mount that was delayed and not failed: three counted closures on Linux WebKitGTK before the repair (the item's "Counted window 2026-10-08").

How it was disposed: `dev/v0104-team/reports/held-observations-Lead104.md` row 5 and `dev/v0104-team/reports/held-observation-dispositions-Lead104.md` row 5 ("Designed cost: failed startup mount still loses its windows"); the release report's Follow-ups ("decide whether a failed startup mount should retain its native windows through a per-window restoration signal") and Known gaps ("A failed startup mount can still omit its workspace from the first admitted window set and close its native windows") in `team/release/release-v0.104.0.md`.

The alternative the record names, in the repair's design (`dev/v0104-team/reports/repair-Desktop104-item4-design-1.md`, section 2, the paragraph "Cost and alternative"): a per-window restoration signal in the authoritative feed plus desktop retention for exactly those identities, letting complete rows and intentional removals through. The design says it needs a new wire contract, coherent registry and lifecycle sampling and wider library and client tests, and the lead ruled it not built in v0.104.0 (`dev/v0104-team/reports/decisions-Lead104.md`, the entries stamped 2026-10-08T09:55:31Z and 2026-10-08T10:19:38Z). The same paragraph proposes neither a desktop-only grace timer nor keeping every omitted row, since either can hide a real turn-off or discard.

Not established: no native arm ran with a startup mount that fails, on any engine, so the close of a failed workspace's windows on a desktop is a reading and not an observation; how often a startup mount fails in use (the design's section 1 says the arms establish no natural slow-root frequency); what a user sees between the close and a later mount; macOS WKWebView and Windows WebView2; a desktop connected through a gateway.

## Desired contract

The item asks for a decision between two contracts. Either the decided behavior stays: a workspace whose startup mount fails is treated as turned off for its windows, and the design document keeps saying so. Or a desktop keeps the native windows of a workspace whose startup mount failed, told apart from a workspace turned off and from a discarded window, and retargets them when the workspace mounts. Under either, a workspace turned off, a discarded window and a buried window still close.

## What to do

Reproduce first on a native engine: a restart fixture in which one root's startup mount fails in each form the record names (past the sixty-second bound, a held lock, a missing root), recording the window's fate and what the launcher shows, so the decision rests on an observation and not on the reading. Then put the choice to the owner with that record and with the cost the design states for the signal. If retention is chosen, design before code: the fact the feed carries, who sets and clears it, what a client that does not know it does, and how a turn-off and a discard stay authoritative; the review reads the design first.

## Boundaries

Observation: the restart fixtures under `scripts/e2e/desktop-observations/`. If retention is built: `crates/chan-server/src/devserver.rs` and `routes/library.rs`, the window feed assembly in `crates/chan-library/src/host.rs`, `desktop/src-tauri/src/window_watcher.rs` and `window_watcher_wiring.rs`, the launcher's window feed client under `web/packages/launcher/`, and the three design documents that state the feed's contract. Not changed: the settled-start gate and its 503, the desktop's declined-round rule, and what a turn-off, a discard and a buried window mean. The whole feed's wait for the slowest startup work is the shipped repair's declared cost and is not this item, though the design names the same alternative for it.

## Acceptance

1. One native observation of a restart in which a root's startup mount fails while a window of that workspace is open, naming the engine and the binaries: the window's fate and the launcher's display, for each failure form the fixture can reach, with the forms it cannot reach listed.
2. The owner's decision recorded here with the text put to the owner.
3. If the decided behavior is kept: no code, the design sentence stays, and the release report records the decision.
4. If retention is chosen: the design is reviewed before code; the window of a workspace whose startup mount failed is kept through the first admitted set and retargeted in place when the workspace mounts, pinned red first on the server and on the desktop; a workspace turned off, a discarded window and a buried window still close in the same arms; a client that does not know the new fact behaves as it does today, pinned.
5. Every native observation names its engine, and the engines not observed are listed.
