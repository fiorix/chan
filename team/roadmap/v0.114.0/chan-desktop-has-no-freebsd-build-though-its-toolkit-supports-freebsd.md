# chan-desktop has no FreeBSD build though its toolkit supports FreeBSD

Status: carried into v0.114.0 at the v0.113.0 GA on 2026-10-27. The build needs tao 0.37.2, which changes every desktop platform's tao code, the macOS key and IME input path among it; by the owner's choice at the GA the lockfile stays on tao 0.37.1, so chan-desktop does not build on FreeBSD in v0.113.0, and the manual's build steps and the FreeBSD workflow's chan-desktop check were taken out (`403f07b34`). The `cfg` arms and the updater gating shipped in [v0.113.0](../../release/release-v0.113.0.md), where they compile the same code on Linux, macOS and Windows as before; the sections from Built on `v0113/a-freebsd` on hold the evidence.

Record before the release: raised on 2026-10-27 by the owner after the v0.112.0 GA; accepted for v0.113.0 by the owner's word of 2026-10-27 ("organise 3 independent worktrees for 3 agents to work on ... they will build in parallel"); built on `v0113/a-freebsd` on 2026-10-27 (the sections below); the owner's real-session readings, the FreeBSD workflow's first run and the merge into `main` remain.

## What was seen

The owner's words of 2026-10-27: "do you think it's possible to build chan-desktop on freebsd, too?", then, after a trial in a FreeBSD 15 Lima guest on a chan checkout at version 0.112.0, "it worked, include this as an item for the next roadmap".

The trial, in order:

1. `pkg install webkit2-gtk_41 gtk3 pkgconf`: WebKitGTK 2.46.6 with the 4.1 API (GTK 3, libsoup 3) that Tauri 2 links.
2. `cargo check -p chan-desktop` failed in tao 0.37.1 with three `E0425` errors: `crate::window::hit_test` is gated to Windows and Linux (`src/window.rs` line 1665), and the GTK event loop that FreeBSD shares with Linux calls it. tao 0.37.2 (2026-10-23) widens the gate to the BSDs; `cargo update -p tao --precise 0.37.2` cleared it.
3. The check then failed in tauri-plugin-updater 2.14.0, the latest stable release, with four `E0433` and one `E0609`: its AppImage update code is compiled on Linux and every BSD, but the crates it uses (`flate2`, `tar`, `dirs`) are declared for Linux only, its `OsStr` import is gated to Windows and Linux, and it reads `Env::appimage`, a Tauri field that exists only on Linux. A local copy of the plugin with those three gaps closed, through `[patch.crates-io]`, cleared it.
4. The check then finished with three `dead_code` warnings, each a path FreeBSD compiles out: `Native::Done` in `crates/chan-workspace/src/no_replace.rs` (line 61; the native no-replace rename is gated to Linux, Android and Apple), and in chan-desktop `DesktopUpdateReadyPayload` (`main.rs` line 68) and `launcher_panel::show_for_attention` (line 203), both reached only from `notify_desktop_update_ready` (`main.rs` line 3661, gated to macOS, Linux and Windows).
5. The next steps proposed were a linked `cargo build -p chan-desktop`, the web bundles (`make web web-launcher`), and a run under an X11 session; the owner's "it worked" followed them. Which of the three was read, and what the running app showed, is not recorded here.

Read at `ff5713172`:

- The toolkit carries FreeBSD: Tauri 2.12.4, tauri-runtime-wry 2.12.2, wry 0.57.0 and tao 0.37 list FreeBSD beside Linux on their GTK and WebKitGTK paths, and the CLI crates chan-desktop embeds have built and tested on FreeBSD since v0.96.0 (`done/freebsd-is-not-a-published-target.md`, which excluded chan-desktop from its suite).
- chan-desktop has 40 `target_os = "linux"` gates (`main.rs` 17, `launcher_panel.rs` 15, `linux_gui_stack.rs` 6, `terminal_mode.rs` 2) and no mention of FreeBSD, so on FreeBSD each takes the macOS and Windows arm. The in-window launcher builds through wry's `build_as_child`, which under GTK works on X11 only, instead of the GTK overlay the slide relies on; the `gtk` dependency is declared for Linux only; `linux_gui_stack.rs`'s GPU detection and WebKit environment fixes fall to their stubs.
- Release: Tauri's bundler has no FreeBSD format, chan.app's `/dl` metadata has no FreeBSD desktop target for the updater, and the FreeBSD CLI is a static cross-build from Linux, which a desktop that links WebKitGTK dynamically cannot be: it needs a native FreeBSD build, such as a FreeBSD virtual machine job in CI.

## Desired contract

chan-desktop builds on FreeBSD from an unpatched checkout with warnings denied, and runs there with the same window, terminal and launcher behaviour as on Linux. Code that is about GTK and WebKitGTK takes the Linux path on FreeBSD too; what is Linux-specific (the systemd unit, the desktop entry, xdg-terminal-exec, AppImage) stays Linux-only; a feature with no FreeBSD backend, the self-updater among them, is compiled out on FreeBSD rather than patched. Whether FreeBSD desktop is a published target or a build-from-source one is decided and recorded here.

## What to do

1. `Cargo.lock`: tao to 0.37.2 or later, with the Nix cargo hash harvested again in the same commit.
2. The updater on FreeBSD: make `tauri-plugin-updater` a dependency off FreeBSD with its uses gated (the update checks and installs in `main.rs`, the `Update` fields, the plugin's registration in `main.rs` and `terminal_mode.rs`, the update-ready notice), or land the plugin's three fixes upstream and take that release. Report the plugin's gaps to tauri-apps either way, and record which path was taken.
3. One condition for GTK platforms (Linux and FreeBSD) in chan-desktop for the code that is about GTK: the launcher's GTK overlay and its `gtk` dependency, `linux_gui_stack.rs`'s WebKit environment, and the GTK-specific window code. Then gate the three dead items above.
4. The runtime readings on a FreeBSD desktop under X11 and Wayland: a window, a terminal, the launcher's toggle and slide on Ctrl+Shift+P, the plasma background's GPU detection, and the file watcher (`bsdfds`) on a real workspace.
5. The release decision: a FreeBSD port or `pkg` recipe and a `/dl` entry, or build-from-source steps in the manual's install page. A CI job on a FreeBSD virtual machine runs `cargo check -p chan-desktop` with warnings denied either way.

## Boundaries

`desktop/src-tauri/` (`Cargo.toml`, `main.rs`, `launcher_panel.rs`, `linux_gui_stack.rs`, `terminal_mode.rs`), `crates/chan-workspace/src/no_replace.rs` for its FreeBSD warning, `Cargo.lock` and the Nix pins, a CI job if one is added, and the manual's install page if FreeBSD desktop is build-from-source. Not changed: chan-desktop's behaviour on Linux, macOS and Windows.

## Acceptance

1. On FreeBSD 15 with `webkit2-gtk_41` installed, `RUSTFLAGS="-D warnings" cargo build -p chan-desktop` from an unpatched checkout succeeds.
2. The built chan-desktop opens a window under X11, runs a terminal, and shows and hides the launcher.
3. The Linux, macOS and Windows gates and CI stay green.

## Built on `v0113/a-freebsd`, 2026-10-27

- Step 1: tao 0.37.1 to 0.37.2 in `Cargo.lock`, as a hand edit of tao's version and checksum (0.37.2's dependency list is the same; `cargo metadata --locked` accepts the lock). `cargo update -p tao --precise 0.37.2` also re-pointed about fifteen unrelated crates' `windows-sys` edges with the pinned cargo, so it was not used. The Nix `cargoHash` was harvested again in an sdme guest in the default Lima VM (`packaging/nix/build-with-sdme.sh`, `NIX_PACKAGE=chan`): the `-vendor-staging` mismatch reported `got: sha256-Nyod/gzvlxs7ezZCByr92u04Ij3GG3OaSo3N4tiRGzU=` (specified `sha256-Uuh424zdHqxL1TFbF5BeGhQZjL3G8aNQ2rWTZmdOFQo=`), pinned with `make nix-hash-pin`; `make nix-hash-check` passes.
- Step 2, the path taken: the plugin is compiled out on FreeBSD, not patched. `tauri-plugin-updater` is a dependency on every target but FreeBSD, its two registrations (`main.rs`, `terminal_mode.rs`) are gated, and the update-ready notice's payload and `launcher_panel::show_for_attention`, reached only from the update paths, are gated with them. Every other updater use already sat behind macOS, Linux or Windows arms, with explicit not-supported arms elsewhere. The plugin's gaps, for tauri-apps (drafted, not filed; the owner files it or says to): in 2.14.0 the "Linux (AppImage, Deb, RPM)" install path (`src/updater.rs`) and the `app.env().appimage` read (`src/lib.rs`) are compiled for Linux and all four BSDs, but `flate2`, `tar` and `dirs` are declared for Linux only (E0433), the `OsStr` import is gated to Windows and Linux (E0433), and `tauri::Env::appimage` exists only on Linux (E0609). Gating that path to Linux, or widening the three dependency tables and the import, fixes it.
- Step 3, one condition for the GTK desktops, `any(target_os = "linux", target_os = "freebsd")`: the launcher's GTK overlay (all of `launcher_panel.rs`'s platform gates) and the `gtk` dependency; the X11 and Wayland clipboard handle kept for the process (`on_clipboard`, `with_cached_clipboard` and their tests); the GLib program name from `--app-id` (`terminal_mode.rs`); and the `/dev/dri` render-node probe, moved out of `linux_gui_stack.rs`'s Linux module into a `dri` module both share. A FreeBSD build is never an AppImage, so `webgl_renderer_available` answers as a Linux package does (no decision; the SPA keeps its DOM renderer), and the AppImage re-exec and the dma-buf environment stay Linux-only, as do the AppImage updater refusal, the systemd unit, the desktop entry and xdg-terminal-exec. The three dead items: `DesktopUpdateReadyPayload` and `show_for_attention` are gated as above, and `Native::Done` in `no_replace.rs` carries the same dead-code allowance off the platforms with a native no-replace rename that its sibling variant carries on Windows.
- Step 4, read headless on the FreeBSD 15.1 guest under Xvfb (1600x1000, no window manager, no GPU, a throwaway `HOME`, `dbus-run-session`): the window maps ("Terminal Window 1", class `chan-desktop`), a terminal runs (`-sh` under chan-desktop, a `$` prompt on screen), and Ctrl+Shift+P shows the launcher's Computers screen over the window, its menubar attached, and a second press hides it again. The guest has no `/dev/dri`, so the GPU probe reads no GPU there, as it should. The file watcher in the desktop, with `~/chan` handed to it (`chan: opened /home/fiorix.guest/chan in chan-desktop`): descriptors 80 before, 3,552 for the next 40 s, 3,442 of them under the checkout and none under `target/`, no registration failure. Observed and not explained: in all three captures the page renders 900 px wide inside the 1200 px window; without a window manager that may be Xvfb's, so compare under a real session. A handoff from an ssh shell is skipped by design (`gui_session_present` refuses whenever `SSH_CONNECTION`, `SSH_TTY` or `SSH_CLIENT` is set), which is worth knowing when reading this over ssh.
- Step 4 left to the owner, under a real X11 session and a Wayland one on a FreeBSD desktop with `webkit2-gtk_41` and a GPU (drm-kmod): build with `RUSTFLAGS="-D warnings" cargo build -p chan-desktop` after `make web` (the debug binary reads the bundles from `web/dist` and `web-launcher/dist`), run `target/debug/chan-desktop` from a terminal in the session, and check (1) the window opens and a terminal takes input; (2) Ctrl+Shift+P slides the launcher in from the left over the window and slides it out again; (3) the welcome's plasma background runs on the GPU (`ls -l /dev/dri/renderD*` openable by the user) and falls back to its 2D drawing with the render node unreadable; (4) `chan serve <workspace>` from that session's terminal opens the workspace in the desktop, and `procstat -f $(pgrep -f target/debug/chan-desktop) | wc -l` stays flat while files change; (5) the page fills the whole window width.
- Found beside this row, the same class as the watcher row's finding: every notify watcher left in the tree uses notify's kqueue backend on FreeBSD, and its event loop panics there (`kqueue-1.1.1/src/lib.rs:661`, an unwrap on an event for a descriptor it no longer lists). It appeared in chan-desktop and in a standalone `chan serve`, and the standalone server then panicked again at shutdown (`notify-6.1.1/src/kqueue.rs:439`, its `Drop` unwraps a send to the dead loop). The users are chan-server's `config_watch.rs`, its registry reload watcher and `standalone_watch.rs`, and chan-desktop's own notify watchers. A follow-up row.

## Step 5, 2026-10-27

- The release decision, the owner's by survey on 2026-10-27: "Build-from-source (recommended): steps on the manual's install page + a CI compile check". FreeBSD desktop is not a published target: no port or pkg recipe and no `/dl` entry. The manual's Install section (`web/packages/marketing/src/pages/manual/install.html`) gives the steps: `pkg install git rust npm gmake pkgconf webkit2-gtk_41`, a clone, then `gmake web && cargo build --release -p chan-desktop`, and says a source build does not update itself.
- Found while checking those steps on the arm64 guest: `gmake web` fails there, because rolldown, vite's bundler, publishes no FreeBSD arm64 binding (`Cannot find module '@rolldown/binding-freebsd-arm64'`) and the lock carries no WebAssembly fallback; lightningcss has no FreeBSD arm64 build either. `web/package-lock.json` carries `@rolldown/binding-freebsd-x64` and `lightningcss-freebsd-x64`, so amd64 builds the bundles natively. The page says so and gives arm64 the route that was read here: build the bundles with `make web` on Linux or macOS, copy `web/dist` and `web-launcher/dist` in, and run only the `cargo build`. Read on the arm64 guest that way: `cargo build --release -p chan-desktop` (the default profile, thin LTO) finished in 9m44s with the bundles built on the Mac. `gmake web` on amd64 is unread here; the CI job below runs it.
- The CI mechanism, the owner's by survey on 2026-10-27: "vmactions/freebsd-vm pinned to the v1.5.9 commit, new freebsd.yml (recommended)". `.github/workflows/freebsd.yml` boots a FreeBSD 15 amd64 VM on `ubuntu-latest` through `vmactions/freebsd-vm@c46abacb49f09938ca4e1702d15d836285d694cc` (v1.5.9, released 2026-10-03; its inputs checked against that commit's `action.yml`, which actionlint cannot see), installs `curl gmake npm pkgconf webkit2-gtk_41` and rustup so `rust-toolchain.toml`'s pin applies, and runs `gmake web`, `cargo check --locked -p chan-desktop` and `cargo test --locked -p chan-workspace --lib -- watch::` with `RUSTFLAGS="-D warnings"`. It runs on pushes to `main` and pull requests that touch `crates/**`, `desktop/src-tauri/**`, `Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml` or the workflow, and by hand. It has not run yet: a dispatch is outward-facing, so its first run is the merge into `main`, or a dispatch on the owner's word. actionlint passes it.
