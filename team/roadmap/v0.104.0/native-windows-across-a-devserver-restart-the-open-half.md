# Native windows across a devserver restart, the open half

Status: accepted for v0.104.0 by the owner's word of 2026-10-08, as a new item from the record of [a-raw-devserver-restart-may-close-desktop-windows](../done/a-raw-devserver-restart-may-close-desktop-windows.md); the delayed arms are built first so the hazard is reachable, each arm says whether it reached the hazard or only the fixture, and every native observation names its engine. The delayed arms ran on 2026-10-08 and counted the hazard three times on Linux WebKitGTK (see Counted window); the repair design follows, red first.

## What was seen

v0.103.0 shipped the shutdown half of the restart item: a stopping devserver publishes no window set its shutdown shortened (the window list and new feed requests answer 503 during the stop). The restart half did not ship: on a desktop built from the candidate, a graceful restart and a kill-and-restart of a raw devserver each kept the workspace window once, and the hazard the item names, a restart whose window feed is incomplete, was observed in neither arm, because the fixture restores within a second. Open, as the v0.103.0 report's Follow-ups record: the incomplete-feed case (a restart whose window feed omits a window the desktop holds), the delayed arms that hold the restore open (designed in the v0103 round, never run), and the gateway path (a devserver behind a gateway restarted with windows open, the reading that acceptance 3 of [the-desktop-probe-takes-a-gateway-404-as-ready](../done/the-desktop-probe-takes-a-gateway-404-as-ready.md) names). The closed item's contract still holds: a graceful restart leaves a connected desktop's native windows of that devserver open, to be retargeted in place; only a discarded window, a workspace turned off, or a window the user buried closes.

## Desired contract

With the restore held open long enough for the desktop to see an incomplete feed, the desktop keeps the native windows of a restarting devserver and retargets each in place once the window set is complete; a workspace turned off and a discarded window still close; the same holds for a devserver behind a gateway, or the item says from the code why the gateway path differs.

## What to do

Build the delayed arms first (a restore held open by a fixture-controlled delay, long enough that the desktop's reconcile runs against a partial window set), then drive the incomplete-feed case through them, with the arm reporting whether it reached the hazard (a desktop reconcile against a feed that omits a held window) or only the fixture. Read the gateway path early and say whether it can be driven in a guest; if it can, run it; if not, say what covers it. Repair only what the arms show: if the desktop closes a window the incomplete feed omitted, repair the lifecycle meaning so an outage is distinguishable from a removal, red first. Linux WebKitGTK is the engine this host runs; macOS WKWebView and Windows WebView2 are not observed unless the owner takes a reading.

## Boundaries

`desktop/src-tauri/src/window_watcher.rs`, `window_watcher_wiring.rs` and the desktop's restart fixtures under `scripts/e2e/`; on the server side only through the lead, since `crates/chan-server/src/devserver.rs` and `routes/library.rs` are leased to the seat of [three-holds-keep-the-workspace-host-alive](three-holds-keep-the-workspace-host-alive.md). The desktop's wait for a restarting devserver and its retarget are not changed by this item.

## Acceptance

1. The delayed arms run on Linux WebKitGTK with the restore held open for a recorded duration, each arm's record saying whether it reached the hazard or the fixture.
2. The incomplete-feed case driven through a delayed arm: either the desktop keeps the omitted window and retargets it in place (observed, with its record), or the defect is shown and repaired red first.
3. A workspace turned off and a discarded window still close in the same arms.
4. The gateway path: run in a guest with its record, or a written reason it cannot be driven there and what stands in for it.
5. Every observation names its engine; readings on other engines are the owner's, listed in [the-owners-display-readings-need-a-checklist](the-owners-display-readings-need-a-checklist.md).

## Counted window 2026-10-08

The desktop seat built the delayed arms first (`dev/v0104-team/reports/observations-Desktop104-item4-window-1.md`): a fixture-controlled delay holds the restore open while the desktop's startup reconcile runs against a window feed that omits a held window, and a reader classifies each arm from the native event chain, saying whether it reached the hazard or only the fixture. Under one granted window on 2026-10-08 (09:03Z to 09:20Z, the guest at 8 GiB and two then four CPUs) nine attempts ran against the frozen fixture `10c4e2443` and a diagnostic observer build `8092317ba` over the integrated product at `ed8cfff9e` (the base with the animation picks; hold 3's later landing differs only in `fdstore.rs`, outside the gated region), on Linux WebKitGTK. Both intentional-removal controls passed: a workspace turned off and a discarded window closed as the contract requires. The three completed delayed arms (graceful at two and at four CPUs, kill at four) each reached the hazard: with the restore held for 1.63, 2.13 and 1.62 s, the desktop consumed the omission, decided the close in the same pass and destroyed the original native window inside the held interval, the window's record returning afterwards and a replacement page opening in its place. The two fast comparisons kept the original window and page but consumed no omission, so they prove the fixture, not survival. Two attempts refused on a fixture prerequisite (two new terminal window ids, so no unique control identity) and are retained; their unchanged retries reached their arms. Every attempt is counted and contended (residual swap and rising host memory pressure; no cap or OOM event; zero throttled periods at four CPUs). The reviewer replayed the completed summaries and the two refusals from the retained inputs in its own guest and accepted the result (`dev/v0104-team/reviews/review-Review104-item4-counted-direct-1.md`). This establishes the defect of acceptance 2: the desktop closes a window an incomplete startup feed omitted. Open: the repair, designed red first with the intentional closures preserved, and its post-repair record; the gateway path (acceptance 4); the owner's readings on other engines.

## Repaired 2026-10-08

The desktop seat's repair is on the integration branch at `91403b0b8bb06f9899fb61ee373530840f697153`, five commits (`dev/v0104-team/reports/repair-Desktop104-item4-design-1.md`, its addendum, and `dev/v0104-team/reports/repair-Desktop104-item4-handback-1.md`). The server half: a devserver's window list and new window-feed watches answer the existing error-only 503 until its start has settled, a fact the startup coordinator records when the inherited state has been applied (at the fd-store apply, or at Ready with the late apply claimed) and every tracked startup attempt has settled; the gate is read before a set is assembled and again after it, the stop gate kept, and a watch admitted before the gate opened never publishes a set assembled without admission. The desktop half: a 503 answer to the feed's upgrade on a direct connection is a declined round, which counts for nothing toward the unreachable mark and clears a mark the restart's downtime set, emitting the restored event and the library-change signal as the first frame's clear does and never attention; a gateway connection's error stays a dead round, since the proxy answers 503 of its own. Red first: seven of thirteen server pins failing on a status or a frame at `21e227273` (the list and the feed refused while a restore is held, Ready at the bound keeping the list refused until the late apply, a tracked attempt keeping it refused, a no-rows start opening it once ended, and the two order pins through a second seam point after the assembly), two of three desktop pins failing at `c4e566483` over a mock feed endpoint; six server mutations each red on the pin written for it, and the reviewer's own two mutations (the before-assembly read removed; the fact recorded at Ready-at-the-bound) failing the order and bound pins in its guest. Gates: fmt and clippy clean for both crates, the `chan-desktop` suite 583 passed, the whole `chan-server` suite 2,137 passed under a quiet window (194.80 s, the host's pressure read at both ends and the other guests idle) after a loaded run had three timing-bound failures at twice that time, recorded as the host's load. The reviewer accepted the design for the red-first build and the range for landing (`dev/v0104-team/reviews/review-Review104-item4-repair-design-1.md`, `review-Review104-item4-repair-range-1.md`).

The cost, stated: the whole window feed waits for the slowest tracked startup work, on every start and not only a restart; while it is withheld no window of that devserver opens on the desktop, a new terminal or workspace window the user asks for and the first-connect boot terminal included, since the watcher is the sole driver of a devserver's native windows; with local roots the interval is the restore itself, under a second in the fixtures, and one root that does not answer costs its sixty-second attempt, up to the restore's eight-minute budget at worst. The repair's boundary: a workspace whose startup mount fails (a root past the sixty-second bound, a lock, a missing root) settles unmounted, is absent from the first admitted set and its windows close as before; pinned as decided behavior, and held as a note for a later version (a per-window restoration signal would be its repair). One follow-up ordered: on a direct connection, declined rounds keep the mark clear only for a span past the restore's eight-minute budget, after which they count as dead rounds again, so a user's own TLS front answering 503 for a dead upstream, or a start that never settles, still reads unreachable; red first, landing on the reviewer's read.

Acceptance 4 takes its written form: the gateway path cannot be driven in a guest. The stock desktop's HTTP and WebSocket clients verify servers against the compiled-in Mozilla roots only (`reqwest` and `tokio-tungstenite` linked with the bundled roots, no call site adding one, the OS store read only by the tunnel dialer; `dev/v0104-team/reports/gateway-Desktop104-stagea-source-1.md`), and a cleartext loopback stack cannot exist because the proxy admits cleartext only for `localhost` or a loopback literal while the identity service mints a tenant origin only one label below the proxy apex (`gateway-Desktop104-cleartext-route-1.md`). What stands for the path: the direct native evidence and the shared post-entry feed and reconcile code; named as unobserved: the cookie, Origin, wss, tunnel readmission and entry differences. Open: acceptance 2's native half and acceptance 3, the delayed arms rerun under a post-repair window at the repaired commit with the fixture range (`1dbf559d5`, the admission mode of the driver and reader) and an observer build of this tip; the owner's readings on other engines.
