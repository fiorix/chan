## What is there now

Read at `342dbe791`; the download was not run.

- The semantic search model is fetched by `Embedder::open_once` (`crates/chan-workspace/src/index/embeddings.rs`) through hf-hub 0.4.3's blocking API (`hf_hub::api::sync::ApiBuilder`, features `ureq` and `rustls-tls`). Three callers fetch it: `chan workspace index download-model` (`crates/chan/src/index.rs`), the Settings download (`api_semantic_download`, `crates/chan-server/src/routes/index.rs`) and the preflight's download choice (`crates/chan-server/src/routes/preflight.rs`). The `embeddings` feature that brings it in is the default of the `chan` CLI and of chan-server, and the desktop turns it on, so the CLI, the devserver and the desktop all download this way.
- hf-hub builds its own ureq 2.12.1 agents in `ApiBuilder::build` and takes no client and no TLS configuration. ureq's `tls` feature verifies against `webpki-roots` alone (0.26.11, which re-exports 1.0.7), and its `native-certs` feature is off. So on every platform a CA in the system's store, such as a TLS-inspecting proxy's, is not trusted for the model's hosts. Every client that takes `chan_tls::client_config()` in the same process does trust it: the desktop's gateway clients, the tunnel, `chan metrics --url`.
- By reading of ureq 2.12.1, a refused certificate surfaces as `hf-hub: request error: <url>: Connection Failed: tls connection init failed: <rustls's reason>`, unless a proxy variable is set to a value ureq cannot use: then `hf_fetch_err` reports that variable instead.
- The download honours `HTTP_PROXY`, `HTTPS_PROXY` and `ALL_PROXY` (http and SOCKS) through ureq, and not `NO_PROXY`. `ApiBuilder::new` reads no `HF_ENDPOINT`, so the host is always the Hub's. A model already in the cache (`global_models_dir`, in hf-hub's layout as `model_files_present` reads it) opens without a fetch.

## Desired contract

1. The model download takes its TLS configuration from `chan_tls::client_config()`, as the other Rust clients do. That means the platform verifier on macOS and Windows, and the system bundle beside the bundled floor on Linux and the other Unixes, with `SSL_CERT_FILE` and `SSL_CERT_DIR` read where chan-tls reads them. No option disables verification.
2. A download refused for its certificate names that cause in the CLI's error line and in the Settings and preflight messages.
3. Nothing else of the download changes: the proxy variables it honours and the `ProxyConfig` error for one it cannot use, the hosts it reaches, and the cache layout, so a model downloaded before is found without a fetch. (The cache layout half changed on the owner's word of 2026-11-18: see "The pinned layout" below. A model downloaded before is still found without a fetch.)

## Boundaries

- chan-workspace's download client and a new dependency of chan-workspace on chan-tls; `crates/chan-tls/design.md`'s list of callers and of clients outside it.
- hf-hub 0.4.3's blocking API takes no agent and no TLS configuration, so what changes is the client that fetches the model. One option is a client of chan's own: ureq's `AgentBuilder::tls_config` takes the rustls 0.23 configuration chan-tls returns, and the workspace has one rustls, 0.23.40. Another is reqwest writing hf-hub's cache layout. A third is another hf-hub surface that takes a client. The build chooses and says why.
- Not here: the CLI's self-update (`crates/chan/src/update.rs`) and the other clients `crates/chan-tls/design.md` lists outside the shared decision; and an `embed-model` build, which carries the model and downloads nothing.

## Built, 2026-11-15: implementation and regression proof

The model download uses ureq 2.12.1 directly, with separate metadata and payload agents taking `chan_tls::client_config()`. A cache hit initializes neither agent. The client keeps ureq's environment proxy lookup, the Hub metadata headers and range request, the hf-hub cache layout, per-blob locking, resumable partial files and progress reporting. Tests compare the layout with a cache captured from hf-hub itself and read chan's cache through hf-hub's own `Cache::get`; the fallback publishes a regular file when symlinks are unavailable.

Two boundary decisions were needed to preserve the row's contract. The inherited unconditional cache wipe on an opening error could destroy another downloader's lock or resumable bytes, so only model decoding, loading and inference-probe failures wipe the model cache and retry. Filesystem and download errors preserve it. Both metadata and payload redirects refuse HTTPS downgrades; same-host redirects retain the Hub bearer, and redirects to another host strip it. The bearer tightening is the metadata path's cross-host strip; hf-hub 0.4.3 already used `RedirectAuthHeaders::SameHost` for its payload agent. The lead accepted both decisions on 2026-11-15 in `dev/v0131-team/tasks/task-Lead131-Web131-20.md`.

Certificate failures retain the transport cause and add the certificate classification through the CLI and HTTP error envelope. Preflight retains a failed decision's message across readiness polls until another choice or a settled step clears it. Settings already displays the cause. The lead accepted its unchanged checked Enable semantic search control: that records the saved preference, while the adjacent refusal explains why semantic search is inactive; the captured refusal sent no enable request.

`evidence/Ops131/J148/` records browser check 252 failing at the intended preflight-message assertion on the base and passing on the implementation, with neighbor check 184 passing. ## Review follow-ups, 2026-11-15

An oversized part also restarts from zero under that lock. Consuming the already received body avoids another request or user retry. ## Cross-platform recovery, 2026-11-15

Partial downloads use a write-capable handle positioned at the end under the blob lock. This permits Windows truncation without append-only access, and both restart paths rewind after truncating so the replacement body starts at offset zero. A portable file-handle regression verifies prefix retention, end positioning, cursor-directed replacement and truncation; it fails on Linux when the handle is append-only. The four existing resume regressions remain in the native Windows selection.

Empty model weights are classified explicitly as model corruption before mapping, so the existing wipe-and-retry path does not depend on a platform's mapping diagnostic. Metadata errors remain filesystem failures and preserve the cache. The new diagnostic regression and the existing empty-weights recovery/inference regression cover those distinct responsibilities. The pinned memmap2 Windows implementation already handles empty files before CreateFileMappingW; this explicit check does not demonstrate a previously missing Windows recovery. The two new regressions bring the selected native Windows list to 62 names.

The local embedding suite passed 73 tests, including 56 download tests, with no failures or ignored tests. Removing either restart rewind or the explicit pre-mmap check produced its intended assertion failure between passing original and restored controls; all three source restoration hashes match. Both new regressions also failed at their intended assertions before implementation. Evidence is under `dev/v0131-team/evidence/Web131/task46/`. Native Windows execution and the refreshed Linux/Windows trust readings remain pending.

## The pinned layout, 2026-11-18

On 2026-11-18 the owner decided that the download writes a pinned layout instead of hf-hub's (`dev/v0132/decisions.md` in the development tree, "The review stage", point 1: "hf-hub: yes agree"). That reverses the layout half of the v0.131.0 decision above, and of contract 3. Built on `v0132/download` from `842532b7d`.

- **The pins.** The model table (`config::EMBEDDING_MODELS`) pins each model's commit and the sha256 and size of each file chan downloads.
  - They were read from the Hub on 2026-11-18: the API's `main` commit, the LFS sha256 for the weights, and the other files fetched at that commit and hashed. Each fetched file's git blob id matched the one the API names.
  - `BAAI/bge-m3`'s main commit publishes no `model.safetensors`: the Hub answers 404 for it, so bge-m3 could not download before this change either, and its repository has no official conversion, only community pull requests. On 2026-11-18 the owner dropped it from the model list (`dev/v0132/decisions.md` in the development tree, "Three badge and model calls", point 2). A workspace whose config names it opens with the default model, and Settings and `chan workspace index status` say why until a model is chosen. Settings offers to keep the default, which ends the note and keeps its vectors; choosing another model ends it and starts the vectors over.
- **The download.** It fetches `resolve/<commit>/<file>` into `snapshots/<commit>/<file>.part` and hashes while it writes (the kept prefix first on a resume). It renames the part into place only when the sha256 matches, then writes `refs/main`. A part of the pinned size that hashes wrong is emptied. The metadata request, `blobs/` and its links, and the Windows rename fallback are gone, with their tests and the captured hf-hub transfer.
- **Earlier caches.** A cache written before opens offline. All of a model's files come from one snapshot: the pinned one while it holds every pinned file, else the one `refs/main` names while that one does, else the pinned one a download is filling. Files of two snapshots are never mixed.
- **The rest of the build:**
  - A failed model probe wipes and refetches only when a cached file misses its pin, so an accelerator error no longer costs a download.
  - The agent has a 10 s connect bound (the updater's) and a 60 s bound on each read.
  - The file lock blocks, so a second download waits for the first and reuses its file.
  - The tests' client ignores the environment's proxy; the proxy test opts back in.
  - An unusable proxy variable is named only for a failed request.
  - The user agent is `chan/<version>`. Errors read "model download: ..." (`EmbedError::Download`); the certificate variant keeps its classification.
- **The end-to-end test.** A Linux test runs the production `Client::new` in a child process. Its `HOME` is a temporary directory, and `HTTPS_PROXY` names a loopback proxy that accepts `CONNECT huggingface.co:443` and terminates the TLS with a leaf from a CA made at run time (chan-tls's `testing::pki`).
  - With that CA in the bundle `SSL_CERT_FILE` names, the pinned `config.json` downloads; without it, the download fails with the certificate error.
  - Run against `842532b7d`, the certificate half passes, since today's trust already refuses the CA. The completing half fails there on the request shape, not on trust: today's client reached the proxy through TLS and asked for `resolve/main`, which the pinned proxy does not serve.
  - Replacing the production trust line with an empty root store turns the completing half red on this branch.
- **The merge record's follow-ups.** All close. The timeouts are set, and every file is checked against its pinned hash. A dangling snapshot link no longer blocks: the download's rename replaces the link at the pinned path (a Unix test holds it). A 206 at another range than the one asked empties the part, so the next attempt starts clean. `fetch-models` skips a `refs/.tmp*` a crash left, and `.part` files. The TLS tests make their CA at run time, so no `ca.der` is duplicated.
- **The real reading** (2026-11-18, in an sdme guest against the Hub):
  - `chan workspace index download-model` into an empty cache fetched `BAAI/bge-small-en-v1.5`'s three pinned files in about 4 s.
  - They landed as plain files under `snapshots/5c38ec7c405ec4b44b94cc5a9bb96e735b38267a/`, beside `refs/main` and an empty lock file each. No link, `blobs/` or `.part` remained, and each sha256 was the pinned one.
  - A second run reported the model present.
  - A three-note workspace with semantic search on, served by `chan serve`, answered `chan workspace search` in hybrid mode. For a query sharing no word with any note, the matching note ranked first.
- **The fix round** (one reader's should-fix items and notes):
  - A resume answered with the whole file restarts from it, and one answered at another range empties the part.
  - A model whose entry pins no copy of a file the embedder reads is refused before any request, in plain words ("... cannot be downloaded: its Hub repository publishes no model.safetensors"); no shipped model is one now, and a test-only entry holds the path.
  - A resume that hashes wrong fetches the whole file once more in the same call, unless the resume was answered with the whole file.
  - One rule decides "downloaded" for the downloader, the resolver and the seeder, and all of a model's files come from one snapshot.
  - The part an earlier chan left in `blobs/` is removed once its file is published.
