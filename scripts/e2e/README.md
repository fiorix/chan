# End-to-end suites

Everything under `scripts/e2e/` is owner-run except the browser suite's Node tests (`browser-smoke/lib/*.test.mjs`), which `make pre-push` runs on Linux as `make browser-smoke-lib-test`. None of the suites is wired into `make pre-push` or a CI workflow: these suites build a real binary, drive a real server over a real filesystem, and some of them are destructive or need a live agent sitting at a terminal. Run them by judgment, typically after a coding session large enough that unit and integration tests would not notice a behavioral regression.

A scenario graduates into the gate only after it has proven stable across several sessions on more than one host. Until then, do not wire one of these into `make pre-push` or a workflow.

## Suites

- **`browser-smoke/`** drives a real chan server through headless Chrome: build the SPA and binary, seed a throwaway workspace, launch `chan serve`, run every check under `checks/`, write `results.json` plus screenshots. `SMOKE_ONLY=` filters by filename prefix. Needs Chrome and the libraries it links against, which no build container carries by default; `make browser-smoke-deps` installs both, once per container. Exits 2 when the environment cannot run it. See [`browser-smoke/README.md`](browser-smoke/README.md) for the check API, the environment, and the exit codes. Checks 214 and 215 paste an image into a document, a draft and the Rich Prompt, and drop one into a document and the Rich Prompt, as Chrome's own trusted input, reading the image on disk and the path the Rich Prompt delivers to a terminal; their counterpart on chan-desktop's WebKitGTK is `desktop-observations/basic-flows.sh`. Checks 216 to 218 paste text into a terminal on both engines by chord and by menu, type and save a document in its rendered view and in source across a reload on both save paths, and open a search's content and tag hits.
- **`manual-scroll.mjs`** serves the built marketing `dist` on a disposable loopback port and checks every built manual page without a fragment, Devserver fragment landings, the Animations control, and the demo's pointer and keyboard path in Chrome; `--baseline` runs the scroll arms without the interaction arm, and `--dist PATH` selects a saved build. It exits 2 when Chrome or the built site is unavailable.
- **`scenarios/program-status.md`** maps the OSC 7501 browser scenarios to their checks and the mutation for each leg; entries without implemented checks stay marked planned.
- **`storm-check.sh`** overflows the host's real inotify queue and asserts rebuild-storm convergence. `CHAN_STORM_ACCEPTANCE=1` scales it to the full torrent.
- **Terminal replay tools** provide a socket-cutting proxy and a controlled raw PTY fixture, with deterministic peer tests; see [`browser-smoke/README.md`](browser-smoke/README.md#terminal-socket-and-pty-tools).
- **`browser-smoke/terminal-replay-node.mjs`** mounts the real terminal page and parser against a debug server through a socket cut, saves wire and buffer receipts, and withholds acceptance for missing required cases; see [its run contract and visual limitations](browser-smoke/README.md#terminal-page-replay-in-node).
- **`terminal-queue-drain.sh`** validates chronological `cs terminal write` batching against a live agent. Run it from a chan terminal whose `CHAN_CONTROL_SOCKET` targets the server under test, over a workspace that agent already trusts.
- **`gateway-zone.sh`** exercises the full gateway control plane: one controller, three proxy nodes, real identity and profile services, real `chan devserver run` processes, tunnel reconnect, and failure scenarios. Its `ctrlplane` scenario covers signed user limits, policy transitions, account cuts, persistent fleet pause, OAuth and tenant-session revocation, and bounded aggregate reports. Its `extension` scenario proves the extension lane end to end: a declared test extension's capability link is refused cookieless, a signed-in frame navigation binds it and the bound path serves the entry doc and module script cookieless through a gateway tenant, a bogus capability answers a CORS-readable 404 while non-extension paths keep the bare session-gate 404, both credential segments stay out of service logs, and a devserver restart rotates the capability under an open watch socket (the stale bound path dies readable, the socket drops, the fresh capability binds). Its `sharedroot` scenario signs a grantee in through the OAuth stub with curl alone and follows a whole-devserver root link of the shape the account page copies to a session at the devserver root, then holds a signed-in caller with no grant, and the grantee after a revoke, to the not-found an unknown handle gets. `gateway-zone-browser.mjs`, `extension-capability-browser.mjs`, and `stub-oauth.mjs` support them.
- **`webview-flip-render.py`** renders the flip cards in a real WebKitGTK view, the engine the Linux desktop app ships on, and asserts which face owns the card at rest and either side of the mid-turn handover. It injects each component's own `<style>` block rather than a copy of it. `browser-smoke/` cannot cover this: Chrome honors `backface-visibility` and WebKitGTK ignores it, so a card hidden only by that property passes every Chromium check and covers the whole window in the shipped app. Needs python-gobject with the WebKit2 4.1 typelib and a display; wrap it in `xvfb-run -a` on a headless runner. Exits 2 when the GUI stack is missing.
- **`webview-deck-export.py`** exports a seeded deck and two image documents through a live `chan serve` window in WebKitGTK, then reads their PDF pixels with the Chrome smoke's inspectors. Chrome cannot show whether WebKit paints nested images in the exported SVG. Build the web bundles and `chan`, install `browser-smoke/node_modules`, and provide python-gobject, the WebKit2 4.1 typelib, GTK 3 and Xvfb; run `xvfb-run -a python3 scripts/e2e/webview-deck-export.py`. Exits 2 when the GUI stack is missing.
- **`terminal-pixels.py`** mounts a real terminal in a real WebKitGTK view, writes a fixed box-drawing and block-element pattern, and measures whether rules join across cell boundaries and solid blocks tile without a seam, over explicit DOM, WebGL and ghostty reference arms for both font preferences. The default xterm rows are DOM and `--include-renderers` adds WebGL, so a run can select the reference matching the Linux AppImage's dma-buf capability without claiming to execute its driver policy; other Linux packages keep the DOM arm. It builds its page against the app's own `ghosttyCompat.ts`, font chain and `@font-face` rule rather than copies of them. Glyph geometry belongs to the engine, the renderer and the resolved face together, so no unit test can see this: jsdom paints nothing and Chrome rasterises differently. Needs python-gobject with the WebKit2 4.1 typelib, a display, and an installed `web/node_modules`; wrap it in `xvfb-run -a` on a headless runner. Exits 2 when the GUI stack is missing.
- **`terminal-pixels.mjs`** is the same suite on Windows, measuring the same page and the same thresholds in WebView2, the engine the Windows desktop app ships on. It is a separate driver rather than a branch in the Python one because that driver reaches WebKitGTK through python-gobject, and neither the typelib nor a system python exists on a Windows box; only the host and the snapshot path differ, and the page, pattern and regions are shared files. It also runs a different shipped arm: `shouldUseWebglRenderer` turns WebGL on for a Windows desktop, so the xterm scenarios carry the WebGL renderer and `--include-renderers` adds the DOM one as the reference. By default it drives Edge, which is the same Chromium build as the WebView2 runtime and can be scripted; `--webview2` instead hosts the page in the real WebView2 of a built `target/{release,debug}/chan-desktop.exe`, which is the only way to measure the shell's own browser arguments, since the runtime refuses to start standalone. Needs Node and an installed `web/node_modules`, no other dependency. Exits 2 when no host is found.
- **`lp-skip-test.sh`** with `lp-mock.py` covers the PPA publish retry-idempotence offline.
- **`devserver-fdstore.sh`** proves the terminal-survival contract against a real `systemctl --user` unit: both a shared-terminal PTY and a workspace PTY survive a bare restart, `chan devserver restart`, a watchdog kill, and a `kill -9` crash restart; session close, `stop`, `restart --force`, and a bare stop end the shells and empty the fd store, with the store count asserted after every phase. It refuses to run outside a container, snapshots and restores any pre-existing `chan-devserver.service` state, and REFUSES an active unit unless `CHAN_FDSTORE_E2E_ALLOW_TAKEOVER=1`, because taking over a live devserver kills its terminals. Run it inside an sdme container, never on a host serving live terminals: it is the one suite that drives a fixed shared unit rather than only processes it started, so rule 8 below cannot be satisfied by a throwaway `CHAN_HOME` and port, and the takeover variable is for a container where nothing else owns the unit. Set `CARGO_TARGET_DIR` to a writable guest-local path when the source checkout is mounted read-only. The check sets a finite start limit on its disposable unit, requires no manager-wide override, and restores any pre-existing unit state. Every `chan devserver restart` the suite runs goes through one function that masks the token on both of the command's streams: in the `CHAN_DEVSERVER_TOKEN=` line it prints on stdout, in the unit's recent journal that a restart whose unit does not come up prints on stderr (the journal holds the devserver's launch URL and its own `CHAN_DEVSERVER_TOKEN=` line), and in a `?t=` of any URL on either, so a run's log holds no token; `CHAN_FDSTORE_E2E_SELFTEST=token-mask` checks that function against a stub `chan`, for a restart that succeeds and for one that fails, and touches no unit. `classifier-table` checks the pure diagnostic without a manager; `classifier-live` checks three causes on a separately named user unit inside a container and exits 2 when the user manager is unavailable, with `CHAN_FDSTORE_E2E_SELFTEST_ARM=A|B|C` selecting one arm. A run that fails keeps its work directory, and the throwaway `CHAN_HOME` inside it, `home/`, holds the devserver's `devserver/config.json` with its bearer token under `devserver_token`. The suite stops that devserver as it exits, but treat the kept directory as holding a credential: do not attach it to a report, and delete it once the failure is read.
- **`devserver-terminal-replay.sh`** proves terminal replay across devserver restarts against the same fixed `systemctl --user` unit, with `devserver-fdstore.sh`'s snapshot, restore, container and takeover rules. It sets the same finite start limit on its disposable unit, requires no manager-wide override, and restores any pre-existing unit state. Two windowed terminals, one focused and one not, each `tail -f` a file the run appends to under `-opost -echo`, so the file is exactly what the terminal was sent. It restarts the devserver in each shape `CHAN_REPLAY_E2E_RESTARTS` lists (default `cli crash`: `chan devserver restart`, then a `kill -9` crash restart) while a writer appends across the restart window, and after each restart asserts that a client which stayed attached (`terminal-replay-client.mjs --mode keep`, redialing from its byte cursor) holds the file byte for byte, and that a fresh attach (`--mode fresh`, since 0), which is what a window the SPA reloads after a restart makes for a terminal it has no cached snapshot for, reports the session's `seq` as the file's length, replays the file's tail, and reports no missed bytes. Every check runs and the run fails at the end if any did. Under `team/roadmap/done/`, its fresh-attach check for a terminal over 128 KiB is the acceptance of `a-restart-replays-only-the-manifest-tail.md`, its crash-restart checks of `a-crash-restart-restores-a-stale-manifest.md` and its CLI-restart checks of `a-graceful-restart-drops-output-past-its-snapshot.md`, while `a-failed-dial-makes-the-next-replay-from-zero.md` is an SPA dial it does not exercise, so a red run on any check is new. It cannot see what the SPA itself renders; the client models the attach protocol, not the view. It masks the token in what its restarts print as `devserver-fdstore.sh` does, and a failed run's kept work directory holds the same `config.json` and token.
- **`survey-reattach-ws.mjs`** proves what a window's `/ws` socket is told about `cs terminal survey` overlays when it drops and comes back. It starts its own `chan devserver run` on a throwaway `CHAN_HOME` and loopback port, mints a terminal window with one terminal, and attaches a socket tagged with that window as the SPA's watcher does. A survey raised with `--timeout 3` has its socket dropped across the deadline: the CLI exits 124, the reattached socket gets a `survey_sync` with an empty list and no `close_survey`, and a reply answers 404. A survey still open when the socket drops is listed by the reattach sync, a Dismiss from that window prints the CLI's dismiss line, and a second reply answers 404. Every frame each socket received goes to `<out>/survey-reattach.json` with the checks and the devserver's output to `<out>/devserver.log`, neither carrying a token. The workspace app's mounted tests replay those frames; this suite sees only the wire. Run it as `survey-reattach-ws.mjs --chan BIN --out DIR` with Node's `WebSocket`; it exits 2 when it cannot run and keeps its work dir on failure.
- **`workspace-on-remote.sh`** proves the remote workspace arms (`chan workspace serve|close|forget WS --on TARGET`) against real processes: a `chan devserver run` on a loopback port, a real chan-desktop under Xvfb that registers and connects it, the three arms from a plain shell, and the devserver's management API asserted after each step (mount, idempotent remount, live-terminal refusals on close and forget, unmount that keeps the row, remount, forget that drops it), plus the flag-grammar refusals (`--on 8787`, `--devserver=lab`) and the unknown and duplicate target refusals. Needs `xvfb-run`, a built chan-desktop (`CHAN_DESKTOP_BIN`, default `target/release/chan-desktop`), curl and python3; it builds `chan` itself unless `CHAN_BIN` is set, exits 2 when the environment cannot run it, and keeps its work dir on failure. It cannot prove an ssh control-terminal connect, the gateway arm of the desktop's add-workspace call, or Windows named pipes.
- **`desktop-observations/tmux-feed.sh`** runs a real devserver, desktop and tmux under Xvfb, then drives the native WebKitGTK launcher through its inspector. It checks the aggregated tmux list and card details, clicks new-window and verifies tmux created it, clicks detach and verifies the session survives while the card disappears and the control window is released, then reattaches and ends the server through selection. Set `CHAN_BIN` and `CHAN_DESKTOP_BIN` to fresh builds. It needs the desktop observation tools (Xvfb, Openbox, xdotool, ImageMagick, Python, curl), Node with WebSocket support and tmux. Results and a screenshot stay in the printed throwaway directory. The default uses a direct devserver connection. `gateway-zone.sh tmuxfeed` runs the same checks through real identity, controller, proxy and devserver tunnel services, with a disposable account PAT in a private kernel keyring (`keyctl` required). This native scenario is opt-in, excluded from gateway `all`; the public identity/proxy listeners and devserver tunnel use TLS. The fixture CA is supplied with `SSL_CERT_FILE`; build the test desktop with `cargo build --locked -p chan-desktop --features reqwest/rustls-tls-native-roots,tokio-tungstenite/rustls-tls-native-roots` so its HTTP and WebSocket clients can trust that CA (the standard build uses bundled public roots). This is a test-build option, with no manifest change. The fixture must run beside the desktop (for its tmux socket), and needs the gateway harness's PostgreSQL and loopback DNS prerequisites. Browser sign-in and macOS WKWebView are outside this scenario; the account PAT is pre-seeded and TLS trust includes the fixture CA. `TMUX_FEED_DISCONNECTS=1` adds the real SSH, explicit disconnect, devserver crash and gateway half-open cases, checking native X window destruction and remote session survival. See the [desktop driver notes](desktop-observations/README.md) for OpenSSH and native WebKitGTK CA prerequisites; `E2E_CA_CERT` and `E2E_CA_KEY` let the harness use a CA already trusted by a disposable guest.
- **`desktop-observations/basic-flows.sh`** checks the basic flows on chan-desktop's own engine, WebKitGTK, under Xvfb: an image pasted into the editor and into the Rich Prompt, with the clipboard shape WKWebView hands the page injected through the engine's inspector and with a real Ctrl+V under three clipboard owners, and an image file dropped there, as a synthetic DragEvent and for real over XDND from a GTK drag source, with a drop outside every zone that must leave the window on its page; then, by X input, a typed command and a text pasted by Ctrl+Shift+V and by the terminal menu on both terminal backends, typing in a note's rendered and source modes under document sessions and with them off until the file holds it and a reload shows it, a double-click on a Files row, a Search hit opened by Enter, and a pane split, focused, given a dragged tab and closed by chord. The desktop's clipboard read, its capability grant, the upload and the Rich Prompt's delivery to a terminal run for real. Every verdict line names the WebKitGTK version and the page's user agent, a ready-File paste on each image surface and a bracketed pair handed to the PTY are its controls, and `BASIC_FLOWS_ARMS` picks its groups. It needs `xclip`, python3-gi with GTK 3 and ImageMagick beside the desktop observation tools; see [`desktop-observations/README.md`](desktop-observations/README.md#basic-flows) for its arms and run recipe.
- **`flaky-mount.sh`** proves the WL-17 mount-flap contract against a real FUSE mount: a mounted workspace whose filesystem dies reports `unavailable` rather than `running` or `error`, never reports its files as deleted, and recovers by itself once the mount is repaired at the same path -- including across a remount, which invalidates the capability handle the workspace was opened with. A second arm repeats the kill while an index pass is walking a seeded tree, the in-flight case that used to leave the row unopenable (`WorkspaceAlreadyOpen`) until the devserver restarted. The mount is a local rclone `:memory:` remote, so no cloud account and no network are involved and only the FUSE transport is real; never point it at a real remote. Needs `mclone`/`rclone`, `fusermount`, `curl`, `python3`, and `/dev/fuse`, which an sdme container needs passed in (`--bind /dev/fuse:/dev/fuse` plus `DeviceAllow=/dev/fuse rwm` on the container unit). Throwaway `CHAN_HOME`, port and mountpoint; exits 2 when it cannot mount, and keeps its work dir on failure.
- **`wireguard-kernel.sh`** proves chan-wireguard, the in-process WireGuard client, against a real kernel WireGuard peer reached over SSH. It provisions the peer for the run with `wg` and `ip` (an interface it creates and deletes, keys from `wg genkey`, a python3 HTTP server on the tunnel address serving a short text and a 1 MiB blob), writes owner-only client files under a throwaway work dir, and runs six default arms, each with its own verdict line and status: `wrong-key` (a wrong peer public key never completes a handshake: the connect times out, the peer's handshake stamp does not move, and the peer's UDP counters show the refused initiations arrived), `get` (the crate's `wg-connect` example returns both files byte for byte, checked by SHA-256, and the public key it derives matches `wg pubkey`), `rekey` (a tunnel held idle past the protocol's 120 s rekey makes exactly one fresh handshake with the kernel and the GET after it works; every arm's client file carries one key, so the handshake stamp the previous arm left, read before the launch, is not counted), `keepalive` (with `PersistentKeepalive` the peer's receive counter grows while nothing is connected), `devserver` (a real `chan devserver run --tunnel-wireguard` logs the tunnel started and its h2 dial reaches a raw listener on the peer's tunnel address with the HTTP/2 connection preface; the dial then fails at the HTTP level, which is expected) and `devserver-wrong-key` (at `RUST_LOG=warn`, the same dial reaches nothing, one `WireGuard session` WARN proves expiry within 100 s of tunnel start, and the ANSI-stripped log holds no ERROR-level line). The opt-in `dns` arm (`--arms dns`) runs one `wg-connect` client through `wireguard-dns.py` in an unprivileged user and mount namespace with private `/etc/hosts` and `/etc/nsswitch.conf`: an unresolved name first fails lookup, then resolves to the first UDP path, moves to a second path to the same peer after the first GET, and disables the first path; the same client must complete a second GET with handshake initiations seen on the second path. Its verdict names the helper stages and both response bodies. The opt-in `dns-late` arm moves the record while the new path is dark, holds the old path's rekey response until the copied probe is seen and dropped, then forwards the client's confirmation before enabling the new path and disabling the old one. With `--hold` between 125 and 140 seconds (default 130), the second request must see the next attempt on the new path and complete within 30 seconds of starting, before stale-session recovery; its timestamped stages identify missing controls and the stage of any failure. The default arms also read the peer's `wg show`. Takes `SSH_TARGET ENDPOINT PEER_ADDRESS` (`user@host`, the peer's UDP `host:port` as this host reaches it, the peer's tunnel address with prefix) plus `--ssh-opt`, `--client-address`, `--listen-port`, `--interface`, `--hold`, `--arms`, `--dns-second-endpoint` and `--dns-second-peer-port`; `--dns-second-endpoint HOST:PORT` names the second UDP path, and optional `--dns-second-peer-port PORT` redirects a distinct guest port to the peer's listen port with nft, removes the table at exit, and refuses an existing table; the peer needs the wireguard module, wireguard-tools, iproute2, python3, sha256sum and `sudo -n`, and the host needs ssh, python3, sha256sum and xxd, plus `unshare` with unprivileged mount namespaces for either DNS arm. It builds `chan` and the example unless `CHAN_BIN` and `WG_CONNECT_BIN` name built ones, exits 2 when a prerequisite is missing, and keeps its work dir on failure; the kept client files hold a private key the deleted peer interface makes worthless, but treat them as a credential until they are gone. A QEMU guest with user networking and a UDP `hostfwd` to its port is a sufficient peer; the guest then sees the client at the gateway address of the user network, and this host dials `127.0.0.1`. Both DNS arms need two UDP paths; under QEMU user networking, the second forward must reach a distinct guest port redirected with nft because the newest forward to one guest port answers both paths. It cannot prove a peer behind a real NAT or a changing address, a tunnel URL by name, or anything the gateway answers past the preface.
- **`wireguard-windows.sh`** proves the same client built for Windows (`x86_64-pc-windows-gnu`) and run on a Windows machine reached over SSH, against the same kind of kernel WireGuard peer reached over SSH, with the host as the driver in between: the peer is provisioned as `wireguard-kernel.sh` provisions it, plus the kernel module's dynamic debug messages switched on for the run (and off again unless they were on), the Windows binaries are cross-built here with `cargo zigbuild` (zig as ring's C compiler and the linker; or named with `WG_CONNECT_EXE` and `CHAN_EXE`), copied into a per-run directory under the client's `TEMP` and checked by hash on arrival, and every client step runs through `powershell.exe` as an encoded command, so no quoting crosses two shells. Six arms, each with its own verdict line and status: `wrong-key` and `get` as in the kernel suite, `crlf` (the same GET from a client file written the way Windows tools write text, CRLF line endings behind a UTF-8 byte order mark, with the file's first bytes read back so the arm is known to test that shape), `rekey` (a tunnel with `PersistentKeepalive` held idle past the 120 s rekey: the peer's handshake stamp moves exactly once after the stamp the `crlf` arm left, on the client's clock, its receive counter grows during the idle hold, the kernel's log for the hold holds no handshake retry of its own, and the GET after the hold works), `devserver` (a real `chan.exe devserver run --tunnel-wireguard`, started detached with its streams in files, logs the tunnel started and its h2 preface reaches the raw listener on the peer) and `devserver-wrong-key` (at `RUST_LOG=warn`, the dial reaches nothing, one `WireGuard session` WARN proves expiry within 100 s of tunnel start, and the ANSI-stripped log holds no ERROR-level line). Takes `PEER_SSH ENDPOINT PEER_ADDRESS CLIENT_SSH` (the endpoint is the peer's UDP `host:port` as the client reaches it) plus `--peer-ssh-opt`, `--client-ssh-opt` (a `-p PORT` pair is passed to scp as `-P`), `--client-address`, `--listen-port`, `--interface`, `--hold` and `--arms`; the peer needs what the kernel suite needs plus journalctl and a writable `/sys/kernel/debug/dynamic_debug/control`, the client needs Windows on x86-64 with the OpenSSH server, key authentication and `powershell.exe` on the PATH, and the host needs ssh, scp, python3, sha256sum, xxd and either the two binaries or cargo-zigbuild, zig and the rustup target for the toolchain pinned by rust-toolchain.toml. Exits 2 when a prerequisite is missing, deletes the client and peer directories as it exits and keeps the host work dir on failure, where only redacted client files remain: their text travels on the ssh channel stdin, so the private key is not in a command line or PowerShell script block. Two QEMU guests with user networking are a sufficient pair: each sees the host's loopback as `10.0.2.2`, so the Windows client dials the peer's forwarded UDP port there and the peer sees the client at `10.0.2.2:<port>`. It cannot prove a peer behind a real NAT, a tunnel URL by name, anything past the preface, the Windows machine sleeping (an SSH session does not survive that) or a build other than the GNU target.
- **`wireguard-freebsd.sh`** proves the same client built natively on FreeBSD and run there, reached over SSH, against the same kind of kernel WireGuard peer reached over SSH, with the host as the driver in between. The peer is provisioned as `wireguard-kernel.sh` provisions it (its own interface, `chanwg1` by default so the two suites can share one peer, keys from `wg genkey`, the HTTP server and the raw listener) plus the module's dynamic debug prints, so the kernel journal names every handshake and keepalive; the client files are written owner-only on the FreeBSD machine with the key carried over the ssh channel's stdin, never as an argument. Seven arms, each with its own verdict line and status: `wrong-key` (the connect times out, the peer's handshake stamp does not move, and the journal shows the initiations arriving and dropped for their MAC), `get` (both files byte for byte by SHA-256, the handshake and the transfer in `wg show`), `rekey` (a 130 s idle hold, a GET and a 3 s settle through the example's `--settle`: by the end exactly one fresh handshake has been made, which the peer's stamp (counted after the one the `get` arm left) and the client's final status both show, with no retry in the journal; when it lands is not asserted, since the core rekeys an idle session at 120 s only when its first data packet carried a later timer stamp than the handshake, and the GET's data sets it off otherwise), `keepalive` (a 60 s idle hold with `PersistentKeepalive`: the peer's receive counter grows on keepalives alone and the handshake stamp does not move), `devserver` (a real `chan devserver run --tunnel-wireguard` on FreeBSD logs the tunnel started and its HTTP/2 preface reaches the raw listener), `mode` (a client file with mode 644 is refused by `chan devserver run` before anything starts, naming the mode and the chmod, with no key echoed) and `rcvbuf` (the tunnel socket's 4 MiB `SO_RCVBUF` hint against the client's `kern.ipc.maxsockbuf`: refused with ENOBUFS and logged at debug when the cap is lower, silent when it is not, and the tunnel comes up either way). Takes `PEER_SSH CLIENT_SSH ENDPOINT PEER_ADDRESS` (the endpoint as the client reaches it) plus `--chan` and `--wg-connect` (the binaries' paths on the client, built there from the commit under test, since nothing here cross-compiles), `--peer-ssh-opt`, `--client-ssh-opt`, `--interface`, `--hold`, `--arms` and `--keep`; the peer needs what `wireguard-kernel.sh` needs plus journalctl and a mounted debugfs, the client needs FreeBSD and `timeout`, and the host needs ssh, python3 and xxd. Exits 2 when a prerequisite is missing and keeps its work dir on failure, with the same credential note. Two QEMU guests with user networking are sufficient: each sees the host's loopback as `10.0.2.2`, so the client dials the peer's forwarded UDP port there and the peer sees the client at `10.0.2.2:<port>`. It cannot prove a peer behind a real NAT, a tunnel URL by name, anything past the preface, or a clock that counts through a suspend, since the guest never sleeps.
- **`desktop-wireguard.sh`** proves the desktop's WireGuard fabric end to end against a real debug chan-desktop under Xvfb: a gateway row naming a wg-quick file whose peer is the crate's `wg-peer` example, a loopback `Tunnel` standing in for a gateway host that writes the client's owner-only file, answers 404 to everything inside the tunnel and prints what it was asked. ### One-CPU test series

Prepare a clean detached worktree outside `/tmp`, then create the fixed-shape guest with build output on its capped btrfs volume. The empty gitignored embed directories let `chan-server` build against read-only source without its build script trying to create them. The main `.git` bind is read-only and exists only so Git can resolve the detached worktree metadata; `/work/chan` is also read-only, while `CARGO_TARGET_DIR` is fixed by the script at `/var/tmp/chan-target` inside the guest:

```bash
rig_tree=/var/tmp/chan-one-cpu-source
git_dir=$(git rev-parse --path-format=absolute --git-common-dir)
git worktree add --detach "$rig_tree" REVISION
mkdir -p "$rig_tree/web/dist" "$rig_tree/web-launcher/dist"
sdme_config_args=()
series_config_args=()
# For another pool, set both arrays to the same file:
# sdme_config_args=(--config /absolute/path/to/sdme.conf)
# series_config_args=(--sdme-config /absolute/path/to/sdme.conf)
sudo sdme create --name chan-one-cpu -r chan-ann-ubuntu \
  "${sdme_config_args[@]}" --storage btrfs --disk 44G --cpus 1 \
  --bind "$rig_tree:/work/chan:ro" \
  --bind "$git_dir:$git_dir:ro" --started
sudo sdme "${sdme_config_args[@]}" exec chan-one-cpu -- env HOME=/root \
  git config --global --add safe.directory /work/chan
sudo scripts/e2e/one-cpu-test-series.sh "${series_config_args[@]}" --container chan-one-cpu \
  --package chan-workspace filtered_registration 20 32
```

The final stdout line records the container, backend, disk cap, host `cpu.max`, thread count, revision, package, selector, selected-test count, red-run rate, throttling delta and result directory. Progress goes to stderr. Per-run logs, exit codes and the same summary remain under the printed `/var/tmp/chan-one-cpu-series.*` directory on the host. The script exits 2 before selector validation or test execution when it cannot prove the instrument.

## Scenario packs

`scenarios/` holds behavioral catalogs: what must hold, when a scenario is worth re-running, and which executable check or test backs it. A pack names the harness it runs on and does not restate harness documentation.

- [`scenarios/workspace-lifecycle.md`](scenarios/workspace-lifecycle.md): startup, shutdown, close and remove, root loss, and durable state across all of them.
- [`scenarios/rich-prompt.md`](scenarios/rich-prompt.md): composing a terminal prompt, sending it through the prompt queue, stopping a send, and restoring every one of those states after a reload.
- [`scenarios/desktop-webview-rendering.md`](scenarios/desktop-webview-rendering.md): what the desktop app's own webview paints, the CSS capabilities that claim rests on, and when to re-measure them.
- [`scenarios/terminal-grid-rendering.md`](scenarios/terminal-grid-rendering.md): what the terminal grid paints across both backends and both font preferences, and which glyphs a renderer may not defer to the font.
- [`scenarios/tab-drag-and-drop.md`](scenarios/tab-drag-and-drop.md): moving a tab between panes and between windows, what each kind must carry with it, which moves must be refused, and why the desktop WebViews stay manual.

Write a new pack when a coding session produces a set of end-to-end expectations worth keeping. Name it for its subject, never for the session that produced it, and state every expectation in the present tense: a pack describes behavior that must hold, not work that was done.

## Rules for every run

These apply to every suite and every scenario pack.

1. Build the exact commit under test and record its SHA.
2. Use a fresh throwaway workspace, `CHAN_HOME`, output directory, and port.
3. Use a small deterministic source tree checked into or generated by the test. Do not clone from the network.
4. Use an explicit readiness or test barrier for startup races. Do not rely on sleep-and-hope.
5. Record command exit status, stdout and stderr, relevant `chan ps --json` or API snapshots, process identity, and file and metadata assertions.
6. Bound every poll and every shutdown wait.
7. Preserve logs, screenshots, and the throwaway workspace on failure.
8. Tear down only processes the run itself started.
9. Recursively delete only a path the run created and positively identified. Never aim a destructive step at a user workspace, a checkout, a home directory, an unresolved variable, a symlink, or a glob.

Report failures, skips, and manual-only coverage explicitly. A skipped check is not a pass.
