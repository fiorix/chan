# v0.77.0 hardening smoke-test plan

Status: living release-blocking test plan. Deterministic H02/H03/H13 coverage
and the destructive H14 browser tail check are implemented on the integrated
hardening baseline. The complete pre-push gate, focused browser
collaboration/editor lane, and destructive H14 run are green. Manual and soak
lanes remain intentionally outside the blocking gate.

## Purpose

Validate end to end that the v0.77.0 hardening work:

- keeps startup responsive and observable;
- cancels startup and shutdown work without resurrection or leaked tasks;
- preserves durable workspace, session, document, and scene state;
- keeps current terminal, editor, collaboration, pane, index, graph, and file
  browser behavior working;
- distinguishes stopping a workspace from removing it;
- treats disappearance of a workspace root as a terminal filesystem state,
  never as an empty workspace or an invitation to recreate it.

This plan separates deterministic release blockers from large-repository and
real-environment soak tests. A network clone, a particular machine's home
directory, or a timing-only race must not be required for the blocking gate.

## Test lanes

| Lane | Purpose | Release blocking |
| --- | --- | --- |
| Rust integration | Deterministic lifecycle, cancellation, persistence, and CLI state | Yes |
| Browser smoke | Real binary, SPA, HTTP, WebSocket, and filesystem behavior | Yes |
| Devserver smoke | Hosted lifecycle and two-client behavior | Yes for bounded fixtures |
| Manual soak | Linux/BuckOS scale, container behavior, and real clipboard integration | No |
| Product follow-up | New UX or commands not present before this hardening round | No |

## Implemented deterministic coverage

The Rust gate exercises the literal host methods reached by the control socket
for both CLI forms:

- `devserver::tests::chan_close_during_startup_stays_off_preserves_metadata_and_reopens`
- `devserver::tests::chan_close_remove_during_startup_forgets_metadata_preserves_source_and_reopens_fresh`
- `host::tests::close_for_root_accepts_registered_starting_before_runtime_lands`
- `host::tests::close_for_root_waits_for_inflight_registration_then_unmounts`

The tests hold explicit mount barriers; none uses a timing sleep to manufacture
the race. The first plain-close run exposed a real defect: a registered
workspace in `Starting` returned `NotFound` through the host path. The corrected
implementation serializes close/remove with host registration and reconciles a
pending attempt against the overlay's newer intent generation before it opens
or publishes. `--remove` already honored the destructive contract; its new test
pins metadata removal, source preservation, non-resurrection, and fresh reopen.

## Common setup and evidence

All automated cases must:

1. Build the exact integrated commit under test and record its SHA.
2. Use a fresh throwaway workspace, `CHAN_HOME`, output directory, and port.
3. Use a small deterministic source tree checked into or generated by the test;
   do not clone from the network.
4. Use an explicit readiness or test barrier for startup races. Do not rely on
   “sleep and hope.”
5. Record command exit status, stdout/stderr, relevant `chan ps --json` or API
   snapshots, process identity, and file/metadata assertions.
6. Bound every poll and shutdown wait.
7. Preserve logs, screenshots, and the throwaway workspace on failure.
8. Tear down only processes started by the case.
9. Recursively delete only a path created and positively identified by the
   current test. Never aim a root-loss test at a user workspace, checkout,
   workspace root, home directory, unresolved variable, symlink, or glob.

## Detailed blocking procedures

### H01 — cold startup and `chan ps`

Fixture:

- a fresh git repository with a stable multi-directory tree;
- enough generated Markdown/source files to exercise reports and indexing;
- reports enabled, with a second variant enabling semantic indexing;
- an isolated `CHAN_HOME`.

Procedure:

1. Start `chan open PATH` with startup held at a deterministic in-progress
   barrier.
2. While startup is held, run both `chan ps` and `chan ps --json`.
3. Open the launcher surface and verify it remains interactive and displays
   the workspace as starting rather than ready.
4. Release startup and wait for readiness.
5. Open the workspace window and confirm the expected reports/semantic mode.

Assertions:

- `chan ps` completes within its bound while startup is in progress;
- the JSON row contains the canonical path and a coherent serving state;
- the launcher can render and accept input during startup;
- exactly one serve wins and the workspace reaches ready;
- no startup task, lock, or temporary file remains after teardown.

### H02 — `chan close PATH` during startup

Procedure:

1. Register and begin opening the deterministic fixture.
2. Hold startup before readiness and verify the row is observable.
3. Run `chan close PATH`.
4. Keep the original startup barrier open long enough to detect a stale
   completion, then release it.
5. Run `chan ps --json`, inspect the launcher/API row, and reopen the path.

Assertions:

- `chan close` returns within the shutdown bound;
- the writer lock is free and the serve process/tenant is gone;
- the workspace remains registered as stopped/free;
- the workspace's chan metadata sentinel remains;
- releasing the stale startup cannot resurrect the tenant or change state;
- an immediate reopen succeeds without a lock race.

### H03 — `chan close --remove PATH` during startup

Procedure:

1. Repeat H02 with a source-tree sentinel and a chan-metadata sentinel.
2. Run `chan close --remove PATH` while startup is held.
3. Release the stale startup and poll both the local registry and hosted
   library state.
4. Run `chan ps --json`.

Assertions:

- shutdown completes and no tenant/process resurrects;
- the registry and launcher/API row are absent;
- `CHAN_HOME` workspace metadata, including saved layouts, is removed;
- the source directory and source sentinel are unchanged;
- a later `chan open PATH` starts with fresh metadata.

This case must also preserve the existing refusal contract: a hosted workspace
with live terminals refuses both close forms, and `--remove` must not remove
the registry entry after that refusal.

### H04 — bounded shutdown and durable flush

Exercise standalone and hosted teardown separately.

1. Open a document and a scene, make acknowledged edits, and hold their
   shutdown flushers at a deterministic barrier.
2. Request normal shutdown.
3. Verify teardown does not report completion before the flush is allowed to
   finish.
4. Release the flush, await shutdown, then reopen the workspace.
5. Repeat with one deliberately non-cooperative task to exercise bounded abort
   and await behavior.

Assertions:

- acknowledged document and scene content survives reopen;
- all owned tasks are completed or aborted-and-awaited before return;
- no post-return state mutation is observed;
- the workspace cell and writer lock are released only after required flushes;
- drop remains a bounded fallback, not the normal shutdown path.

### H11 — index and graph during startup

Use the bounded fixture, not Linux, for the blocking case.

1. Open a workspace window as soon as the hosted surface is available.
2. Open the dashboard indexing page and a graph tab before indexing completes.
3. Inspect first-degree directory nodes that are already available.
4. Wait for completion and verify the graph settles without a reload.

Assertions:

- opening the window, dashboard, graph, and inspector does not wait for the
  complete index;
- incomplete data is safe and does not masquerade as an error;
- available directory nodes are inspectable;
- completion updates the current view without corrupting graph state.

Orange/pulsing nodes, explicit “graph incomplete” text, and asynchronous
population of already-open depths are good UX proposals. They are product
follow-ups unless those surfaces already exist before this release.

### H12 — shared file browser

First audit the current product contract. If expansion state is shared as part
of the window session:

1. Open one devserver workspace window from two clients.
2. Expand a bounded directory depth in client A.
3. Verify client B converges.
4. Collapse it in client B and verify client A converges.
5. Close/reopen and verify the intended persisted state.

If expansion state is intentionally client-local today, record that behavior
and treat shared expansion as a product feature rather than a hardening
regression.

### H13 — workspace root disappears during startup

Use a generated workspace whose exact root is owned by the test. Put the mount
behind a deterministic barrier after registration but before the tenant can be
published.

1. Begin mounting the workspace and verify its launcher row is `starting`.
2. Recursively remove only the generated root while the mount is held.
3. Release the mount barrier and await the attempt.
4. Inspect the host, overlay, launcher row, lock, metadata, and filesystem.
5. Recreate the directory explicitly and request a new mount.

Assertions:

- the attempt returns a typed workspace-root-missing error and settles within
  the startup bound;
- no tenant is published and no process, task, watcher, lock, or retry loop
  survives the failed attempt;
- the registered row remains off/failed and displays the root-missing reason;
- neither the server nor a background recovery task recreates the directory;
- releasing stale work cannot later turn the row on;
- recreating the directory does not auto-mount it, but a fresh explicit open
  succeeds.

The deterministic barrier—not the speed of recursive deletion—makes the
startup assertion release-blocking. A real deletion during browser startup is
an additional smoke check.

Implemented regressions:

- `host::tests::mount_rejects_root_removed_while_tenant_builds`
- `devserver::tests::workspace_root_removed_during_startup_fails_closed`

### H14 — workspace root disappears while fully in use

Fixture:

- a generated, disposable multi-level tree large enough that recursive deletion
  produces observable intermediate states;
- a Markdown file of approximately 2 MiB;
- one file-browser tab with the generated directory hierarchy expanded;
- one workspace graph at maximum depth after indexing has settled;
- one editor tab with a visible unsaved edit in the large Markdown file.

Procedure:

1. Capture the expanded paths, graph node set, editor content/dirty state, API
   health, and on-disk root identity.
2. Start recursive deletion of the positively identified test root from outside
   chan.
3. While deletion is in progress, sample the file-browser, graph, editor, and
   server APIs. Partial-tree snapshots and leaf-not-found responses are valid;
   crashes, hangs, unsafe path fallback, and root recreation are not.
4. Wait for filesystem deletion and bounded watcher/index reconciliation.
5. Attempt, separately, to create a draft, create a terminal, open a new graph,
   and open a new file browser.
6. Verify the deleted path is still absent after all background work and
   autosave intervals.

Required UI contract:

- **File browser:** progressively removes entries and ultimately shows one
  stable “workspace root unavailable” state. A missing root must not be
  presented as an empty valid workspace, and the surface must not enter a
  reload/toast loop.
- **Graph:** may shrink incrementally as watcher/index delete events arrive,
  then converges without phantom file nodes. It may retain only an explicitly
  unavailable virtual root; it must not serve stale indexed files as if they
  still exist.
- **Existing editor:** keeps the in-memory 2 MiB buffer and unsaved edit
  intact, shows the current “File moved or deleted” treatment, retains the
  dirty indicator, and does not autosave or recreate the root. The focused
  state-level regression proves the buffer bytes survive even though the
  current missing-file panel replaces the editor canvas.
- **New root-dependent surfaces:** draft creation, terminal creation, graph
  creation, and file-browser creation all fail promptly with the same
  root-missing condition. A tab may render that stable error state; it must not
  crash the window or silently become an empty workspace.
- **Whole window/server:** remains responsive enough to close or remove the
  workspace. Repeated events and requests are idempotent, bounded, and cannot
  resurrect files or the tenant.

The implementation may observe any consistent prefix of the tree while
deletion is underway. The release-blocking property is eventual convergence
after the root is gone, preservation of the dirty editor buffer, and strict
failure of all new root-dependent operations without recreation.

Run the destructive H14 check separately or as the lexical tail of the full
browser suite:

```sh
SMOKE_ONLY=98 node scripts/e2e/browser-smoke/run.mjs
```

The executable check lives at
`scripts/e2e/browser-smoke/checks/98-workspace-root-loss.mjs`. It validates the
throwaway path shape immediately before invoking `/bin/rm -rf -- <exact-root>`;
its filename must remain last because the workspace is intentionally absent
when it returns.

## Manual and soak matrix

### Large repositories

Use existing local checkouts where possible. Record repository URL, exact
commit, file count, disk use, enabled report/semantic modes, peak memory, and
elapsed milestones.

Suggested repositories:

- Linux with reports enabled;
- BuckOS build sources with reports and semantic search enabled.

Observe:

- launcher progress and responsiveness;
- `chan ps` while each workspace is starting;
- early workspace-window availability;
- index/report progress and final readiness;
- one `chan close` and one `chan close --remove` run on disposable copies.

Do not make a network clone or full Linux indexing part of the automated gate.

### Fresh container/devserver

In a fresh supported container:

1. build the exact commit;
2. repeat H01–H04 and H13–H14 with bounded fixtures;
3. repeat document and scene collaboration with two clients;
4. repeat the graph and file-browser checks;
5. verify one hosted leader/owner and the expected follower/origin roles.

### OSC 52

Keep protocol parsing/unit coverage automated. Manually validate one real
terminal clipboard write on a supported host because browser/container
clipboard policy can produce false results.

Record:

- terminal kind and host;
- OSC 52 enabled/disabled setting;
- clipboard value before and after;
- behavior when the sequence is rejected.

Explanatory settings text and new mouse toggles in the command launcher or
`cs terminal new` are product follow-ups unless already part of the shipped
surface.

## Exit criteria

The hardening smoke pass is accepted when:

- every H01–H14 assertion that matches the current product contract is green;
- both close-during-startup variants are deterministic and green;
- both root-loss variants fail closed and never recreate the workspace root;
- all reused browser checks are green against the exact integrated binary and
  web bundle;
- standalone and hosted shutdown preserve acknowledged document/scene state;
- no case leaves a live process, held writer lock, stale tenant, stale graph
  node, or misleading empty-workspace state;
- failures, skips, manual-only coverage, and product follow-ups are reported
  explicitly rather than counted as passes.
