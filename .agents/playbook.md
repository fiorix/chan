# Agent playbook

The operational rules an agent follows when it works on chan alongside other agents, each with the reason behind it. The reasons come from the project's release retrospectives in [`../team/release/`](../team/release/), which hold the full stories; this file holds the rules. The runtime surface the rules refer to (the control socket, pokes, surveys, team provisioning) is documented in [orchestration/](orchestration/README.md), and the process itself (rounds, roles, the roadmap and release trees) in [`../team/README.md`](../team/README.md).

## How a round is organized

Lanes work in per-lane git worktrees for code, while the coordination documents stay in one shared, append-only bus directory inside the workspace, driven by cs-terminal tooling (pokes and surveys). An isolated gate worktree gates the committed state and is immune to peers' work in progress.

## Coordination discipline

- Append-only, even in coordination. Once an agent has started a task, new asks become new tasks, not amendments to the one in flight; rewriting under someone loses the audit trail.
- A poke is a one-line pointer to a specific append-only section ("see <file>, <heading>"), never the content itself. Fat pokes stack, truncate, bury the substance and cannot be re-read later. Write the section first, then poke it.
- Every poke to an agent CLI ends with the agent's submit chord (`--submit=<agent>`), or it parks unsubmitted in the compose box and stalls the round.
- The chord names the target's agent, not your own. The server derives the target's real agent from its spawn command (plus a recognized `CHAN_AGENT` in its spawn env) and corrects a mismatched `--submit`, noting the applied chord in the ack; read the ack instead of assuming your guess landed. `CHAN_AGENT` is target-side identity, and `CHAN_MODE` is read by nothing.
- Neither `offline` nor a deep queue means an agent is stuck. `cs terminal list` reports tabs `offline` while their agents are alive and working, and a lane can look unresponsive to several messages while its queue shows it has drained none of them. Judge a lane by the artifacts it produces (commits, journal writes, worktree changes), confirm liveness with `pgrep` on the agent process, and read the queue depth before concluding anything. Restarting a tab on either signal destroys the agent's context and its uncommitted work. Do not re-send: the queue reconciles the backlog into one turn, so duplicates only make that turn noisier.
- Workers route decisions to the lead; the lead consolidates and surveys the host with `cs terminal survey` (a blocking overlay in the host's window). Workers do not survey the host directly, and never raise a TUI survey.
- Verify a write landed before you poke about it: grep or read the file, then poke. Never bundle a heredoc write, a poke and a grep into one shell command; truncation silently drops the later steps.
- Redistribute spillover from the queue tail, not the head: the lane is already working its next item.
- Status reports are curated highlights, lowlights and contention, not tabular dumps; the detail stays in the task files.
- Moving a round's raw data to the `chan-dev` archive at close is a sanitization step, not a copy. Rounds run in `dev/` and agents are routed by absolute path, so briefs, configs, tasks and journals name the worktree they ran in; archived verbatim they become literal home paths in a public repository, and cleaning up afterwards leaves the original in history. Rewrite paths and identity before the commit; see [skills/archive-round/SKILL.md](skills/archive-round/SKILL.md).

## Git and commit discipline in a shared worktree

- The only race-proof commit when peers stage concurrently is an explicit pathspec: `git commit -F msg -- <path> <path>` (flags before the `--`). A plain `git add` plus `git commit`, even chained with `&&`, lets a peer's concurrent staging contaminate your commit.
- `git add <single-path>` does not unstage other files. Run `git diff --staged --stat` before committing and `git show --stat HEAD` after, every time.
- Stage explicit pathspecs even when you are alone in the tree: `git add <directory>` sweeps in editing artifacts and drafts other agents left there. Read `git diff --cached --name-only` before committing, not after.
- Merge is not push. "Merge to main" means a local merge; never push without an explicit ask from the owner. A standing commit clearance is not a standing push clearance.
- Push in the foreground, redirect to a file, and verify with `git ls-remote` before tagging. A backgrounded gated push can exit 141 (SIGPIPE, from the hook's long output) and silently fail to update the remote while reporting its gate steps green, and the same bites a tag push: `rc=0` is not proof, only `git ls-remote --tags` settles it. `--no-verify` is classifier-blocked.
- When snapshotting a worktree defensively, `git diff` is not enough: it omits untracked files, which is where new work lives. Capture `git ls-files --others --exclude-standard` separately, and check `git diff --cached` for staged-but-uncommitted work.
- If a lane rewrites history after you merged and pushed it, do not merge the rewritten branch: that replays merged content as duplicate commits. Verify main's content by reading the files, use `git log --cherry-pick --right-only main...<branch>` to find what is genuinely new, cherry-pick only that, and have the lane reset to `origin/main`.

## The gate and the quality bar

- Run a scoped own-gate before any "done" report. Rust: `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` and `cargo test`, scoped with `-p <crate>`; re-check `--no-default-features` when you touched feature gates. Frontend: `make web-check` (the launcher bundle, svelte-check and vitest for web-shared, the launcher, the workspace app and profile, then the workspace app's production build; the marketing site has its own `npm run check -w @chan/marketing`). Desktop: `cd desktop && make build`. Shell or workflow files (`packaging/`, `scripts/`, `install.sh`, a git hook, `.github/workflows`): `make shell-check` and `make workflow-check`, which no other scoped gate implies.
- The lead owns the full-tree `make pre-push` from an isolated gate worktree, which gates the committed state and is immune to peers' work in progress. Lanes report scoped-green plus a pathspec sha; they do not block on the main-tree gate, which false-reds on concurrent work. See [skills/gate/SKILL.md](skills/gate/SKILL.md).
- The release gate builds every workspace CI ships. `gateway/` is a separate Cargo workspace, and `desktop/src-tauri` and the gateway hold construction sites for shared structs; a `crates/`-scoped check misses all of them. Grep the whole repository and build them.
- Do not pipe the command whose exit code you are verifying: `cargo ... | tail` reports tail's 0. Run it bare and capture `$?`, or set `pipefail`. Do not suppress stderr on a destructive command either; `rm -rf target 2>/dev/null` hides whatever stopped it.
- Every new check must be provably able to go red, and must not go red on success. Break it on purpose once, capture the red, then fix it; and make sure a run that shipped does not report failure, because a check that fires on success trains the operator to discard it, and the next genuine failure arrives with the same job name. A red that means nothing is worse than no check.
- The instrument that reads your evidence needs its own proof that it can see a failure. A probe whose regex does not match the test runner's output reads a genuine red as silent; a classifier inferring test-versus-production from line order misfiles production paths; a `2>/dev/null` on a tracked symlink drops an entry from a content hash and reports success; a gate wrapper ending in `; echo "EXIT=$?"` returns the echo's 0. Probe the harness; do not only read it.
- A skip and a pass must not emit the same signal. A check that cannot run its case fails or says it skipped, and never returns the success value: `git status --porcelain | wc -l` yields 0 when git itself errors, and a test that `return`s green when its precondition never arrives asserts nothing on exactly the systems where its claim is false. Use `if ! VAR=$(cmd 2>&1); then refuse; fi`, and remember that `exit` inside `$( )` kills only the subshell.
- A `publish=false` dry run exercises nothing gated on publish: the release asset verifier and the `/dl` metadata generators first run for real at the GA. When changing the published asset set, download the dry run's artifacts and diff the real filenames against the verifier's required list.

## Verification discipline

- rust-embed bakes the frontend bundle at build time. To smoke a frontend change, `npm run build`, then `cargo build -p chan`, then restart; there is no hot reload, and a stale `web/dist` gives a false "the flag is broken". Grep the served bundle, not the source, when a flag looks broken.
- When re-walking a previously failed test, stop the old server, rebuild, verify the binary's provenance (`chan --version`), then restart; stale binaries cause long wild-goose chases. In multi-agent runs a broad `pkill chan` kills every lane's server: serve from a renamed binary copy and scope kills to your own path.
- Static gates (svelte-check and the source scanners vitest runs) miss Svelte 5 runtime reactivity errors such as `state_unsafe_mutation`, and a mounted vitest sees one only on the path it drives. Browser-smoke any reactivity change.
- When you work around something, ask what else assumes the thing you just worked around. A resolved obstacle reads as closed business rather than information. Three engineers each worked around the same mtime collision locally, and none asked what else assumed that mtime advances; a write compare-and-swap did, and silently overwrote external edits. The same shape: a `fallocate` that fixed one disk problem and filled the host, and a `CARGO_TARGET_DIR` moved off `/` that broke a gate step reading a relative `target/release/chan`.
- An assumption recorded at the dependent site can be worse than none. A docstring that names the failure exactly and then asserts it is handled closes every later reader's question, where an absent note would invite one. Ask of each recorded assumption: what test fails if this sentence is false? None means a hypothesis dressed as a fact.
- Isolated-run counts do not certify a load-sensitive test: hundreds of consecutive isolated runs were green on known-broken code. Use [`scripts/e2e/one-cpu-test-series.sh`](../scripts/e2e/one-cpu-test-series.sh), which fails closed unless the host cgroup proves the one-CPU cap and records the parallel instrument with its red-run rate; reading the cap inside the container reports `max` and misleads. Measure a flake, never report it: "3 red / 20 on a quiet box" is a decision; "it failed once" is an anecdote.
- A frame-rate acceptance needs guards that can fire, and a renderer string is not one: "60 fps through ANGLE" is satisfied end to end by a software rasterizer. An fps acceptance carries four things or it proves nothing: a baseline arm with nothing mounted; a liveness check per arm, because the most dangerous failure presents as the best result; an identification step that refuses rather than assumes; and a renderer string the instrument printed. [`scripts/e2e/animation-fps.py`](../scripts/e2e/animation-fps.py) implements all four.
- Under tooling flakiness, agents confabulate: they invent file content matching their hypothesis or mistake a stale edit echo for a landed change. Anchor on `git status`, a sha or `curl`, read atomically, and verify a hash before reasoning.
- Terminal render glitches (focus switch, paste) are WKWebView and desktop specific and do not reproduce in Chrome automation. Ask which client first; verify desktop fixes in chan-desktop, which only the owner can hand-smoke.

## Wire, rename and cross-crate discipline

- A green cargo gate does not prove a rename is complete. serde enum tags, Tauri permission strings, JS `invoke` names and route strings are validated at runtime: audit and smoke them, and pin wire strings with `serde(rename)`. Watch ambiguous words and rename only the one you mean.
- Adding a required field to a shared type: grep all literals in both casings and run svelte-check; vitest strips types, so a scoped vitest passes with fixtures missing the field.
- A multi-file Rust signature change leaves a transient non-compiling window that blocks same-crate peers, since file ownership does not isolate the build. Make the signature change and all call sites in one burst and get `cargo check -p <crate>` green before pausing. `.ts` edits are interleave-safe.
- Cross-crate kinds (the Rust `FileClass` and indexer kind, and their TypeScript mirrors) stay in lockstep.

## Release norms

- Compatibility is bounded, not absent. A user's `~/.chan` outlives every release, so persisted state is read in its old shape and written in the new one: the registry upgrades a stock default list on open and leaves a customized one alone, the desktop migrates old config rows once at startup and ignores rows it no longer uses without writing them back, a devserver restart manifest from before ring files still restores, and a known prior systemd unit render is migrated in place. Keep the old reader until the migration has shipped, then delete it; never keep an old writer.
- chan's own processes talk across one release boundary. The CLI-to-desktop and devserver handoffs and the gateway tunnel carry a protocol number, a mismatch falls back or refuses with a message rather than decoding an unknown shape, and a wire field the previous release's peer may lack is optional with a stated meaning for its absence. That is the whole promise: no support matrix across several releases, no deprecation period, and no graceful-degrade path for third-party clients. Raise a compatibility question with the owner only when a change would strand a user's persisted state or break the previous release's peer; otherwise drop the old shape.
- Keep the full gate green and ship no known bug. The owner accepts a few small bugs as the solo user but not a lower gate. Give a final validation pass and a local desktop build before any tag.
- Bump every version pin together (`[workspace.package]` in Cargo.toml, `tauri.conf.json`, the lockfiles and `web/`). Tagging `vX.Y.Z` fires the release workflow, and self-upgrade is data-driven from the published metadata, so cutting a release supersedes prior versions. macOS signing and notarization run only on Actions; dry-run through `workflow_dispatch` before tagging. The full cycle is [skills/release/SKILL.md](skills/release/SKILL.md).

## Working as an agent inside chan

chan is the orchestration host. A terminal chan launches gets a `CHAN_TAB_NAME` it self-identifies from, and, when MCP env is opted in (it is off by default), the `CHAN_MCP_*` variables to reach chan's in-process MCP server. The integration contracts (the cs control socket, the team-directory contract, MCP discovery) live in [orchestration/](orchestration/). Secrets never appear in journals, chat or commits; signing secrets are consumed by name through GitHub Actions secrets only.

Your own terminal is a PTY held by the devserver you run on, and so is every teammate's. Anything that restarts, stops or takes over that devserver ends the whole round's sessions at once, uncommitted work included, and it reaches further than a throwaway `CHAN_HOME` and port suggest. Systemd fd-store testing runs inside an sdme container for that reason; see [`../scripts/e2e/README.md`](../scripts/e2e/README.md).
