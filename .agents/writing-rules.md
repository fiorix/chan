# Writing Rules

- **No em dashes** in comments or documentation.
- **Tables**: pure ASCII, target 80 columns.
- **Prose: no hard wrap.** Paragraphs, list items, and blockquotes roll as one logical line each; let the editor soft-wrap. Do not reflow prose to 80 columns. Only **tables** target 80 columns (or break the columns into bullets). Commit-message bodies keep their own ~72-column wrap; the `dev/` coordination tree is exempt.
- **Factual**: no marketing language. Include analysis with benchmarks; explain whether numbers meet expectations.
- **Comments**: explain WHY, not WHAT.
- **Source citations anchor on content, not position.** A line number keeps resolving after the code moves: it points at whatever now occupies that position and looks entirely valid, so it fails OPEN and silently. A commit sha fails CLOSED, because `git cat-file` errors on an orphaned one, which looks worse and is better. A content needle is robust against every edit that does not change the thing being cited, and when it does break, the breakage is a fact about the file rather than a coincidence about numbering. This is the whole reason for the rule: the failure mode being removed is not "the citation is wrong", it is "the citation is wrong and nothing can tell you". Cite by a quoted fragment of the code plus its enclosing symbol name, and give the repository-relative path so the reader can re-resolve it by hand when the needle breaks. Where a position genuinely is the subject, for example a recorded panic site, anchor it to the revision it was read at and say so.
- **A content needle declares how many times it is expected to match.** An undeclared count is unverifiable in a second way, because a checker cannot distinguish an intended two from a drifted two. Two is a real expected value, not a defect: `!readiness.is_ready()` occurs exactly twice in `crates/chan-server/src/routes/search.rs` and a roadmap item cites both deliberately. Citations under `team/roadmap/` that are meant to be checked go in a `citations` fenced block, one record per line, tab-separated as `path`, `symbol`, `expect`, `needle`, with the needle LAST because a needle is arbitrary source text and may contain any delimiter a table would use. `expect` is an integer, or `DEAD` for a reference that is deliberately dead and must not be "fixed". Run `scripts/citation-check.py` over a file to verify them.
- **Snapshot, not changelog**: comments, project docs, and commit subject lines describe the code as it IS, in the present tense (the WHY behind its current shape). Never narrate change over time or cite plan / round / phase numbers or task ids ("§2b", "until §2a splits this out", "previously X, now Y", "TODO round 2"). Change history belongs only in `CHANGELOG.md`, `team/`, and the `dev/` coordination tree (plans, journals, task files); never in code comments, other project docs, or commit headlines. A real runtime phase ("embed phase", "BM25 phase") is fine; this bars PLAN-phase references, including in commit subjects.
