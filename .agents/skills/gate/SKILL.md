# The pre-push gate

`scripts/pre-push` is the git hook: it changes to the repository root and runs `make pre-push`, teeing the output to `target/pre-push.log` so a red gate stays diagnosable after the push process is gone. Install it with `./scripts/install-hooks` (or `make hooks`). The root Makefile is the one step list for the hook and for CI: the `linux` job in `ci.yml` and `linux-validate` in `release.yml` run `make ci-linux`, which is `make pre-push` plus the two checks described below.

## What `make pre-push` runs

The gate runs these targets in order. The static checks come first because they take seconds and a finding there is not worth a full compile to discover.

1. `make shell-check`: shellcheck over every tracked shell script (`*.sh`, `*.bash`, and executables whose shebang names a shell), then `scripts/check-sdme-storage.py`, which checks the tracked sdme creating calls and their build-limit flags.
2. `make workflow-check`: actionlint over `.github/workflows`, with shellcheck on the `run:` blocks held to the same `.shellcheckrc` rules as a `.sh` file.
3. `make build-matrix-check`: `scripts/check-build-matrix.py` plus its two test scripts. It ties every shipped build surface (native CI, distro and container jobs) to a real build target; derives from the manifests the root crates the gateway compiles by path and requires the Gateway CI path filter to list them; requires every bundle a workflow, a `packaging/docker/` image or a Nix package builds to use the one node major `.nvmrc` declares; holds both AUR recipes' `check()` to building cargo calls that select only the installed package with no feature flag; and drives `desktop/Makefile`'s `build` through a stand-in Tauri CLI (on Linux a dashed version builds deb and AppImage, then an rpm with the undashed Version and a `0~<suffix>` Release; anything else is one plain build). The gateway contract parses manifests with `tomllib`, so it needs Python 3.11 or newer; on an older `python3` the other contracts still run and this one prints a `FAIL:` line naming the interpreter. Then `make rust-floor-check` runs its graph/control fixtures and checks the locked external normal and build dependencies reachable from `chan` and `chan-desktop` for `x86_64-unknown-linux-gnu` against `packaging/distros/debian/rust-floor`, reporting each newer Rust requirement with its root path. The floor must equal the lowest versioned rustc alternative in both Debian control files; workspace members are exempt because Debian builds them with `--ignore-rust-version`. This is a declared dependency-floor check; the vendored builds with the archive compilers verify source compatibility.
4. `make sdme-contract-check` (Linux only): the sdme storage, parser and limit-policy checks, and the AUR, COPR, desktop, gateway package, gateway database-roles, end-to-end-binaries and Nix sdme drivers, each exercised against a stand-in without starting a guest.
5. `make browser-smoke-lib-test` (Linux only): installs the browser suite's own locked dependencies when they are absent or stale (`run.mjs --deps-only`), then runs every `node --test` file under `scripts/e2e/browser-smoke/lib/`. The browser checks themselves stay outside the gate (below). Then `make desktop-entries-check` (Linux only): `scripts/test-check-desktop-entries.py` shows the checker refuses each way an entry, or an AppImage's extracted tree, can break, and `scripts/check-desktop-entries.py` checks the shared `chan-files.desktop`, `chan-edit.desktop` and `chan-term.desktop`: the openers run their own name with a field code and declare their MIME types (`inode/directory`, `text/markdown`), the terminal runs `chan-term` with the `TerminalEmulator` category and the `X-TerminalArg*` keys mapped onto its options, no other shared entry claims that category, and each passes `desktop-file-validate`.
6. `make nix-hash-contract-check`, then `make nix-hash-check`. The `cargoHash` pins in `packaging/nix/chan.nix` and `packaging/nix/chan-desktop.nix` are one fixed-output hash over the crates vendored from the root `Cargo.lock`; both derivations vendor the same lock, so both carry the same value. No cargo step reads them, so without this step a lock change (a new edge to an already locked crate is enough) gates green and turns CI's Nix job red on `main`. `packaging/nix/cargo-lock.sha256` records the digest of the `Cargo.lock` the pins were harvested for. The contract check proves `scripts/check-nix-cargo-hash.sh` and `scripts/cachix-pin.sh` against throwaway trees; the check then fails when the live lock digests differently, when the digest file is absent or malformed, when a `.nix` file has no `cargoHash` line or more than one, when a pin is a placeholder (`lib.fakeHash`) or not a quoted SRI `sha256-` value, when a pin equals the same file's `npmDeps.hash`, or when the two pins differ. It reads files only, so it runs on every host. A pinned value is accepted as written: only a Nix build can prove it. Harvest with `make nix-sdme-check NIX_PACKAGE=chan` on Linux, or `make nix-check` on a Linux host with Nix (both Linux-only), with the `Cargo.lock` you will pin in the working tree; the value is the `got:` line of the mismatch whose derivation name ends in `-vendor-staging` (a `-npm-deps` mismatch is `npmDeps.hash`, which a build reports first when both lockfiles changed; re-pin it by hand in both files). Then `make nix-hash-pin CARGO_HASH=sha256-...` writes both derivations and records the lock digest. The pin helper refuses a value the same file pins as `npmDeps.hash`, and the value both files already carry when the digest file names another lock (that is the `specified:` line a Nix build prints beside `got:`). The release skill has the full harvest procedure.
7. `make web-lock-check`: a strict `npm ci --dry-run --ignore-scripts`, which rejects a desynced `web/package-lock.json` that every other web target's `npm install` silently repairs in place. It requires npm 10 or newer, because older npm removes `node_modules` under `--dry-run`, and names the resolved version when it refuses.
8. `cargo fmt --check`.
9. `cargo clippy --all-targets -- -D warnings` with `RUSTFLAGS=-D warnings`.
10. `cargo doc --locked --no-deps --workspace` with `RUSTDOCFLAGS=-D warnings` and `RUSTFLAGS=-D warnings` (cargo keys dependency artifacts on `RUSTFLAGS`; dropping it would give this step a dependency build of its own). It is the only step that runs rustdoc, so it alone catches an intra-doc link that does not resolve, prose rustdoc parses as HTML (a bare `<name>` outside a code span) and a redundant link target; clippy reads doc comments but renders none of them. `--no-deps` keeps `-D warnings` off third-party docs. `--workspace` never selects `gateway/`, which is its own Cargo workspace; step 13 covers it.
11. `cargo test --all-targets` with `RUSTFLAGS=-D warnings`, then `make casefold-test-verdict`, which prints whether the casefold pins asserted (`CHAN_CASEFOLD_TEST_DIR` set to a case-folding directory, as the macOS CI jobs do) or skipped.
12. `cargo build --no-default-features` with `RUSTFLAGS=-D warnings`.
13. The gateway block (Linux only): `make gateway-fmt`, `make gateway-lint`, `make gateway-doc`, `make gateway-test`, `make gateway-build`. The gateway is a separate Cargo workspace, so none of the root steps reach it. `gateway-lint` runs `make gateway-version-pin-check` first (the gateway deb version pins and the static packaging isolation contracts, both sub-second, in `packaging/gateway/scripts/`), then clippy over all gateway targets with warnings denied. `gateway-doc` is step 10 for the gateway. `gateway-test` executes the database-free tests: every library's unit tests, all of devserver-proxy's tests, and every gateway binary's unit tests (`--lib` never selects those: admin has no library, and the identity and profile binaries keep tests beside their libraries); it prints the Postgres-backed profile and identity integration-test files as NOT RUN, and Gateway CI runs them against its Postgres service. `gateway-build` builds the identity SPA first (`make gateway-spa`; `identity` embeds it through rust-embed and cannot compile without it), then the release crates. Every gateway cargo recipe passes `--locked`, so a stale `gateway/Cargo.lock` fails here with cargo's own message instead of re-resolving silently inside a release build.
14. `make web-check`: svelte-check and vitest for `@chan/web-shared`, `@chan/launcher`, `@chan/workspace-app` and `@chan/profile`, then the production build of the workspace app; the launcher bundle is built as a prerequisite.
15. `make web-marketing-check`: the marketing site's check script (svelte-check, vitest, `node --check` over its scripts, the build and its smokes).
16. `make e2e-check`: `scripts/check-e2e-syntax.py` checks syntax over the e2e harness and the desktop shell's JavaScript, which no cargo or npm target reads. On Linux it also runs `make wireguard-enrollment-test`, the host-safe Node tests of the identity stub, enrollment oracle and mocked desktop shell helpers; no desktop or gateway is started.
17. `make shortcuts-check`: diffs the generator's output from `shortcuts.ts` against the `KEYBINDINGS_TABLE` const that `chan serve --help` prints.
18. `make file-classes-check`: compiles the workspace app's `state/fileTypes.ts` and diffs its `SERVER_CLASSIFIER_MIRROR` sets against the `classify_ext` and `classify_basename` match arms in `crates/chan-workspace/src/fs_ops.rs`, so a file extension widened on one side alone fails here. `FRONTEND_ONLY` in `scripts/check-file-classes.py` names each difference carried on purpose, and an entry that stops being a difference fails too.
19. `make host-build-check`: the release CLI build, `scripts/smoke-built-devserver.sh` (boots the binary's foreground devserver and proves its health route), then the native desktop package: an AppImage on Linux, checked by `scripts/check-desktop-entries.py --appimage` (its root and its `usr/share/applications` each hold Chan's desktop file alone, since AppRun runs the first desktop file it reads in the root and linuxdeploy links there the first it lists under `usr/share/applications`; the three entries it carries under `usr/share/chan/applications` pass the checks step 5 applies to the shared ones), or on macOS a `.app` built with `tauri.ci.macos.conf.json` and checked with `codesign --verify`. Any other host fails here.

### Hosts

Steps 4, 5 and 13 are Linux-only: the sdme drivers use Linux and GNU tooling, the browser suite's Node tests use a shell-script npm stand-in, the desktop entries' check runs `desktop-file-validate`, and the gateway builds inside an sdme container. Step 16 keeps its syntax check on every host and runs its WireGuard helper tests only on Linux, because their mocked shell calls use Bash and GNU tools. `make pre-push` skips them on macOS and Windows so the git hook stays usable there, and a Linux-only target invoked on another host refuses and names `make ci-macos` or `make ci-windows`. `make ci-linux` is the gate CI runs for those steps.

sdme is the project's systemd-nspawn container manager, a third-party tool (installed from sdme.io) that drives the disposable local builds: the containerized Nix recipes, `make windows-cross-check`, the COPR matrix builds and the Linux desktop bundles. CI never uses it. The contract checks in step 4 run the drivers against stand-ins and never start a container. The real containerized Nix build (`make nix-sdme-check`, the hash-harvesting tool) is deliberately not part of `pre-push`; step 6 checks only that the lock is the one the pins were harvested for, never that the pins are right.

`scripts/lint-static.sh` fetches shellcheck and actionlint at pinned versions, each verified against a checksum, into `${XDG_CACHE_HOME:-~/.cache}/chan/lint-tools` (override with `CHAN_LINT_TOOLS_DIR`). The cache is outside `target/` on purpose: the gate discipline wipes `target/`, and every isolated gate worktree has its own, so a cache there would mean a download per gate. Only a cold cache needs network. The severity and the exclude list, with the reason for each exclude, live in `.shellcheckrc`.

`make windows-cross-check` is a separate, mandatory release step. It compiles the CLI for `x86_64-pc-windows-gnu` with warnings denied inside a disposable sdme container, plus the chan-library and chan-server library test binaries and chan-desktop's test targets (`--no-run`); it does not cover chan-workspace and does not run a Windows binary. It needs sdme, an imported Ubuntu rootfs with an `ubuntu` build user whose uid and gid match the caller and whose home is `/home/ubuntu`, btrfs storage under sdme, which applies its CPU and memory limits (no disk cap: the guest is removed after the run, and sdme refuses `--disk` where the btrfs already has quotas enabled by something else), and a clean committed source tree with no uncommitted or untracked files. Native Windows CI supplies Windows execution and packaging; the `release.yml` dry run supplies the macOS compile. Both meet a candidate's code through the `ci.yml` dispatch the release skill asks for at every candidate, not only at the GA commit.

A `crates/`-scoped check misses the gateway workspace and the `chan-desktop` crate (`desktop/src-tauri`). When a change touches a struct used across workspaces, build the whole repository, not just the default workspace.

## What `make ci-linux` adds

`ci-linux` keeps `pre-push` as its prerequisite, then runs two targets in order. The pre-push hook runs only the shared prerequisite.

1. `make test-symlink-tmpdir` runs `cargo test -p chan -p chan-library -p chan-server -p chan-workspace --no-fail-fast` with `TMPDIR` pointing through a symlink under `/tmp` and `RUSTFLAGS=-D warnings`. It exposes raw temp-path comparisons that pass only because Linux's temp directory already has its canonical spelling. It refuses to start unless the link resolves to a different directory, restores owner permissions before removing both paths (a test can leave a directory without write permission, which stops a non-root user such as a CI runner from removing it), names anything it still cannot remove on stderr, and exits with the suites' status either way. Selecting four crates can rebuild dependencies with different features from the workspace test build.
2. `make check-windows-test-target` runs `cargo clippy --tests --target x86_64-pc-windows-gnu --no-deps -- -D warnings` with `RUSTFLAGS=-D warnings` over the non-desktop crates in `CHAN_WINDOWS_TEST_CRATES` (chan-workspace, chan-server, chan-library), then clippy with `--all-targets` for chan-desktop. The native Windows arm reads the same crate list. Linting the desktop's production targets also catches code kept alive only by tests on a non-Linux platform. It refuses when the Rust target or the MinGW compiler is absent, naming `rustup target add x86_64-pc-windows-gnu` or `apt-get install gcc-mingw-w64-x86-64`; both Linux workflow jobs install them. Tauri validates `target/release/chan.exe` as a bundle resource during the check, so the target creates an empty placeholder only when the path is absent and removes only that placeholder on exit.

The native Linux and macOS arms run every crate's full suite with `--all-targets`. The macOS jobs set `CHAN_CASEFOLD_TEST_DIR`, so a green run there means the four casefold pins asserted (their helper fails on a directory that does not fold case; elsewhere they skip and the verdict names the skip). The native Windows arm (`make ci-windows`) runs the full chan-library and chan-desktop suites, the named chan-server tests in `CHAN_SERVER_WINDOWS_TESTS` (the named-pipe control socket, handoff and devserver paths) and the named chan-workspace tests in `CHAN_WORKSPACE_WINDOWS_TESTS` (the `MoveFileExW` no-replace rename and the race windows that commit through it), after checking that each name resolves and is not ignored. The GNU check compiles and lints tests without running a Windows binary:

| Crate | Linux/macOS | Symlink | Native Windows | GNU check |
| --- | --- | --- | --- | --- |
| chan | full | full | none | none |
| chan-library | full | full | full | library + integration |
| chan-server | full | full | named | library tests |
| chan-workspace | full | full | named | library + integration |
| chan-desktop | full | none | full | all targets |

The GNU check includes chan-workspace's integration-test targets, which the native Windows arm does not select, and excludes chan-server's example target. Warnings in compiled workspace path dependencies are denied too. Neither Windows arm runs the `chan` crate's own tests; `make ci-windows` smokes the built `chan.exe` instead.

## The browser smokes are outside the gate, deliberately

The browser checks under `scripts/e2e/browser-smoke` are outside `make pre-push` and CI. The suite's Node tests are the exception: `make browser-smoke-lib-test` runs them in the Linux gate without a browser or a server. The checks stay out for three reasons, each naming what would have to change:

- **Graduation.** `scripts/e2e/README.md` admits a suite to the gate only once it has proven stable across several sessions on more than one host. Green runs on one host are evidence for that host, not for the rule.
- **No runner carries what it needs.** Chrome and the libraries it links against are hundreds of megabytes that neither a CI runner nor a build container has by default. `make browser-smoke-deps` installs them per container; wiring the suite into `pre-push` would put that on every contributor's push.
- **It costs a build and a server.** The suite builds the web bundle and a debug binary, launches a real `chan serve`, and drives a real browser through every check, which takes minutes against a gate whose other steps are seconds. A check that slows a push down gets disabled rather than fixed.

Run it by judgment after a session that touched the editor, the terminal, the launcher, or anything the SPA renders, as the other `scripts/e2e/` suites are run: `make browser-smoke-deps` first in a fresh container, then `node scripts/e2e/browser-smoke/run.mjs` with a private `XDG_RUNTIME_DIR` (the runner refuses an unset one or the user's own `/run/user/<uid>`; see its README). It exits 2, not 1, when the environment cannot run it, so a caller can tell a missing browser from a real failure; treat that 2 as work to do, never as a pass.

The editor's external-edit convergence path is what this suite covers that nothing else does. A change to `flushed_mtime_ns` or the doc-session reconciler is the clearest case for running it before pushing, gate or no gate.

## The packaging isolation simulation is outside the gate

`make gateway-packaging-isolation-test` (Linux) is the behavioural half of the packaging isolation checks and is not in `make pre-push`. It runs `packaging/gateway/scripts/test-packaging-isolation.sh`: the six gateway package postinsts against a scratch root, in all 120 install orders of the five account-plane packages with the WireGuard agent's at each position, with the resulting modes checked, the database readiness check with invalid versions, the postinst refusals of a retained owner-URL or auto-migration conffile, the admission keypair helper, and every sdme provisioner refusal path against stubbed `id` and `getent`. That is about half a minute against a static step that takes a fraction of a second, so only the static half is gated. The target runs `gateway-version-pin-check` first, so one invocation covers both halves. Gateway CI runs it on every run, in its `gateway packaging (linux)` job, beside the Kubernetes manifest test (`python3 packaging/kube/test-manifests.py`) and the database-roles suite.

Run it when a change touches a gateway package postinst or packaging env file, `packaging/gateway/scripts/configure.sh`, `check-database-ready.sh`, `generate-admission-keypair.py`, or `packaging/sdme/chan-devserver-provision.sh`, and before cutting a release that carries such a change.

## The database-roles suite is outside the gate

`make gateway-database-roles-test` runs `packaging/gateway/scripts/test-database-roles.sh` and is not in `make pre-push`. The suite needs a real PostgreSQL and rewrites the cluster-wide `chan_gateway_identity` and `chan_gateway_profile` roles, so its only local route is a disposable sdme guest: the target boots the `chan-psql` rootfs (built on first use) with a private network, runs the suite inside it against the working tree's role scripts and migrations, and removes the guest. It never runs against a host PostgreSQL. Gateway CI's packaging job runs the same suite on every run.

The suite is an exact privilege matrix in both directions: each privilege the role scripts grant must be held, and the two application roles and `PUBLIC` must hold nothing else on any schema, table, column or sequence of `public` and `tower_sessions`. A refusal counts only as SQLSTATE 42501, so a statement that fails for another reason is not read as a denial. A run is green only when the suite exits 0, prints no `FAIL` line and reaches its final `PASS` line; the sdme driver and the CI step both apply that verdict, and step 4 holds the driver to it against a stand-in. The routes run different majors: Gateway CI uses PostgreSQL 16, the major the Kubernetes manifests deploy, and the sdme guest runs PostgreSQL 18, so a local green certifies 18 alone.

## Discipline

- **Re-run after the last edit.** A check that ran before a later edit is stale. `cargo fmt --check` and `make gateway-fmt` in particular must run after the final edit, or an "own-gate-green" report is wrong.
- **Do not pipe the command you are verifying.** `cargo ... | tail` reports tail's exit 0 and hides cargo's failure. Run it bare and check `$?`, or set `pipefail`. `${PIPESTATUS[0]}` is not a fix: it holds only the most recent pipeline, so a `;` and an intervening command leave it empty. A backgrounded or notified run reports the status of the whole pipeline, so a suite piped through `grep` or `tail` is announced as exit 0 while its own summary says fifteen failures. Take the verdict from the artifact the run wrote (`results.json`, a status file, the summary line), not from the number on the notification; where a wrapper needs the real status, capture it inside the wrapped shell (`cmd > log 2>&1; echo "rc=$?" > status`) before anything downstream can overwrite it.
- **Let setup fail loudly.** A setup step run as `apt-get ... >/dev/null 2>&1` that fails leaves its tool absent, and the failure surfaces later as some probe failing for its own apparent reason, pointing at the wrong subsystem. When a probe reports a subsystem down, confirm with a second mechanism that shares none of the first one's dependencies before believing it.
- **Do not truncate the log.** `| tail -40` keeps the end of a run and drops the middle, and a failing or slow run prints more than a clean one, so truncation drops most from exactly the runs that matter; a harness reading a fixed tail sees a biased sample that hides reds and manufactures findings. Redirect the whole log to a file and search it; if you must narrow, grep for the result pattern rather than slicing by position.
- **The gate gates every push, including tags.** A backgrounded gated push can SIGPIPE (exit 141) and silently fail to update the remote. Push in the foreground, redirect to a file, and verify with `git ls-remote`.
- **Prove the instrument can see a failure.** A harness that reads results by pattern-matching a runner's output can miss a red and report silence; a classifier that infers from a grep line rather than from the source can misfile working code. Before trusting what a tool says about a check, confirm it goes red on a known failure.
- **Gate the commit, not the working tree.** A scoped gate run on a dirty tree and committed afterwards has not gated the commit it reports: the tree can move under a long run, and `git diff HEAD --quiet` afterwards proves only that the tree matched at that moment. Either commit first and gate the committed state, or hash the tracked content before and after the run and withhold the green if it moved. Print `HEAD` and a dirt count so a mismatch is visible.

## Isolated / own-gate model (multi-agent rounds)

In a multi-agent shared worktree, the full-tree `make pre-push` gates the committed state and is run by a single owner (the round's lead) from an isolated gate worktree, so it is immune to peers' in-flight working-tree changes.

Worker lanes report a scoped own-gate green against that commit, plus the pathspec they committed, and do not block on the main-tree pre-push, where a concurrent peer's WIP causes false reds. The committed-state rule applies to lanes too: a scoped green names a sha, so it has to have gated that sha rather than the working tree that became it. The scoped own-gate for frontend work must run `make web-check` (vitest included), not just svelte-check plus build, or a failing frontend test slips past the scoped check and the integrated gate catches it later.

A lane that touches any shell script (`packaging/`, `scripts/`, `web/packages/marketing/src/install.sh`, a git hook) or any `.github/workflows` file owns `make shell-check` and `make workflow-check` in its scoped own-gate. Both run in seconds and neither is implied by a Rust, frontend or desktop scoped gate, so without this the linters first fire at the lead's integrated gate, on someone else's clock.

A backgrounded process does not outlive the `sdme exec` that started it, and `setsid nohup cmd &` does not change that: the command returns, the session ends, and the child goes with it. Run anything long-lived as the exec's own foreground command and background the caller instead, or the run dies silently and its absence looks like a fast failure.

Run the container gate as `ubuntu` (uid 1000), with its own home and writable target, so file permissions affect the gate as they affect CI's runner. Both linters enumerate their inputs with `git ls-files`, so they need to see the repository, which a container running against a bind-mounted linked worktree does not by default: the worktree's `.git` is a file pointing at the main checkout's `.git/worktrees/<name>`, and that path is not mounted. Bind the main checkout's `.git` at its real path alongside the worktree, and set `git config --global --add safe.directory` for `ubuntu` if the bind mount has another owner. Without it `make shell-check` dies with `found no tracked shell scripts to check`, which fails closed but names the wrong cause; git's own `not a git repository` is printed just above it.
