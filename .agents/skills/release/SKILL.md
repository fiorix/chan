# Cut a release

A release is a single annotated tag `vX.Y.Z` on `main`. Pushing that tag fires `.github/workflows/release.yml` with publish semantics: it builds the CLI for Linux, macOS, Windows and FreeBSD, the gateway packages for Linux, and the desktop artifacts for Linux, macOS and Windows, signs and notarizes the macOS desktop build, uploads the GitHub Release assets, regenerates the chan.app `/dl` metadata (moving `latest`), and deploys GitHub Pages. A successful Release run then triggers `.github/workflows/publish-downstream.yml` once for Docker Hub, Cachix, COPR, the PPA, the AUR, and the Homebrew tap. The tag push is the public release; everything before it is preparation.

## Publication layers

The release boundary is the tag, signed artifacts, GitHub Release, `/dl` metadata, and Pages deploy. Docker, Cachix, and every distro publication are secondary downstream targets. No secondary target may fail the release or block another secondary target. Non-blocking means decoupled, never hidden: each downstream failure stays red, attributable, and independently retryable.

## Actors

- **Release owner** (@fiorix): owns `main`, the RC branches, the final tags, and the publish decision, and types the two publishing pushes of a cycle: the fast-forward of `main` to the GA commit and the tag (step 8). The owner's word of 2026-10-12: it is fine for a seat to stop for his permission there; whether a version goes through an rc or straight to GA is his call once the version's roadmap is complete, before a candidate is cut.
- **Host agents**: run in the owner's session and clone; they review, gate, and report, but never own the release decision. A seat does not run the two publishing pushes, whether or not its session would allow them: it prepares that step as one reviewed line and hands it to the owner. The pushes of candidate, backup and staging branches, the workflow dispatches and a documents push of `main` after the freeze a seat runs on the owner's word, read no wider than its words (see Publishing acts).
- **Contributor**: works in their own clone, owns their branch and local test cycle until they open a PR.
- **RC branch**: the public integration branch for one release candidate, named `X.Y.Z-rcN` (no leading `v`; see Invariants). A merge into it is provisional until GA.

## The cycle

Solo and contributor modes run the same cycle; the only difference is the merge boundary. The owner merges accepted candidates locally; a contributor opens a PR onto the public RC.

1. **Feature work.** Branches and worktrees off `main`, pushed and shared for review. Before an RC target exists, a branch holds and keeps iterating: build, test, hand-smoke, agent review.
2. **Open the RC.** The owner cuts the candidate: bump every version pin from the current GA to `X.Y.Z-rc0` (a version's first candidate is rc0) and harvest both Nix fixed-output hashes for the regenerated lockfiles (see Version pins) in one commit on a branch named `X.Y.Z-rcN`, and push it. This is the concrete integration target contributors rebase onto.
3. **Intake.** A candidate is ready when it is rebased onto the RC, locally validated (format, tests, hand-smoke), and carries its RC report (below). The owner plus host agents gate it; the owner accepts it into the RC as a provisional merge, or sends it back with the report updated.
4. **Dry-run build.** Dispatch `release.yml` on the RC branch with `publish=false`. This is the only way to exercise the macOS sign and notarize path and the Tauri updater signing off a workstation, so it is mandatory before GA. The dry run is also the macOS half of the mandatory platform verification in step 6; it does not replace the Windows cross-check. Every build job fans out off the `context` job: the Linux and macOS validation jobs and the Linux, macOS, Windows, FreeBSD, and gateway artifact jobs all start once `context` passes, and only `publish-release` waits for validation, so a dry run whose artifact jobs start after a validation job finishes signals a workflow regression. Download the run artifacts and validate them (`cs download` them locally when the build host is remote). Separately dispatch `publish-downstream` twice on the RC branch with the planned tag and `publish=false`: once with `targets=docker`, which builds every image cache-only without reading registry credentials, and once with `targets=cachix`, which builds and smokes `chan-desktop` natively on both Linux architectures without pushing. Dispatch `ci.yml` on the RC branch as well, at every candidate when it is cut (`gh workflow run ci.yml --ref X.Y.Z-rcN`), and Gateway CI with it (`gh workflow run gateway-ci.yml --ref X.Y.Z-rcN`); wait for both. `ci.yml` runs by itself only on `main` and pull requests, so without this dispatch a version's code meets `make ci-windows`, the Linux deb and rpm job and the COPR and PPA source packages for the first time at the GA commit, where a red costs the cut a repair commit and a second round of proofs (v0.102.0's Windows time guard) instead of costing a candidate; v0.103.0 and v0.105.0 ran it on their candidates and v0.104.0 did not. A red on the candidate run is read to its failing test first. A red in the version's code is a blocker like any other and goes to step 5. A rerun of the failed job does not erase the first red: it stays in the record with its cause, as v0.103.0 and v0.105.0 kept theirs. What the candidate run covers that the dry runs and the cross-check of step 6 do not: the native Windows test suites, the Linux deb and rpm packages and the COPR and PPA source packages. It repeats `make ci-linux` and `make ci-macos`, which the `release.yml` dry run runs in its validation jobs, and the Nix build, which the `targets=cachix` dry run makes. What it cannot see, and only the GA commit's own run in step 8 covers: the AUR builds, which skip at a prerelease pin and build for real only at the GA pin, and the GA pin's own lockfiles and hashes. A branch run never writes the shared Rust cache keys (the workflow's header), so its cost is wall time alone: 38 minutes for v0.105.0's run on its integration branch, and 48 and 56 minutes to the end of the first attempt of the rc0 runs of v0.105.0 and v0.103.0, whose longest job is `make ci-linux`. Both rc0 runs took 85 and 89 minutes in all because `make ci-macos` was red once in each and its rerun began only after the run had completed; Gateway CI took five minutes. Artifact testing can still reject work already merged into the RC. Note what this dry run cannot see. Two things, and they fail differently.

First, it runs before the GA version pins move, so a lockfile desync or a stale Nix hash introduced by that bump is out of its reach by construction. Those are caught by the post-bump checks in **Tag and publish**, not here: `make pre-push` on the GA commit for the lockfile sync and for a `cargoHash` re-pinned against the bumped `Cargo.lock` (it cannot tell a right value from a wrong one), and the GA commit's own `ci.yml` run, whose Nix job is the only check of both hash values.

Second, and less obvious: a green dry run is evidence about the dry run's inputs, not about the tagged run's. `release.yml` caches `target/` with `Swatinem/rust-cache@v2` in nine jobs, so any step whose behaviour depends on what a cache handed it can pass here and fail at the tag on the identical commit. v0.87.0 did exactly that: the dry run on `479c102e` passed `macOS desktop package`, the tag at the same commit failed it, because the dry run created the dmgbuild venv fresh and the tagged run restored a broken one. The tag had to be deleted and re-pushed, which was only safe because nothing had consumed it yet. The rule this leaves behind is that build TOOLING never lives under a cached path -- `.build-tools/` exists for it, and `desktop/Makefile` keeps the tauri-cli root and the dmgbuild venv there -- and that a tool is validated by running it rather than by testing for its file. Putting a tool back under `target/` re-opens this, and the failure will present as a different error in a different file.
5. **Iterate.** A blocker returns to the owner or to a contributor PR, or overflows to the next version. If fixes land, cut the next candidate by bumping the pins `X.Y.Z-rcN` to `X.Y.Z-rc(N+1)`, with both Nix hashes harvested again for the regenerated lockfiles, and repeat the dry run. An rc is a pin state only; no rc tag is ever pushed (see Invariants).
6. **Platform verification.** Before GA close, run `make windows-cross-check` on the release candidate and require it green, then confirm the `release.yml` dispatch and the `ci.yml` and Gateway CI runs from step 4 are green for the same candidate. The release `make pre-push` gate is Linux-only and cannot see Windows or macOS breakage. The cross-check compiles and lints the CLI crate graph for `x86_64-pc-windows-gnu` inside a disposable sdme container (it needs sdme, an imported Ubuntu rootfs and a btrfs pool that applies its explicit CPU, memory and disk limits); it requires a clean committed source tree with no uncommitted or untracked files, and the rootfs must have an `ubuntu` build user whose uid and gid match the caller and whose home is `/home/ubuntu`. It does not link or smoke a Windows binary, and `ci-windows` remains the authority for that. The dry run and the candidate's `ci.yml` run are the macOS compiles available off a macOS workstation; only the dry run signs and notarizes. Neither platform check substitutes for the other. Also run `make gateway-packaging-isolation-test` on the candidate and require it green; it is Linux-only, takes about 30 s, and exercises the 120-order postinst simulation and the sdme provisioner refusals that `make pre-push` does not run.
7. **GA close.** When no blockers remain, write the release report and cut GA in one commit. The report `team/release/release-vX.Y.Z.md` consolidates the accepted RC reports (or, for a no-rc patch, the round's own notes) into an era-report structure: what shipped, team/process, validation, a short retrospective (highlights, lowlights, honest feedback), and follow-ups. Match a recent report such as `team/release/release-v0.70.2.md` and the conventions in `team/release/README.md`, then add its one-line entry (with any `-rcN` sub-entries indented) to the `team/release/README.md` release index and keep that index current through the latest release. The GA commit carries the report, the README index entry, the CHANGELOG (rename `## [Unreleased]` to `## [vX.Y.Z] - <date>` with a one-line summary, or add a fresh dated section for a no-rc patch), and every version pin (workspace, gateway, desktop, web, plus the fedora specs; see Version pins). Strip `-rcN` from every pin. Stage it on a branch `X.Y.Z-ga` and push that branch; `main` moves to it in step 8, by the owner. This GA commit is the last commit of the cycle. The report names the GA commit and the branch it was staged on; it does not carry the ids of the dispatches that prove it, because those runs postdate the commit. Record them after the tag (see Downstream publications), or leave them to `gh run list --commit <sha>`, which resolves every run on the GA commit. Do not re-cut the GA commit to write ids into it: a re-cut is a new sha that needs its own green `ci.yml` run before the tag, which costs the cut a second 35-55 minute CI wait for a change to report text alone.
8. **Tag and publish.** The GA commit proves itself before the tag, because the bump is the one change no earlier check has seen. Require two greens on the GA commit itself: `make web-lock-check` (it runs inside `make pre-push`, so a green gate on the GA commit covers it), and the GA commit's own `ci.yml` run. `ci.yml` triggers on `main` and pull requests only, so a release branch gets no automatic run; dispatch it with `gh workflow run ci.yml --ref <branch>` and wait for it. Its `Nix chan-desktop` job is the only place the Nix fixed-output hashes are actually verified against a real build, and this is the last moment that verification is worth anything: `publish-downstream` checks out the tag, so a hash that is wrong here cannot be repaired for this release afterwards. v0.83.3 is the cautionary case: that GA commit's own CI run was red on `Nix chan-desktop` before the tag was pushed, and the release shipped without its Cachix lane. Only then the owner fast-forwards `main` to the GA commit and annotates and pushes the tag on it: `git tag -a vX.Y.Z -m "chan X.Y.Z"`, then `git push origin vX.Y.Z`. The owner types these two pushes. An agent seat prepares them before the greens are in, as one guarded script with a check mode (read the remote first; refuse a dirty tree, a `main` that has moved, a tag that exists or a GA commit the greens do not name; push in the foreground to a log; read `main` and the tag back with `git ls-remote`), has it reviewed and its refusals rehearsed in the check mode, and when the greens are in shows the owner the one line to run. The seat does not run that push. In v0.104.0 (2026-10-09) the lead seat's reviewed script was denied by its client's permission check before anything ran, and in v0.105.0 the seat did not try; a refusal is reported with its text, and the seat does not retry it in smaller pieces, through another tool, another mode or another seat, changes nothing while it waits, and after the owner's line reads both refs back and takes the release watch of step 9. The tag push runs `release.yml` with `publish=true` and ships the core release. Delete the RC branch, local and remote.
9. **Downstream publications.** A successful tagged Release run triggers `publish-downstream` once for Docker Hub, Cachix, COPR, the PPA, the AUR, and the Homebrew tap. Each target has an independent job chain: a failure is red and attributable there, but cannot fail the core Release or suppress another target. Verify the Docker manifest of every image the `docker-manifest` job publishes, each on both platforms; the Cachix pins `vX.Y.Z-chan-desktop-{x86_64-linux,aarch64-linux}` plus both fresh-runner substitution smokes; COPR `fiorix/chan` (`chan` on every enabled Fedora chroot plus all four CentOS chroots; `chan-desktop` on Fedora plus Stream 10, with no EL9 desktop job); `ppa:fiorix/chan` (noble + resolute); AUR `chan` + `chan-desktop` at `X.Y.Z-1`; and the fiorix/homebrew-chan tap serving `chan-desktop` + `chan` at `X.Y.Z` (the `homebrew-publish` contents-API check is the detector). Keep `main` frozen from the GA tag push until both COPR packages report complete: the COPR SCM packages build main's HEAD on an empty committish, so a push inside that window ships a package labelled `X.Y.Z` but built from a later tree; the `copr` job's publication probe (`packaging/distros/copr/verify-copr-publication.sh`) is the detector and reds when a built version is not the tag. Once the freeze lifts, the first commit on `main` may add the cycle's run ids (the GA commit's `ci.yml` run, the dry-run dispatches, the tagged Release run, and the downstream run) to the report's platform-and-pipeline paragraph; nothing downstream reads that commit (`cachix-build`, the AUR, Homebrew, and the PPA all check out the tag). The COPR chroot list, the per-chroot EPEL repository, and the `chan-desktop` EL9 chroot denylist are console state that nothing in the repo asserts and no API call confirms; read them in the COPR web UI whenever a CentOS job is missing, an EL9 job resolves the wrong EPEL, or an EL9 `chan-desktop` job appears. A red x86_64 `aur-validate` cell blocks both AUR pushes and nothing else. CI does not validate aarch64; the aarch64 PKGBUILD ships for users to build natively. The workflow needs the Docker Hub configuration plus `CACHIX_AUTH_TOKEN`, `COPR_WEBHOOK`, `LAUNCHPAD_GPG_PRIVATE_KEY`, `LAUNCHPAD_GPG_PASSPHRASE`, `AUR_SSH_PRIVATE_KEY`, and `HOMEBREW_TAP_DEPLOY_KEY_BASE64`. Retry via `workflow_dispatch` with the tag, `publish=true` (dispatch defaults to a dry run), and `targets` narrowed to the failed publisher. See `packaging/nix/README.md`, `packaging/distros/README.md`, and `packaging/docker/README.md`.

## Publishing acts and who performs them

Every act of a cycle that reaches the public remote, with who performs it and what the last two cycles observed. A seat performs an act only on the owner's word for the round, read no wider than its words; an act the seat's session refuses is reported with the refusal's text and handed to the owner as one line, never split, rerouted or retried by another seat. A seat's standing authorization for a round does not include deleting a remote branch or publishing anything.

- **Backup pushes of the round's integration branch to a `backup/` branch.** The lead seat, on the owner's word for the round. Observed: v0.104.0 and v0.105.0, pushed by the seat without refusal.
- **The candidate branch push (`X.Y.Z-rcN`, the pin commit).** The lead seat, on the owner's word. Observed: v0.104.0, `0.104.0-rc0` pushed by the seat at 03:12Z on 2026-10-09 without refusal; v0.105.0, `0.105.0-rc0` likewise.

Observed: v0.104.0, `release.yml` and the two `publish-downstream` dry runs dispatched by the seat without refusal, `ci.yml` and Gateway CI not dispatched on the candidate; v0.105.0, all five dispatched by the seat without refusal; the macOS reruns on the v0.103.0 and v0.105.0 rc0 runs were the seat's.
- **The staging branch push of the GA commit (`X.Y.Z-ga`) and the GA commit's `ci.yml` dispatch.** The lead seat, on the owner's word. Observed: v0.104.0, `0.104.0-ga` pushed at 05:11Z without refusal; v0.105.0 likewise.

## RC report files

Each candidate branch owns one report, `team/release/release-vX.Y.Z-rcN-{feature-branch}.md`, with a filename-safe branch name (`/` becomes `-`, kept short and recognizable). It records scope, commit range, test commands, hand-smoke notes, known risks, and changelog-worthy user impact. One branch never edits another branch's report. Only accepted RC reports feed the final `team/release/release-vX.Y.Z.md` and the CHANGELOG.

## Version pins (bump together)

Every pin moves to the same `X.Y.Z` (or `X.Y.Z-rcN`) in one commit. Missing one breaks the release at tag time, where the workflow's context job asserts the Cargo, desktop, and gateway versions all equal the tag:

- `Cargo.toml`: the `[workspace.package]` `version` AND every internal path-dep pin under `[workspace.dependencies]`.
- `gateway/Cargo.toml`: the separate nested workspace, versioned in lockstep through its own `[workspace.package]` version.
- `gateway/crates/profile/Cargo.toml`: the `[package.metadata.deb]` `depends` pin on `chan-gateway-identity (= X.Y.Z-1)`. cargo-deb copies the string verbatim into the control file, so a stale pin ships a profile deb that apt and dpkg refuse to install beside the same release's identity deb. `make gateway-version-pin-check` (a prerequisite of `make gateway-lint`, so `make pre-push` covers it on Linux) asserts it against the gateway workspace version.
- `desktop/src-tauri/tauri.conf.json`: the `.app` bundle version. The desktop Rust package inherits the workspace version, so once this matches, the `.app` and the workspace stay aligned.
- The web `package.json` versions (root plus each package under `web/packages/`), and the marketing `package.json` `@chan/*` dependency pins.
- The three regenerated lockfiles: `Cargo.lock` and `gateway/Cargo.lock` (each refreshed with `cargo update -w`, which moves only the workspace-member versions), and `web/package-lock.json` (refreshed with `npm install`). Run `make web-lock-check` after the npm regen and require it green before harvesting any Nix hash. `npm install` repairs a desynced lockfile in place, so a broken regen is invisible to every other target; only the strict `npm ci` that check runs rejects it. v0.83.3 shipped a regen that dropped the root `@chan/workspace-app` workspace link and lost its Cachix lane for the whole release, because the only strict `npm ci` in the system was the Nix sandbox, which checks out the tag and therefore runs too late to repair. Regenerate with npm 10 or newer; npm 9.2.0 is the known-bad tool that produced that corruption.
- The Nix fixed-output pins: the `npmDeps.hash` shared by both `packaging/nix/*.nix` derivations (invalidated by the regenerated `web/package-lock.json`), and the `cargoHash` shared by them too, pinned in both `packaging/nix/chan.nix` and `packaging/nix/chan-desktop.nix` (invalidated by the regenerated `Cargo.lock`; both derivations vendor the same lock, so both carry one value, and `make nix-hash-check` fails when they differ, when either is a placeholder, or when the lock is not the one `packaging/nix/cargo-lock.sha256` records as harvested for). Re-pin both values, in all four fields, in the SAME commit: set the stale fields to `lib.fakeHash`, build, and copy each `got: sha256-...` from the mismatch error (one surfaces at a time, npm first: the `-npm-deps` mismatch is `npmDeps.hash` and the `-vendor-staging` one is `cargoHash`, so both `npmDeps.hash` fields are re-pinned before a build reaches the cargo mismatch), or run `make nix-check` on a Linux host with Nix installed; pin the cargo value with `make nix-hash-pin CARGO_HASH=sha256-...`, which writes both `cargoHash` fields and records the lock digest. On a host without Nix, use the sdme container recipe below. The Cachix publish job checks out the TAG, so a hash missed here cannot be repaired for that release afterward; v0.81.0 shipped without Cachix pins for exactly this reason.

  **Harvest at every version bump, release candidates included.** An rc bump moves the version pins and regenerates the lockfiles, which makes both hashes stale, and `make pre-push` fails on the bump commit until `cargoHash` follows the lock: `make nix-hash-check` compares the live `Cargo.lock` with the digest recorded when the pins were harvested, so a stale pin blocks the bump commit's own gate and every candidate rebased onto it. The bump commit therefore carries the harvest. The gate does not check `npmDeps.hash`, but the harvest reaches the cargo mismatch only through the npm one: with the `npmDeps.hash` fields stale, `make nix-sdme-check NIX_PACKAGE=chan` stops at the npm fixed-output derivation (`-npm-deps`) and reports its `got:` value, and the run after both npm fields are re-pinned stops at the cargo vendor derivation (`-vendor-staging`) with the cargo value. So an rc bump re-pins both `npmDeps.hash` fields, then runs `make nix-hash-pin CARGO_HASH=sha256-...`, in the bump commit. This costs two disposable Nix builds per bump, each stopping at a fixed-output boundary rather than building the closure, and buys early warning: a hash CI's Nix job would reject is found at the candidate rather than at the moment you want to tag. The GA commit repeats the harvest for its own regenerated lockfiles, and its CI run must still be green before the tag, which is the requirement in **Tag and publish**.

The marketing site reads the workspace version at build time, so it needs no separate bump; confirm nothing else has drifted.

GA only (not rc pins), the distro source packages -- both publish after the tag via `publish-downstream`, so neither gates it, but keep them current in the GA commit:

- Fedora COPR: bump `%global upstream_version` in BOTH `packaging/distros/fedora/chan.spec` and `chan-desktop.spec` (a fallback -- COPR's `make-srpm.sh` rewrites it from the workspace Cargo.toml), and prepend a dated `%changelog` entry to BOTH.
- Ubuntu Launchpad (PPA): no manual version edit. `packaging/distros/debian/build-source.sh` derives the version from `HEAD:Cargo.toml` and fills the `debian/{chan,chan-desktop}/debian/changelog.in` `@VERSION@`/`@DATE@` template at build time; there is no per-release Debian changelog to hand-edit.
- Arch: no manual version edit and no GA pin. `packaging/linux/arch/PKGBUILD` remains the local binary QA path. The AUR renderer under `packaging/distros/arch/` derives `pkgver` from the GA tag and uses `pkgrel=1` unless a packaging-only repair is dispatched explicitly.
- Nix: no manual version edit. The flake reads the root Cargo workspace version, and the GA downstream job creates the two versioned Cachix pins after building the tagged source.
- Homebrew: no manual version edit and no GA pin. The tap renderer under `packaging/distros/homebrew/` derives the version from the GA tag and hashes the published release assets; `publish-downstream` regenerates and pushes both fiorix/homebrew-chan files.

### Nix hashes on a host without Nix (sdme)

Use the tracked supplementary Ubuntu sdme workflow. It mounts a snapshot of the indexed working-tree files read-only, returns only the log and status to the host, and discards the source snapshot, guest packages, Nix store, and closures:

```sh
sudo sdme fs import docker.io/ubuntu:26.04 --name ubuntu --install-packages=yes -v
make nix-sdme-check
make nix-sdme-check NIX_PACKAGE=chan
make nix-sdme-check NIX_PACKAGE=chan-desktop
```

`NIX_PACKAGE=all` delegates to the native `make nix-check` contract. Use a named package while harvesting one fixed-output hash so the other package is not forced first. Each failed build records its combined output in `/var/tmp/chan-nix-sdme-check/build.log`; copy the reported `got: sha256-...` (not the `specified:` line above it, which is the stale pin) into the field the derivation name selects, `npmDeps.hash` for `-npm-deps` and `cargoHash` for `-vendor-staging`, and repeat. Both `npmDeps.hash` and `cargoHash` are pinned in both derivations and carry the same value in each, since the two packages vendor the same `web/package-lock.json` and the same root `Cargo.lock`; a value harvested from one package goes into both files (`make nix-hash-pin` does that for `cargoHash` and records the lock digest), and harvesting the other package as well cross-checks it. The workflow builds only: it never pushes or pins Cachix, publishes a release, tags, or copies release artifacts. Native `make nix-check`, GA CI, and the Cachix publication jobs remain authoritative for release validation and publication.

**Harvesting as a user who is not root, in a capped guest.** The tracked workflow above runs its whole payload as root under the Nix driver's measured limits (2 CPUs, 11G memory, a 3600-second timeout; `packaging/sdme-build-policy.sh`). The route proved in the v0.106.0 round for a harvest under a team's guest bounds is this one, and it is the one to use when the harvest must not run on the host or as root. Prerequisites: an Ubuntu sdme guest (the round measured a standing one) whose caps are read from the host (at least 2 CPUs, 6 GiB and a 44 GiB btrfs quota; `--cpus`, `--memory`, `--storage btrfs --disk`), Nix from the Ubuntu packages `nix-bin` and `nix-setup-systemd` (2.18.1 at the time), with `NIX_REMOTE=local` so the build never goes through the daemon those packages enable and `NIX_CONFIG` set to `experimental-features = nix-command flakes`, `max-jobs = 2`, `cores = 2`, `sandbox = true` (the command below is the new CLI with a flake reference and was never run without that line), a real `/nix` created by root and `chown`ed to the build user (a private rooted store under the user's home fails: the builder cannot execute its own bash through the store's physical path, measured in that round), and the repository at a clean commit in the guest. Shape: in a scratch working tree, set the one hash field the derivation name selects, in both derivations, to a deliberately wrong value of the right form, then as the build user run `nix build --no-link --max-jobs 2 --cores 2 path:<tree>#chan.npmDeps` and, after pinning its result, `path:<tree>#chan.cargoDeps.vendorStaging`, each under `timeout -s TERM -k 30s 1800s`; each build must end at exactly one fixed-output mismatch whose `got:` differs from the stale `specified:` pin, with its status recorded; copy the `got:` value into both derivations (`make nix-hash-pin` for the cargo one, which also records the lock digest) and check the lockfile identity (`make nix-hash-check`). Bounds measured in that round: about 20 to 35 s a build (the cargo build fetched its own closure in its run, so the times stand for a cold store), a memory peak of 5.5 GB under the 6 GiB cap (the cap is the size measured, not a margin above a need), about 3 GB of store from empty for the two. If the cap or the store preflight fails, a build times out or reports any error other than the expected mismatch, or the status or the mismatch is absent, the route is refused: stop and report to the release owner; neither a host harvest nor a pin is taken on a refused route.

## Invariants

- **An rc is a pin, never a tag.** Any `v*` tag push, including `vX.Y.Z-rcN`, runs `release.yml` with `publish=true`, and `/dl/{cli,desktop}/latest.json` is regenerated to the pushed tag's version with no prerelease filter, so an rc tag rides the live self-update channel to every client. Validate rc builds with `publish=false` dispatches; only the GA `vX.Y.Z` tag is ever pushed. The RC-branch name carries no leading `v` (`X.Y.Z-rcN`), so it is not tag-shaped and cannot collide with a pushed tag; recent dry runs use this form (`0.70.0-rc1`).
- **A working branch must not be named after its future tag.** A feature, delivery, or round branch for version `X.Y.Z` named `vX.Y.Z` collides with the eventual GA tag `vX.Y.Z`: Git reports an ambiguous ref and a checkout, push, or `git show` can resolve to the wrong object. Name working branches and their worktrees distinctly from any tag. The delivery convention is a `../chan-vXYZ` worktree (for example `../chan-v0650`) on a descriptively named branch; RC integration branches use the tag-free `X.Y.Z-rcN` form (no leading `v`). If a branch does end up sharing the version string, fast-forward `main` onto it and delete the branch, local and remote, before tagging.
- **The GA commit is the tagged commit.** Strip the rc pins and cut the CHANGELOG in one commit, tag that commit, and push nothing after it before the tag. Do not tag a later notes or lockfile-refresh commit, do not re-cut the GA commit to record run ids (they are recorded after the tag), and do not ship a version with no CHANGELOG entry.
- **The gate covers every workspace, not every platform.** Run the full `make pre-push` gate green before cutting (see the gate skill); it must include the separate gateway workspace, or a green core gate can still die at tag time. The release gate is Linux-only, so its green result says nothing about Windows or macOS; the two platform checks in step 6 remain mandatory. A fresh clone may have no pre-push hook installed, in which case the manual gate is the only gate.
- **Push tags in the foreground.** A backgrounded gated push can SIGPIPE (exit 141) and silently fail to update the remote; push in the foreground, redirect to a file, and verify with `git ls-remote`. Pushes go over HTTPS with the gh credential helper when SSH is unavailable.
- **A version bump forces a full workspace rebuild.** New crate fingerprints invalidate the incremental cache; reclaim `target/` (drop `target/debug/incremental`, or `cargo clean`) if disk is tight before the gate.

## Self-upgrade is data-driven

Self-upgrade reads the latest manifest from `/dl` on chan.app. Cutting a release moves `latest` to the new version; the `/dl` generator also retains the last 5 GA versions as per-version manifests, so `chan upgrade --version X.Y.Z` resolves older releases. No `update.rs` edit is required. The desktop updater probes the static manifest at `https://chan.app/dl/desktop/latest.json`, generated at release time by `web/packages/marketing/scripts/generate-release-metadata.mjs`; it carries the macOS payload, both Linux AppImages, and the Windows NSIS installer, which the macOS, Linux, and Windows desktop jobs sign with the same `TAURI_SIGNING_PRIVATE_KEY` (all three fail fast when it is absent). Package-manager builds, including `CHAN_PACKAGED=nix`, suppress those probes and refuse self-upgrade; their package manager owns the update path.

## Signing notes

- macOS Developer ID signing and notarization material lives in GitHub Actions Secrets; the secret NAMES the workflow requires are declared in `.github/workflows/release.yml`, and the private per-secret table is kept in the team's gitignored `dev/` tree. The macOS desktop job validates the secrets up front and fails fast with a pointer if one is missing.
- The Tauri updater minisign key is separate from the Apple Developer ID cert. Rotation procedures for both live in `.agents/desktop.md`.
- Secret VALUES never appear in journals, chat, or commits. Only the secret NAMES are referenced in workflow YAML and docs.

## Rollback

A published release cannot be un-published; a bad GA is superseded by the next patch (`X.Y.(Z+1)`). Because rc builds are never tagged, an rc that fails validation costs nothing to discard.
