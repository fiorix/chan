# Contributor Patterns

- **Atomic writes via chan-workspace**: every user-content write goes through `Workspace::write_text` or `Workspace::write_bytes`. These enforce the editable-text gate, the path sandbox, and the special-file refusal. Don't bypass.
- **Subcommand parity**: every chan subcommand has a clap definition + a `cmd_*` function in `crates/chan/src/lib.rs` (`main.rs` is a thin shim so chan-desktop can dispatch the same CLI in-process; `cs` is the argv0 alias into chan-shell). Help text must reflect actual behavior; don't claim env vars or flags that don't exist.
- **CLI grammar: noun families, pinned elevation**: the structural layer is the noun families (`chan workspace`, `chan devserver`); a verb names one object kind with one selector grammar and never dispatches on argument shape to pick its object. `serve` and `close` are the only family verbs with top-level spellings, thin delegates over the same flattened args structs, and the elevation list is pinned by `flat_workspace_subcommands_are_rejected` so it never grows by habit. One `chan devserver` noun holds two faces because the grammar separates them: server-side verbs (run/start/stop/restart/status/join/rotate-token) take no target since the process is a per-CHAN_HOME singleton, client-side verbs (register/ls/connect/disconnect/forget) require a URL or label target and a running desktop. `forget` is the record-drop verb everywhere (workspace forget, devserver forget). Wire tags and internal identifiers (`ControlRequest::Close` and its `remove` field, `UnserveMode`, `cmd_serve`) never chase CLI spellings. Both clap trees set `infer_subcommands` at every level, so an unambiguous prefix is a valid spelling (`chan w ls`, `cs te l`) and an ambiguous one is refused rather than guessed; a new command name must not steal an existing sibling's short prefix, and `subcommand_prefixes_resolve_iproute2_style` / `ambiguous_subcommand_prefixes_are_rejected` pin the chan-tree contract beside chan-shell's `window_subcommand_prefixes_are_unambiguous`.
- **Server routes go in chan-server**: never inline an axum handler inside the binary crate. The `chan` crate parses args and calls `chan_server::serve`. New routes belong in the matching `crates/chan-server/src/routes/<area>.rs`; cross-area shared types live in the module that owns them. Route tables are assembled in exactly four places, all in chan-server: `router_with_extensions()` in `lib.rs` (the per-tenant app), `terminal_router()` in `lib.rs` (the slim workspace-less terminal tenant), `routes::library::launcher_router()`, and `build_devserver_app()` in `devserver.rs`.
- **App-level config files**: anything new under `<config>/chan/` goes through `crate::store::{load_toml, save_toml}` so atomic writes + parent-dir fsync match the rest of the app. Don't roll a fresh `tempfile + rename` by hand.
- **chan-llm is MCP-only**: the crate exposes the chan MCP `Server`, its tool schemas, and embedded prompts, with the MCP surface behind the non-default `mcp` feature. There is no in-app agent session and no CLI backend wrappers; external agents connect through the in-process MCP server in `crates/chan-server/src/mcp_bridge.rs`.
- **Pinned toolchain**: do not introduce code that requires a newer Rust than `rust-toolchain.toml` declares without bumping the pin in the same commit.
