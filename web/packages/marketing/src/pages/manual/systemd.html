Run the devserver under systemd

On Linux, chan devserver start runs the devserver as a systemd user service, chan-devserver.service. chan writes the unit itself and drives it with systemctl --user, so the service is also yours to inspect and manage with systemd's own tools. Under systemd the devserver can restart, and upgrade, without closing a single terminal.

Set up the devserver first as in Devserver. On macOS the devserver runs under launchd, and on Windows and FreeBSD under chan's own daemon, which a Linux machine without systemd uses too, with --service=chan. Both run it the same way, but a restart there closes its terminals.

The devserver service

The chan devserver actions map onto the unit:

  • chan devserver start writes ~/.config/systemd/user/chan-devserver.service, enables it so it starts at boot, starts it, and prints the launch URL and token. It turns on linger first, so the service survives logout. When the service is already running it changes nothing and prints the launch URL and token again.
  • chan devserver status says whether the service is running and shows the command the unit runs. In a terminal it then prints the launch URL with its token; through a pipe it prints the address instead, and --url prints the launch URL there too.
  • chan devserver restart rewrites the unit for the chan binary you run it with, enables it, then restarts the service, or starts it when it is stopped. Your terminals keep running; see Restart without losing terminals.
  • chan devserver stop closes every terminal, stops the service, and disables it so it does not come back at boot. The unit file stays, so status still shows its command.
$chan devserver status {{copyButton}} 
chan devserver (systemd): running -- chan-devserver.service
  command: /home/user/.local/bin/chan devserver run --bind=127.0.0.1 --port=8787
chan devserver: listening on http://127.0.0.1:8787/?t=Zr8mT2xQwN6vLb3HcY5dKp7sJf9aGe4u

The unit is an ordinary user unit. systemctl --user cat chan-devserver shows it, systemctl --user status chan-devserver shows the process tree, and journalctl --user -u chan-devserver has the devserver's log:

$systemctl --user cat chan-devserver {{copyButton}} 
# /home/user/.config/systemd/user/chan-devserver.service
[Unit]
Description=chan devserver
After=network.target

[Service]
Type=notify
NotifyAccess=main
FileDescriptorStoreMax=1024
KillMode=process
Environment="PATH=/home/user/.local/bin:/usr/local/bin:/usr/bin:/bin"
ExecStart=/home/user/.local/bin/chan devserver run --bind=127.0.0.1 --port=8787
TimeoutStartSec=10min
Restart=on-failure
WatchdogSec=30

[Install]
WantedBy=default.target
  • Type=notify: the devserver tells systemd it is ready once it has rebuilt every terminal. When a workspace takes more than a minute to mount, it reports ready without waiting for it, and that workspace's terminals follow. NotifyAccess=main keeps the shells under it from talking to systemd in its name.
  • WatchdogSec=30 and Restart=on-failure: the devserver checks in every 15 seconds. When it hangs or crashes, systemd restarts it, and the terminals come back as in any restart.
  • KillMode=process: a restart signals only the devserver process, never the shells.
  • FileDescriptorStoreMax=1024: room for 512 terminals in systemd's file descriptor store, two descriptors each.
  • TimeoutStartSec=10min: time to rebuild a large set of terminals before the devserver reports ready.
  • Environment= carries CHAN_HOME when you set one, and the PATH of the terminal that last ran start or restart, because a user service otherwise starts with the user manager's environment. A run from a script, with no terminal, keeps the PATH already recorded.
Let chan own the unit

start, when the service is not running, and restart rewrite the unit, which keeps its directives current across chan releases, and refuse a unit they do not recognize. For your own settings, add a drop-in with systemctl --user edit chan-devserver instead of editing the file.

Restart without losing terminals

Restart the devserver either way:

$chan devserver restart {{copyButton}}
$systemctl --user restart chan-devserver {{copyButton}}

Your terminals keep running through it. Every terminal in a window hands its PTY to systemd's file descriptor store when it opens, along with a memory file that holds its scrollback. A restart stops only the devserver process: the shells, and everything running in them, stay where they are, with the same process ids, the same process tree below each shell, and the same control group. Your systemd user instance adopts the shells when the old devserver process exits. The new devserver process receives the descriptors back from systemd, rebuilds each terminal with its scrollback and screen as they stood at the last byte read, and then reports ready.

What you see is a pause. Open windows show reconnecting to the chan server and come back by themselves, and a desktop connected over ssh or Eternal Terminal stays connected when the devserver is back within 30 seconds. A coding agent in the middle of a turn keeps working through it, and cs keeps working in shells that are older than the new devserver process.

The same restore follows a restart that systemd does on its own: the watchdog replacing a hung devserver, or a crashed one coming back.

These end your terminals:

  • chan devserver stop or systemctl --user stop chan-devserver. A stop releases the store, and every shell gets a hangup.
  • chan devserver restart --force, which closes every terminal before it restarts.
  • A reboot of the machine.

A terminal opened while 512 are already stored runs normally, but a restart ends it.

Upgrade a running devserver

A restart starts whatever binary the unit names, so a restart after an upgrade is a live upgrade:

$chan upgrade && chan devserver restart {{copyButton}}

chan upgrade replaces the binary in place and leaves the running devserver alone; it keeps serving the old release until it restarts. chan devserver restart then brings the unit up to date for the new release and restarts into it. Every terminal, and every program running in one, carries on under the new devserver. systemctl --user restart chan-devserver also starts the new binary, but it keeps the unit as it was; chan devserver restart is the one to use after an upgrade.

To check, run chan metrics or open the Dashboard's Metrics slide; both name the version, build, and process id of the running devserver.

A package from a distribution repository (the Ubuntu PPA, Fedora COPR, the AUR) or from Nix is upgraded by its package manager, and chan upgrade refuses there: upgrade the package, then run chan devserver restart. A .deb or .rpm downloaded from a release upgrades with chan upgrade. With Chan Desktop's chan, chan upgrade updates the desktop in the background instead; run chan devserver restart once it has relaunched.

Watch the devserver

The devserver samples itself once a second and keeps the last ten minutes in memory. Two places show it:

  • The Dashboard's Metrics slide, in any window on the devserver: version, build, process id, uptime, CPU, memory, I/O, chan's own traffic, file transfers, tunnels and channels, and the size of the chan home, with graphs of the last ten minutes. After a restart the process id and uptime are new and the graphs start over, while the terminals carry on.
  • chan metrics, on the devserver's machine, prints the same readings. It reads the running devserver and never starts one.
$chan metrics {{copyButton}}
  • --json prints one JSON document, and --history with it adds the retained samples.
  • --watch prints once, then only newer samples, about once a second, until Ctrl+C. With --json it prints one JSON object per line. A read that fails ends it, so a watch outlasts a devserver restart only when the devserver answers again by the next read, about a second later.
  • --url reads another chan server by a URL it printed, such as the URL of chan serve.

chan metrics --help has the examples, and docs/metrics.md says what each reading counts on each platform.

Report the devserver to systemd-report

systemd-report, in systemd 260 and later, collects metrics from the services on a machine. From systemd 261 it also builds them into one JSON report that it can upload to a server of yours, and from 262 it can sign the report; It starts upstream: systemd-report explains the design, and systemd-report(1) the command. The devserver can be one of its sources. An optional pair of user units serves the readings of chan metrics over systemd's metrics interface, io.systemd.Metrics, on a socket in the directory systemd-report --user reads: systemd starts chan metrics --varlink for each connection. A client needs no token: the source reads the devserver's token itself, as chan metrics does.

Write the two units. The service runs the chan your shell finds, and the block prints that path so you can check it:

$mkdir -p ~/.config/systemd/user && cd ~/.config/systemd/user cat > chan-metrics.socket <<'EOF' [Unit] Description=chan devserver metrics for systemd-report [Socket] ListenStream=%t/systemd/report/io.chan.Devserver FileDescriptorName=varlink SocketMode=0600 Accept=yes MaxConnections=16 RemoveOnStop=yes [Install] WantedBy=sockets.target EOF command -v chan cat > chan-metrics@.service <<EOF [Unit] Description=chan devserver metrics for systemd-report [Service] Type=exec ExecStart=$(command -v chan) metrics --varlink StandardInput=socket StandardOutput=socket StandardError=journal NoNewPrivileges=yes EOF cd - >/dev/null {{copyButton}}

When the devserver runs with its own CHAN_HOME, add the same Environment="CHAN_HOME=..." line to the service's [Service] section, so the source reads that devserver. Then enable the socket:

$systemctl --user daemon-reload systemctl --user enable --now chan-metrics.socket {{copyButton}}

systemd-report now lists the devserver as the source io.chan.Devserver, and every reading is a metric family named under it, such as io.chan.Devserver.MemoryResidentBytes. systemd installs systemd-report in /usr/lib/systemd/, outside PATH:

On systemd 260 the describe command is called describe-metrics. --json=short prints each metric as one JSON object.

  • Counters and gauges, not rates: a report is a snapshot, and two reports give the rate. chan metrics --json --history has chan's own rates and the last ten minutes.
  • Counters start over when the devserver restarts. io.chan.Devserver.InstanceId names the devserver process, so a reader can tell a restart from a counter that went down.
  • A connection does not start the devserver. While it is down the source reports no metrics, and the report carries on without them.
  • The source finds the devserver's address and token again on every read, so it follows a restart and a rotated token.

Any Varlink client can read the source too: varlinkctl --more call "$XDG_RUNTIME_DIR/systemd/report/io.chan.Devserver" io.systemd.Metrics.List '{}'. To turn it off, run systemctl --user disable --now chan-metrics.socket. docs/metrics.md lists every family with its type and unit.
