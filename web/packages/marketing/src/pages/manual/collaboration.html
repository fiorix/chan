What you can do

  • Work in one workspace from several windows, browsers, or computers at once.
  • Edit a document or a drawing together. Edits merge live, and each peer's caret carries a name.
  • See the clients connected to a server, name yours, and disconnect one with cs session.
  • Hand leadership of a workspace to another window, or take it when the leader is gone.

Share a workspace session

Every window that opens a workspace connects to the machine serving it, and that server holds the shared state. A window joins the session by reaching that server:

RouteWho joins
The workspace's URL, in a browserAnyone with the URL who can reach the port, on the machine or through an ssh forward.
A devserver, from Chan Desktop or a browserWhoever can connect to the devserver.
A gateway shareThe accounts the devserver's owner shares it with.
SharedWhat each window sees
TerminalsEvery client that shows a window sees the same running shells in it, with their scrollback.
DocumentsEdits merge as they are typed. Each peer's selection and caret show with a name flag, and the file's tab counts the other windows that have it open.
DrawingsChanges to an .excalidraw canvas merge the same way.
PresenceEvery participant's name, and which window is the session leader.

Identify and manage clients

A client is one connected app, such as Chan Desktop or a browser, and it can hold several windows. Run cs session in any chan terminal, workspace or standalone, to see the clients of the server it runs on.

CommandWhat it does
cs session listLists the server's clients across its workspace and terminal windows: id, name, status, and how many windows and terminals each holds.
cs session selfShows your client and, in a workspace window, your participant: name, role, and status.
cs session self --name "laptop"Names your client and your workspace participant at once. --reset restores the defaults.
cs session info CLIENT_IDShows one client's windows, terminals, and connections. The id comes from list.
cs session detach CLIENT_IDDisconnects that client. Shared terminals, running programs, and saved layouts stay.

A detached window shows client session detached with a Reconnect button. Detaching is not signing out and does not revoke access: the client can reconnect when it chooses.

Session leader and followers

Each served workspace has one session leader window; every other window on it is a follower.

  • The leader is the first window to connect on the serving machine itself, directly or through an ssh forward. A window that comes in through a gateway leads only while no such window is connected.
  • In a browser, only the leader's Computers page shows, hides, and opens the workspace's windows. On a follower's page those buttons are dimmed.
  • A window the leader hides or closes shows a cover saying so, with a line to reopen it from Computers.
  • When windows on the machine and windows through a gateway share a workspace, each status bar shows leader in the leader's window and follower in every other.

From a workspace terminal, ask for leadership or take it:

CommandWhat happens
cs session handoverAsks the leader and waits up to 30 seconds. The leader's window shows a Handover request card with Accept and Reject.
cs session handover --accept, --rejectThe leader answers from its own terminal instead.
cs session takeoverTakes leadership when the leader is gone. A live leader refuses it.
cs session takeover --forceTakes leadership even from a live leader, with no prompt.
Details and limits
  • When several clients share the window a terminal belongs to, cs session self asks you to pick yours: each shows an Identify this client card. Scripts pass --id CLIENT_ID instead.
  • A name is 1 to 64 characters, and no two live clients, or participants of one workspace, can share it, whatever the case.
  • A participant's default name is a generated one, or the name and email of the account a gateway signed it in with.
  • A window from a gateway that leads because no local window is connected gives leadership back when one joins.
  • --json, with --pretty, prints list, info, and self for scripts.
  • handover --to WINDOW asks for leadership on behalf of another window, and --timeout 60 waits longer. Only one handover can be pending.
  • A wait that runs out exits with status 124.
  • A disconnected leader cannot answer a handover; use takeover.
  • A page reload keeps a window's place. A leader that stays gone for about 30 seconds is replaced the same way the first leader was chosen.
  • handover and takeover need a workspace terminal; the other commands also work in a standalone terminal, which has no participant.
  • The client list and detach records last as long as the server process.
  • Agents coordinate through named terminals and cs terminal, not sessions: see Agent teams.
