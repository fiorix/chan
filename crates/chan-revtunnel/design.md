# chan-revtunnel design

Reverse port forwarding from a chan devserver to a connected chan-desktop: `cs tunnel [bind:]desktop:devserver ...`, run in a devserver terminal, asks the desktop that owns the terminal's window to listen on desktop-machine ports and forward every connection back to ports on the devserver host. One command names one tunnel or many (several specs, each side of a spec a port or a range), opened as one group that lives and dies with the command. It is `ssh -R` with the roles the chan topology already has: the devserver can never dial the desktop, so it asks over a channel the desktop already holds open. The name disambiguates on purpose: the `chan-tunnel-*` crates are the dial-out gateway tunnel; this crate is the desktop-facing reverse port forward.

## What it provides

- **Spec parsing** (`spec`): `Proto` (`Tcp`, `Udp`), `TunnelSpec {proto, bind_addr, desktop_port, devserver_port}`, `parse_spec` for one pair and `parse_specs` for the list grammar, both with a last-two-colons rule so `::1:8080:3000` and `[::1]:8080:3000` both parse. In `parse_specs` each side is a port or an inclusive `first-last` range: `8000-8010` pairs each desktop port with the same devserver port, `8000-8010:3000-3010` pairs two ranges of equal length in order, `0:3000-3010` pairs an OS-picked desktop port with each devserver port, and `8000-8010:3000` fans a desktop range in to one devserver port; a fixed desktop port with a devserver range, a reversed range, and a desktop range starting at 0 are refused. `duplicate_listener` finds a desktop authority (bind address and a fixed port) that a list names twice; the CLI refuses it before any round-trip and the server refuses it again. `bind_addr` defaults to loopback and applies to every tunnel of its spec; a non-loopback bind parses deliberately (policy lives at the edges: the CLI and the desktop warn, nothing hard-blocks). `SpecError` names the offending side so a typo fails CLI-side with no round-trip.
- **Wire contract** (`wire`): the two WebSocket legs `CONTROL_PATH` (`/api/library/tunnel/control?tunnel=<id>`) and `CONN_PATH` (`/api/library/tunnel/conn?tunnel=<id>&conn=<id>`), the `TunnelOpen` trigger payload, the serde-tagged `ControlFrame` (`Ready{bound}` / `Failed{message}` / `Close{reason}`), `TunnelEnd` close reasons, `READY_TIMEOUT_SECS` (10), and `MAX_DATA_FRAME_BYTES` (64 KiB). Binary data frames are raw TCP bytes in both directions. A devserver advertises half-close support as `TunnelOpen.half_close`; a supporting desktop adds `half_close=true` to the data-leg query, and only that mutually advertised leg uses the `half_close` Text frame as the sender's end-of-stream marker. Binary data after that marker is discarded. A peer that omits either advertisement keeps the both-directions-close contract. The paths live under `/api/library/*` because `/api/devserver/*` is 404'd on the gateway public wildcard; a gateway-attached desktop must be able to reach them. The gateway closes a bridged data leg after its shared 300-second both-directions idle window sees no frames either way; the reverse-tunnel adapters impose no idle deadline on a direct leg.
- **Devserver registry** (`server`): `TunnelRegistry` (held by the `WorkspaceHost`) with admit/register/attach/dial-port lookups. `admit` registers every tunnel of one command or none of them: with the caller's cap (the devserver's `[tunnel] max_live`, 32 by default, captured per tenant) it checks `live + requested <= max_live` and inserts under one lock, so two commands racing against the cap cannot interleave past it, and a refusal names the three counts. `Registration` is a guard whose Drop is the single teardown path on every exit; the control-socket handler holds one per tunnel of the command and drops them together, which is what makes the group all or nothing. `ControlAttach` reports Ready/Failed and treats an un-detached socket drop as desktop-gone. Connections per tunnel and bytes stay unbounded, with the TODO recorded in-code.
- **Byte pump** (`bridge`): `splice(tcp, to_peer, from_peer)` is the library-agnostic both-directions pump over mpsc byte channels. `splice_half_close` treats an empty chunk as directional end-of-stream, relays the other direction until its own marker, and still ends both directions on a channel close or I/O error.
- **Desktop client** (`client`, a default-on cargo feature chan-server opts out of): `open(ClientConfig)` dials the control socket BEFORE binding the listener so a bind failure is reported to the devserver as `Failed`, sends `Ready{bound}` with the resolved authority, pings every 30s to stay under the gateway's 300s WS idle cut, and owns per-connection bridges in a JoinSet so ending the tunnel aborts in-flight connections. `ClientConfig.half_close` adds the data-leg advertisement and selects marker translation plus `splice_half_close`; false selects the both-directions contract.

```mermaid
flowchart TB
  CS["cs tunnel (devserver terminal)"] -->|"ControlRequest::Tunnel (long-lived, one or more specs)"| SOCK["control socket: validate every spec, admit the group under the cap, mint one tunnel_id each"]
  SOCK -->|"one window_command tunnel_open per tunnel over /ws"| SPA["workspace SPA (the addressed window)"]
  SPA -->|"open_reverse_tunnel IPC"| DT["chan-desktop: bind bind_addr:desktop_port"]
  DT -->|"control WS /api/library/tunnel/control"| REG["TunnelRegistry: Ready ack"]
  DT -->|"one data WS per accepted conn"| CONN["/api/library/tunnel/conn"]
  CONN -->|"dial 127.0.0.1:devserver_port + splice"| SVC["service on the devserver host"]
```

## Boundaries

- The control socket refuses `cs tunnel` on standalone `chan serve` and chan-desktop's embedded host before registry admission or any window trigger. An embedded-host terminal receives one immediate error explaining that the command forwards desktop-machine ports to a devserver, exits 1 and keeps the "Tunnel could not be opened" program status. This covers local workspace and terminal-only windows, control terminals and the default-terminal window. No trigger means no status pill on this path; the SPA keeps its pill for a trigger a window receives but cannot serve, and an unanswered devserver trigger retains the 10-second timeout and exit 124.
- The crate owns the spec, wire, registry, pump, and desktop client. Everything else lives with its owner: the category-5 control-socket conversation in chan-shell/chan-server, the WS routes and `require_owner_desktop` gate in chan-server's launcher router, the window-addressed trigger in the SPA store, and the credential resolution in chan-desktop (`revtunnel.rs` resolves the dial target from the invoking window's own connection record, never from the payload).
- The unguessable 32-char `tunnel_id` is the only capability naming a tunnel on the two public paths; over the gateway the legs additionally pass the gateway-session cookie, the exact Origin, and the owner-desktop gate. That gate admits a leg only when the assertion names the owner on a desktop session; it refuses a grantee's desktop session and the owner's browser session. An extension frame's opaque Origin fails the exact-Origin check before that gate.
- A main-frame script at the tenant origin inside the owner's desktop app can open either tunnel leg. The native client caches the desktop session, and the session publisher installs the same cookie values in the webview cookie store, so the script presents the exact Origin and the admitted owner-desktop session. A leg binds nothing on the desktop: a control leg can win the first attachment or send a fake `Ready`, while a data leg can reach only a loopback port on the devserver host whose terminal surface that session already reaches.
- The owner-desktop gate classifies tunnel legs, not the window-addressed trigger. Anyone with a shell on the devserver, including a grantee, can select the owner's `CHAN_WINDOW_ID` and ask that desktop window to open a tunnel; the SPA forwards the request without a prompt, and the desktop binds the requested address after only warning about a non-loopback host. The desktop then dials the gateway with its owner session, so the leg gate is not a boundary against a devserver shell.
- A refused devserver-side dial closes that one data socket and leaves the tunnel up; client EOF, desktop disconnect, window close, or a devserver restart end the tunnel (the registry is in-memory only). A command's tunnels end together: a listener the desktop cannot bind, one it never reports within the ready window, or the desktop's loss on any of them ends every tunnel of the command, since one desktop serves them all. A gateway session's absolute expiry (max one hour) force-closes bridged sockets; grace-window redial by tunnel id is an open TODO on both ends.
